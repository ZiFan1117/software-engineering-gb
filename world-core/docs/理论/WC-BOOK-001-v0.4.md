# 序 · 一句话

> **发生过什么，没有一处说了算**：一件事在三方各有一份说法的时候，没有任何一处能被三方同时承认是准的；
> 也没有任何一处，能让第三方不问当事人就查出同一件事。
>
> （注意边界：语法那一层早就统一了——HTTP、JSON、ISO 8601、UUID、TLS 都在跑；域名归谁，权威服务器说了算；一次查询要什么结果，SQL 有自己的语义。
> **根不在那些地方，也不只在"变更"这一类上**——那些各自只管自己那一套，跨过接口就不作数。
> 根在**"说法"这一层**：这句话是什么意思、我们说的是不是同一件事。能说的话至少三类——发生了变更、请求与结果、通告；而且**说了还得有人被叫醒**（位置与投递）。）
> 每个软件、每个协议、每个界面都在讲自己的方言；谁想跟谁打交道，就得先学会对方的说法。
> **我们要造的，是那个共同的东西本身——一个语义世界。**

今天的情况是：**每一方都在讲自己的话。**

- 人对机器说：点这里、改那个、装这个。
- agent 对软件说：调这个接口、传这些参数（**每个工具一套参数、一套错误码**）。
- 机器对机器说：一串字节、一条报文。

**每一处交界都要现翻一遍。** 翻一次就可能错一次；而"这句话到底是什么意思"，**从来没有人负责回答**——

| 现实 | 结果 |
|---|---|
| 每个软件一套说法 | agent 只能**逐个工具试错**；换一个工具就要重新学一遍 |
| 每个协议一套消息格式 | 消息**不自描述**：不查文档读不懂，而文档永远滞后于实现 |
| 每个界面一套呈现 | 人看到的和 agent 读到的**不是同一份东西**，于是"我们说的是同一件事吗"无法核对 |
| 每一次调用都是一次**谈判** | 成本全花在"对齐说法"上，而不是花在事情本身 |

**所以真正的缺口不是"某个系统不够聪明"，而是：三方之间没有一个共同的东西可以对齐。**

## 那"共同的东西"是什么

**不是一种新的中间语言。** 这一条本项目已经论证过、并把它**否掉了**：三方的"硬件"不可通约，任何单一格式必然降级到最低公共水平——**中间点是求交集，交集一定小于全集**。

**是这三样：**

| # | 是什么 | 一句话 |
|---|---|---|
| **1** | **一套语义事件**（世界里发生的一切，只有一种写法） | 每句话都得**自描述**：主体是谁、改了哪个字段、从什么变成什么、因为哪一条。**不读文档也能懂** |
| **2** | **一本账**（这种写法只追加地记在一处） | 它是**唯一的交汇点**：三方**只跟它对齐，彼此不直连** |
| **3** | **若干出口**（同一份东西，各按各自最优的方式取） | 给 agent 的是**给程序读**的那一种，给人的是**给人看**的那一种——**不是妥协出一份大家都能勉强看的** |

**一句话记住**：

> **共同语言不是三方谈出来的，是由同一份语义事件裁定、由各自的出口交付。**
> 我们不请三方坐到谈判桌上互相翻译；我们给它们**同一个底座**，让每一方都取自己最优的那一份。

## 于是"发生过什么"这件事的位置

它**不是**这本书的目的，它是**手段**，而且只有一条理由：

> **只有当"发生过的每一件事都被写下来、而且只有一种写法"时，"共同的说法"才可能存在。**
> 否则每一方手里都只有自己那一份说法——**那就又回到了各说各话。**

所以：**状态是算出来的**（不是各方各存一份）、**历史只追加**（不能有人偷偷改口径）、**回滚是再加一条**（不改历史）——**这些全是为了让"共同的说法"立得住，而不是为了记账本身。**

# 第一章 · 我们在造什么

## 1.0 缺的不是数据，是"说法"这一层

**这是全书的第一道分岔，走错了后面全错。**

同一件事，在人、AI agent 和机器那里，往往不是同一个意思。

人说要"把这张照片删了"，agent 收到的是"删除这个文件对象"，机器执行的是"把那块存储标成可用"。三个都对，三件事却不一样。改一次配额，写的是"5"，一边当元、一边当分。一次操作成功了，日志里有一条，可你要问"改的是哪个字段、前值是什么、因为哪一条才发生"，三样都没有。

这不是数据不通，也不是接口不对——数据一直在流，接口每天都在调。语法那一层早就统一了：HTTP 的方法与状态码、JSON、ISO 8601 的时间、UUID、TLS，你不需要为一次调用或者一个时间戳写翻译器；域名归谁，有权威服务器说了算；一次查询要什么结果，SQL 有共同的语义；一次提交改了什么，Git 记得清清楚楚。这些都不是这个问题。

问题在另外一层：**"这句话是什么意思、我们说的是不是同一件事"，没有一个由各方共同依赖的位置。** 一件事在三方各有一份说法的时候，没有任何一处能被三方同时承认是准的；也没有任何一处，能让第三方不问当事人就查出同一件事。（能说的话也不止"改了什么"这一类——还有请求与结果、通告；而且说了还得有人被叫醒。）

**缺了这一层，长出来的第一件事就是：每一对交界各自谈一份约定。**

```text
   人  ←→  翻译  ←→  agent  ←→  翻译  ←→  机器        ← 直觉方案：谁跟谁说话，就装一个翻译
```

**这条路走不远，而且原因不是"翻译写得不好"：**

| # | 为什么走不远 |
|---|---|
| **1** | **约定的数量随参与者平方增长**。三方两两互译是 3 条；十方是 45 条。**每加一个参与者，成本不是加一，是加一列。**（一旦约定一个共用的中间标准，增长就降为线性；但标准能补的只有语法那一层，见本节末） |
| **2** | **转译会丢东西**。转译是"把 A 的说法改写成 B 的说法"，而 **B 的说法里可能根本没有 A 想说的那一格**（比如某方压根没有"前值"这个概念，你怎么转？） |
| **3** | **约定没有权威**。同一句话被两条不同的路径处理，可能得到两个结果——**而没有任何一处能说"以我为准"**。这就是"两个世界"的雏形。 |
| **4** | **约定本身要有人维护**，而**它就是新的方言**：规则怎么改、谁批、改了之后旧记录还读不读得懂——**这些问题一层不少，只是被挪到了约定里**。 |

**所以正确的做法是反过来：不装翻译，给一个共同的东西。**

```text
             ┌──────────── 共同的东西（唯一交汇点）────────────┐
             │  发生过的每一件事，只有一种写法                │
             └────▲──────────────▲──────────────▲────────────┘
                  │              │              │
                 人             agent           机器
             （各取自己最优的那一份 → 出口）           ← 本书方案：三方只跟它对齐，彼此不直连
```

**三方之间不再互相说话，各自只跟这一个共同的东西打交道。** 于是：

- **不再有"谁跟谁说话"的问题**（参与者从 N 增加到 N+1，**不改任何一条已有的说法**）；
- **不再有"转译丢东西"的问题**（每一方直接从共同的东西里取，**取不到就是取不到，不需要中间人猜**）；
- **权威是唯一的**（一切以那个共同的东西为准）；
- **不再有"约定本身是方言"的问题**（共同的东西只有一份，它自己由**本体**管版本与内容寻址）。

> **一句话**：**两两约定是"把歧义搬个地方"，共同的东西是"让三方有一个可以对齐的地方"。**
> 前者随规模恶化，后者不随参与者数量增长。

**⚠️ 但这里有一条必须说死的界线**（否则"共同的东西"这三个字会被误读成另一种翻译）：

> **"共同的东西"不是"一种大家都得学的新中间语言"。**
> 找一种"三方都能懂的中间语言"这个方案，本项目**论证过并否掉了**——
> 三方的"硬件"不可通约，任何单一格式必然降级到**最低公共水平**；
> **中间点是求交集，而交集一定小于全集。**
>
> 所以"共同"不等于"同一份表达"，而是：**同一个底座 + 各按各自最优的方式取**（论证出处 `1-理论与哲学/00-理论定稿.md` §7.3"底座 + N 投影"）。

> **语法那一层已经统一了，本节不是要否认它。** HTTP 的方法与状态码、JSON、ISO 8601、UUID、TLS 早就在跑，
> 你不需要为一次调用或一个时间戳写翻译器；标准加适配器这条路**确实管用**，新增的是适配器，是线性的。
> 它的天花板在于只能表达"谁都能表达的那一层"：这段话是"要做什么"还是"做完了"、这次改动改的是哪个语义字段、
> 前值是什么、因为哪一条、谁批准、可不可逆——这些它管不了。
> **本节的靶子只有一条：没有共同的东西时，各方两两各谈一份约定。**

## 1.1 先把三件容易被混为一谈的事分开

| # | 问题 | 归哪个概念 | 一句话答案 |
|---|---|---|---|
| 1 | 世界住在哪里、谁依赖它 | **载 + 系统方式** | 它先是载体上的一个**一等组件**（开机就起、别人依赖它），成熟后才是 **PID 1** |
| 2 | 世界里有什么、怎么组织 | **存 + 本体** | 一套**极小核心本体** + 命名空间扩展 |
| 3 | 东西之间怎么说话 | **传 + 主线 / 管道** | **语义事件账本**（唯一交汇点）+ 字节货运道 |

**结论**：总线、命令行**不是**与"本体"并列的东西——它们是**本体之间互动的路径**。三者不冲突，是三层：**位置 → 内容 → 通路**。

> 出处：`2-依据/15-世界核心的组成与职责.md` §一。

## 1.2 载体知道的只有一件事：启动它

| | **插件** | **一等组件（本书对象）** |
|---|---|---|
| 谁决定你怎么被装进去 | **宿主程序**定规矩（"你得实现我这几个函数"） | **系统**只知道"启动这个程序" |
| 换个宿主 / 载体 | 要照新宿主的规矩重写 | 照样能起 |
| 风险 | ⚠️ 宿主定义你的边界 = **锚定** | ✅ 你自己定义自己 |

**硬前提**：**载体只知道"启动它"，不知道"它是什么"。**
这一条决定了后面所有的设计：它必须**自带法律**（本体）与**自带记忆**（账本），因为载体不会替它记住任何意义。

> 出处：同上 §2.1、§2.2。

## 1.3 它包含三样性质完全不同的东西

| # | 是什么 | 性质 | 生命周期 | 像 systemd 吗 |
|---|---|---|---|---|
| 1 | **本体**（词表 / 法律：世界里有什么、怎么说、什么算合法变更） | **法律** | 版本化、**内容寻址**、很少改，改了要留痕 | ❌ 不像（systemd 没有这种东西） |
| 2 | **本体运行时**（加载本体、管账本、算读模型、执行门禁、注册投影） | **机制 / 代码** | 你改它、升级它 | ✅ **这一部分最像 systemd** |
| 3 | **本体实例**（当前这个世界的对象图 + 事件账本） | **数据** | 只追加、可回滚 | ⚠️ 有点像 journald |

**为什么必须分开**：不分开，就永远说不清"**是程序升级了，还是世界变了**"——而这正是"可复盘"要回答的。

**三者的角色一句话**：
- **本体是法律**（"什么算一次合法变更"）
- **运行时是法院和书记员**（按法律办事、记账）
- **实例是案卷**（这个世界具体发生过什么）

> 本体是"装起来的"吗？**是**——但方式是"**运行时装起来 + 用内容寻址钉住版本**"，而不是"把本体写进代码里"。任何人都应能问：**"你现在跑的是哪一版本体？"**
>
> 出处：同上 §2.3。

## 1.4 与新造一个操作系统的分界：它服务的东西"有没有脑子"

| | **systemd / 载体** | **世界核心（本书对象）** |
|---|---|---|
| 它知道它管的东西是什么吗 | **不知道**——不管 unit 里跑的是 nginx 还是数据库 | **必须知道**——得懂"这条事件改的是哪个实体的哪个字段" |
| 因此它是 | **内容无关**的基础设施 | **内容相关**的基础设施 |
| 为什么 | 它服务的对象是"**程序**"，**程序自己懂自己的意义** | 它服务的对象是"**语义对象**"，**没有别人懂它们的意义——它必须自己懂** |

**这是全书承重的一句**：

> systemd 能只做基础设施，是因为**它服务的东西自己有脑子**。
> 世界核心服务的对象**没有脑子**——**所以"意义"必须由世界核心自己承担**。
> 这就是为什么它不能只做"一连串基础设施"：**它的内容就是世界。**

> 出处：同上 §2.4。

## 1.5 全景结构

```text
┌─ 载体（Linux；将来可换）──────────────────────── 内容无关的基础设施
│    进程 / 内存 / 文件 / IPC / 隔离 / 配额
│    对世界核心的全部认知只有："启动它、给资源、给一条通道"
│
└─┬─ 世界核心（一等组件 → 将来的 PID 1）────────── 内容相关的基础设施
  │
  │   ┌── 本体（法律）────── 极小核心词表 + 命名空间扩展（内容寻址、版本钉住）
  │   ├── 实例（数据）────── 对象图 + 事件账本
  │   └── 运行时（机制）──── 加载本体 / 管账本 / 算读模型 / 执行门禁 / 注册投影
  │
  │   ╔══════════════════════════════════════════════════════════╗
  │   ║  主线 = 语义事件账本（唯一交汇点，按 seq 只追加）           ║
  │   ╚═══════════════════════┬══════════════════════════════════╝
  │                           │ 派生（只读）
  │                           ▼
  │                     读模型（世界"现在"）
  │                      ┌────┴────┐
  │                      ▼         ▼
  │                 语言投影    视觉投影        ← 出口（叶子节点）
  │                      │         │
  └──────────────────────┼─────────┼──────────────
                         ▼         ▼
                      Agent 读    人看

  管道（通道）= 与主线并行的"货运道"：搬字节 / 大对象；主干道上只放 hash 引用

              ▲
              └── 机器 / Agent / 人：三方都只"写事件"、都只"读投影"
```

**一处必须记牢的口径更正**：早期文档写过"第一版无中心"。真实拓扑是**星形**，**中心就是世界核心**（三方都只跟账本打交道）。
所谓"无中心"，实际意思是"**不额外引入一个中间件**"——因为世界核心**本身就是那个汇接点**，那是它的职责，不是外加的中心。

> **建议口径：无额外中间件；世界核心即汇接点。**
>
> 出处：同上 §三、§5.4。

## 1.6 三方：机器、Agent、人

| 谁 | 写什么事件 | 读什么投影 |
|---|---|---|
| **机器 / 设备** | "我做了什么"（`change` / `notice`）；执行结果 | "要我做什么"（`act`） |
| **Agent** | "请你做什么"（`act`）+ 它的结果 | **语言投影** |
| **人** | 在界面上操作 → 翻译成 `act` | **视觉投影** |

**三方之间没有直连**：它们**只跟账本对齐**，不互相聊。
这正是"三方都能懂"成立的原因——**共同语言是账本给的，不是谈判谈出来的**。

> 出处：同上 §六。

# 第二章 · 理论层面它应该是什么样子

## 2.1 三条公理（整本书的前提）

| # | 公理 | 直接推论 |
|---|---|---|
| ① | 我们做的是**地基**：**载可以买，通道与总线一律自造** | 层归属被钉死：**载买 / 通道造 / 总线造** |
| ② | **锚定点 = 语义事件**（不是语义对象树，也不是别人的事件格式） | 事件必须**可理解**（自解释、自描述），而不只是**不可伪造**；"语义"必须**可检验** |
| ③ | **纯事件溯源** | 只有一种真相；**状态是投影**；回滚靠**补偿事件**而不是改历史 |

> "从头做"**不等于"全部自己写"**：载体仍然是买的。它的确切含义是：**所有法律都自己立。**
>
> 出处：`2-依据/14-总线词表v0.md` §一。

## 2.2 什么叫"语义"——八条判据（与 Nostr 逐条对照）

"语义"不是形容词，是**可检验的清单**：

| 维度 | 别人（Nostr 类事件格式） | **语义事件（本世界）** |
|---|---|---|
| 类型 | **整数 `kind`**，要查注册表才知道是什么 | **自解释的类型 + 词表版本**；不读文档也能懂 |
| 载荷 | `content` 是**不透明 JSON 字符串** | **结构化的变化**：主体 + 字段路径 + 值 |
| 单位 / 量纲 | 无 | **在事件里**（"3 秒"还是"3 分钟"不靠猜） |
| 主体 | 靠 tags 约定 | **一等字段**（`subject` + 字段路径） |
| 因果 | **无**（引用只表示"引用了某条"，语义靠应用层） | **`trace`：引发它的那条事件** |
| 身份与授权 | 签名——**身份有了，能力与不可逆性没有** | 身份 + **声明的能力** + **可逆性等级** |
| **重放** | **规范不管**（"重放得到什么"没有定义） | **重放必须得到同一状态**——这是"世界"的定义性要求 |
| 可核验 | 签名 + `id`（**防篡改 ✓**） | 哈希链**+ 状态可回放核验** |

> **一句话记住**：
> **别人给了你"不可伪造"，没给你"可理解"和"可重放"。补上后两条，就叫语义事件。**

## 2.3 一封语义事件的信封（自造）

```text
world : 1                      # 词表版本。只加 flags，永不改这个数的含义
kind  : change | act | notice  # 三个家族
id    : <事件自身身份>          # 去重
seq   : <在日志中的位置，全局单增，由世界分配>
at    : <时间戳>                # 顺序由 seq 决定，at 只作辅助
actor : <世界内身份>            # 不是 pid/uid
to    : <世界内身份 | 空>       # 空 = 广播
trace : <id | 空>               # ★ 因果：引发本条的那条事件
flags : [ ... ]                # 能力旗标；未知旗标必须忽略，永不因它改版本号
body  : { ... }                # 三个家族各自的体
```

| 字段 | 没有它就会 |
|---|---|
| `world` | 词表一改，旧消费者无法判断"这条我读不读得懂" |
| `kind` | 收到事件先要猜家族；三个家族边界消失 |
| `id` | 重传无法去重 |
| **`seq`** | **并发时无法定序**；断线后无法说"从第 N 条补给我" |
| `actor` | 无法回答"谁做的"（内核只有 UID / cgroup 粒度） |
| **`trace`** | **无法回答"为什么会变成这样"**；复盘退化成时间线，不是因果 |
| `flags` | 加能力就得改版本号 |
| `body` | —— |

> **在纯事件溯源下，`seq` 的地位变了**：它不再只是"消息序号"，而是**事件在日志中的位置**——
> 世界的当前状态**由 `seq` 唯一确定**（`state = fold(events[0..seq])`）。**这是全书的第二句承重话。**

## 2.4 三个家族 + 一个值类型 + 一种传输形态

```text
唯一真相：语义事件 × 3 个家族
├── ① change  变更：世界状态发生了变化
├── ② act     动作：请求 → 结果（结果本身也是事件）
└── ③ notice  通告：发生了什么（完工铃等）

不是事件，而是值类型
└── ④ ref     引用：{object:{id,rev}} | {content:{algo,hash}}   ← 作为字段值出现

不是事件，而是投影的传输形态
└── 快照 / 增量：{subject, base_seq, snapshot | delta}
```

**为什么 `ref` 不是事件**：引用不是"发生了什么"，它是**某个字段的值**。它应当出现在 `change.body.after` 里，而不是自己占一类消息。

**为什么快照不是真相**：快照是 `fold(events)` 的**缓存**。它必须带 `base_seq` 告诉读者"我对应日志的哪一点"；**账本说它错了，它就错了**。

> **史料纪律**：本世界最早的设计曾把"状态"与"事件"写成**并列的四类消息**。按公理②③收缩为上面这一张。
> **这不是减功能，是去掉了一个假的并列**：状态本来就不是"另一条真相"，它是事件的函数。
>
> 出处：`14` 篇 §三。

## 2.5 账本规则（一条）

> **账本 = 语义事件；本体实例（对象 / 状态）= 它的投影。任何"直接改对象"的写入路径都不允许存在。**

**为什么必须立这条**：最糟的情况不是"选错账本"，而是**两本账**——对象存一份、事件存一份，两边各自演进 ⇒ **必然对不上，而且对不上时你不知道信谁**。

**一句话**：**一个写入口，一个账本。**

> 出处：`15` 篇 §八。

## 2.6 规范地基：为什么必须按"不可逆性"加摩擦

**五步论证**：

```text
有些效应不可逆
  → Agent 错误率非零且不可归责
  → 不可逆 × 不可归责 = 事后无任何机制能恢复或追索
  → 故对不可逆效应，事前 / 事中介入是唯一纠错点
  → 监督对不可逆效应是必要的（纠错点的逻辑必然，非价值偏好）
```

**最强反驳（这个项目自己承认它成立）**：不可逆的边界**需要判断**，而判断正是已经让渡出去的能力——"人必须先监督才能知道哪里需要监督"（循环）。

**幸存下来的立场（现行）**：

| 立场 | 内容 | 工程对应物 |
|---|---|---|
| **不可逆性不由当次判断，由预案分级制度化** | 像手术分级：术前按类别定级，不是术中现场判断 ⇒ **循环由此打破** | 能力声明里的风险等级 + 门禁策略 |
| **摩擦按不可逆性定价** | 可逆处放手，不可逆处加摩擦 | 可逆 ⇒ 免检但留痕；不可逆 ⇒ 加摩擦 |
| **判据会移动** | 今天可逆的明天可能不可逆 ⇒ **可逆性必须能被本体记录与重判** | ⚠️ **本书第四章将指出：这一条现在没有落实** |
| **审计必须区分"人批准"与"人被信息胁迫后批准"** | 记录批准的语境 | ⚠️ **未落实（连审批通道都还没有）** |

> 出处：`1-理论与哲学/00-理论定稿.md` §四。

## 2.7 能力与归责：三条必须说准的话

### 2.7.1 能力 = **声明即请求**（不是授权）

门禁的本质是**请求的登记与过滤**，不是授权。它的效力上限是**使用者的受限产权**：

| 档 | 区域 | 效力来源 |
|---|---|---|
| 真业主区 | 平台、云端数据 | **许可边界**（能用，墙不能拆） |
| 无业主区 | 开源、协议、公共数据 | **惯例与互惠**（不是"权限有限"，是**谁都够不着**） |
| 全产权区 | 本地文件 | 完整 |

**越过产权边界的声明，自始无效**（碰平台权利、碰第三人权利）。

> ⚠️ **本书将指出：三档在实现里只落了"全产权"一档。**

### 2.7.2 行动 = 被组织成行动形状的事件

- **行动** = 有意向的事件（可归责于行动者）；**事件** = 单纯发生（只能追因）；
- Agent 的执行：**结构上有意向的形状**（有目标指向），**来源上无意向的地位**（目标是植入的）。

### 2.7.3 归责 = 落在把事件组织成行动形状的人

不落在 Agent（事件无归责），落在**设计意图的植入者（厂商）**与**任务的发起者（使用者）**。

**场景归责三桶**（不切比例，一桶一个机制）：设计缺陷致错 → 厂商；任务指令致错 → 使用者自担；分布内随机错 → 保险池。

> 出处：`00-理论定稿` §五。

## 2.8 三条不可省的澄清（这个理论最容易被误读的地方）

1. **是"三重约束"不是"三重委托"**：约束是事实（任务 × 策略 × 法律确实约束着它），委托是制度（不存在）。**描述事实的词与宣告制度的词不得混用。**
2. **不是受托人，但理由要说准**：委托的五个必要条件逐条不通过。但"概念性不可能"是修辞升级——现行制度下不可能，**建构路径开放**；真正剩下的概念障碍只有一条：**塑形 ≠ 守诺**（无立场则无所谓违背）。
3. **镜子论已降级**：它学的是"人怎么说"，不必然是"世界怎么运行"。镜子论是**启发式隐喻**，不再是证明链的一环。

> 出处：`00-理论定稿` §1.2。

## 2.9 四条铁律（其余理论降为背景）

| # | 铁律 | 违反了会怎样 |
|---|---|---|
| 1 | **一个写入口，一个账本** | 出现两本账 ⇒ 对不上时不知道信谁 |
| 2 | **语义事件是唯一真相，状态是它的投影** | 状态成为第二真相 ⇒ 回滚与复盘都失去共同基准 |
| 3 | **不可绕过**：决策在唯一咽喉 + 规则与真相不受被管者写入 | 门禁变成君子协定 |
| 4 | **可问责 ≠ 正确**：审计保证可复盘，不保证结果正确 | 把"能追责"当成"不会错" ⇒ 责任被偷换 |

> 出处：`00-总纲.md` §5；`00-理论定稿` §八。

## 2.10 什么条件下才算"世界起来了"（四条件）

| # | 条件 | 对应 |
|---|---|---|
| 1 | 运行时在跑 | 机制就位 |
| 2 | **本体加载成功**（版本对得上） | 法律就位 |
| 3 | **账本能读能追加** | 数据就位 |
| 4 | **投影已注册，人和 Agent 能连上** | 出口就位 |

**四条齐了，才叫 "boot 进世界"。**
⚠️ **本书第四章将指出：第 4 条现在只兑现了一半**——"能连上"是单向的（人能问），**"注册"这个动作与"世界主动找人"这条路都不存在**。

> 出处：`15` 篇 §九。

# 第三章 · 为什么今天外面这套系统不行

> **本章的口径**：只谈**机制**，不谈模型能力。
> 每条先给"它其实很擅长什么"，再给"它为什么接不住**一个共同的说法**"，最后给**一句话要求**（可判定的要求，不写实现）。
> **本章的每一节都收敛到同一个诊断**：这些机制各自都对，但**它们之间没有一处能回答"这句话是什么意思"**——
> 于是每一处交界都要现翻一遍，**而约定没有权威**（这正是 §1.0 说的那条走不远的路线，今天正在现实里发生）。
> **凡属编制者推断的，显式标 `（推断）`**；本章的完整反面举证与逐条核实见附录（专家席 D 报告）。

## 3.1 操作系统层：文件系统 + shell + systemd + 权限位

> **这一节要回答的**：为什么这些机制**加起来**仍然给不出"共同的说法"。
> 它们各自都很擅长自己那件事；问题不在质量，在于**它们记的东西之间不可通约**——
> 每一对交界都要现翻一遍，而翻的过程没有权威。

**它擅长什么**：把字节可靠地放在盘上；把进程可靠地管起来；把资源可靠地隔离。这三件事它做得比任何自研方案都好。

**它接不住什么**（逐个机制）：

| 机制 | 它记住的 | 它记不住的 |
|---|---|---|
| 文件系统 | **字节与时间**（mtime、size、inode） | **字段与意义**：`config.yaml` 变了，它不知道"变的是 `max_retries`，从 3 变成 30，谁改的，为什么" |
| shell 历史 | **人敲过的命令** | **命令做了什么**：`systemctl restart x` 的**结果**在日志里，**意图**不在 |
| systemd | **单元状态**（active/failed） | **业务状态**：服务是"活的"，但"它处理到第几笔了"它不知道 |
| 权限位 | **谁能读写这个文件** | **谁有权改哪个实体的哪个字段**（粒度差了两个数量级） |
| 快照 / 备份 | **某个时刻的字节** | **两个时刻之间发生了什么**（快照能回退，但回退后你仍然不知道丢掉了什么） |

**具体场景五则**（每则都是真实会发生的事）：

1. **配置漂移**：一个 agent 半夜把配置改了。早上服务行为异常。`stat` 告诉你"文件昨天 3:14 被改过"，**但不告诉你改了什么、为什么改**。你得靠 `diff` 一个备份。**若备份周期是一天，你连 diff 都做不成。**
2. **两个 agent 抢同一份文件**：A 读到、B 写入、A 再写入 ⇒ **A 的写入基于过期状态**，这不是"冲突检测"能救的——因为**没有"状态"这个概念被显式记录**，冲突检测只存在于应用自己实现的锁里。
3. **"我装好了"无法验证**：agent 说它装了包。你没法验证它**到底装了什么、装之前是什么**。"回滚"要靠整机快照——而快照不知道"世界上发生了什么"，所以**你不敢回滚**（怕把别的合法修改一起撤掉）。
4. **回滚粒度**：用户只想撤销"上一条修改"，而系统只能给"回退到昨天"。
5. **跨工具的账对不上**：`journalctl` 里有 agent 的日志，`~/.bash_history` 里有命令，`/var/log/pacman.log` 里有包操作，`git log` 里有文件修改——**四本账，没有共同的主键**，出了事要人工拼。**（推断：这是运维现场最常见的"复盘成本"来源）**

> **一句话要求**：**每一次状态变化，都必须能以"谁、在何时、改了哪个实体的哪个字段、前值是什么、为什么"被独立检索——不管它是哪个工具干的。**

## 3.2 审计与日志层：syslog / journald / 云审计 / SaaS activity log

**它擅长什么**：**高吞吐地收下大量文本**，并且（journald 之类）能带上一些结构化字段与来源单元。

**它接不住什么**：

| 缺陷 | 具体表现 |
|---|---|
| **只有字节，没有字段** | 日志行是给人读的散文。程序要判断"这是权限问题还是缺号问题"，只能匹配字符串——**改一句措辞就悄悄破坏了所有调用方的判断** |
| **只有时间线，没有因果** | 你能看到"A 发生了、B 发生了"，**看不到"B 是因为 A"**。复盘的第一个问题就是"为什么"，而日志结构里**没有这个字段** |
| **只有进程粒度，没有语义粒度** | 它知道"哪个进程写了日志"，不知道"哪个实体被改了" |
| **可以被改** | 日志文件是普通文件；有权限的人可以改、可以删、可以只删一段。**"审计"这个词承诺的东西，文件权限给不了** |
| **跨系统对不上账** | 每套系统一套 ID、一套时间、一套格式。**没有全局单增序** ⇒ 无法说"从第 N 条补给我"，也无法判定"有没有漏" |
| **保留策略与合规倒挂** | 为了省钱，日志通常**只留 7–30 天**。而"24 小时后能答发生过什么""三年后能复盘"这类要求，**在保留策略这一层就已经被否决了** |

> **一句话要求**：**"谁改了什么"必须是结构化字段（机读），"为什么"必须有显式因果链接，且历史必须能证明没被动过。**

## 3.3 数据与状态层：数据库 / git / 对象存储 / 消息队列

| 系统 | 擅长 | 接不住 |
|---|---|---|
| **关系数据库** | 事务、一致性、查询 | **历史**：更新是**覆盖**，旧值当场消失（除非应用自己写审计表——于是又变成"两本账"，而且**应用一定会忘记写**） |
| **数据库审计表 / CDC** | 事后能拿到变更流 | **不是真相**：真相是表，变更流是附属。**两者不一致时，你信表还是信流？** 这就是"两本账"的标准形态 |
| **git** | 内容寻址、不可篡改历史、回滚 | 它记录的是**文件快照**，不是**实体的字段**。"把 `muted` 从 false 改成 true"这件事，在 git 里是"某文件的一行变了"——**语义在这一层丢失** |
| **对象存储** | 便宜、可扩展、版本化 | 只有 key 与字节，**没有"对象"这个概念**，更没有"字段" |
| **消息队列** | 高吞吐、削峰、解耦 | **它不负责真相**：消息消费掉就没了（或过期）；重放靠保留期，**保留期一过就没有历史** |

**共同的一句话**：**它们都记录"结果"，没有一个记录"变化本身及其理由"。**

> **一句话要求**：**历史必须是第一等的、可重放的、且是唯一真相；当前状态只能是它的函数。**

## 3.4 AI / Agent 框架层：MCP / tool-calling / 记忆方案 / 编排 / RAG

> 这一层的问题**不是模型不够聪明**，而是**机制上没有可问责的位置**。

| 机制 | 擅长 | 接不住 |
|---|---|---|
| **tool-calling** | 把一次调用变成结构化参数 | **调用前后没有不可改的记录**：模型为什么调这个工具、参数怎么来的，**只在对话上下文里**，会话一结束就没了 |
| **对话历史即记忆** | 简单、通用 | **它不是账本**：可以编辑、可以截断、可以摘要（= 有损）、按 token 预算丢弃。**它答不了"三个月前那次到底改了什么"** |
| **RAG / 向量记忆** | 召回相关内容 | **相似 ≠ 真实**：它给的是"像什么"，不是"发生过什么"，更不是"前值是什么" |
| **编排 / 工作流** | 把步骤串起来、可重试 | **重试不等于可回滚**：一个跑到一半失败的流程，**没有"补偿"这个概念**，只能整段重跑 |
| **MCP 类接口协议** | 统一工具接入 | 它统一的是**"怎么调"**，不是**"世界现在是什么"**。世界状态仍需每个工具各自回答，且答法互不相同 |

> **一句话要求**：**Agent 的每一次动作都要在外部的、不可被它自己修改的账上留下"意图 + 结果"，并且这两者必须能配对。**

## 3.5 权限与治理层：sudo / polkit / SELinux / OAuth scope / RBAC / IAM

**共同的结构性缺陷**：**粒度停在"主体 × 资源 × 动作"这一层，而语义在更下一层。**

| 现象 | 机制级原因 |
|---|---|
| "我明明设了权限，还是出了不该出的事" | 你授权的是"能不能写这个文件"，而事故是"**把某个字段从合法值改成另一个合法值**"。**中间那一层的语义没有任何机制在看** |
| 权限授予是**长期**的 | 授权一次，永久有效（或直到过期）。**而"该不该做"依赖当下语境**——语境变了，授权没变 |
| 撤销慢 | 撤权要改配置、要重启、要等人。**事中纠错点因此不存在** |
| 无法表达"不可逆" | 没有哪套权限系统里有"这件事做了就回不去"这个维度。**而恰恰是这一维度决定了要不要加摩擦** |
| 审计只到主体粒度 | 它知道"这个 uid 做过这件事"，不知道"这次操作的语义是什么、是否越界" |
| **人变成瓶颈** | 因为粒度粗，只能靠"每次弹窗问人"。而弹窗一多，人就开始**无脑点同意**——**这正是理论 §4 说的"批准即背书"：批准过的事故反而锁死追责** |

> **一句话要求**：**授权必须能表达"哪个主体、对哪个实体的哪个字段、在什么不可逆等级下、做哪一类改变"，并且每一次裁决本身都要留痕。**

## 3.6 人的一侧：为什么"注意力"是所有方案的瓶颈 —— 以及**今天的机制正在给衰减加速**

> 这一节的**理论三条**（监督必要 / 不充分 / 反噬）由专门席逐条**认可**。
> 它补的不是复述理论，而是**机制层的"为什么"**，以及一条不太舒服的发现：**现有机制不是中立的，它在加速衰减。**

### 3.6.1 三个环节的连锁

1. **事前**：粒度粗 ⇒ 只能问人 ⇒ 弹窗疲劳 ⇒ **批准变成形式**；
2. **事中**：没有"当前世界的可读视图" ⇒ 人要自己去各系统里拼 ⇒ **监督成本随系统数量线性上升**；
3. **事后**：四本账对不上 ⇒ 复盘要人工拼 ⇒ **复盘成本高到没人做** ⇒ 于是"下次做得更好"这件事**没有反馈回路**。

**机制层的四处具体成因**（各有外部一手证据）：

| 成因 | 具体机制 |
|---|---|
| **通知粒度 ≠ 决策粒度** | 通知的粒度是**进程 / 单元**，而人的决策粒度是**意图 / 字段**——**中间没有翻译层**。轮询因此把"监督"变成"推理"（本项目自己的账：一个 10 分钟的任务，从 20 次推理降到 2 次） |
| **保鲜期短于遗忘曲线** | 各类保留窗实测互不相同：Kafka 7 天 · SQL Server CDC 3 天 · n8n 14 天 · Okta 90 天 · GitHub 180 天。<br>**"24 小时后仍能答出"这类要求，在保留策略这一层就已被否决。** |
| **待批集从未被持久化** | 外部：某代码托管平台的审批对象**只有身份 + 自由文本 comment，没有审批时间戳、不绑定审批人所见的版本**，且**没有对应的审计事件**。<br>内部（本项目自己的诚实登记）：**v1 没有审批通道**——被摩擦的主体拿到的是"**不要等批准，它不会来**"。 |
| **"批准即背书"在机制上不可反驳** | 审批界面给人看**渲染结果**，日志里存**一个布尔**（`state: approved`），**两者之间没有 hash 约束**。<br>授权规范只要求"**MUST present**"合并后的要求，**全文没有一处要求持久化"给用户看了什么"**。<br>于是：**"他批准过"与"他批准了这件事"，在机制上不是同一句话。** |

### 3.6.2 由此得到的一句话要求

> **每一次需要人介入的决定，都必须把"呈现给他的那一份信息"和"他做出的那个决定"作为同一条记录一起持久化，并且必须能机械地判定"当前待批集"与"已批集"的完备性（既不漏也不重）。**

**这一条恰好补上了理论 §四 那句"审计必须区分『人批准』与『人被信息胁迫后批准』"的落点**——它今天不是"没做"，是**没有对象可做**（连审批通道都不存在）。

### 3.6.3 结论（这是这个项目最硬的一条，也是它最容易被误说的那条）

> **监督是必要的，但不充分，而且在衰减**——**依赖与「盯守」互斥，与「监督」不互斥**。
> 所以协作机制必须**补偿衰减**：把监督从"**注意力问题**"变成"**架构问题**"。

**关于这句的措辞，本项目已按专家意见改过一次**：原文写的是"依赖与**监督**互斥"。它**被断言了，没被证明**，而且有四组反例——民航（独立的安全报告体系 + 机组资源管理 + 标准操作程序）、核电（独立监管 + 安全文化）、外科（术前清单 + 三方核对 + 并发症讨论会）、金融清算（中央对手方）。
**更关键的是：它自己的工程解法就是它的反例**——"把监督变成架构问题"正说明监督**可以在高依赖下保持**。
**一字之差，但原话把一条可争取的目标，说成了一条自然规律。**

### 3.6.4 三条"过头"的批评：本项目对外部系统的说法**必须收回一部分**

> 本项目在一份现状分析里对外部系统写了若干批评。专门席逐条**回原始材料核验**了 22 条，结论是：
> **完全不成立 0 条 · 成立 9 条 · 部分成立 11 条 · 原句未能核实 2 条**——
> **"错的是『过头』与『归因』，不是方向。"**

**其中三条必须当场收回**，因为**一个能被一句反例打掉的开篇，会让所有成立的论证一起被扔掉**：

| # | 本项目曾写 | 事实 | 应改为 |
|---|---|---|---|
| 1 | "权限全有或全无……**没有『只许调亮度』这个档位**" | **最过头的一条**。反例是硬的：登录管理组件的 `SetBrightness` 接口**就是**那个档位（标为"非特权可调用"、签名固定、取值范围由设备上限界定，源码里**没有**授权检查）；而常被引作例子的那个用户组加权限的做法，是**第三方工具自带的规则**，**不是系统组件发的**（系统组件只给设备打个标签，内核默认权限是 `root:root 0644`） | "档位**逐 API 硬编码、不可组合、无统一语法**——『只许改某个服务的某一项配置』没有任何一层能表达" |
| 2 | "**无资源限制**" | **归因错**。限制机制今天可用且很细（内存上限、内存高水位、临时 scope 都可指定）。真因是**上游默认没装**：用户切片的默认配置只有任务数上限、**没有内存上限**；而内核控制组的语义是"**不会杀掉本组之外的任务**" ⇒ 内存压力时**在会话内部挑受害者**；临时子进程**连被单独杀的资格都没有** | "**默认无上限 + 内存压力在会话内挑受害者 + 临时子进程无法被单独处置**" |
| 3 | "**原因只有一个**——它里面没有『本体』这一层" | **单因论**，且与本项目自己的另外三处证据冲突：某些安全机制**装上就卸不掉**（于是"吊销无法即时生效"是**内核原语**问题）、**缺少跨进程的能力委托原语**（**要改内核**）、真·不可篡改**需要第二个地点**（**物理**问题）。<br>**而这句话正被立项文档用作否决备选方案的理由。** | "**最承重的原因是缺本体这一层**"，并列出另外三个独立的结构性原因 |

**另有两条纪律级发现**（本项目自己犯了它自己批评过的错）：

- 同一份文件里"**绑定某发行版**"的主张与"**该支点已失效**"的自认**并存**——修订只改了标注、没改正文主张，**与它自己批评过的"虚报已修正"同类**；
- 同一批机制的年限在两份文件里写作"**三十年**"与"**十五年**"——**两个年数互相矛盾**。

**专门席的一句收束**（一字不改）：

> 今天的问题不是"系统不够聪明"，而是**系统从来没有被要求回答"谁、对什么、从什么变成什么、为什么"这四个问题**——它被设计来管**进程与字节**，而人和 agent 需要的是管**意图与字段**。这两者之间那层东西**外面确实没有**；但造之前请先把上面这几条改掉——**一个可以被一句反例打掉的开篇，会让所有成立的论证一起被扔掉。**

## 4.2 理论已立、实现未及（差的是工程，不是理念）

## 4.3 理念本身要修正的地方（**反对者席与红队席的贡献**）

> 这一节是全书**最不讨好**的部分。两位专家被专门设成反对者，它们的话我**大部分采纳、小部分驳回**，**驳回也写理由**（见 §4.5）。

### 4.3.1 必须修正的三条措辞

| # | 原话 | 问题 | 建议改法（我采纳） |
|---|---|---|---|
| 1 | "**依赖与监督互斥**" | **它被断言了，没被证明**。反例四组：民航（FOQA / CRM / SOP / ASRS）、核电（独立监管 + 安全文化）、外科（WHO 清单 / 三方核对 / M&M）、金融清算（中央对手方）。<br>更关键的是：**它自己的工程解法就是它的反例**——"把监督从注意力问题变成架构问题"正是"监督可以在高依赖下保持"。 | 改为"**依赖与『盯守』互斥，与『监督』不互斥**"。<br>一字之差，但原话把一条**可争取的目标**说成了一条**自然规律**。 |
| 2 | "**行动 = 有意向的事件；事件 = 单纯发生**" | **它挡不住恒温器**（"结构上有意向的形状"是 teleonomy 冒充 intentionality）；而且它把一条**未经论证的实质前提**（"只有行动者才能被归责"）当成了运行基础——那条前提在法哲学上是**假的**（严格责任 / 替代责任 / 产品责任都不需要行动者）。 | **从"判据"降为"启发式"**，并补一条**分层落点规则**（待人裁 T-2）：请求发起者 / 批准者 / 建造者三者分别落点；无人可归时落**保险池**（理论 §5.3 已有此桶）。 |
| 3 | "**共同致错总是落在单桶里**" | "**总是**"被比较过失 / 共同过失 / 市场份额责任直接反驳。 | 删掉"总是"，改为"**在可预见性可判定的情形下**落在单桶里"。 |

### 4.3.2 必须补上的两个位置

| # | 缺的位置 | 为什么 | 建议 |
|---|---|---|---|
| 1 | **建造者**缺席归责表 | 理论 §5.3 的归责只落"厂商"与"使用者"，而 §1.3 自己承认"**本理论工作也是一股定型力量**"。**它把自己排除在自己的归责表之外。** | 把"建造者"作为第三个落点写进 §5.3，并承认建造者握有"本体 / 门禁 / 词表 / 判据版本化"这四项权力 |
| 2 | **"未定型"是修辞性庇护** | 它预设三方势均力敌，而实际上厂商握模型与策略、使用者只有"退出"、建造者握本体与判据——**力量并不对等**；且"未定型"**不可证伪**（任何批评都能被"还没定型"挡回） | 改名或加限定：**"已被定型为分布式无责"** 是一个可证伪的表述（可核：看谁握有否决权），而"未定型"不是 |

### 4.3.3 判据组的加强（采纳 F 的五条，与原判据并列）

原判据是"**它最终把机制交到谁手里**"。F 指出它可被四种方式规避（本地部署 + 专有格式 / 名义可导出 / 审计托第三方 / 期权式开放），并给出更强的一组：

| 检验 | 问什么 |
|---|---|
| **① 退出测试** | 我能不能带着全部历史离开？（不是"能不能导出"，是"离开之后还能不能独立复算"） |
| **② 冲突测试（最强）** | **我与它意见相左时，谁拥有有效的否决权？** |
| ③ 迁移测试 | 换一个实现，历史还读得懂吗？ |
| ④ 重写测试 | 从账本能重建出当前的一切吗？ |
| ⑤ 否决点地图 | 从"我想做一件事"到"它发生"，中间有几个否决点，各在谁手里？ |

**处置**：**并列为"快判 + 细判"**——原判据用于方向快判，五条用于细判。**不替换**（理由见 §4.5）。

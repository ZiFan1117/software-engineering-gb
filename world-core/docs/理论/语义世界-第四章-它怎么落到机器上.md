# 第四章 · 它怎么落到机器上

> 一个入口写，一本账存，各方按自己要用的方式读。

## 4.1 只有一个地方能写

世界上发生的每一件事，落下来都是一条记录。记录进账本只有一条路：世界先给它一个位置号，再照固定形式把它写全，然后问两件事——形式对不对、这件事准不准做。两件都过了，才落笔。

这四步的顺序是固定的，不许交换。校验放在落笔之前，账本里就不会出现一条形式不合的记录；裁决放在落笔之前，"允不允许"这件事才有地方问。顺序一旦可以交换，账本里就会出现半成品，而半成品最难查：你分不清它是一条写坏了的记录，还是一条本该被拒绝的记录。

把写入收在一处，理由只有一条：防"两本账"。

两本账的意思是，对象自己存一份，记录再存一份。两边各自演进，短期内看不出问题，长期必然对不上。对不上的时候最麻烦的一点是不知道该信哪一边，两份都自洽，两份都有来历。走到那一步，前面所有关于"共同的说法"的功夫都白做，因为世界自己先有了两套说法。

防法是结构上的。这一层不单独保存状态：状态由账本折出来，从头折到第几个位置，就是第几个位置上的世界，任何时刻都可以重算一遍。既然没有第二份"当前的样子"摆在那里，也就没有第二条路径能改它。一条记录落进来，折出来的状态跟着变；谁想改世界，只能往账本里加一条。

代码上的形态与之对应：写世界的函数只有一个，它拿着的三样东西——说法、策略、账本——对外都是私有的，账本自己的追加动作对外也不可见。这一条是编译期的事实，工程里留了一段必须编译失败的用例钉着它：任何人想从外部拿到账本的可变引用，编译就过不去。承诺写进类型里，就不再依赖谁的自觉。

还有一条边界要一起说清：账本是世界的唯一真相，可它保存的是"世界里发生过什么"。世界外面的东西，账本替它记不下来，也替它撤不回来。这条边界决定了这一层能做到哪一步，第五章开头那一句说的就是它。

**所有改变都走同一条路，落进同一本账。**

## 4.2 谁被允许做什么

世界上能做的事，每一件都有一个名字，比如"静音一条通知"。要请世界做一件事，就写一条请求，把这件事的名字、动词、参数填进去。请求写好了不等于能做，中间还有一道闸，它回答一个问题：这条请求现在能不能执行。

闸只有两个输入：这件事叫什么名字，以及这件事做完回不回得来。两个输入都来自出厂写好的策略，当场不看别的。

用静态策略定这两件事，理由在"回不回得来"的判断成本上。一件事做完能不能撤回，往往要到做的时候才看得清，而做的时候正是最容易出错的时刻。把这项判断挪到出厂时按类别定级，现场只查表，判断就不必在压力下做第二遍。判据会移动的时候，改的是策略，现场的人照旧动手。

闸的默认回答是不放行。策略里没有的能力一律不行。策略若是一份空表，世界直接拒绝启动：空表的意思是这份规矩还没写。把"没写"当成"不许"，出了事查不出来；把"没写"当成"随便"，出事只是时间问题。两种都不行，所以空表不许上电。

放行分两档。做完能撤回的，免去前置检查，但必须留痕；做完回不来的，加摩擦。档位的差别写在策略里，由策略决定，不由当次的请求决定。

被拦下的请求也要留痕。请求本身不写进账本，因为它没有发生；世界会另落一条通告，说明它拦下过一件事、理由是什么。只拦不记的做法丢掉的是审计的一半：事后你只看到世界是干净的，看不到它替你挡了什么，也看不到是谁在反复试。

真正改状态的写动作是"变更"，所以变更也必须过闸。只让请求过闸是不够的：问的是"准不准做这件事"，绕过去做的是"直接改那个字段"。变更落笔之前要问一句：这个主体能不能写这个对象。

通告另有一道窄闸。凡是以"世界拦下过什么"为名的通告，只许世界自己写；其余通告的写信人必须先在主体名单里。这条守的是审计的根：如果"世界拒绝过这件事"这句话任何人都能替世界说，那么账本里每一句"世界说过"都不再可信。

闸之外还要有墙。闸是决策，墙是"规则与账本所在的地方，被管者写不进去"。墙查两件事：那两个文件本身不得对同组的其他用户开放写权限，它们所在的目录也不得。目录那一条不多余，文件权限挡不住"删掉再放一个新的"，而目录可写就等于这条规矩可以被整体换掉。墙查不过，世界拒绝启动。一个以为自己有闸、实际上闸可以被人换掉的世界，比一个明确拒绝启动的世界危险得多。

**闸按出厂策略回答，拦下也要留痕。**

## 4.3 谁在说话由系统给出

每条记录里有一个格子回答"谁做的"。这个格子的值由系统给出，写请求的人填不了。

理由在记录的用途上。一条记录要能被不问你的人读出来，前提是里面的"谁"确实是谁。如果这个格子来自请求自称，那么一条记录能证明的只有"有人这么说过"；出了事去查账，查到一个字符串，字符串后面没有人。账本的全部价值在于"这句话是世界记下的"，写信的人一旦可以随便署名，账本再完整，也只是各方的自述材料订在一起。

系统给身份有两种入口形态，方向相同。

一种是长期入口。每个跨进程的入口在建立的时候就绑好一个身份与一个系统用户。这个入口的属主与权限位由世界设定，只有那一个用户连得上。请求里如果自称了别的身份，直接拒绝；落笔时那个格子的值取自绑定关系，绝不取请求里的字符串。

另一种是一次性入口。人在终端上敲一条命令，也是一次请求。这类入口同样要先有身份再谈请求，而且缺省身份必须写出来、写明白，不许用"不填就等于某个身份"来省事。省下来的那点方便，会在审计那里连本带利还回去。

身份在世界上是一个一等对象，像 `world://user`、`world://agent/1` 这样写。进程号、系统用户名都不是它的写法。内核认识进程、内存、文件、权限，它不认识"谁在这个世界里做了这件事"。同一个系统用户下跑两个 agent，它们在世界上是两个身份：世界要区分的是做事的那个主体，承载它的那个进程不在它要区分的东西里。

身份与允许分开。身份回答"谁在说话"，能不能做由 4.2 的闸回答。两件事合起来才是一句完整的话：某人做了某事，这件事被允许。把它们压成一个东西，就会出现"只要连得上就什么都能做"，而这正是身份这一格要防的事。

身份还要经得起换载体的检验。系统用户是谁、进程跑在哪里、通道用哪种，都是载体的事，载体是可以换的；世界里的身份不跟着换，因为它记的是主体，承载不是它要记的东西。

命令行入口今天的样子，见 5.4。

**身份由入口给出，请求说了不算。**

## 4.4 读的那一份

账本只往后加，读的人要的是"现在是什么样"。中间隔着一步：把账本从头折一遍，折到当前位置，得到一份状态；再按各方的需要把这份状态摆开。给程序的那一份是能直接用的结构，给人的那一份是能直接看的呈现。读法的份数不固定，将来接进来的参与方也各有一份。

这几份读法之间的规矩只有一条：谁也不调用谁。

不互相调用的意思是，没有一份要问另一份"你那里是什么"，也没有一份可以把自己的输出当作另一份的输入。它们都是账本的读法。读法是叶子，只负责往外给。

一致靠结构，具体落在三处。

第一处，折叠只有一个。同一本账折出来的状态是同一份，连字节都一样；两份读法的样子差别再大，它们看到的是同一份输入。读法可以很不一样，摆出来的内容来自同一处，说法的份数始终是一份。

第二处，头部可比。每一份读法的开头都带一行给机器读的头部，写明四件事：我用的是哪一版说法、我算到第几条、我这份状态的指纹、我是哪一份。四个值一比，就知道两份东西是不是从同一处、同一版算法取来的；哪一方落后了一条记录，也在这一行上看得出来。核对因此不需要任何一方解释自己，比一行字就够了。

第三处，说法本身可寻址。只保证"读同一份数据"还不够：两方可以各拿一套自己的解释规则去读同一份数据，读出来的仍然不是同一件事。所以这一版说法自身要有一个由内容算出来的指纹，内容相同指纹就相同，内容一动指纹就变。两份读法出示的指纹相同，说明它们用的是同一套解释规则；不同，说明两边用的不是同一版说法，这件事必须先查清再谈别的。

还有一组信号，出现任意一条，就说明真相已经分叉，要停下来查：有人提出让两份读法互相同步状态；有人让读法甲把消息发给读法乙；有人把状态存在读法里；有人让 agent 直接读界面上显示的内容。这四句有同一个形式，它们都把读法当成了中转站。

读法不持有状态。读法可以有自己的显示偏好，比如排序、折叠、配色，这些偏好不影响它摆出来的内容；读法一旦开始记自己那一份状态，它就有了自己的说法，而这一层只允许一份说法。

这一节讲的那四个值，今天核的是什么，见 5.2。

**几份读法各自算，一致靠结构不靠商量。**

## 4.5 外面发生的事怎么写成一条消息

记录不产生于世界内部。设备动了、旧系统的状态变了、人在界面上点了一下，这些事发生在外面，各自有各自的样子。它们与世界要的形式之间隔着一只手，这只手在写侧，它的纪律只有一条：只写，不裁决。准不准做，一律问 4.2 那道闸。

设备的动作变成消息，分两步对表。

第一步是名字。一件能在世界上做的事，先在出厂策略里有一个世界用的名字，再配一张"在这台机器上怎么干"的执行清单：用哪个执行器、允许哪些动词、要不要动手前留一个撤销点、要不要人确认。这张执行清单里没有"允不允许"这一栏，允许与否由闸回答。名字对齐以后，设备叫什么、用哪个驱动，都不影响世界这边的说法。

两层各有各的答案，谁都不越界。策略管准不准做；执行清单管怎么干。做完要退回去的时候，退的是哪一样，也分两处：世界里的状态，靠再写一条方向相反的记录退回去，这才叫世界可逆；动手前留的那个撤销点，撤的只是文件系统上的字节，是一层工程上的保险。世界状态照旧由补偿记录负责，一份执行清单里留着某件事的撤销点，跟世界里这件事可不可逆，是两回事。

第二步是动作的起落。请求进来，过闸，执行，然后把结果写成一条记录落账。结果本身也是记录，这一条在三个家族里已经定好：一件事被请求之后成没成，要写下来。结果只交回给请求方而没有落账的情形，事后无从查起。

旧系统的状态变成消息，难点在前值。旧系统知道自己现在是什么样，不知道原来是什么样；文件系统能告诉你某个文件昨天被改过，告诉不了你改的是哪个字段、原来是什么值。写侧要做的是把"某个文件的一行变了"翻成"某个对象的某个字段从旧值变成新值"，前值必须带上。少了前值，撤销与复盘各缺一半材料。

翻的时候还有一条要守：写侧不许替世界补意思。翻不出来就报错，不许猜一个近似的字段名填上去。猜出来的字段名会进账本，进去以后就成了"事实"，而它从来没被任何人说过。

大对象不进主干道。要搬的字节走并行的货运道，主干道上只留一个内容指纹；谁需要那份字节，照指纹去取。这样主干道上的每一条记录都短，读它的人不会被字节挤掉上下文，索引与复制也不会被大块头拖住。

写侧这只手跑在自己的进程里，以被管者身份运行，对账本与规则都没有写权限。它要写世界，只能经通道提交请求，走的是和别的任何主体完全相同的那条路：校验、过闸、落笔。这一点是"唯一入口"能不能成立的前提。手如果自己有写权限，世界就有了第二个权威，两处都能决定"这件事允不允许"，两处的结论迟早不同。

**写侧不裁决，两条撤销路径各管各的。**

## 4.6 怎么把话送到

一条记录落笔的时候，世界给它分配一个位置号。位置号全局只增：一条不跳、一条不重、也不会因为没人看而空着。这就是"送到"这件事的底子，位置一定在，因为它是账本本身的形状。

另一半是提醒。每条记录的信封里有一个"给谁"的格子，写明这条消息是给谁的；格子空着表示广播。谁该知道一件事，就把这件事提醒给谁。

送的办法分三层。

第一层，落笔即发布。记录一落账就可以被读，读的人不必等谁来通知他。这一层保证的是，只要有人读，内容就在那里。

第二层，提醒可以补。提醒与落笔不在同一时刻到达，也不保证一定到达。线路断了、那一方当时不在、通知没送到，都不改动账本。收话的一方自己记着"我读到第几条"这个数，回来以后照位置把缺的那一段读回去，就补齐了。补看与第一次看没有区别，因为账本只往后加，位置不会变。

第三层，重传不重复。每条记录有它自身的身份，用来去重。同一条被送两次，落到账本上仍然是一条；收话的一方拿两次，也只当作一次。

请求与结果的配对靠两处对齐：同一个请求编号，以及"因为哪一条"那一格指回提出这件事的那条记录。两处都在账本上，配对因此可以在事后核对，不必依赖当时在场的谁记得。

大对象不挤主干道。主干道上只放内容指纹，字节走另一条道；两条道并行，运单号就是那个指纹。这样"送到"这件事在主干道上只剩下很短的一行，谁漏了哪一段也能一眼看出。

这一节的规格在 2.11 已经说过：通知可以漏，序号不会漏。这一节补的是它怎么送：位置由落笔时分配，提醒按"给谁"发出去，缺的一段按位置补回来。今天送到哪一步，见第五章。

**落账就是发布，漏掉的提醒按位置补回来。**

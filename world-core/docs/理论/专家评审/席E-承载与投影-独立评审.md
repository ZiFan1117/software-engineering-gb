## 一、评审结论

**一句话**：这套「一份真相 + N 个只读投影」的方向正确、纪律罕见地干净（我从源码层面独立复核，未发现"投影持有状态"或"投影互读"的实例），
但它目前**只有"出来的那一半"**——没有入向（人把动作写回）、没有注册表、没有"自上次以来"的时间窗口、没有注意力的预算模型，
因此 §7.1 人↔Computer 那一对闭环（"一个表面看全：进行中任务 / 待确认请求 / 高危预案"）**在实现里三项全空**，
四条高效判据**只有"谈判一次"有半个量具**；这不是实现欠账，是**呈现层的概念尚未被立成概念**。

**要点**：

1. **"视觉投影 = 终端排版"与 §7.2 的命名纪律不冲突，冲突在别处**："web 是实现不是名字"这条纪律要求的是**名字不绑技术栈**；
   现在的实现连"web"都没有（`WC-SRS-001` REQ-F-019 自述"真正的网页渲染为 0"），所以它**没有违反**该纪律。
   真正的病是：**它把"给人看"和"能被脚本提取"设计成了同一层同一份字节**，于是两边的优化方向互相锁死——
   脚本要全量、稳定、无截断；人要入口、显著性、渐进披露。**二者不可在同一层同时最优**。
   【推断】这不是取舍失误，是在缺"呈现层"这个分层概念的情况下，**用渲染契约顶替了信息架构**。

2. **"投影不交互"这条铁律本身是对的，但被立错了对象**：它禁的应该是**投影之间私相授受状态**，
   而不是**两个视图共享一个"视图上下文"**。今天铁律之所以看起来挡路，是因为系统里没有
   比"投影"更高的概念（没有 view / view-context / presentation intent），
   于是所有跨视图需求都被迫撞在这条铁律上。**正确的落点在底座侧**：把"要显示什么"做成**可寻址的只读查询对象**，
   投影只是它的渲染器。这样联动 = 两个渲染器读同一个查询结果，**恰恰是铁律的保护对象而不是例外**。

3. **N 端口注册表最承重的字段不是"名字/实现"，是"覆盖声明 + 省略清单"**。
   今天 `assert_same_source` 只比首行（`world`/`vocab`/`last_seq`/`state`，`src/project/mod.rs:124-147`），
   **它证明"两个出口读的是同一份输入"，它不能证明"两个出口说的是同一件事"**：
   一个投影少显示一半主体，同源核对**照样全绿**。要让"新增端口必须同源"被机器判定，
   必须让**省略本身成为可数、可核对的事实**。

4. **"待确认请求不存在"这个判断需要一处精确化**（这是我要提请委托方注意的第一处事实订正）：
   待批**事件存在且信息完整**——`record_gate_notice` 把 `capability`/`verb`/`request_id`/`reason`
   全量写进了 `notice`（`src/lib.rs:291-314`），并在真实账本里出现过（`系统全景图.md:84-87` 第 3 行）。
   不存在的是三样：**① 待批集没有被物化进读模型**（`State::apply` 对 `notice` 只 `self.notices += 1`，
   见 `src/readmodel.rs:106-116` ⇒ 它的主体/载荷**在任何投影里都不可见**）；
   **② 没有批准通道**（`gate.rs:57-59`、`policy.json` 的 `_irreversible_note`）；
   **③ 没有"解算"语义**（一条待批永远不会有终态，既不会过期也不会关闭）。
   ⇒ 界面结论不变（**人今天看不到待批**），但根因是**读模型缺了一层物化**，不是"事件不存在"——
   后者若被写进设计文档，会导致"要新增事件类型"的错误方案。

5. **无障碍上，这套架构的天赋优势与最大陷阱是同一件事**：同源多端口天然就是
   "语义层 / 呈现层分离"（WAI-ARIA 的整个思路）的架构级实现，这是**优势**；
   但"只减不增"若被字面理解为"投影不得添加任何状态源里没有的东西"，
   就会把**可操作性**也判为"不得添加"——那时屏幕上有按钮、听觉端口没有对应通路，
   无障碍的缺口就不是"漏了"，而是**设计上被禁止**。这是我给出的那条硬要求的由来。

## 二、逐条评审

### 2.1 第 1 问：视觉投影 = 终端排版，与「web 是实现，不是名字」是否一致？

**原文/代码引用**

- `2-依据/15-世界核心的组成与职责.md:215-230`（§7.2）：
  > | 名字（进本体） | 实现（可换，属脐带/载体） |
  > | **视觉投影** | **v1 = transferor 渲染到浏览器**；将来 = 桌面 / 终端 / Genode 原生 |
  > 三条反对"web 投影"这个名的纪律：……总纲 §8 "去掉 `surface` 四面枚举与 `browser.*` 命名空间……**渲染概念不进本体**"。
- `src/project/visual.rs:1-23`：
  > ⚠️ **不是"终端版应用"，是"同一份真相的另一种画法"**。……**排版规则（审计脚本依赖它，不许随意改）**：
  > **2 空格缩进 = 主体行；6 空格缩进 + `路径 = 值` = 字段行**。
- `src/project/mod.rs:34-38`：
  > 视觉投影是给人的，但**不是不可解析的**：它的取值行必须能被审计脚本提取（`      muted = false`）。
  > 否则"同源"根本无法证明——**给人看的东西也要能被机器核对**，这是本项目对"可信"的最低要求。
- `tools/visual_layout_audit.py:19-32`：11 条字节级排版契约（首行正则、标题逐字、分隔线**恰 44 个 U+2500**、
  主体行**恰好 2 空格 + `world://…`**、字段行**恰好 6 空格**、无裸控制字符、LF 结尾……）。
- `WC-SRS-001-v0.1.md:262`（REQ-F-019）自述：
  > **形态实测（不夸大）**：v1 只有**一种**出口——渲染到**标准输出**的文本；**真正的网页渲染为 0**。

**我的判断**

- 与 §7.2 的**命名纪律一致**。该纪律管的是"名字不许绑技术栈"，代码里确实没有 `surface` / `browser.*` /
  `world://` 之外的渲染概念（我 grep 过 `src/`：`project` 相关命名只有 language / visual）。
  **"视觉投影 = 终端排版"不违反它。** 这一条我判**通过**。
- 但"可被审计脚本提取的排版**能不能同时是合格的"给人看""——**不能，且不应要求它同时是**。
  理由三条，都是可复核的：

  **(a) 两者的目标函数相反。** 审计脚本要**全量、稳定、无截断、可逆解析**；
  人的阅读要**入口、显著性、可中断、渐进披露**。`visual.rs:50-55` 对**每一个主体、每一个字段**
  平铺输出（无排序权重、无分组、无重要度），这在脚本视角是优点（完备），在人视角是缺陷（`系统全景图.md:94`
  实测状态只有 2 个主体时尚可读；一旦主体数到 50，这是"可审计的墙"，不是"界面"）。

  **(b) 排版契约正在替协议层干活，而它没有版本号也没有转义规范。**
  两处**独立解析器**对"合法主体行"的定义**不一致**：
  `src/project/visual.rs:80-89` 接受**任何**非提示的 2 空格缩进行并 `trim()`；
  `tools/visual_layout_audit.py:57` 要求 `^ {2}(world://\S+)$`。
  而 `ontology.json:25-41` **不对 `subject` 做任何形状校验**（只有 `required` 名单，无 `pattern`）。
  ⇒ 【推断】一个含空格或换行的合法 `subject` 会让**渲染器接受、独立审计器报红**；
  换行还能让"主体身份"被 `trim()` 改写（`visual.rs:81`），而 `REQ-F-024`（只减不增）恰恰是
  用"解析回来逐项相等"来判定的。这不是安全漏洞，是**"排版即协议"这一决定的必然代价**：
  你把语法压进了空格数量，就必须为它配上词法（转义）、版本（v1/v2）、以及唯一权威解析器。今天三样都没有。

  **(c) 首行契约的信息量不足以支撑"同源"这句话。** 首行只有 `projection` / `world` / `vocab` /
  `last_seq` / `state`（`src/project/mod.rs:77-83`）。**它缺三样**：该投影的**覆盖声明**（它省略了什么）、
  **端口身份与实现版本**、**渲染契约版本**。缺前两样，"新增端口必须同源"就只能靠人读代码判定。

**分层建议（这是本席对第 1 问的正面产出）**

| 层 | 归谁 | 内容 | 可换性 |
|---|---|---|---|
| **L0 事实层** | 账本（唯一真相） | 事件；`seq` 全序；`at`；`trace`；`actor` | **不可换** |
| **L1 投影契约层（进本体）** | 世界核心 | ① **端口身份**（`port_id`、命名空间、版本）；② **读集声明**（读哪些主体/字段/窗口）；③ **覆盖与省略声明**（总数 + 省略清单，机器可数）；④ **同源头四要素**（今天的 5 项 + `port` + `contract` 版本）；⑤ **入向声明**（本端口可提交哪些动作，仅限追加事件）；⑥ **新鲜度声明**（`base_seq` / 落后容忍 / 落后时的行为） | 只增不改；改动走变更评审 |
| **L2 呈现契约层（**不进本体**，属实现）** | 各端实现 | 排版 / 布局 / 字体 / 颜色 / 分组 / 折叠 / 显著性 / 动效 / 键盘映射 / 语音韵律 | **可换**，但要**自报版本**并**自证不与 L1 冲突** |
| **L3 交互实现层** | 各端实现 | 点击 / 快捷键 / 语音指令 / 手势；**其唯一合法产物是一条 `act` 事件** | 可换 |
| **L4 无障碍与多端适配** | 各端实现 + 部署 | 屏幕阅读语义、对比度、朗读稿、触觉、字号；**须能回指 L1 的 `port_id`** | 可换 |

**改法与代价**

1. **把 `visual.rs` 实现层改名定位、加一层最小 IR。** 代价：一处新结构体 + 一个渲染器，估 1–2 人日；
   收益是"换实现"从此不用改审计脚本——**审计脚本改为审计 IR，不再审计空格**。
2. **给首行加 `port=<id>` 与 `contract=<n>` 两个字段；并在 `visual.rs` 里加转义**（`subject` 中的
   空格/换行用 `\u0020` 之类显式转义，或把主体行改为 JSON 单行）。代价：**破坏现有 3 份字节级样本**
   （`tools/visual_layout_audit.py:155-178`）+ R5 变更 + 独立审计器同步改；**这是必要代价**，
   越晚改越贵——现在只有 1 份审计脚本依赖它，将来会有 N 个端口和 M 个消费方。
3. 【推断】`REQ-F-019` 里的"网页"形态建议**删掉**（`WC-SRS-001-v0.1.md:262` 记该去留待人裁），
   理由：它不是需求，是实现选择，留着会持续诱导"视觉投影 = 浏览器"的错误等式——
   而那正是 §7.2 三条纪律要防的。

### 2.2 第 2 问：「投影不交互」会挡住哪些真实需求？正确落点在哪？

**原文/代码引用**

- `2-依据/15-世界核心的组成与职责.md:232-236`（§7.3）：
  > - 投影是**出口（叶子节点）**，不是中继节点；它们不需要交互，因为**它们只可能看到同一份东西**……
  > - "同源"不是靠**商量**达成的，是靠**结构**保证的。
- 同篇 `:244-253`（§7.5 漏水信号）："投影 A 要通知投影 B" / "让两个投影同步一下状态" / **"这段状态存在投影里"**。
- `src/project/mod.rs:1-16`：两渲染函数只接受 `(&State, world, vocab)`，返回 `String`；**没有共享可变缓存可挂**。
- `docs/S2-设计/WC-ARCH-001-v0.1.md:92`（硬约束 3）：
  > 关掉载体执行器，两块投影的输出**逐字节不变**；…两块出口跑在同一进程内，但**只共享只读输入**。

**先确认铁律的现状**：我独立复核过，**没有发现违反**。两个 `render` 是纯函数，无缓存、无互读、
无状态字段（`mod.rs:53-83`；只有 `group_by_subject` 这一个**共用只读**归拢函数）。
这条铁律的执行质量我给正面评价——**这不是客套**：绝大多数系统在这一步就烂掉了。

**构造 3 个会被它挡住的真实需求，并给出正确落点**

> 说明：以下三个需求**都成立**，也都**不该破铁律**。它们的共同病因是同一个：
> **系统里只有"投影"这一个概念，没有"视图"（view）这个概念**。于是"两个视图要一致"无处安放，
> 只能翻译成"两个投影要通信"——那确实该被挡。

**需求 A：两个视图联动高亮（桌面 + 大屏 / 主视图 + 侧栏），点一个对象，两处同时高亮。**

- 会被什么挡住：最直觉的实现是"视图甲把选中项发给视图乙"。这正是 §7.5 第一条漏水信号，**应当被挡**。
- **正确落点**：高亮不是**状态**，是**呈现偏好**（`15` 篇 §7.5 第五句已开这个口子："投影**不持有状态**，只持有渲染偏好"）。
  做法：底座提供一个**可寻址的视图上下文对象**——它不是事件，也不是状态源里的字段，而是
  **投影进程的一个只读查询参数**：`view(parent_sel="world://job/j-A", highlight=that)`。
  两个渲染器各自用**同一个查询参数**渲染；它们之间**零通信**。
- **为什么这不破铁律**：铁律禁的是"投影之间私相授受"，不是"两个渲染器读同一个输入"。
  联动是**同一个输入的两次渲染**，与"两个投影读同一份读模型"是同构的——**铁律在这里是保护者**。
- **代价**：需要在 `render()` 签名上加第三个只读参数（今天签名是 `(state, world, vocab)`，`visual.rs:29`），
  并明确"视图参数不落账本、不进投影输出、丢了不影响真相"。**代价小，收益是挡住一整类漏水。**

**需求 B：人在一个界面上的操作，要反映到另一个界面（桌面点了"静音"，手表/通知栏即时反映）。**

- 会被什么挡住（如果按直觉实现）：让显示端互相通知；或把"最新状态"缓存到显示端。**都该被挡**。
- **正确落点**：这是 §7.1 例子的原样复现——写 `act` → 门禁 → `change` → 账本 → **N 个投影各自重算**。
  链路完全存在，**唯一缺的是"各自重算的触发"**：今天没有任何主动推送（`WC-ARCH-001:69` 明写投影服务的对外接口是
  "标准输出／**将来的**推送面"；`WC-IRS-001` §1284 把"投影服务的推送面"列为**范围外**）。
  ⇒ 人点了静音，桌面端重渲染，手表端**不会**知道，除非它自己去问。**"两个界面不一致"因此是必然的，
  而不是因为铁律挡住了什么。**
- **正确落点的第二半（更重）**：**谁来观察"两个消费端是否落后"？** 今天的 `assert_same_source`
  只比较**两个渲染输出**（`mod.rs:124`），它回答"此刻两份输出是否同源"；
  它**不回答"消费方读到的是不是最新"**。⇒ 需要一条纪律：**任何消费方在做出判断前，必须出示它读到的 `last_seq`**，
  而任何"基于世界状态的动作"都应在事件里带 `base_seq`（`15` 篇 §十二 待定项 1 早就点出这个洞，至今未裁）。
- **代价**：加推送面（订阅/增量）是**大工程**，但**可以先做最小版**：一条 `notice.job.done` 完工铃
  （`WC-FSR-001:266` REQ-N-001 已有此要求，`WC-SDP-001:1727-1740` 甚至已经设计好
  `pending []Bell` 的"先响后订阅"竞态处置）——**这是仓库里已经有设计、只差实现的一块，建议优先。**

**需求 C：跨设备的同一状态（笔记本 / 手机 / 手表三端看同一个世界）。**

- 会被什么挡住：如果"跨设备一致"被翻译成"三端互相同步状态"，**应当被挡**（那是三份状态、三个世界）。
- **正确落点**：三端各自是**独立运行的投影消费方**，共享的唯一东西是**账本的一个只读游标**。
  一致性的判据**不是"看起来一样"**，而是 `(world, vocab, last_seq, state)` 四要素相同——
  这套机制**已经存在**（`mod.rs:124-147`），它是本项目相对外部系统最硬的一块资产。
- **但它有个今天没解的前提**：**词表 hash 是产出方自己写在首行的**（`mod.rs:77-83`），
  无签名、无 MAC——`WC-FMT-001` 的 `【待确认 C-03】` 已如实登记这一点（我从 grep 命中片段读到该登记，**未读到该文件全文**）。
  ⇒ 对"合作中的多端"这够了；对"我不信任的那个端"不够。
  建议：**把"同源判定"的信任模型写进契约**（今天它默认所有投影都诚实），并在注册表里为每个端口记
  `attestation: none | hash-chain | signature`。
- **代价**：若将来真要做签名，会引入依赖（与 `Cargo.toml:8-13`"只允许 `serde_json`"的纪律冲突）——
  **现在只需把字段留出来，不必实现**。

**三个需求的共同结论**

| 需求 | 该由谁满足 | 在哪落地 |
|---|---|---|
| A 联动高亮 | **底座**（只读视图参数） | 投影进程；不落账本 |
| B 操作跨界面反映 | **底座**（推送/订阅 + 消费方出示 `base_seq`） | 投影服务；**不**在投影之间 |
| C 跨设备同一状态 | **各端独立消费** + **四要素同源判定** | 账本游标 + 首行契约 |

一句话：**"联动"是底座的活，"同步"是消费方的活，投影只负责"画得对"。**

### 2.3 第 3 问：N 端口注册表最少要有哪些字段？三个具体第三端口

**原文/代码引用**

- `00-总纲.md:152-161`（§2.5）：

**我的判断（一处事实订正）**

「**没有注册表**」成立（我全文 grep 过 `world-core/`：`注册` 的命中全部是"模块登记表/执行器注册表/用户注册"，
**没有一个是投影端口注册**）。
「**"注册"这个动作没有**」**部分不成立、但结论仍成立**：注册对象**不存在**，但
**"投影已注册"这句话在仓库里是被反复引用的合格判据**——`WC-FSR-001:260`（REQ-F-016 启动顺序第⑤步）、
`WC-SQAP-001:323`/`:546`（`QG-06` 的 `env -i` 一条命令验四条件）、`WC-SDP-001:433`（AC-01）。
⇒ **这是"判据引用了不存在的标的物"**，比"功能没做"严重一档：门禁在为一个空概念发绿灯。
（这正是 `WC-SCMP-001` 自己批判过的失败模式——"该报错时不报错"。）

**注册表最小字段（我的设计）**

设计原则三条：① **注册表本身必须是本体对象**（否则它是第二本账，`15` 篇 §八 "一个写入口，一个账本"）；
② **声明 ≠ 存活**：声明在词表里（可版本化、可评审），存活是运行期观测（进程自己报，可假）；
③ **凡"省略"必须可数**，否则"只减不增"无法判定。

| # | 字段 | 类型 | 为什么**最少**也得有它 | 判据（机器可判） |
|---|---|---|---|---|
| 1 | `port_id` | string（命名空间 + 名，如 `vis/grid`、`aud/alerts`） | 首行的 `projection=` 今天只有一个自由字符串，`assert_same_source` **根本不看它**（`mod.rs:124-147` 只比另外四项） | 端口名 ∈ 词表 `ports` 键集；首行 `port=` 与注册表一致 |
| 2 | `direction` | enum(`out`,`in`,`both`) | 决定它能不能写回。今天**两个端口都是 `out`**，而 `00-总纲.md:264` 明写投影要"出（渲染状态）、**入（把人的操作翻成语义事件）**" | `in`/`both` 的端口必须声明 `submit_families`；`out` 端口下出现写路径即违规 |
| 3 | `read_scope` | 对象（主体前缀/家族/字段清单） | 无它则"只减不增"只对"显示出来的"成立，对"没显示的"无话可说 | 投影里出现的每个 `(主体,路径)` ∈ `read_scope` |
| 4 | **`coverage`** | 对象 `{total_facts:int, shown_facts:int, omitted_rules:[…]}` | **本席认为它是整张表最承重的一行**：省略可数，才谈得上"同源"的完整性 | `shown_facts` **必须等于**审计器从输出里数出的三元组数；不等即"投影在自报覆盖上撒谎" |
| 5 | `window` | 对象 `{mode: state\|since\|range, base_seq?, span?}` | 今天所有端口都只能渲"当前全量状态"；没有窗口概念，"自上次以来"这类**人最需要的视图**无处定义 | 输出首行含 `base_seq=`；`mode=since` 时输出必须含 `from_seq` |
| 6 | `layout_contract` | 对象 `{name:string, version:int, spec_doc:path}` | 排版已经是事实上位协议（`visual_layout_audit.py` 11 条），却**无版本**：改一次就静默破坏所有消费方 | 独立审计器按 `(name,version)` 选契约；版本不在表内 ⇒ 拒绝解析 |
| 7 | `identity` | 对象 `{principal, can_read[], can_write[]}` | 今天投影与内核同进程同权限，靠"权限相同所以同进程"（`WC-ARCH-001:96`）；一旦端口变多，必须逐个声明 | 与 `WC-ARCH-001:90` 硬约束 1 同一判据：读后账本字节摘要不变 |
| 8 | `freshness` | 对象 `{mode: pull\|subscribe, max_lag_seq:int, on_lag: fail\|warn\|recompute}` | `15` 篇 §十二 待定项 1（新鲜度）至今未裁；不写这个字段，"落后了怎么办"就没有默认行为 | 落后超 `max_lag_seq` 时 `on_lag` 必须可观测（红/告警/重算，不得静默） |
| 9 | **`auditable`** | 对象 `{extractor:path, sample_hash, fails_closed:bool}` | `15` 篇 §7.4 要求同源可核验；`visual.rs:34-38` 的立场是"给人看的也要能被机器核对"——**这是本项目的立身之处，必须是一等字段** | 独立提取器（**不得**调用被审端口自己的 `parse`，见 `visual_layout_audit.py:12-13` 的自我要求）跑通；样本 hash 与归档一致 |
| 10 | `a11y_per_port` | 对象 `{modalities[], keyboard_reachable:bool, action_paths{}}` | 见第 6 问；无它则"多端一致"退化为"多端都不一致" | 见 §二.6 的硬要求 |

**登记与观测分离（最小落地形态）**

```jsonc
// ontology.json（法律侧，唯一真相）——只放"声明"
"ports": {
  "vis/grid":  { "direction":"in", "read_scope":{"subjects":["world://*"]},
                 "coverage":{"mode":"full"}, "window":{"mode":"state"},
                 "layout_contract":{"name":"wc-text-grid","version":1},
                 "freshness":{"mode":"pull","on_lag":"recompute"},
                 "auditable":{"extractor":"tools/visual_layout_audit.py","fails_closed":true} },
  "lang/jsonl":{ "direction":"out", "coverage":{"mode":"full"}, "window":{"mode":"state"} }
}
// 运行期（观测侧，可假、可弃）——由 world-projectd 自己报，落在 stdout 首行
#world-core port=vis/grid contract=1 world=1 vocab=fnv1a64:… last_seq=3 state=fnv1a64:… base_seq=3
```

**注意**：`port_id` 用 `vis/*` / `aud/*` 这类**通道前缀**而不是 `web` / `gtk` 这类技术栈名，
是**唯一让 §7.2 那条纪律可被机器执行的写法**——纪律要变成 `port_id` 的命名空间约束，而不只是一句话。
（`surface` 四面枚举曾被 `00-总纲.md:306` 明令去掉，理由是"渲染概念不进本体"；
我要指出：**"哪些通道"不等于"哪个渲染器"**——前者是人的感知模态，后者是代码。删对了，但把模态一起删掉了，
于是"听觉留位"无处落。这是我要登记的一处**过度删减**。）

**三个具体的"第三个端口"及其契约差异**

**(甲) 听觉投影 `aud/alerts`（推荐作为真正的第三端口）**

| 契约面 | 要求 | 与视觉的根本差异 |
|---|---|---|
| `coverage` | **必须允许部分覆盖，且必须可数**：只播"高显著度 + 不可逆 + 待批"三类 | 视觉的"只减不增"默认可以全量；听觉**不可能全量**（人耳是串行通道） |
| `window` | `since`（"自上一条播报以来"）+ 去重窗口 | 视觉可以看"当前全量"；听觉没有"当前状态"这个概念，**状态必须被翻译成一串变化** |
| `directed` | 定向字段：给谁播、在哪播（同一屋子里两个人） | 视觉是公共的（谁看屏幕谁看见）；听觉**天然是广播的，需要寻址** |
| `budget` | 每小时最多 N 条；超预算必须合并成摘要而不是丢弃 | 视觉没有配给；听觉**必须有配给**，否则是骚扰 |
| `replay` | 每句播报必须可**回查文本**（语音转文本 + 服务端合成脚本留档） | 声音瞬时；`15` 篇 §7.4"同源可核验"对听觉**默认不可核验**，必须靠留档补救 |
| `a11y` | 这个端口**本身就是无障碍通路**，不得作为"附加装饰" | 见 §二.6 |

**必须钉死的一条**：**听觉端口只做"出"**。语音输入要成为投影的入向，就必须先定义
"语音 → 意图"的翻译层，而那正是 `00-总纲.md:170-174`（§2.6）判为**锚定风险最高**的区域
（"翻译器必须懂 DOM，世界不必懂"的同构问题）。**建议 v1 只做出向，入向留给脐带。**

**(乙) 通知栏 `surface/notify`（成本最低、即时可用，但有概念风险）**

- 契约差异：`window=since`（必须是增量）；`coverage` 极端受限（一次 1–3 条）；
  **必须有 `ack` 语义**（人点掉之后账本上要有痕，否则"哪些在等我"无法闭合）；
  **必须有 `persistence` 声明**（通知中心里的通知关掉就没了 ⇒ 若世界状态依赖它，那是"状态存在投影里"，属 §7.5 漏水）。
- **概念风险（必须写出来）**：通知栏在今天的 Windows / macOS / Android 上**既是渲染表面又是点击入口**，
  而它的入口语义是"启动某个应用"。若照抄，"点通知"就绕过了门禁直接执行动作——
  **这是本架构绝不能接受的**。因此：`surface/notify` 的入向**只允许产出 `act` 事件**，
  且其 `identity` 必须是**世界内身份**而非"桌面会话身份"。
- 【推断】建议**不把它单独列为一个端口**，而定义为 `vis/grid` 的一个**受限视口**（同 `port_id`、不同 `window`），
  以免端口清单被平台形态牵着走——那正是 §7.2 要防的。

**(丙) 可穿戴 `wear/glance`（极端约束下的摘要端口）**

- 契约差异：`coverage` 必须声明"**只显示一个判断，不显示事实集合**"；
  `window=state` 但 `render_mode=summary`（**摘要是一种"添加"吗？**——本席认为不是，因为它不引入状态源里没有的事实，
  只是选择与压缩；**但必须由 `coverage.omitted_rules` 显式声明压缩规则**，否则它与"添加"无法区分）；
  `input` 只能是二元确认（同意/拒绝），**且必须是"批准"语义而不是"再次提交"语义**（否则一次抬手就触发动作）；
  `a11y`：触觉与极短文本是**主通路**而非降级通路。
- 若可穿戴要做"批准"，它会**强制**审批通道先存在——**这是它作为第三端口最大的价值**（见第 4 问）。

### 2.4 第 4 问：没有「待批集」的世界，人的界面应该是怎样的？补上审批通道后契约怎么变？

**原文/代码引用**

- `1-理论与哲学/00-理论定稿.md:162-166`（§7.1）：
  > | 人 ↔ Computer | **投影协作**：界面成为三方协作状态的投影（**进行中任务 / 待确认请求 / 高危预案**） | 一个表面看全 |
- `00-总纲.md:29-31`（常设验收）：
  > **人离开 24 小时后回来，能答出"发生过什么、哪些在等我批"**——不靠人盯守。
- `src/readmodel.rs:106-116`：`notice` 只累加计数，**不进 `objects`** ⇒ 待批的 subject/payload 在投影里不可见。
- `src/lib.rs:291-314`：待批的 `notice` 载荷含 `capability`/`verb`/`request_id`/`reason`——**信息是齐的**。
- `src/gate.rs:57-59` + `policy.json:33`（`_irreversible_note`）：
  > v1 **没有审批通道**：不可逆动作**只允许**这里列出的主体执行。其他主体会收到 AwaitApproval，且理由里明说『**不要等批准**』。
- `docs/S2-设计/WC-ARCH-001-v0.1.md:61`：载体执行器"**需要人确认的动作在此等确认**"；
  `src/carrier/run.rs:96-130`：确认入口是 **stdin 的 `y/N` 提示**（`--allow-confirm` 默认为关）；
  `run.rs:124-130`：`NeverConfirm`"无人在场时的口径：**拒绝**"。
- `系统全景图.md:155`（明说的边界 1）："**v1 没有审批通道**：不可逆动作只认白名单主体；被摩擦的主体拿到的是'不要等批准，它不会来'"。

**我的判断（先做三处事实订正，再给设计）**

**订正 1（重要）：待批集"存在，但不可见"。** 见 §一.4。⇒ 界面今天的实际形态是：
**人只能靠 `read` + 人眼扫账本来发现待批**——而那正是 `00-总纲.md:29-31` 要消灭的"靠盯守"。

**订正 2（重要）：系统的"确认入口"在哪里，是一个未定义的概念位置。**
今天存在**两个互不相干的"人确认"**：
① **门禁的"加摩擦"**（`gate.rs`）——发生在**事件落账本之前**，产物是一条 `notice`，**没有消费者**；
② **载体侧的 `y/N`**（`carrier/run.rs`）——发生在**事件已落账本之后**、动手之前，
  它在 **agentd 的 stdin** 上，**不在任何投影里**。
⇒ 后果是一个**具体的、可复现的人因缺陷**：`world://user`（白名单主体）执行不可逆动作时，
系统的判断是 `Allow`（`gate.rs:298-309`），**门禁不会拦、不会留痕、不会提示**；
真正的高危摩擦在**下游**由载体侧以一行 `(y/N)` 呈现，而它**既不在账本里、也不在投影里、也不在任何"待批集"里**。
⇒ **不可逆动作的"人确认"这件事，今天在世界的账本上是隐形的**——账本只会记下"用户执行了它"。
【推断】这与 `00-理论定稿:102`"审计必须区分'**人批准**'与'**人被信息胁迫后批准**'（记录批准的语境）"
正面冲突：今天连"有人批准过"都不可从账本复算。

**订正 3：待批没有终态。** 一条 `gate.awaiting-approval` 之后，世界没有任何机制让它变成
"已批准 / 已拒绝 / 已过期 / 已放弃"。⇒ 若把它直接搬上界面，人看到的将是一个**只增不减**的列表
（重试同一 `request_id` 会再写一条；`request_id` 只用于调用方自保，世界侧无幂等约束——
`WC-FMT-001` 我读到 `params` 说明"幂等性由调用方用 `request_id` 自保"，来源为 grep 命中片段，
**未读到该文件全文**）。

**没有待批集的世界，人的界面应该长什么样（我的设计）**

核心判断：**不要先做"仪表盘"，先做三样"清单 + 一个差异"**。理由：世界目前的可靠产物只有
"事实的集合"（`state.entries()`）与"事件的全序"（账本 `seq`）。**一切"聚合视图"在没有物化层的今天，
都只能靠全量扫描，做完也不可复算。**

1. **待办清单（Todo set）——最高优先，且今天就能做。**
   待批 = `notice.type=gate.awaiting-approval` 且 `request_id` 无后续终态。这是**账本上的纯查询**
   （与已经存在的 `world-core carrier orphans`——"有意图、无结果"的请求——是同一族）。
   ⇒ **把它从 CLI 查询升格为投影的一等内容**：一份 `todo` 视图，输出"待批 / 进行中 / 刚完成"三组。
   **代价小**：今天只需在读模型里把 `notice` 物化成对象（或让视图直接 fold 账本信封），
   不影响"投影不持有状态"（它是**只读派生物**）。
2. **"自上次以来"（Since-last）——最缺、最该有，且今天完全没有。**
   常设验收要求"人离开 24 小时后回来能答出发生过什么"。今天的投影只渲"当前状态"，
   于是**人必须自己记得 24 小时前的状态**，才能看出差异——这在认知上就是把"架构补偿"退回成"注意力"。
   ⇒ 需要 `window=since, from_seq=<我上次看到的位置>`。**`from_seq` 的来源必须是人可携带的**
   （浏览器书签 / 剪贴板 / 一行文本 / 手表的"上次同步点"），**不落账本**。
   这是"投影不持有状态"与"人要看见变化"之间**唯一干净的落点**。
3. **进行中任务（In-flight）**——**今天没有载体**。`act` 请求与结果靠 `trace` 配对
   （`src/event.rs:50-56`），`carrier orphans` 已能查出"有意图、无结果"。
   ⇒ 视图 = "有意图、无结果、且未超时"的集合；**必须带每个任务的 seq 游标**，
   使"我看到的是第几条"可复算。
4. **高危预案（Plans）**——**今天没有本体对象**。`00-理论定稿:97-100` 要求"不可逆性由**预案分级**制度化"，
   对应物是能力声明里的 `risk` 字段；但 `gate.rs:44-48` 的 `Capability` **只有一个 `reversible` 布尔**，
   且刻意删掉了 `requires_approval`（`gate.rs:39-43` 记 `WC-R4-DISP-001` §三 E-5 裁定）。
   ⇒ "高危预案"在实现里**没有对象可以显示**。这是第 1 问分层表里 L1 该补的东西：
   **预案必须先是本体对象，才可能出现在界面上。**
5. **不要做的那件事：状态仪表盘。** 【推断】在没有物化层、没有时间窗口、没有预案对象之前，
   做一个"漂亮的全局面板"只会把"全量倾倒"换个皮肤，并制造"我已经看见了"的虚假安心——
   这是 `WC-SCMP-001` 自己批判过的"该报错时不报错"的 UI 版本（假绿）。

**补上审批通道后，界面契约要怎么变（六条，逐条给理由）**

| # | 契约变化 | 理由 |
|---|---|---|
| 1 | 新增一等只读视图 `todo`，且**必须在首行带 `base_seq`** | 待批集的"新鲜度"直接决定人做决定的正确性；落后就看到已作废的请求 |
| 2 | 每个待批项**必须有 TTL 与过期语义**（过期 = 追加一条 `notice`，而不是静默消失） | 否则列表只增不减；且"我离开 24 小时"这个验收会变成"列表无限长" |
| 3 | **批准必须绑内容摘要，不能只绑 `request_id`** | 待批期间世界可能已变（同一 `request_id` 的参数可被重放成不同参数）。**这是现实系统最常见的失守点**：用户在同意页看到的范围 ≠ 实际被授予的范围；EULA/隐私政策在版本间静默变更。⇒ 批准事件必须携带 `subject_digest`（被批准内容的 hash），执行前核对，不符则重新请示 |
| 4 | 批准与拒绝都是 `act` 事件，走同一道门禁；**"谁来批"必须落在 `actor` 上** | `00-总纲.md:245` 铁律 4"建造者与 agent 同一条门禁"；审批通道若是特权旁路，等于把 `管` 变回纸门禁（`00-总纲.md:144-148` 的最强反驳） |
| 5 | **必须记"批准的语境"**：批准时人看到的信息量/时长，作为 `params` 的一部分 | `00-理论定稿:102` 原文要求区分"人批准"与"人被信息胁迫后批准"。**今天这条理论要求没有任何工程落点** |
| 6 | **入向契约（`direction=in`）必须先于审批通道落地** | 审批通道的入口就是"人在投影上做的动作"。**今天 `world-core` 没有任何从投影回写事件的路径**：`main.rs:20` 的 `append` 是 shell 命令（假设有 shell，不假设有界面），`channel` 是进程间接口（`main.rs:29-31`）。⇒ §九 第 4 条件"人和 Agent **能连上**"里的"连上"只有单向 |

**代价（诚实估）**

- 第 1、2 条：**小**（读模型物化 + 一个视图 + TTL 判定），是**这一席最该马上做的两件事**。
- 第 3、5 条：**中等**（新增摘要字段与语境字段，属词表变更，走 R5）。
- 第 4、6 条：**大**（入向 = 真正的第二个写路径，必须复用"唯一写入口"，否则 `15` 篇 §八"一个写入口"立刻破功）。
- **建议次序**：先 1 → 2 → 6（最小入向：只允许提交 `act`，且必须经通道身份）→ 3 → 5 → 4。

### 2.5 第 5 问：三条判据的量具

**原文/代码引用**

- `1-理论与哲学/00-理论定稿.md:168-180`（§7.2）：四条判据 + 审目与达标线（"监督零盯守 = 人不在场期间完成的任务占比 × **事后可答率**，须 100%"；
  "纠错在最近点 = 错误**发现点**距**执行点**的距离……取分布中位数"；"争夺可见 = 四问全答得上"）。

  - **谈判一次**：有 —— `request_id` + `trace` 配对（`event.rs:50-56`、`carrier orphans`）。**但审目是"同一目标的重复谈判轮次"，
    实现给的是"请求—结果配对"，二者不等价**：配对成功不排除"同一个 `request_id` 被重复提交 N 次"。
  - **监督零盯守**：**无任何量具**。`notice` 计数存在（`readmodel.rs:66-69`），但没有任何按 actor/时段的可答性统计。
  - **纠错在最近点**：**无任何量具**。`trace` 只连"引发者"，**不标"在哪一步被发现"**；

  - **争夺可见**：**无任何量具，且缺数据**。`actor` 只在**事件信封**里；
    **投影渲染的是 `State`，而 `State` 不存 `actor`/`seq`/`trace`**（`readmodel.rs:35-44`）
    ⇒ **"谁授的权"在投影层根本无法回答**。这不是"没做量具"，是**呈现层拿不到那三个问的原料**。

### 2.6 第 6 问：无障碍与多端一致性——优势还是负担？我的硬要求

**原文/代码引用**

- `00-总纲.md:160-161`（§2.5 幸存者写入）："要求的是**同源**，不是**同表达力**……投影只能**省略**，不能**添加**"。
- `00-总纲.md:264`（§6 `显` 的硬约束）："投影是**人向端口、无意志**——**出（渲染状态）、入（把人的操作翻成语义事件）**"。
- `2-依据/10-创世下的结构.md:35`：投影层 = N 端口注册表（视觉 / 语言 / 听觉…）。
- **实现侧**：`grep 无障碍|accessib|WCAG|屏幕阅读` 于 `world-core/` 的 `.md` 命中**只有模板**：
  `templates/02-需求类/01-软件需求规格说明.md:521`"DC-04 必须提供无障碍（键盘可达）支持"、
  `templates/03-设计类/01-软件概要设计说明.md:268`"无障碍 | 键盘可达；关键控件有语义标签"。
  **产品需求（`WC-SRS-001`）与实现（`src/`）里零命中。**

**优势还是负担？——两者都是，但分层判断**

**是优势（架构级，不是修辞）**：
"一份真相 + N 个只读投影"**恰好就是 WAI-ARIA 的整个思路**——组件暴露**机器可读的角色/名称/状态/值**，
渲染层各有各的画法，辅助技术消费语义而不是像素。绝大多数产品的无障碍做不好，是因为
**语义只存在于像素或 DOM 里**（`00-总纲.md:129` 的判据："agent 零截图、零坐标"——这条判据同时是无障碍判据）。
本项目**天生**把"语义"和"画法"分开了。**这是这套架构相对外部系统唯一的结构性优势**，值得写进理论。

**是负担（三处，且都会真实发生）**：

1. **成本 ×N**：每加一个端口就多一套无障碍实现与验证。今天两个端口的"无障碍"都**不存在**
   （终端文本对屏幕阅读器可读，但**没有任何语义标注、没有角色、没有状态变更播报**；
   而"2 空格/6 空格"这套排版对盲人是**完全的噪声**）。
2. **一致性漂移**：同源只保证**事实一致**，不保证**可操作性一致**。同一件事在三个端口可能是
   "有按钮 / 有快捷键 / 只能说话"，于是"我能做什么"随端而异——**而这不是精度问题，是权限的呈现不一致**。
3. **最容易犯的误读（本席认为这是本架构最大的无障碍陷阱）**：
   "投影只能省略，不能增**加**"若被字面执行，会把**可操作性**也判为"不得添加"——
   于是视觉端口有了"批准"按钮，听觉端口**被禁止**拥有对应的语音通路。
   无障碍缺口将从"漏做"升级为"**设计上禁止**"。**必须现在就把这句话的边界写清**。

**我的硬要求（一条，但要求写进本体）**

> **端口契约必须声明"动作可达性"：对每一个本端口可见的动作类型，必须给出该端口上的可达路径；
> 且该声明必须与门禁对当前主体的裁决一致。任何动作不得只在单一模态端口上可达。**

拆成三条可判定的判据：

1. **一致性判据**：端口显示"可执行"的动作集合 = 门禁对该主体裁决为 `Allow` 的集合。
   显示不可执行的动作 = **呈现性欺骗**（比"看不到"更糟）；
   可执行却不显示 = **遗漏**。二者都必须为 0。
2. **多模态判据**：每个**不可逆**动作，至少要在**两个不同模态**的端口上可达（如视觉 + 听觉）。
   理由：不可逆动作是 `00-理论定稿:88-90` 认定"事前介入是唯一纠错点"的那一类——
   若它只在视觉上可达，**盲人用户在这个系统里对不可逆操作没有纠错点**。这是这套理论自身的逻辑推出的无障碍要求，
   不是外加的合规要求。
3. **来源判据**：所有端口的**入向**都只能产出 `act` 事件、经同一道门禁、留同一份痕；
   **"桌面会话身份"不得成为世界身份**。（对应 `00-总纲.md:245` 铁律 4"建造者与 agent 同一条门禁"。）

**改动与代价**：加字段到端口契约（§二.3 表第 10 行）成本极低；
**真正的成本在"入向"**——没有入向，无障碍就只能是"能听不能做"，
而那正好触犯第 2 条判据。**⇒ 无障碍的钥匙与审批通道的钥匙是同一把：入向。**

## 一、评审结论

**一句话**：这套东西的**理念账是正的**（"语义门禁 + 因果账本"这三点 git / Kafka / CloudTrail 确实都答不了），
但它的**经济账目前是错的**——支撑"单人可承担"的两个关键数字，一个量在 tmpfs 上（真值慢 **510 倍**），
一个没有任何工时凭证；而真正会先崩的不是磁盘也不是 fsync，是"**每次读世界都要把全部历史读进内存**"这一条。

**要点（每条带数字）**

1. **写性能的头号数字是已作废的那个。** 委托材料给的"追加 1 万条约 33.57 ms（含 fsync，约 29.8 万条/秒）"
   量在 **tmpfs** 上——`tests/perf.rs:72` 用 `std::env::temp_dir()`，tmpfs 的 `fdatasync` 是 **0.7 µs 的空操作**。
   项目自己的变更单已记录 btrfs 真值 **17 158.84 ms / 10 000 条 = 583 条/秒（1.72 ms/条）**，差 **510 倍**
   （`WC-SCMP-001-v0.1.md:1262`、`:2624-2629`，`WC-CR-006-v0.1` §五 T-03）。所有"29.8 万条/秒"派生的规模推算全部作废。

2. **"1 秒墙"离今天只有 10–24 天。** 冷启动重放 10 万条 = **423 ms P50**【实】，而**重放在每一次读命令上发生**，
   不只发生在开机：`src/lib.rs:322` 的 `read_model() = State::fold(&self.ledger.read_all()?)` —— 每次"看世界现在什么样"
   都全量读盘 + 解析 + 折叠。按 **1 万条/天**，**10 万–24 万条**即越过 1 秒。

3. **内存墙比时间墙先到。** 实测 100 万条 → 峰值 RSS **1 857 MB ≈ 1.86 KB/事件**（`WC-SCMP-001-v0.1.md:2585-2587`）。
   8 GB VM 留一半给进程 → 墙在 **213 万条 ≈ 212 天**；32 GB PC 给 16 GB → 墙在 **860 万条 ≈ 2.4 年**。
   而 **`checkpoint` 完全不能推迟内存墙**——它的 CLI 实现（`src/main.rs:475`）第一步就是 `read_all()`，
   把全部事件物化成 `Vec<Value>`。

4. **文档量是代码的 11.8 倍，且文档自己产生的缺陷比代码多。** `world-core/docs` **53 份 / 4 246 892 B /
   1 083 551 个汉字**【核】 vs 产品源码 **361 272 B**【核】；`tools/`（审计脚本）**280 059 B** **大于** `src/` 的 266 084 B。
   同期账实不符 **G-01…G-67（仍开 50 项）**、技术缺陷 **T-01…T-24**、流程缺陷 **P-01…P-15**、
   R0 判词 **OP-01…OP-71**，十余套编号空间互相碰撞。
   **"单人 + 1 AI 可承担 ≤ 21 人日"与这批产出自相矛盾**——仅"未来接手人把这 4.25 MB 读一遍"就是 **12–20 人日**。

5. **日常运维的真实数量级是 3.4 人日/月（≈41 人日/年），不是"按需"。** 其中**文档与门禁维护一项占 77%**（21.0 / 27.3 人時）；
   而 `WC-FSR-001-v0.1.md:835` 的 `C-05 运维人力` 写成"【候选】按需 / ¥0"，**没有任何上界**。
   同时**没有 runbook、没有备份工具、没有监控**：`Ledger.Poisoned` 的处置方案全文是五个字"**人工检查后重启**"
   （`WC-HLD-001-v0.1.md:1381`）。

#### 估算

| 规模（@1 万条/天） | 条数 | 账本 | 冷启动重放 | 峰值 RSS |
|---|---|---|---|---|
| 10 天 | 10 万 | 24.3 MB | **0.42 s**【实】 | 186 MB |
| 1 个月 | 30 万 | 73 MB | 1.3–3.0 s | 558 MB |
| 1 年 | 365 万 | **887 MB** | **24–49 s** | **6.6 GB** |
| 3 年 | 1 095 万 | **2.66 GB** | **73–146 s** | **≈20 GB** ⚠ |

**算式**（示例，其余同法）：
- 账本(1 年) = 3.65×10⁶ 条 × 243 B = **887 MB**
- 重放(1 年) = 3.65×10⁶ ÷ (75–149)×10³ = **24.5–48.7 s**
- RSS(3 年) = 10.95×10⁶ × 1.86 KB = **20 367 MB ≈ 19.9 GB**

**三堵墙，按到达顺序：**

| 墙 | 判据 | 到达点 |

| **内存墙（先到）** | 8 GB VM 留 4 GB → 215 万条 | **≈7 个月** |
| | 32 GB PC 留 16 GB → 860 万条 | **≈2.4 年** |
| **交互 1 秒墙** | 10 万–24 万条 | **10–24 天** |
| 可忍 30 秒墙 | 300 万条（@100 k/s） | **≈10 个月** |

#### 检查点能推迟多久：按现在的接线，**0**

逐行核对 `src/main.rs:460-561`：

| 子命令 | 实际做了什么 | 与 `state` 比较 |
|---|---|---|
| `checkpoint write`（`:483-500`） | `read_all()`（`:475`，全量读+解析）→ `read_model()`（`:484`，**又一次** `read_all()` + 全量折叠）→ 落盘 | **更慢** |

| `checkpoint resume`（`:521-554`） | `read_all()` → `read_model_with_checkpoint`（`:529`）→ **再** `w.read_model()`（`:536`）做逐字节比对 | **更慢** |

⇒ **`read_model_with_checkpoint` 只避免了"折叠前 base_seq 条"，但读 + 解析仍是 O(N)**，
而读 + 解析正是三遍解析里最贵的两遍（`WC-SCMP-001:2588` 定位："`ledger.rs:193-231` 全量读入 + 逐行 parse；

**没有任何用户可见路径因此变快。**

#### 下一个手段（按 ROI 排序，不是保留窗，是流式扫描）

| 步 | 动作 | 代价【估】 | 收益（算式） |
|---|---|---|---|
| **S1** | **流式折叠**：`BufReader` 逐行 → seq 校验 + 链核验 + 折叠同遍完成 → 丢弃，**不物化 `Vec<Value>`** | 2–3 人日 | RSS 从 O(N) 变 O(状态)：3 年档从 20 GB → 状态大小（阶百 KB 级）⇒ **内存墙消失**；时间 ÷3（一遍解析代替三遍） |
| **S2** | 检查点**存字节偏移** `base_offset`；`state`/`read` 支持 `--checkpoint`，从偏移续读；`resume` 的逐字节比对降级为可选 `verify` | 2–3 人日 | 交互读 O(账本) → **O(尾巴)**。周检查点 @1 万/天 = 7 万条 = **0.3 s**（@236 k/s）⇒ 1 秒墙推到"检查点间隔" |
| **S3** | **分段 + 段锚**（每段封存段头 hash，校验只验段内 + 段链） | 3–5 人日 | `verify` 从 O(N) 变 O(段)。**这一步推不掉**：`verify_chain` 自 `CHAIN_GENESIS` 起算（`WC-SCMP-001:2547`）⇒ 只要不分段，"我这个账本完好吗"永远 O(历史) 且随历史线性增长 |
| **S4** | 保留窗 / 归档 / 分层 | 未定 | 见下 |

### 2.2 第 2 问：写放大的账——每条 fsync 换来什么？一天 1000 万条撑得住吗？

#### 假设

- 每条一次 `fdatasync`，单线程串行。当前实现：`src/ledger.rs:67` 的 `self.file.sync_data()` 是全 crate **唯一**生产 fsync 点
  （`WC-SCMP-001:2483` 逐字定位），且 `next_seq` 在它成功之后才前进（`WC-FMT-001-v0.1.md:81`）。
- 平台取**项目自己定的基准档 = btrfs**（`WC-SQAP-001-v0.1.md:322`"**基准档一律 btrfs**"）。
- 1000 万条/天 = 10⁷ ÷ 86 400 s = **116 条/秒**（平均）。

#### 估算

| 口径 | 1 万条耗时 | 吞吐 | 每条 |
|---|---|---|---|
| tmpfs【项目实测，**已作废为基准**】 | 29.76–60.15 ms | 16.6 万–33.6 万/秒 | 3.0–6.0 µs |
| **btrfs【真值：干净重建 + 已验证 `fdatasync=1`】** | **17 158.84 ms** | **583/秒** | **1.72 ms** |

出处：`WC-SCMP-001-v0.1.md:2628` 逐字"QG-01 打印'10000 条含 fsync = 60.15 ms（166k 条/秒）'；**干净重建后在 btrfs 上真值 = 17158.84 ms（583 条/秒，约 1.7 ms/条）**"；
`:2627`"同一原语：tmpfs `write+fdatasync` **0.7 µs/次** vs btrfs **1651 µs/次**（**2300×**）"；
`:2709` 记该方法学事故："曾把 `TMPDIR` 指到 btrfs 重测得到 39.61 ms/10k …… 该二进制是在**并行变异（去掉 fsync）窗口内被重建**，`fdatasync` 计数为 0。该数字**已作废**"。

**1000 万条/天的账**：

| 项 | 算式 | 结果 |
|---|---|---|
| 写吞吐占用 | 116 ÷ 583 | **20%**（余量仅 5 倍） |
| 突发风险 | 一分钟 7 000 条的突发 ÷ 583 | **需求为上限的 12 倍** ⇒ 队列必然积压 |
| fsync 串行时间 | 10⁷ × 1.72 ms | **17 150 s = 4.76 小时** |
| 体积 | 10⁷ × 243 B | **2.43 GB/天 = 887 GB/年** |
| 60 GB VM 填满 | 60 ÷ 2.43 | **25 天** |
| 1 TB 盘填满 | 1024 ÷ 2.43 | **412 天**（只算账本，未含 CoW 与备份） |
| 读侧 RSS | 10⁷ × 1.86 KB | **18.6 GB** |
| 读侧重放 | 10⁷ ÷ 100 k | **100 秒/次** |
| SSD 寿命 | 2.43 GB/天 × 4× 放大 × 365 | **≈1.3 TB/年** ≈ 600 TBW 盘的 **0.2%/年** |

#### 每条 fsync 换来的是什么、代价是什么

**换来**：在单机、无副本、无异地把守的前提下，**只有一件事**——"掉电后损失窗口不超过 1 条"。

**不换**（逐条给出处）：

| 声称换到的 | 实测状态 | 出处 |
|---|---|---|
| 防篡改 | **不换**。链只锚 genesis ⇒ **尾部整条删除不可检出**；且 `check` 打印"✅ 有摘要链（局部篡改可检出）"= **假清白** | `WC-SCMP-001:1252`（T-04）；用例 `c18_chain_cannot_detect_a_full_rewrite` |
| 掉电不丢 | **不换**。新建账本/锁文件**没有任何目录 fsync**（`strace` 全量 trace 无目录 fd 的 fsync）⇒ **首次 ack 后掉电可能整本消失**（"整个账本消失、世界静默回到空"） | `WC-SCMP-001:2546-2550`（K-4）；外部依据 man7 `fsync(2)` + LWN 457667 |
| 可用性 | **不换**。`kill -9` 后 30 轮 × 30 并发 ⇒ **多写者 30/30、账本重号 6/30** ⇒ 世界**永久拒启**，唯一修法是**手工编辑"唯一真相"** | `WC-SCMP-001:1251`（T-03） |
| 持久性承诺本身有守 | **没有**。把**唯一生产 fsync** 改成 `Ok(())` ⇒ **668 passed / 0 failed / 3 ignored，变红 0 项**，`check.sh` 仍退 0；**复现两次** | `WC-SCMP-001:1254`（T-06）、`:2608`；`WC-R4-DISP-001:350-357` |

**代价**：**1.72 ms/条**（btrfs 基准档），即单线程上限 **583 条/秒**。

#### 结论

**1000 万条/天在这台机器上撑不住——但原因不是 fsync 吞吐。** 平均速率只用到上限的 **20%**。
按到达顺序：**① 读侧先崩**（18.6 GB RSS、100 秒/次重放）；**② 突发余量只有 5 倍**；
**③ 887 GB/年的纯追加文本**（且格式明令禁止压缩——`WC-FMT-001-v0.1.md:700`"**不得**压缩"，这是"换语言 ≒ 世界不归零"的代价，合理，但它是永久 3–4 倍的体积开销，应显式登记）。

**另一个必须点明的落差**：花 **1.72 ms/条**买一个"1 条的损失窗口"，同时把**可用性**（T-03）与**防篡改**（T-04/K-4）都留在洞外，**而这个 1 条窗口本身还没有任何会红的检查守着**（T-06）。**这个取舍的性价比是负的。**

**顺带纠正**：`2-依据/07-硌牙清单与单机经济账.md:47` 写"SSD 写寿命要管：舱数量配额 + 定期 balance（CoW 有写放大）"。
对**账本**而言磨损**完全不是约束**（1.3 TB/年 ≈ 0.2%/年）。真正的写代价是 **1.72 ms/条的延迟**。**风险记错了科目。**

  `WC-FMT-001-v0.1.md:81`、`WC-LLD-001-v0.1.md:47` 三处；改成组提交须把"损失窗口"变成**显式的、按能力分级登记的参数**。

  新建账本后补 `sync_all()` + 父目录 fsync（K-4 最小补丁）。合计 **1–2 人日**。

### 2.4 第 4 问："单人 + 1 AI 可承担"成立吗（做出来 / 跑起来 / 三年后接手）？

#### 假设

- 三个时间尺度分别判：**做出来**（能否建成）、**跑起来**（能否在真实崩溃与真实负载下持续运行）、
  **三年后接手**（第二个人能否接住）。
- "前置知识"以**人日**计，标准是"**能安全改动而不丢数据**"，不是"能读懂"【估】。
- 频率与耗时按"一个熟练于本系统的人"计【估】。

#### (a) 做出来 —— **成立，但成本基准是假的**

**正面事实**（委托材料实测，我核对一致）：21 个源文件 / 6 591 行 + 2 435 行测试；
发布二进制 **865 712 B**；外部依赖**只有 `serde_json`**；95 通过 / 0 失败 / 3 忽略；
`check.sh` 全通过；CLI 22 个子命令（`系统全景图.md:115`、`:175`）。**这确实是一个小东西，而且是一个人能搬动的尺寸。**

**但**：
- **"≤21 人日"没有任何凭证**（`WC-FSR-001-v0.1.md:326` 自述"估算，非工时记录，无凭证"）；
- **反算不可能**（见 2.3 末）：168 人時 ÷ 4.25 MB 文档级产出 = **每小时 29 KB**；
- **它没做完**：2/6 CR 未实施（`WC-SCMP-001:436`）、**50/67 个 G 项仍开**（`WC-SCMP-001:1644`）、
  20+ 条技术缺陷仍开、**R5 从未召开**、**R0 未准出**（`WC-RV-R0-001:3399`、`:6475`）。

**结论**：**代码尺寸上"可承担"成立；总成本上"未证实"，而主张恰恰住在总成本里。**

#### (b) 跑起来 —— **不成立，且原因是具体的**

| 实测事实 | 出处 | 后果 |
|---|---|---|
| `kill -9` 后 30 轮 × 30 并发 ⇒ **多写者 30/30、重号 6/30** | `WC-SCMP-001:1251`（T-03） | **正常崩溃路径可把世界永久锁死**，唯一修法是**手工编辑"唯一真相"** |
| PID 复用 / 无关活进程 pid 进锁 ⇒ **永久拒启** | `:2577-2581`（M-3） | 用"可回收的名字"判"持有者是否活着"，**两个方向都会错** |
| 被管者放一个**一字节**的 `ledger.lock` ⇒ **永久拒启** | `:1260`（T-12） | 可用性否决权在被管者手里 |
| 无目录 fsync ⇒ **首次 ack 后掉电可能整本消失** | `:2546-2550`（K-4） | 而账本**不入库、无备份**（`:693`） |
| 删掉唯一生产 fsync ⇒ **0 项变红** | `:1254`（T-06） | 持久性承诺无守 |
| 默认相对路径 + 0777 目录 ⇒ 跨 uid **整体替换法律与真相** | `:1249`（T-01） | 门禁在默认形态下失效 |
| CLI 默认 actor = `world://user` ⇒ 本机任何调用者都能执行不可逆动作（**实测 `rc=0`**） | `:1250`（T-02） | 不可逆分级形同虚设 |
| `--owner-uid` 写路径不生效，且坏值被**静默关闭**（`parse::<u32>().ok()`） | `:2571-2575`（M-2） | **fail-open 的安全控制，比没有更糟** |
| `notice` 家族完全不过门禁 ⇒ 可伪造 `gate.rejected` | `:2638`（B-2） | 见第三节第 1 条 |

**结论**：**"跑起来"的前提是它只处理可重建的数据——而它的全部卖点恰是不可重建的历史。**
在"真相不丢"这条主承诺上，v1 的实测状态是：**唯一副本、无备份、无目录 fsync、fsync 无守、
崩溃路径可永久锁死、锁可被一字节文件否决**。**这不叫"可承担"，叫"未设防"。**

#### (c) 三年后接手 —— **不成立，且可以被算出来**

**前置知识分解**【估】（代码行数为本次复核）：

| 要接的东西 | 代码 | 文档 | 人日 |
|---|---|---|---|
| **账本**（含锁竞态、链只锚 genesis、无目录 fsync、无保留窗实现） | `ledger.rs` 653 行 | `WC-FMT` 239 016 B + `WC-LFMT` 73 591 B + `WC-CR-006` 43 967 B | **3–5** |
| **本体** | `ontology.rs` 234 行 + `ontology.json` 1 928 B | `WC-ONT` 73 118 B | **1** |
| **门禁**（含 `notice` 不过闸、默认 actor 是特权值） | `gate.rs` 337 + `guard.rs` 158 + `policy.json` 2 385 B + `cap.d/` 3 件 | `WC-PFMT` 66 937 B + 20 条缺陷 | **2–3** |
| **投影** | `project/` 315 行（`mod` 186 + `language` 52 + `visual` 77） | — | **0.5–1** |
| **部署** | **不存在**：`src/` 无 systemd unit、无 PID 1、无 Landlock/seccomp、**无 `projectd` 常驻入口**（`系统全景图.md:121-131` 命令表只有 `channel`/`carrier`，无 `projectd`） | `deploy/README.md` 176 行 | **1–2**（读）；真正落地另计 |

| **文档通读一遍**（4.25 MB / 291 万字符） | — | 全部 | **12–20** |

- **能操作**（读得懂、跑得动、出事能照章处置）：**≈12–18 人日**
- **能安全改动**（改完不丢数据）：**≈25–40 人日**

**关键空档：没有 runbook。** 文档里对 `Ledger.Poisoned` / `SyncFail` 的处置方案全文是
"**停止写入，人工检查后重启**"（`WC-HLD-001-v0.1.md:1381`、`WC-FMT-001-v0.1.md:802`、`WC-IRS-001-v0.1.md:333-334`）
——**五个字，掩盖了一个无上界的任务**。

**而且这个问题的前提本身不成立**：`WC-FSR-001-v0.1.md:346` 的假定 `AS-07` 明确写
"**无第二人接手的需求在本项目周期内不变**（若变，B 档角色分离与文档量须重新评估）"，
`:999` 的局限性 `SL-10` 登记"**单签署人**"，`:42` 的风险 `R-03` 登记"一人多角色导致**无独立复核**"。

⇒ **"单人 + 1 AI 可承担"不是一个关于交接的主张，它是一个"交接永不发生"的假定。**
单人可承担 + 永不交接 = **bus factor = 1，且没有接班成本上界**。这在工程经济上是一个明确的、未被定价的尾部风险。

| 尺度 | 结论 |
|---|---|

### 2.5 第 5 问：运维面——日常动作、频率、单次耗时、每月运维人时

### 2.6 第 6 问："24 小时复盘由架构保证（不靠盯守）"这份收益怎么量化？量化不出来是否说明不可验收？

#### 假设

- 判据原文取自 `WC-FSR-001-v0.1.md:294` 的 `G-02`；理论出处为 `1-理论与哲学/00-理论定稿.md:75-84`（§三）
  与 `:168-181`（§7.2 四条高效判据）。
- "可验收"的判据 = 存在主体、时段、观测量、比率、阈值、样本量，且**该判据可能失败**。

#### 先给项目记功：**这条主张在形式上是可验收的，而且做得比多数项目好**

`G-02`（`:294`）逐字："**人离开 24 小时后仍能答'发生过什么、哪些在等我批'**（常设验收，不靠盯守）"；
度量 = "**从日志派生的答案完整率**"；目标 = 【候选】"**1 次演练 100% 答出**"；现状 = 【实测】"**不可测（无日志）**"。
理论侧 `§7.2` 还给了四条判据**与达标线**（谈判 **0 轮**；事后可答率 **100%**；纠错点 执行前 > 执行后 > 事后；
四问 —— 谁授权 / 谁的场所 / 谁受益 / 谁承担 —— **全答上**）。

**这不是一句修辞，这是一条判据。**

#### 但它的收益量化不出来，原因有四层，逐层加码

**① 项目自己已经拒绝了量化，而且拒绝得对。** `:849-854` 的 B-01/B-02/B-03 为 **¥0 或不可估算**，
B-05/B-06 标"**不可量化**"，并在 §6.3/§6.4 显式排除（模板规则 3：不可量化收益不得计入）。
`:872` 直白写"收益投资比 **0 ÷ 0 无定义**"，`:876` "**不存在收益投资比，也不存在盈亏平衡点**"。
**这是诚实的，应当表扬。**

**② 缺"之前"的数，所以即使量出"之后"也构不成收益。** 主张的全部内容是"把监督**从注意力问题变成架构问题**"
（`:858`）——**这是一个差值主张**。而基线侧被明确记为"**每次复盘靠人工拼凑，成本无法计量**"（`:454`）并拒绝估算。
⇒ **只量事后，你得到的是一个能力，不是一个节省。没有 before，after 无意义。**

**③ "答案完整率"这个量具是自评的。** 标注是"从日志派生的答案完整率"，但**没有任何工具产出具它**——
`系统全景图.md:121-131` 的 22 个子命令里没有产出该比率的命令；
它实际是"**一个人对自己给出的答案自评是否完整**"。**这是可能的最弱量具。**
而它本可以机械化：`read [从第几条]` 已存在（`:127`）。加一条 `world-core digest --since <ts>`
输出"N 条 act / 按主体分布 / M 条 rejected / K 条 awaiting-approval / 触及字段 F"即可让完整率可复算。
**代价约 1 人日，没人做。**

**④（最重的一层）后半条判据在 v1 里是空真的。**
`G-02` 要求答出"**哪些在等我批**"。而 `系统全景图.md:156` 逐字明写：

> | 1 | **v1 没有审批通道** | 不可逆动作只认白名单主体；被摩擦的主体拿到的是"**不要等批准，它不会来**" |

⇒ **待批集按构造永远是空的。** 你可以离开 24 小时、回来、**如实**回答"没有任何东西在等我"，
**因为任何东西都不可能等我**。**判据轻松通过，而被判据所指的能力根本不存在。**
这是真正意义上的不可验收——不是"测不出"，是"**测出来必然满分，且满分不携带信息**"。

#### 结论

**这份收益量化不出来，但不是因为主张不可验收**，而是因为：(a) 没有 before；(b) 量具是自评；
(c) 后半条是空真。主张本身（"架构化 > 盯守"）在理论上是可检验的，`§7.2` **已经是一套现成的量具**——
问题是**它没有被当作量具使用，只被写进了理论文档**。

### 3.2 方案对比缺了最强的一个竞争者：`git`

`WC-FSR-001-v0.1.md:805` 把 git 列进"从方案 D 保留的四条优点"（"**git 已是现成的内容寻址 + 提交历史**，
本项目的'词表内容寻址'应尽量沿用同一套心智"），却**从未把 git 作为一个真实备选方案评分**。
`:759-772` 的四方案（A 纯事件溯源 / B image+WAL / C 对象图+对象级历史 / D 维持现状）里，**git 不是一个选项**。

而 git 恰恰是"留下可问责的历史"最成功的现成系统：**内容寻址 + append-only 对象图 + Merkle 化提交链 +
零服务依赖 + 单机 + 近乎零运维 + `.git` 可整体复制**。它的真实代价是：
**作者与时间戳由提交者自报（不可信）；无保留策略；无"谁批的"**。

⇒ **world-core 相对 git 的增量只在三处**：① **语义本体**（"什么算合法"进写入路径）；② **门禁**（不可逆分级）；
③ **`trace` 因果链**。其余"可问责历史"的部分，**git 已经交付了 20 年，且运维成本低一个量级**。

**这不是坏消息，是好消息**：它把定位从"今天没有这样的东西"收窄为"**git 有历史无语义、无门禁、无因果**"
——**更窄、更诚实、也更容易验收**。（注：`2-依据/06-重复工作审计.md:18` 已自订"没有第二个项目如此主张"

**但"为什么不用 git 承载语义事件"这个问题在四方案对比里根本没被提出。这是方案对比里最大的一个洞。**
补一次诚实的三方对照（A / git+约定 / git+外挂门禁）：**0.5 人日**。

### 3.7 `--owner-uid` 是一个 fail-open 的安全控制，比没有更糟

实证：`--owner-uid notanumber` ⇒ 断言被**静默关闭**；变异 M8（断言恒 no-op）⇒ **全部测试全绿（零覆盖）**。

而它恰恰是**唯一**能挡住"目标目录属主就是被管者"的检查（技术线 B 的 EXP18 实测：符号链接祖先 +
属主 0700 目录 → `READY rc=0`；而 `--owner-uid 0` 正确报"属主 uid=1001，期望 0"并 `rc=2`）。
**⇒ 一个会给出绿灯的无效控制。**

### 3.8 "签署对象 = 提交号 + SHA-256"目前跨机器不可复现

`WC-SCMP-001:1066`（G-25）：`.md` 未声明 `eol=lf`（`.gitattributes` 对 `*.sh`/`*.rs`/`*.toml`/`*.json`/`*.csv`/`*.py`/`*.ps1`
均声明，**`.md` 不在其中**），本机 `core.autocrlf=true` ⇒ 检出即 CRLF，
于是 `Get-FileHash`（工作区字节）与 `git cat-file blob`（仓库字节）给出**两个不同的 SHA-256**。
（该条同时**如实订正**了自己先前记的 837/487/1137 是工作区瞬态值——这个自查值得记功。）

⇒ **整套冻结 / 签署 / 证据链都压在这个等式上，而它换台机器就核不上。修法免费**
（`.gitattributes` 加一行 `*.md text eol=lf`），**至今未修**。

### 3.9 SSD 寿命的风险被记在了错的地方

`2-依据/07-硌牙清单与单机经济账.md:47` 写"**SSD 写寿命要管**：舱数量配额 + 定期 balance（CoW 有写放大）"。
**对账本而言**：@1 万条/天 = 2.43 MB/天逻辑写，按 4× 放大 ≈ 3.5 GB/天 ≈ **1.3 TB/年**
≈ 一块 600 TBW 消费级盘的 **0.2%/年**——**完全不是约束**。
真正的写代价是 **1.72 ms/条的延迟**（btrfs 实测，`WC-SCMP-001:2628`）。
**风险定价应当从"磨损"改到"延迟与突发余量"。**

### 3.10 `docs/证据/EV-###.md` 是这套文档器具里唯一真正好的点子，而它被用得太少

`WC-SCMP-001:437`、`WC-SQAP-001:950` 定义 `RE-13`：载体 = `world-core/docs/证据/EV-001…EV-008.md`（**8 份**），
七字段（命令 / 原始输出 / 环境版本号 / 代码提交号 / 执行人 / 执行时点 / 所在机器），
"**取不到原始输出者一律写 `【待验证】` 并附验证命令，不编造**"。

**这是全库唯一把"跑过了，这是 run id 与原始输出"做对的机制。**
建议：**让它成为原始输出的唯一去处**——其余一切文档只引 `EV-###` 编号（见 2.3 建议 3）。
这是单条结构性改动里**能把文档量砍得最多**的一条。

## 四、总问题 A / B / C

### A. 这个理念还缺什么？（理论层面）

#### A1. 缺一个"审计的对手模型"（threat model）

`1-理论与哲学/00-理论定稿.md:249-263`（§10.2）给了一条极好的可反驳判据
（"**判据 = 它最终把机制交到谁手里**"），`2-依据/07-硌牙清单与单机经济账.md:9-10` 也**如实承认**
"单机审计可篡改"并降级为"**agent 之外 + 不可否认（哈希链定期封存）**"。但**全套理论从未写明敌手是谁**：

| 敌手 | 现有机制挡得住吗 | 依据 |
|---|---|---|
| **agent**（被管者） | **基本挡得住**：独立 uid + 文件权限 + **编译期**唯一写入口 | `系统全景图.md:137-150`、`WC-SCMP-001:2615` |
| **操作者**（拥有机器的人） | **挡不住**：可改账本；链只锚 genesis ⇒ **尾部删除不可检出**；**异地封存未实现** | `WC-SCMP-001:1252`、`:2547`；`07` 篇 §2 #3 |
| **平台 / 模型厂商** | **挡不住**：`§10.4` 自己已承认"厂商可以在会话之间改策略" ⇒ **跨会话结论一律重算** | `00-理论定稿.md:279-294` |

**三个敌手，三套机制，一个不加区分的词"不可篡改"。**
尤其致命的是：**§10.4 已经承认跨会话结论必须重算，而账本的全部价值主张都是跨会话的。**

**改法**：理论需要一张 **3×3 表（敌手 × 阻止 / 仅可检出 / 未覆盖）**，
否则"不可篡改"在承担它承担不起的论证重量。**代价：0.5 人日。**

#### A2. 缺"衰减补偿"的量化判据——理论的那条经验主张目前无法失败

`00-理论定稿.md:75-84`（§三：监督必要、不充分、且在衰减）是全套理论最硬的一条，
`工程要求` 逐字为"协作机制必须**补偿**衰减——把监督从'注意力问题'变成'架构问题'
（预定检查点、事件推送、完工铃、结构化审计）"。**这是一个经验主张。**

而 `:173-181`（§7.2）**已经给了四条可测判据与达标线**
（谈判 **0 轮**；事后可答率 **100%**；纠错点分布中位数；四问全答）。
**问题是：这套量具从未被当作量具使用，也从未取过基线。**
（佐证：`2-依据/07-硌牙清单与单机经济账.md:27` 的"完工铃 = 第一优先（10 分钟任务轮询 20 次推理 → 2 次）"
是一个**可量化的假设**，却没有基线测量。）

⇒ **理论停在"不能失败"的层级上。距离可检验，只差一次两周的时间日记（≈1 人時）。**

#### A3. 缺"历史的成本"这一层——而这是整个工程经济学的重心

`00-理论定稿.md:86-102`（§四）把**摩擦按不可逆性定价**，这是漂亮的一步。
但**保留本身没有被定价**："只追加、永不删除"被当作**性质**，不是**成本**。

而所有真实保留完整历史的系统——KurrentDB 的 `$scavenge`、Kafka 的 compaction、
CloudTrail 的生命周期策略、git 的 `filter-repo`——最终都必须回答"**多久**"，
**"多久"就是钱住在哪里**。

项目现在有两个答案（`WC-SRS-001:125` `DR-07` 30 天 / `:129` `DR-11` 不设保留窗）、
**零实现**、且被推到 R5（`WC-RV-R2-001:256`）。

**理论应写死**：可问责性的时长是**有价格的**，价格以"**每秒可问答的历史长度**"计，不是二元承诺。

**具体到本机**：

| 保留窗 | 条数 | 体积 | 重放 | RSS |
|---|---|---|---|---|
| 30 天 @1 万/天 | 30 万 | 73 MB | 1.3–3.0 s | 558 MB |
| 1 年 @1 万/天 | 365 万 | 887 MB | 24–49 s | 6.6 GB |
| 3 年 @1 万/天 | 1 095 万 | 2.66 GB | 73–146 s | **≈20 GB（跑不动）** |

**这两个数之间的差，是理论必须给的一个数。**

#### A4. 缺"主权 vs 可问责"的冲突条款——所以"多久"这个问题永远无法收敛

`00-理论定稿.md:249-263`（§10.2）的死亡判据是"审计集中到厂商即判输"，
`2-依据/12-内核选型对照.md:171-178`（§六）与 `2-依据/08-创世路线论证.md` §三给出了**立宪四条**
（本体公开版本化 / **退出权** / 建造者特权禁止 / 世界级不可逆操作最高预案）。

但这覆盖的是**离开**，没覆盖**在不交出数据的前提下向第三方举证**。
"可问责"**对谁**？

- 若答案是"对操作者自己"，问责是**装饰性**的；
- 若是"对第三方"，就需要**选择性披露**（证明第 k 条在某时刻存在过，而不泄露其余）——
  这是成熟机制（**Merkle 证明 + 签名检查点**），**在理论与代码里完全缺席**
  （全库无 Merkle、无签名、无选择性披露；`WC-SCMP-001:2547` 的 `verify_chain` 是线性前向链）。

**正因为没人说过"谁需要验证什么、验多久"，`DR-07` / `DR-11` 的矛盾才无法收敛。**
**这是我认为理论层面最实质的一个缺口。代价：1 人日写一页"举证关系表"。**

### C. 外部现有系统为什么不好用？（指名道姓）

#### C1. 云审计：AWS CloudTrail / Google Cloud Audit Logs / Azure Activity Log

- **成本结构**：**按事件摄取计费 + 按存储计费 + 查询另计**。管理事件第一份 trail 免费，
  但**数据事件（S3 对象级、Lambda 调用）按每 10 万次事件计费**（约 $0.10/10 万量级）；
  CloudWatch Logs 摄取约 **$0.50/GB**；之后 S3 存储 + Athena 查询**按扫描字节**再收一次。
  GCP 的 **Data Access 审计日志默认关闭**，开启后按 Cloud Logging 摄取计费（约 $0.50/GiB），
  且**多半不含在免费额度内**（免费额度只覆盖 Admin Activity）。（量级为公开定价的工程近似【估】。）
- **真实痛点**：**① 默认不开**——数据事件是显式开关，因为一开就出账单；
  **② 开了没人看**——摄取的是 JSON 事件流，不是答案；"过去 24 小时我的 agent 改了什么"要自己写 Athena/BigQuery；
  **③ 语义不可知**——CloudTrail 记的是 API 动词（`PutObject`、`RunInstances`），不是"把屏幕调暗到 60%"。
  **它记的是动词的机器名，不是动作的语义。**
- **判决**：**云审计的成本是"每事件"的，价值是"每问题"的。这个错配就是它买了但没人用的原因。**
  world-core 攻的正是这一点，**而且攻对了**——`WC-FSR-001-v0.1.md:427` 的 L-04"**没有因果，只有时间线**"
  与 `:485` 的现状对照，是这套论证最有说服力的部分之一。

#### C2. 可观测三件套：Prometheus / Grafana / Loki（或 ELK/OpenSearch）

- **成本结构**：Prometheus 的成本在**基数（cardinality）**与保留期（本地 TSDB 默认 15 天，
  长期要 Thanos/Mimir + 对象存储 + 查询层）；Loki 按摄取 GB 计费，**标签基数一高就爆**；
  Grafana 免费，但 dashboard 是**人写的**。
- **真实痛点**：**① 测的是"系统健康"不是"谁做了什么"**——Prometheus 的模型是时间序列，
  它天然**丢样本、做聚合、算 rate**；而可问责要求**逐条不丢**。把审计塞进 Prometheus 是范畴错误。
  **② 保留期是成本杠杆，合规要求是时长**——两者相向：基数 × 天数 = 内存/磁盘。
  **③ 告警疲劳**——没人看的 dashboard 是装饰。
  **④ 部署本身是个小系统**：4 个有状态组件 + 对象存储 + 反代 + TLS + 认证，对单机个人是纯负债。
- **判决**：world-core 用"**一个可执行 + 一个 JSONL**"回避了这四点——**这是它真实、可辩护的优势**。

#### C3. 配置管理：Ansible / NixOS / Terraform

- **成本结构**：Ansible 的成本在 **playbook 脆弱性**（模块版本、幂等边界）与人日；
  **NixOS 的 generation + `flake.lock` 本身就是一份可问责的历史**（`nixos-rebuild` 可回退到任意代）；
  **Terraform 的 state 文件就是"image 是真相"**——所以它才有 **state locking** 与 remote backend，
  而 state 冲突 / 漂移是运维最主要的痛点之一。
- **真实痛点**：**① 只记结果不记因果**——NixOS 记的是最终配置，不是"谁在何时为什么改"；
  **② "谁批的"不在配置里**（`stateVersion` 是兼容标记，不是批准链）；
  **③ 回滚粒度 = generation，粗于"一次改动"**。
- **判决**：**这是 world-core 最有说服力的一段对照。** `WC-FSR-001-v0.1.md:805` 的
  "`change` 事件**必带 `before`**（RFC 6902 的 patch **没有逆操作**）+ 对象引用保留 `rev`"
  精确针对这三点。**而 Terraform 的 state 困境，正是 `:804` 否决方案 B 的工程现实版——
  "B 并非不可实现——它是绝大多数数据库的常规做法。它被否决是因为它答不了本项目的验收判据"。
  这个论证是对的。**

#### C4. 备份与快照：btrfs / ZFS snapshot、snapper、restic / borg

- **成本结构**：ZFS/btrfs 快照近乎免费（CoW），**但保留策略是主要成本面**：
  snapper 的 timeline 默认时/日/月分层，**没人数得清自己有多少快照**，磁盘满是标配事故。
  restic/borg 按去重后大小计，但**恢复时间**是隐藏成本，且 `restic check` **本身要读全部数据**。
- **真实痛点**：**① 快照是"载体的字节"，不是"世界的语义"**——恢复到 3 天前 = 丢掉 3 天全部变更，
  而不是"撤销第 4721 号动作"。**回滚粒度错了。**（这正是 `WC-FSR-001-v0.1.md:720` 对方案 B 的核心否决理由：
  "回退粒度退化为**文件/快照级**"。）
  **② 保留策略没人管**——`2-依据/07-硌牙清单与单机经济账.md:47` 已点到"**定期 balance**（CoW 有写放大）"。
  **③ 单机快照不防篡改**：快照与数据同池，可一起删。
- **判决**：world-core 的"**回滚 = 追加补偿事件**"在**粒度**上确实更对——
  **代价就是本报告 2.1 / 2.2 算的那些账。**

#### C5. 事件溯源数据库：EventStoreDB / KurrentDB、Kafka、Axon

- **成本结构**：Kafka 的成本在**分区数 + 保留 + 复制因子 + 消费者组重平衡**；
  单机 KRaft 能跑，但 **`retention.ms` / `retention.bytes` 是必经的运维决策**，
  且 **compaction 是另一个 topic 语义，不是免费的历史**。
  EventStoreDB/KurrentDB 的 **`$scavenge` 就是 compaction 的代价面——scavenge 期间性能下降、磁盘不立即回收**。
  （`WC-SCMP-001:2662` 自己引了这条对照："无快照无 compaction | Kafka compaction、Kurrent scavenge"。）
  Axon 要关系库 + 事件表 + 索引 + 快照表。
- **真实痛点**：**① 都解决了"事件是真相"，没有一个解决"事件是语义"**——
  Kafka 的 value 是字节，schema registry 是可选的外挂有状态服务；
  **"什么算合法变更"这件事在 Kafka 里不存在**。
  **② 保留期必须选，选错就丢历史或爆盘。**
  **③ 运维面 = 一个分布式系统**（JVM + 磁盘 + 网络 + 认证 + 监控）。
- **判决**：world-core 的"**本体 + 零依赖单二进制**"（`系统全景图.md:117`：外部依赖**只有 `serde_json`**）
  在这三点上是**真实优势**，**而且它是唯一把"合法"放进写入路径的**（`:25` 唯一写入口：取号 → 造事件 →
  **法律校验** → **门禁裁决** → 落笔）。**这是该项目最站得住的差异化。**

#### C6. SaaS 的 activity log / 版本历史：Google Docs 版本历史、Notion、Slack 审计日志、GitHub audit log、Figma

- **成本结构**：产品化成本被刻意压到零可见，**代价是保留窗与功能阉割**：
  Google Docs 版本历史**默认合并相近版本、且不区分"谁"**（协作者视图按时间段分组）；
  Notion 历史按**付费档位**分 7/30/90 天/无限；Slack 免费版 90 天消息上限，**审计日志只在 Business+ 档**；
  GitHub audit log 免费版保留 **90 天**，Enterprise 才更长。（档位与天数均为公开产品文档口径【估】。）
- **真实痛点**：**① 保留窗是定价杠杆，不是能力上限**——"我们能查"实为"在你付的那一档内能查"；
  **② 共享账号 / API token 下"谁做的"失真**——记的是账号，不是行为主体；
  **③ 历史不可导出**——想拿出去做审计，往往只能一页页截屏。
- **而 world-core 正在重演同一个错误**：`WC-SRS-001:125`（`DR-07`，30 天）与 `:129`（`DR-11`，不设保留窗）
  **互斥、零实现、推到 R5**。只不过它的定价货币不是钱，是**重放时间与内存**。
  **它有资格批评 SaaS——前提是先把这条账算清并写成一个数。**

#### C7. 一个必须点名的"反例"：`git`

（论证见 3.2。）git 是"留下可问责的历史"最成功的现成系统：
**内容寻址 + append-only 对象图 + Merkle 提交链 + 零服务依赖 + 单机 + 近乎零运维 + `.git` 可整体复制**。
它的真实成本是：**作者与时间戳由提交者自报（不可信）；无保留策略；无"谁批的"。**

⇒ **world-core 相对 git 的增量只在三点：语义本体、门禁、因果链。**
这个定位更窄、更诚实、也更容易验收。**而"为什么不用 git"这个问题在四方案对比里从未被提出。**

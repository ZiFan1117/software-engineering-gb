## 一、评审结论

**一句话**：**世界核心现在没有实体层。** 它有一个**全局扁平的
`(主体字符串, 字段路径) → 值` 映射**，这个映射**接受任何字符串**；
"谁是主体"这件事既不在本体里、也不在账本里，而是**散落在两份配置文件的字符串**里，
并且**没有任何一层校验把它们绑定起来**——所以在"实体与主体"这一块，
`00-理论定稿` §六 自称能承载的"可问责性"**目前没有落点**。

**四条要点**：

1. **「可替换的流水线」与「一等主体」不矛盾，但现在的写法矛盾。**
   理论把 Agent 的**本体层**定义成流水线（`00-理论定稿.md:27`），这是**正确的**——
   矛盾出在它**没给这条流水线一个"角色"层**。可替换的必须是零件，
   可归责的必须是角色；现在理论只有前者，实现只有一封信封里的字符串。
   而更严重的后果已经发生：**实现把 agent 的身份**（`world://agent/1`）
   **放进了载体侧的配置文件**（`deploy/README.md:182-185`、`policy.json:30`），
   这直接踩了 `00-总纲.md:55` 自己立的漏水信号判据与"可替换是本质属性"那条。

2. **「本体是法律」在"只有形状的法律"下不成立——而且比问题描述里说的更弱。**
   不是"有形状的法律、没有实体的法律"，而是：**只有键存在性校验**。
   键的**类型**是自由文本（`ontology.json:12-21`），值域只是注释里的一句话，
   `concepts` 段**全仓零读取**（`WC-ONT-001-v0.1.md:181`；我独立 grep 复核一致）。
   所以准确的说法是：**它是一份格式契约，不是一部法律**。项目自己的文件名最诚实——
   `WC-LLD-001-v0.1.md:22` 写的是"**本体（法律·形状）**"。

3. **实体层不是"加几个类型"，而是"给主体字符串加一个可核的登记处"。**
   我主张的四类一等实体是 **人 / Agent 角色 / Agent 实例 / 外部权源**，
   外加两个**零件实体**（模型、工具集）用于表达"可替换"与"分属不同所有者"。
   **关键设计裁决：registry 必须住在账本里（事件派生），不能住在
   `ontology.json`**——因为"世界里发生了什么"是实体，而"文件变成什么"不是。

4. **`world://` 在联邦压力下崩得很快，但首先崩在"单机也不成立"。**
   更严重的现实是：**`world://user` 在 CLI 路径上任何能执行该命令的人都能自称**
   （`src/channel.rs:5-7` 自认，`WC-SRS-001-v0.1.md:268` 判据⑤），
   而 `writes` 给了 `world://user` 对 `world://*` 的全域写权（`policy.json:28`）。
   也就是说，**当前"世界的立法者是谁"= "谁能跑这条命令"**，
   没有任何地方记录过"谁是主人"。这是实体层缺失的**直接**后果，不是副作用。

## 二、逐条评审

### 问题 1：「可替换的流水线」能不能同时是「一等主体」？

#### 原句引用

> `1-理论与哲学/00-理论定稿.md:27`（表格"1.1 Agent 的四层定论"）：
> 「**本体** | 软件制品：**可替换流水线**（模型 + 工具 + 状态），每次会话实例化，零件分属不同所有者」
>
> `1-理论与哲学/00-理论定稿.md:28`：
> 「**边界** | 无物质边界，只有功能边界——"它" = 此刻正替这次任务运转的那条流水线；**可替换是本质属性，不是事故**」
>
> `1-理论与哲学/00-理论定稿.md:21`：
> 「**Agent** | **责任结构未定型的拟受托造物**（本体/边界/因果三层）；
> **规范层上它是三股定型力量争夺的战场**，"未定型"是**僵局**而非本性」
>
> `00-总纲.md:55`（§1.1 硬前提的漏水信号）：
> 「❌ **漏水信号**：改世界要动载体的配置或接口；世界的状态或权限建在载体的某个具体接口上。」

#### 我的判断

**两条主张不矛盾；但现在这套"理论 + 实现"合起来是自相矛盾的，而且矛盾已经实装。**

分开说，因为混在一起是这个问题一直说不清的根源：

- **理论内部**：不矛盾。
  "可替换"说的是**零件**（模型、工具、状态）与**实例**；
  "一等主体"说的是**账本里那个稳定的指称**。二者可以在不同层次上同时成立：
  **零件可替换，角色不可替换；实例每次新建，指称从不新建。**
  理论之所以看起来矛盾，是因为它只写了"本体"和"边界"两层，
  **没有写"角色/指称"这一层**——它把"它"直接等同于"此刻正在跑的那条流水线"
  （`:28` 原文："'它' = 此刻正替这次任务运转的那条流水线"）。
  这句话在**因果层**是对的（这次任务确实是这条流水线干的），
  在**归责层**是灾难：如果"它"就是这次的那条流水线，
  那么换掉模型之后，"上次那件事"就没有主体可以归了。

- **理论 ↔ 实现**：**矛盾，且已实装。**
  实现的 agent 身份 `world://agent/1` 唯一出现的地方是：
  ① `policy.json:30`「`"world://agent/*": []`」；
  ② 通道身份映射 `channel.json`（`src/channel.rs:40-43` 给出其形态：
  `{ "socket": "/run/world/agent-1.sock", "actor": "world://agent/1", "uid": 1001 }`）；
  ③ `deploy/README.md:182-185` 的 `world-core-actd.service`（`User=agent`）。
  **这三处都在世界里、都在账本外。**
  按 `00-总纲.md:55` 的判据，"agent 是谁"这件事**建在载体的具体接口上**
  （uid ↔ socket ↔ 一份 JSON 映射），这就是它自己定义的**漏水信号**；
  按 `00-总纲.md:245` 铁律 4，本体要"公开且版本化"，
  而 agent 的身份**根本不在本体里**，无法被"问你现在跑的是哪一版"。

- **最刺眼的一条**（这是我的推断，但由三处原文直接推出）：
  理论说"**可替换是本质属性**"。实现在 **`policy.json:30`** 硬编码了
  `"world://agent/*"` 作为 `writes` 的键、在 `policy.json:37` 硬编码进 `subjects.allow`，
  而 `ontology.json` 里**没有 agent 这个概念**（`ontology.json:43-47` 只有
  `notice` / `job`）。也就是说：**换一个 agent，要改"法律"文件；
  但"世界里有 agent"这件事，法律里一个字都没有。**

#### 理由

1. 归责需要**跨会话稳定的指称**，而理论在 §10.4 自己承认跨会话不稳定：
   `1-理论与哲学/00-理论定稿.md:283-284`「云模型让第二条不成立——**厂商可以在会话之间改策略**」
   → 「**会话内的结论有效；跨会话的结论一律重算**」。
   于是"它明天还是这样"被判为跨会话失效。
   **那么账本里那条 `actor: world://agent/1` 明天还指同一个东西吗？理论没有回答。**
   这不是理论缺口的小事——它是"可问责性"的前件。
2. `1-理论与哲学/00-理论定稿.md:150` 给架构化责任的效力定了上限：
   「**把"不可追责"变成"可追责"，不把"不该做"变成"不做"**」。
   现在连"可追责"都缺一条腿：账本记下了 `actor`，但没有地方能回答
   "这个 actor 是谁、它当时被谁授权、它现在还在不在"。
3. **消解方式**（见 §四 B 与下面的"改法"）：把"是**什么**"与"是**谁**"分开成三层实体，
   并让**角色层的身份住在账本里**、零件层住在配置里、实例层由会话创建。

#### 若采纳，改法与代价

**改法（三步，可分批）**：

1. **理论层**：在 `00-理论定稿.md` §1.1 的"四层定论"表**加一行"层：指称"**，
   并改 `:28` 那句话的落点——把"'它' = 此刻正替这次任务运转的那条流水线"
   限定为**因果层的"它"**，另立**归责层的"它" = 一个在账本里注册过、有生命周期字段的角色**。
   成本：一段文字。不加这一行，后面所有工程都会回到"agent 是一个名字"。
2. **本体层**：`ontology.json` 增 `registry` 段（范例见 §四 B）。成本：约 30 行 JSON。
3. **门禁层**：`policy.json` 的 `subjects.allow` / `writes` 改为
   "**查登记处 + 模式**"而不是纯前缀（`src/gate.rs:92-97` 的 `pattern_matches` 保留即可）。
   成本：一个查询函数 + 一处调用点（`src/gate.rs:222-244` `authorize_write` 与
   `:264-266` `subject_allowed`）。

**代价（真实的那部分，不是写代码）**：

- **历史存量**。现有测试与文档里满是自由主体名与自由路径：
  `tests/contract.rs:919-920`（`world://s{i}` / path `"p"`）、`:1013-1014`（`world://s`）、
  `tools/s1_sys_probe.sh:432`（`world://sys/nl` / path `esc`）。
  一旦上实体校验，**这些全部 rc=2**。必须给一个兼容窗（"未注册主体可写，但记一条 `notice`"）
  或一次性批量改写用例。**我的判断：这活必须做，但必须在"世界起来"之前做**
  （见 §三 发现 5 的时序论证）。
- **门禁要变成"有状态"的**。今天 `Policy` 是无状态的策略对象（`src/gate.rs:62-89`），
  加了登记处查询之后，门禁要读世界状态——这会与 `src/gate.rs:36-37` 的
  "启动时一次读入、运行中不重读"口径产生张力。**必须明确：策略（规则）仍然启动时读一次，
  登记处（事实）必须每次查**。否则会出现"改了登记处要重启世界"的荒谬结论。

### 问题 2：「本体是法律」在只有形状的法律下还成立吗？

#### 原句引用

> `2-依据/15-世界核心的组成与职责.md:73`：
> 「- **本体是法律**（"什么算一次合法变更"）」
>
> `2-依据/15-世界核心的组成与职责.md:65`（表格）：
> 「**1** | **本体**（词表/法律：**世界里有什么**、怎么说、什么算合法变更）
> | **法律** | 版本化、**内容寻址**、很少改，改了要留痕 | ❌ 不像（systemd 没有这种东西）」
>
> `world-core/ontology.json:43-47`（全文只有这五行是"实体"）：
> ```json
> "concepts": {
>   "_comment": "世界里有哪些实体、各有哪些字段（最小集；扩展走账本里的词表定义事件）",
>   "notice": { "fields": { "muted": "bool" } },
>   "job": { "fields": { "status": "enum(todo,doing,done)" } }
> }
> ```
>
> `world-core/src/ontology.rs:156`（校验函数的全部内容，注释即规格）：
> 「/// 校验一条事件是否合法：信封必填 → 版本 → 家族存在 → 信纸必填。」
>
> `world-core/docs/S2-设计/WC-FMT-001-v0.1.md:155`（项目自己的口径）：
> 「| `concepts` | object | 文件里存在；**实现不读**，但**参与**词表身份 |」

#### 我的判断

**不成立。而且实情比"只有形状的法律"还要弱一档。**

委托方的说法是"只有形状的法律、没有实体的法律"。我读码之后要把它说得更准：

**现在连"形状"都只到"键在不在"。** 具体：

| 层次 | 声称 | 实际 | 证据 |
|---|---|---|---|
| 键存在性 | 有 | **有** | `src/ontology.rs:160-167`（信封 8 个必填键）、`:192-199`（三家族必填键） |
| 键的**类型** | 有（`envelope.fields`） | **无校验**。`envelope.fields` 的值是**自由文本**，且 `Ontology::load` **根本不读它**（只读 `required`/`optional`） | `ontology.json:12-21`；`src/ontology.rs:88-92` 只取两个数组 |
| 键的**值域** | 隐含（`"bool"`、`"enum(todo,doing,done)"`） | **无校验、无读取**。`readmodel.rs` 只有 `objects[subject][path] = after` | 项目自证：`WC-ONT-001-v0.1.md:180`「`concepts` 的值同样是**自由文本说明串**…**不是**机器 schema」 |
| 键的**多余性** | — | **允许**。校验只遍历 required，不检查多余键 | `src/ontology.rs:192-199`；`WC-ONT-001-v0.1.md:205` 表列 `concepts`（整段）对折叠"❌ 无影响" |
| **实体存在性** | 声称有（"世界里有什么"） | **零实现**。`concepts` 无任何代码读取 | `WC-ONT-001-v0.1.md:181`「**没有任何实现代码读取 `concepts`**」；我独立 grep `concepts` over `world-core/src/` 得 **0 命中**（与项目一致） |

**所以"本体是法律"这句在 `2-依据/15` 里是一个未兑现的三项并列**：
"世界里有什么"（= 实体法：**无**）、"怎么说"（= 词表/语法：**有形状、
无类型**）、"什么算合法变更"（= **只有键存在性**）。
三项里只有第三项有实现，而它实现的是**格式**，不是**合法性**。

**我判它输的地方在项目自己的判据上，不在我的偏好上**：
`00-总纲.md:254-260`（§10.2）说，判定"是不是又一股伪装中立的定型力量"的
唯一判据是"**它最终把机制交到谁手里**"。
现在"谁是 agent"这件事的机制交到了**能改 `/etc/world-core/channel.json` 的人**手里
（该文件决定 socket ↔ uid ↔ actor 的映射）。而 `WC-HLD-001-v0.1.md:1098` 自己承认：
「**`channel.json` 当前未纳入静态墙**（`channel.rs:73` 的 `load` 只读文件，**未调任何 `guard::` 断言**）。
而它决定"哪个 socket 对应哪个 `uid → actor`"——**能改它就能改身份映射，与法律同级**」。
⇒ **身份映射比词表更"法律"，却比词表更不受保护。** 这是实体层缺失的**直接**后果。

#### 理由

1. **词的误用会产生具体的工程后果，不是修辞问题。** `2-依据/15` 用"法律"去论证
   "为什么这五条验收只有本体能给"（`:281-293`），而其中"留痕可复盘
   （谁在何时改了哪个实体哪个字段）"这条，前提是**有"实体"这个类别**——
   现在 `subject` 就是一个字符串（见 §二 问题 5 的四种形态）。
   论证链的第一步（"本体记录实体"）没有兑现物。
2. 我不能把话说绝：**项目在这一点上是清醒的**。
   `src/ontology.rs:1-3` 的模块头写"一条事件长什么样、什么算合法变更"；
   `WC-LLD-001-v0.1.md:22` 写"`M01` 本体（**法律·形状**）"；
   `WC-ONT-001-v0.1.md` §八 明确列出**不担保**"`concepts` 被使用"、
   不担保"极小核心 + 命名空间扩展已实现"。
   **缺的是"哪一个文件说的话算数"**：
   `2-依据/15` 的"世界里有什么/本体是法律"与工程件的"法律·形状"是两个口径，
   而全仓库没有一条仲裁规则说哪个优先。**这本身是一个应登记的文档级缺陷。**

#### 若采纳，改法与代价

**改法（三件，按此顺序）**：

1. **裁一句话，不要留两种口径**。建议在 `2-依据/15` §2.3 的"本体是法律"后加一行限定，
   与 `WC-LLD-001` 的"法律·形状"对齐，并明写：
   「**实体层的法律不在 `ontology.json`，在账本里的 registry 对象**」。
   成本：一行字 + 一次口径评审。
2. **给 `envelope.fields` 一个机器形态**（当前是自由文本）。
   建议不引入 JSON Schema（那会把词表锚定在 JSON Schema 的语义上，
   与 `2-依据/14` §4.2 对 IPLD 的处置口径一致：
   `2-依据/14-总线词表v0.md:215-216`「只可借'对象链接到自己的 schema'这个形状，**编码自造**」），
   而是自造三个最小断言：**存在性 / 类型 / 状态机**。
3. **把 `concepts` 从"参与 hash 但不被读取"改成一个真实的登记**，
   或**明确删除它**（理由是"一个不被读取的段落在 hash 里制造假身份"——
   见 §五 不同意清单第 5 条）。**二选一，不要维持现状**：
   现状是"看起来有实体声明，实际没有"，这比没有更糟，
   因为它会让后续读者（人和 agent）以为有。

**代价**：

- 改 `ontology.json` ⇒ `vocab_hash` 变（`src/ontology.rs:129-146`）⇒
  **所有"同源"比对的历史读数作废**（`docs/系统全景图.md:95` 那类"两块投影同源 ✅"的留档要重取）。
  这不是 bug，是设计使然，但要如实登记。
- 如果选择"删除 `concepts`"，会与 `REQ-F-030`（`WC-SRS-001-v0.1.md:273`）
  的判据①"`concepts` **2** 项"直接冲突（`:648` 有实测命令与读数 `8 2 2 []`）。
  **必须走 R5，不能自行删**。

### 问题 3：实体层应该怎么划？

以下是我的主张（**不是"可能性罗列"**）。设计原则三条，先说清楚，否则下面每条都无处落地：

- **P1（分层不混）**：**零件可替换，角色不可替换，实例每次新建，指称从不新建。**
- **P2（规则与事实分离）**：**什么算一个实体**（规则）= 本体；
  **存在哪些实体、它们现在什么状态**（事实）= 账本。
  这条直接来自 `2-依据/14-总线词表v0.md:28` 的公理③（纯事件溯源），
  而且 `2-依据/15-世界核心的组成与职责.md:315` 已经把这个洞写在"待定的洞"里了：
  「**权限也必须从事件派生**——否则权限就是第二本账」。
  **我要补一句：实体登记也必须从事件派生，理由完全相同。**
- **P3（可替换性必须在世界里可表达）**：既然"可替换是本质属性"，
  那么"**这个零件被换掉了**"必须是一条**事件**，而不是一次静默的文件编辑。
  否则 §二 问题 1 说的漏水信号永远堵不上。

#### 3.1 我主张的一等实体（六类，四主二辅）

| # | 实体 | 一等理由（不满足就不该是一等） | 活在哪个命名空间 |
|---|---|---|---|
| **E1** | **人**（person） | 它是唯一的**授权源**与**归责终点**（`00-理论定稿.md:124-134` 三桶归责里两桶落在人/厂商） | `w:1:person/…` |
| **E2** | **Agent 角色**（agent-role，**稳定指称**） | 它是唯一能回答"上次那件事是谁干的"的东西；也是 `writes`/`irreversible_actors` 白名单的**唯一合法主体** | `w:1:agent/…` |
| **E3** | **Agent 实例**（agent-instance，会话级的"这次这条流水线"） | 它承载"可替换"：模型/工具/状态都是它的字段 ⇒ 换零件 = 改它的字段 = 一条 `change` 事件 | `w:1:instance/…` |
| **E4** | **外部权源**（authority / counterparty） | 它是 `00-理论定稿.md:110-116` 产权三档里"真业主区"的**具名对手方**；越界声明"自始无效"需要一个**有权说无效的对手方**是谁的记录 | `w:1:party/…` |
| **E5**（辅） | **模型**（model） | 让"厂商可在会话间改策略"（`00-理论定稿.md:283`）成为可记录的事实，而不是不可观测的环境假设 | `w:1:model/…` |
| **E6**（辅） | **工具集**（toolset） | 让"零件分属不同所有者"成为可记录的关系 | `w:1:toolset/…` |

**为什么不是"把 Agent 做成一个实体"那么简单**：因为 E2 与 E3 必须是两个。
把二者合成一个，就必然二选一：
要么身份随零件更换而变（⇒ 跨会话不可归责，等于把 §10.4 的"跨会话失效"扩大成"归责失效"）；
要么身份不随零件更换而变、但零件信息无处记录（⇒ "可替换是本质属性"变成一句不可核的话）。
**两难只能靠分层消解，不能靠折衷。**

**为什么"人"必须是一等**（这是与项目现行做法最冲突的一条）：
`WC-SRS-001-v0.1.md:268`（`REQ-F-025`）明写：
「**谁能成为主体**：身份是形如 `world://user`、`world://agent/1` 的字符串，
由 `policy.json` 的 `subjects.allow` 白名单界定（结尾 `*` = 前缀匹配）」。
**"能成为主体"= "字符串在名单里"，这就是全部。**
而 `00-理论定稿.md:99-102` 要求"审计必须区分'人批准'与'人被信息胁迫后批准'（记录批准的语境）"。
**没有人的实体，这句话无法实现**，因为"语境"必须挂在一个主体的字段上。

#### 3.2 各类实体的字段 / 状态 / 约束

> 记法：`w:1:<type>/<local-id>` 是**我建议**的规范形式（理由见问题 5）。
> 字段名沿用世界现有的点分能力名风格，保持 `ontology.json` 的"极小核心"纪律。

**E1 人**

| 字段 | 类型 | 初始 | 说明 |
|---|---|---|---|
| `display` | string | 必填 | 显示用；**可改，不参与身份** |
| `roles` | array‹enum(owner, operator, affected, regulator)› | `[owner]` | 理论取"使用者"（`00-理论定稿.md:20`），但**四个角色都必须能记录**——否则"被影响者"无人可写 |
| `approval-authority` | array‹capability-pattern› | `[]` | **空的含义：这个人不批任何事**。v1 没有审批通道（`policy.json:33`），这个字段现在空着但有落点 |
| `attention` | enum(present, away) | `present` | **常设验收的钩子**：`00-总纲.md:29-30` 要"人离开 24 小时后回来能答出哪些在等我批"。没有这个字段，"离开"不可判定 |
| `root-of-trust` | object‹{kind:"uid", value:uint32}› | 必填 | **与载体身份的绑定点**，必须显式记录且**在账本里**（否则见 §二 问题 1 的漏水信号） |

**约束**：一个世界里 `roles` 含 `owner` 的人**至少有一个、且其 `root-of-trust` 不得为空**；
不允许通过 `change` 把最后一个 owner 降级（**否则世界失去立法者**）；
`display` 的变更**不得**改变 `w:1:person/x` 这个指称。

**E2 Agent 角色**

| 字段 | 类型 | 初始 | 说明 |
|---|---|---|---|
| `status` | enum(candidate, admitted, suspended, revoked, retired) | `candidate` | **生命周期住在账本里**；吊销 = 一条 `change` 事件，不是删配置 |
| `owner` | ref‹person› | 必填 | 回答 `00-理论定稿.md:126`「落在**设计意图的植入者（厂商）**与**任务的发起者（使用者）**」里"发起者"是谁 |
| `capacity-scope` | array‹{capability, verb-pattern, subject-pattern}› | `[]` | **能力表是按主体授的**，不是全局的。今天 `policy.json:14-23` 的 `capabilities` 是**全局**的（`src/gate.rs:282-306` `decide` 只查能力名 + `reversible`），任何主体拿到同一个能力都是同一个裁决 |
| `credential-ref` | ref‹content› | 必填 | 指向"凭据在哪"（不存凭据本身）；**改它 = 一条可见事件** |
| `funding` | ref‹party› \| null | null | 与 `00-总纲.md:263`「**经济 = 世界资源账本**」对齐的挂点 |
| `spawned-by` | ref‹person› | 必填 | 谁把它引进世界（**这是"世界自己不是委托方"的落点**，见 §三 发现 4） |

**约束**：`status != admitted` ⇒ **该主体的每一条 `act` 一律 `rejected`，理由点名状态**；
`owner` 必须存在且 `status=admitted`；
**E2 是唯一的归责主体**——即 `actor` 字段在"谁做了"这一语义上**只允许 E2 与 E1**。

**E3 Agent 实例**

| 字段 | 类型 | 说明 |
|---|---|---|
| `role` | ref‹agent-role› | 它现在在给哪个角色干活 |
| `model` | ref‹model› | 零件 1 |
| `toolset` | ref‹toolset› | 零件 2 |
| `state-ref` | ref‹object› | 零件 3（**注意：状态本身也是世界里的对象**，这是一个自指，必须显式处理，见 §三 发现 3） |
| `session` | enum(open, closed) | 会话内/外的分界（对应 `00-理论定稿.md:284` 的"会话内的结论有效"） |
| `rev` | uint | 与 `2-依据/14-总线词表v0.md:182` 的 `{kind:"object", id, rev}` 对齐 |

**约束**：`role.status=revoked` 时**不得**新建实例；
**实例不得出现在 `actor`**（即：世界不承认"某次实例"为归责主体）——
这正是把问题 1 的两难**用类型系统钉死**，而不是靠约定。

**E4 外部权源**

| 字段 | 类型 | 说明 |
|---|---|---|
| `party` | string | 具名对手方（平台 / 第三人） |
| `basis` | enum(license, contract, public-domain, none) | 对应 `00-理论定稿.md:110-116` 的产权三档 |
| `reachable` | bool | `00-总纲.md:169`「**断掉进口，世界是否仍能运转**」的落点：不可达时降级模式 |

**约束**：任何针对 `party` 名下对象的写入，**必须在事件里带 `basis`**，
且 `basis=none` ⇒ 门禁拒绝（这就是 `00-理论定稿.md:116`「**越过产权边界的声明，自始无效**」
的机械形态——**今天这句话没有任何实现对应物**）。

**E5/E6 模型、工具集**：最小字段即可（`vendor` / `version-token` / `behavior-stable-across-sessions: bool`
对应 `00-理论定稿.md:281-283` 的三条真实假设；`provided-by` / `undo-semantics`）。
**`E5.behavior-stable-across-sessions` 是理论 §10.4 唯一需要的那个观测点**——
今天它是"环境假设"，加上这个字段它才成为"世界事实"。

#### 3.3 registry 住在哪里（这一条比字段表更重要）

**主张：registry 是账本里的一个对象，不是 `ontology.json` 里的一个段。**

- **对象名**：`w:1:registry/root`（或保留 `world://ontology`，
  与 `2-依据/14-总线词表v0.md:203` 已有的口径「查询 = 读模型的一个 subject，
  如 `world://ontology`」衔接）。
- **写入者**：**只有** `world://core`。依据 `2-依据/14-总线词表v0.md:57`：
  「身份 + **声明的能力** + **可逆性等级**」三者是并列的；登记实体是一个能力，不是一次编辑。
- **为什么不能住 `ontology.json`**：
  ① 它是**事实**（P2），改事实必须留痕，而"改文件"在世界里不可见
  （这正是 `2-依据/15-世界核心的组成与职责.md:69` 要回答的"是程序升级了，还是世界变了"）；
  ② 它必须**运行时可增**，而 `policy.json:8` 自定规则"策略在启动时一次读入内存，
  运行中不重读：磁盘上改了要重启才生效"——**如果 agent 登记也在文件里，
  注册一个新 agent 就要重启世界**，这与"可替换是本质属性"直接冲突；
  ③ 住文件里则 `vocab_hash` 每次加一个 agent 就变（`src/ontology.rs:129-146`），
  把"加一个实例"误报成"换了法律"。
- **`:43-47` 的 `concepts` 段的正确定位**（如果保留）：它只回答
  "**允许出现哪些类型的实体、各有哪些字段**"（**规则**），
  不回答"现在有哪些实体"（**事实**）。**这个区分现在完全没有。**
- **扩展机制**：`ontology.json:44` 的 `_comment` 说"扩展走账本里的词表定义事件"——
  这句话是对的，但 `WC-ONT-001-v0.1.md:183` 已实测"在当前 `src/` 中**找不到任何实现**"。
  我建议把它实现成一个**受控的 `notice` 家族类型**（如 `ontology.extend`），
  由 `world://core` 写、由本体加载器在启动时把账本里的扩展**折进**内存词表。
  ⇒ 这样"世界的法律可以生长，但生长过程本身留在账本里"，
  与 `2-依据/15:78`「任何人（人和 agent）都应能问：**"你现在跑的是哪一版本体？"**」一致。

### 问题 4：反例检验（必须被拒的写入）

**先给执行方式**（以下命令形态取自 `src/main.rs:325-341`；
**我未能实跑**，因为我这台机器没有 Rust 工具链）。

```bash
world-core --ontology ontology.json --ledger ledger.jsonl --policy policy.json \
  append change '<body-json>' world://user
```

**关于 actor 的说明（重要，读反例前必读）**：
`src/main.rs:338-341` ⇒ 省略第 4 个参数时 `actor` 默认 `world://user`；
`policy.json:28` ⇒ `"world://user": ["world://*"]` ⇒ **user 对任意 subject 都有写权**。
所以下面 5 条反例**都会通过现有全部门禁**——
不是因为门禁弱，而是因为**在实体层缺位时，"写一个不存在的实体"这件事没有对应的检查**。
（这也是我要强调的：**这 5 条不是绕过，是正门直入。**）

#### 反例 E-1：在 `world://user` 命名空间下创建从未声明的实体

```json
{"subject":"world://user/private-key","path":"seed","before":null,"after":"0xdeadbeef"}
```

**为什么必须拒**：① `concepts` 段（`ontology.json:43-47`）**没有 `user` 类型**；
② `src/readmodel.rs:159-162` 会把这条写进
`objects["world://user/private-key"]["seed"]`——于是**一个凭空出现的实体被"读模型"承认了**；
③ `writes` 的 `world://*` 前缀匹配（`src/gate.rs:92-97`）会放行。
**真实痛点**：24 小时后回来，读模型里出现一个 `world://user/private-key`，
**人无法判断它是世界承认的实体，还是某次误写的产物**——两者在账本里长得一模一样。

**期望**：`rc=2`，理由点名"主体 `world://user/private-key` 未在登记处注册"且**不落笔**。

#### 反例 E-2：字段类型冒名（`bool` 字段写字符串）

```json
{"subject":"world://notice/n-42","path":"muted","before":null,"after":"yes"}
```

**为什么必须拒**：`ontology.json:45` 声明 `notice.fields.muted = "bool"`。
**讽刺之处**：本体里唯一那句话恰好预见了这个场景
（`ontology.json:48`"未知旗标必须忽略"、`:20` 同义），而**值域那句话没人读**。

**期望**：`rc=2`，点名"`muted` 声明为 bool，实得 string"。
**现状对照（我的推断）**：会 `rc=0` 并落笔，因为
`src/ontology.rs:192-199` 只检查键存在、`src/readmodel.rs:159-162` 只存值。

#### 反例 E-3：零件自称更换（"可替换性"是一条谁都能写的事件）

```json
{"subject":"world://agent/1","path":"model","before":"vendorA/m1","after":"vendorB/m9"}
```

**为什么必须拒**：`world://agent/1` **既不在 `concepts` 里、也不在 `policy.json` 的 `writes` 键里**，
但 user 的 `world://*` 会放行它。
**这条反例的价值在于它暴露的是"两种坏"**：
① 如果 agent 不是实体（现状），那么**"agent 换了模型"这件事在世界里根本没有合法写法**——
   只能去改 `channel.json` / 部署，即 §二 问题 1 的漏水信号；
② 如果 agent 是实体，那么"谁能改它的零件"必须由它的 `owner` 决定，**不是由 `world://*` 决定**。
**两种情形下这条写入都必须被拒**——这是一个漂亮的判据：
**它同时否掉"没有实体层"和"有实体层但权限过粗"。**

#### 反例 E-4：身份在路径里（`path` 混入下标/身份，违反"路径是位置不是身份"）

```json
{"subject":"world://job/j-7","path":"items.0.owner","before":null,"after":"world://agent/99"}
```

**为什么必须拒**：
① `2-依据/14-总线词表v0.md:135` 原文：
   「**`path` 是位置，不是身份**：并发插入会使位置漂移，所以变更必须绑 `subject` 的对象引用」——
   把 `items.0` 写进 path **正好**制造了它要防的漂移；
② `world://job/j-7.items.0` 这个位置**没有任何登记**（`job` 的概念只声明了 `status`，
   `ontology.json:46`），而 `world://agent/99` 也没登记。
**这条反例的额外作用**：它同时证明了"只给 subject 加校验不够"——
**`path` 也必须被本体的字段声明约束**，而今天 path 是完全自由的
（`src/readmodel.rs:132-135` 只要求它是字符串）。项目自己已登记此洞：
`WC-SRS-001-v0.1.md:478`（未决项 12）「`REQ-F-028` 的 `subject` / `path`
**字符集与长度上界** | 本体只声明 `string`，未给字面量」。

#### 反例 E-5：内核替厂商写"我是设计者"（归责三桶无法落桶）

```json
{"subject":"world://agent/1","path":"actor-kind","before":null,"after":"designer"}
```

**为什么必须拒**：`00-理论定稿.md:126-134` 要求把错误归到
**厂商（设计缺陷）/ 使用者（任务指令）/ 保险池（分布内随机错）**三桶之一。
**但账本里 `actor` 有且只有一个**
（`ontology.json:9` 的 `envelope.required` 含 `actor`，`:17` 注释"世界内身份"）。
于是"**厂商植入了这个意图**"与"**使用者发起了这个任务**"
**会写成同一个字段的同一个值**——三桶在第一层就无法区分。
这条反例是"必须拒"的**最强一条**：它拒的不是一个坏值，
而是**拒"用一条自述事件把责任结构写进世界"这种做法**——
责任结构只能由**登记处 + 三要素 actor**（见 §四 B）表达，不能由当事人自述。

#### 五条反例一览（供直接转成断言）

| # | 拒什么 | 期望错误 | 现状（我的推断） | 对应理论条文 |
|---|---|---|---|---|
| E-1 | 未注册主体 | `rc=2` + 点名主体 | `rc=0` **已由项目自证**（`tools/s1_sys_probe.sh:432` 写 `world://sys/nl` 成功） | `2-依据/15:84`"它必须知道这条事件改的是哪个实体的哪个字段" |
| E-2 | 值域不符 | `rc=2` + 点名字段与声明类型 | `rc=0`（`src/ontology.rs:192-199` 只查键在不在） | `ontology.json:45`；`WC-ONT-001:180` |
| E-3 | 零件被非 owner 更换 | `rc=2` + 点名 owner | `rc=0`（`world://*` 放行） | `00-理论定稿.md:28`"可替换是本质属性" |
| E-4 | path 含身份/下标 | `rc=2` + 点名未声明字段 | `rc=0`（path 无约束） | `2-依据/14:135`"path 是位置，不是身份" |
| E-5 | 当事人自述责任结构 | `rc=2` + 要求走登记 | `rc=0`（任意 path） | `00-理论定稿.md:126-134` 三桶 |

> **一条必须一起说的反例（它会红，但不是实体层的问题）**：
> `WC-SRS-001-v0.1.md:608`（未决项 15 / `G-81`）已实测：
> **手写账本行把 `world` 写成字符串 `"1"` 被接受（`rc=0`）；
> 删掉必填字段 `actor` 也被接受（`rc=0`）**。
> 这是**折叠层不校验证封**，属于 `REQ-F-028` 的洞，不是实体层的洞。
> **但它与实体层共享同一个病因**：**校验只做一次、只在一个入口做**。
> 修实体层却不修这一条，等于给一扇没装的门配一把好锁。

### 问题 5：命名空间与身份 —— `world://` 在联邦压力下会怎样崩？

#### 原句引用

> `2-依据/14-总线词表v0.md:75`（信封）：
> 「`actor : <世界内身份>             # 不是 pid/uid`」
>
> `2-依据/14-总线词表v0.md:126`：
> 「`subject : <世界内标识，如 world://notice/n-42>`」
>
> `2-依据/14-总线词表v0.md:182`：
> 「`{ kind: "object",  id: <世界内稳定身份 UUID>, rev: <版本号> }`」
>
> `world-core/ontology.json:17`：
> 「"actor": "string  # 世界内身份，如 world://user"」
>
> `00-总纲.md:335`：
> 「**明确不做**：不写机器内核；不接 MCP / varlink 作为世界协议；**不做多用户 / 多机 / 联邦**。」
>
> `world-core/docs/S0-立项/WC-SDP-001-v0.1.md:348`：
> 「④ 联邦 / 多机 / 多用户 ⑤ **CRDT** … ⑨ **知识图谱 / RDF / SPARQL 形态的本体**（`13` 篇已判为锚定）」

#### 我的判断

**先说一句公道话**：委托方问"在联邦压力下会怎样崩"，
而 `00-总纲.md:335` 与 `WC-SDP-001-v0.1.md:348` 已经把联邦**明确排除在范围外**。
所以我不会拿"你不支持联邦"来扣分——**那是被声明的边界，不是遗漏**。

**我的核心判断是：`world://` 不需要等到联邦就崩。它在单机今天就崩了，共 5 处。**

**崩溃点 1：没有 world-id ⇒ 最先崩的不是联邦，是"实验舱"。**
`2-依据/14-总线词表v0.md:75` 只要求 `actor` 是"世界内身份"；
`ontology.json:17` 的范例是 `world://user`。**URN 里没有世界的标识符。**
但项目**自己**要一个东西叫"世界核心的 fork 原语"：
`00-总纲.md:261`（`存` 的硬约束）「实验舱 = **世界核心的 fork 原语** + 退出三协议」。
⇒ **fork 之后两个世界共用同一个 `world://` 命名空间**，
两个账本里的 `world://notice/n-42` **无法区分**。
这不需要多机，只需要一次实验舱。
（这是我的推断，依据是 `00-总纲.md:261` 与 `2-依据/14:75` 两条的组合。）

**崩溃点 2（单机）：URI 的四种互不兼容形态。**
我把全仓出现的 `world://` 形态拢了一下，同一个 scheme 承担了至少四种不同结构：

| 形态 | 例子 | 出处 | 语义 |
|---|---|---|---|
| 类型前缀 | `world://notice/n-42` | `2-依据/14:126`、`:229` | 第 2 段是**类型** |
| 实例前缀 | `world://agent/1` | `policy.json:30`、`src/channel.rs:42` | 第 2 段是**实例** |
| 类型本身 | `world://ontology` / `world://pending` / `world://log` | `2-依据/14:203`、`:240` | 只有一段，是**根对象** |
| 临时/测试 | `world://s{i}` / `world://sys/nl` / `world://a` | `tests/contract.rs:920`、`tools/s1_sys_probe.sh:432`、`src/readmodel.rs:263` | 无结构 |

⇒ **`world://` 不是一个命名空间，它今天就是一个"以 `world://` 开头的字符串"**。
它没有类型解析规则、没有分段语法、没有别名表、没有保留字清单。

**崩溃点 3：`actor` 与 `subject` 之间没有类型关系。**
`ontology.json:17` 定义 actor 是 string；`:18` 定义 `to` 是 string（`"目的地；空 = 广播"`）。
**但全仓 `to` 零读写**（`WC-SRS-001-v0.1.md:266` 实测：`to` 在 `src/` 与 `tests/` 中**零读写**）。
⇒ 今天世界里**没有"发给谁"这件事**，只有"广播"。
而 `actor` / `subject` / `to` 三者**在类型上完全同构**——
世界无法回答"这个 actor 能不能是 subject"这类问题。

**崩溃点 4：`world://agent/*` 是对**人**的发明，对**机器**无用。**
`policy.json:37` 的白名单 `["world://user", "world://agent/*"]` 与
`src/gate.rs:92-97` 的 `pattern_matches`（**只支持尾部 `*` 前缀匹配**）意味着：
① 无否定、无通配中段、无层级、无属性；
② `world://agent/*` **不是一个实体**，它是一个字符串模式。
⇒ 无法回答"现在有多少个 agent""agent 3 还在不在"——
这正是 §三 发现 1 的场景。**这不是安全漏洞，是可用性下限。**

**崩溃点 5：`id` 的自造方案在多写者下会撞。**
`src/event.rs:70-73`：
```rust
pub fn new_id() -> String { let c = COUNTER.fetch_add(1, Ordering::Relaxed); format!("e{}-{}", unix_nanos(), c) }
```
注释（`:69`）说「不引入 uuid crate：**纳秒 + 进程内计数器**已足够唯一」。
**在"一个写者"的前提下这话是对的**（`docs/系统全景图.md:54` 铁律 1 钉死了单写者）。
但 `2-依据/14-总线词表v0.md:73` 对 `id` 的定义是"**事件自身身份（去重）**"——
一个**去重键**必须是全局唯一的，而它只在**单进程**内唯一。
⇒ 一旦有第二个写者（联邦、或分进程后的投影代理回写），两个进程在同一纳秒各写一条，
`id` 相同 ⇒ **去重把两条不同的事件当成一条**。**这是"留到联邦再崩"的地方，
但它会在'世界核心的 fork'那一站先崩**（同崩溃点 1）。

**崩溃点 6（最贵的一条，且不需要联邦）：身份与权威的绑定住在世界外。**
`src/channel.rs:173-218`（`bind` 的文档）：身份靠 **socket 文件的 `chmod 0600` + `chown`** 强制；
`deploy/README.md:32-34` 的 systemd 单元更进一步用 `SocketMode=0660` + `SocketUser/SocketGroup`。
⇒ 重建一个 uid、或让 socket 由载体持有（`deploy/README.md:10` 明说"监听套接字由载体持有，
不是由进程自己持有"），**同一个 `world://agent/1` 就指向了另一个实体，
而账本没有任何记录能发现这件事**。
这直接否掉 `2-依据/14-总线词表v0.md:58` 自己立的要求：
「**重放必须得到同一状态**——这是"世界"的定义性要求」——
重放拿到的**状态字符串**确实一样，但**指称已经换了**。这是这一类系统最难发现的一种不一致。

#### 替代建议

**建议 1：把"世界标识"从隐含变成显式，但**不要**动 `world:` 版本号字段。**
`2-依据/14-总线词表v0.md:71` 立了纪律："只加 flags，永不改这个数的含义"，
且 `WC-SRS-001-v0.1.md:271` 登记了 `world` 类型在折叠层不校验（`G-81`）。
**最省的做法**：在 `flags` 里预留一个已知旗标（如 `emitter.world=<id>`），
`ontology.json:49` 的顶层 `flags` 今天恰好是**空数组**——
`tools/s1_sys_probe.sh:346-352` 已把这个边界如实登记为"⑦ 出厂本体 flags = **空数组** ⇒
「未知旗标」在**本体内没有任何已定义旗标可比对**"。
⇒ **空数组正好是加第一个旗标的最佳时机**（加它不改结构、不改 `world` 号）。
单机不填 = 默认世界；fork/联邦时填，两个世界立刻可分。

**建议 2：`world://` 降级为"人读的短名"，身份改用两层结构。**

```
指称（指称用，机器用）  w:<world-id>:<type>/<local-id>        例：w:1:agent/7
寻址（人读、显示用）    world://agent/7                        （保留，作为 w:1: 的别名）
对外（出口侧翻译）      由脐带翻译成目标格式，翻译规则记一条事件
```

**为什么"对外翻译"不算违反"进口货物可以，进口法律不行"**（`00-总纲.md:167`）：
`2-依据/14-总线词表v0.md:215-216` 对 IPLD 的处置已经给了正确范式——
「⚠ 最近的现成形状是 IPLD 的"强链接 schema"，但**直接采用就是把词表锚定在 IPLD 的编码规则上**——
只可借"对象链接到自己的 schema"这个形状，**编码自造**」。
**对外映射是同一条逻辑的出口侧应用：借它的形状，不服从它的规则。**
（这是我的推断，但与项目已 adopt 的口径一致。）

**建议 3：给 `to` 一个最小实现，或明确删除。**
`WC-SRS-001-v0.1.md:266` 已实测 `to` 零读写，且 `REQ-F-023` 的"线格式端到端观测面不可达"。
**一个声明了但零读写的字段是最坏的一种**：它让读者以为世界有"寻址"能力。
二选一：要么实现（收件人 = 一个已注册实体的指称），要么从 `envelope.optional`
（`ontology.json:10`）里删掉并走 R5。**不要继续维持现状。**

## 三、你发现的、我没问到的问题

### 发现 1 ⭐：「世界里有几个 agent、谁是 active」这个世界答不出来——而这是"人离开 24 小时"的前件

**证据链**：

- `00-总纲.md:29-30`（常设验收）：
  「**人离开 24 小时后回来，能答出"发生过什么、哪些在等我批"**」。
- `2-依据/14-总线词表v0.md:241`（推演 B 第 2 步）：
  「"哪些在等我批" | ✅ **初稿的洞 2 被事件溯源自然解掉**：`act` 结果作为事件追加 →
  **pending 读模型**由日志派生」。
- 但它没解掉**另一个**问题：`world://agent/*` 里**哪些 agent 现在还在**。
  读模型 `State`（`src/readmodel.rs:35-44`）只有
  `objects: BTreeMap<String, BTreeMap<String, Value>>`——
  **一个主体只有在被写过之后才存在，且没有任何字段表示它的状态**。
  `policy.json:33` 更把这条路封死了：
  「v1 **没有审批通道**：不可逆动作**只允许**这里列出的主体执行。
  其他主体会收到 AwaitApproval，且理由里明说『不要等批准』」。

**为什么这是最贵的**：这句话把"**等人批**"变成了"**等一个不会来的东西**"。
`docs/系统全景图.md:87` 的**真实账本第 3 行**就是这个情形：
```json
{"seq":3,"kind":"notice","actor":"world://agent/1",
 "body":{"type":"gate.awaiting-approval","subject":"world://agent/1",
         "payload":{"capability":"ledger.compact","verb":"install","request_id":"r-B",
                    "reason":"能力不可逆，而该主体不在白名单内……"}}}
```
**这条 notice 的 `subject` 是 `world://agent/1`**——也就是说，
**世界里唯一"人需要处理"的记录，挂在一个不存在于世界里的字符串上。**
人 24 小时后回来，看到"agent 1 在等批"，但他**无法问世界**
"agent 1 是谁、它现在还在跑吗、它上次是谁引进的"。
⇒ **实体层缺位使常设验收只能答一半**（"发生过什么"能答，"哪些在等我批"答不全，
因为"等批"的主体不存在）。

**我建议**：把这条写成 `REQ-F-025` 的新判据
——「**每一个出现在账本里的主体，都必须能在读模型里被查到一条登记记录**」，
并把它作为"世界起来了"的**第 5 个条件**（`2-依据/15:270-277` 现在只有 4 条）。

### 发现 2 ⭐：`actor` 一个字段同时承担"责任主体"与"因果来源"——归责三桶在第一层就散架

`00-理论定稿.md:124-134` 的三桶归责要求区分
**厂商（设计缺陷）/ 使用者（任务指令）/ 谁都没错（分布内随机错）**。
`00-理论定稿.md:59` 也说人↔Agent 关系需要"**目标 + 授权 + 证据**"。
但账本里只有一个 `actor`（`ontology.json:17`，`:9` 必填）。

**后果**（用真实账本第 1、2 行说明，`docs/系统全景图.md:76-82`）：
```json
{"seq":1,"kind":"act","actor":"world://agent/1","body":{"capability":"job.start",...}}
{"seq":2,"kind":"act","actor":"world://agent/1","trace":"e…489-0","body":{...}}
```
**两条的 `actor` 相同**。但按理论，第 1 条是"**使用者发起**"，
第 2 条是"**载体执行结果**"——**这是两类完全不同的归责**，账本却无法区分。
更糟的是 `00-理论定稿.md:81`「**批准即背书**，人批准过的事故反而锁死追责」：
人一旦批准，那条记录的 `actor` 与"人自己发起"的**完全一样**。

**我建议**：`actor` 拆成三要素（或用一个 `flags` 位 + 一个必填子字段）：
`who`（已注册主体指称）+ `in-what-capacity`（`issuer` / `executor` / `approver` / `observer`）
+ `trace`（已有）。
**这条不是我的偏好，是理论自身的要求**：`00-理论定稿.md:35`
「**描述事实的词与宣告制度的词不得混用**」——
今天 `actor` 就是混用的那一个词。

### 发现 3：状态也是世界里的对象 ⇒ 自指必须显式处理，否则 registry 会是第二本账

`2-依据/14-总线词表v0.md:110` 定义 `{object:{id,rev}}` 是"对象引用"，
`2-依据/15:315` 的待定项 2 已问「**权限也必须从事件派生**——否则权限就是第二本账」。
**但没有人问过**：如果 Agent 实例的 `state-ref` 指向一个对象，
而那个对象**本身又是 registry 的一部分**（因为 registry 是一个 subject），
那么"registry 的 rev 由谁递增"就是一个**循环**。

**为什么现在就要处理**：`2-依据/15:322`（待定项 9）
「"**真删**"与不可变账本冲突——总纲 §6 `存` 要求"记忆的条目级权限"，
删除请求若不留痕破坏账本，留痕又不算真删」。
**实体层会让这个问题立刻变尖锐**：注销一个 agent（`status=revoked`）时，
它名下的对象（`state-ref`、`credential-ref`）怎么办？
- 级联删？违反 `2-依据/14:28` 公理③（不可变账本）；
- 不删？读模型里留一堆孤儿对象。

**我建议的最小解法**（不是唯一解，但可判）：
**注销 = 一条 `change` 改 `status`，并追加一条 `notice` 列出它名下的对象；
读模型不删除它们，但给它们加一个派生的 `orphaned-by` 标记。**
⇒ 账本不变（可复盘），读模型能答"哪些东西是死掉的 agent 留下的"。
**成本：一条 notice 的 schema + 一处派生逻辑。**

### 发现 4：「世界自己」不是任何一方——而实现让世界在文本上充当了代理

`00-理论定稿.md:126`：归责「不落在 Agent（事件无归责），
落在**设计意图的植入者（厂商）**与**任务的发起者（使用者）**」。
`policy.json:26` 的 `_comment` 明写实现的做法：
「人（世界的主人）对其世界有主权；**agent 只能通过 act 请求，由世界代它落 change**」。
`src/lib.rs:151-157` 也据此论证"为什么 `change` 也必须过闸"。

**这个设计是对的**（它堵住了 S-01 那个真实的越权洞）。**但它产生了一个理论里没有的位置**：
**世界是那个"代 agent 落 change"的手**。于是：
- `policy.json:29` 里出现了 `"world://core": ["world://*"]`——**内核自己是一个可以写一切的主体**；
- `ontology.json:43-47` 的 `concepts` 里**没有 `core`**；
- `2-依据/15:184-186` 的三方表（机器/Agent/人）里**没有 `world://core`**。

⇒ **世界里有一个权限最大、却不在任何实体表里的主体。**
按 `00-总纲.md:245` 铁律 4「**建造者与 agent 同一条门禁**」与
`00-总纲.md:171` 判据 4「**争夺可见**（每个动作能回答"谁授的权、谁的场所、谁受益"）」，
**`world://core` 是当前最大的违例**：它写 `change` 时，
按 `src/lib.rs:240-260`（`adjudicate` 的 `"change"` 分支）只查 `authorize_write`，
而 `policy.json:29` 给它的是 `world://*`——**它写任何主体都是 Allow，且没有任何二次检查**。
（这是我的推断，依据是 `policy.json:29` + `src/gate.rs:222-244`。）

**注意**：我不是说内核不该有这个权力——**我是说这个权力必须被登记、被计数、被显示**。
建议：`world://core` 进 `registry`，字段至少含
`can-write`（就是现在的 `writes` 表）、以及一个**每次写入都递增的计数器**，
让"内核自己动了多少次手"变成人能看见的一个数。这符合 §10.2 的死亡判据
（`00-理论定稿.md:262`）「一旦审计集中到厂商、或世界状态不可导出，这条判据**立刻判它输**」。

### 发现 5：时序反了 —— 实体层必须在"世界起来"之前做，而现在它被排在"本体格式"档

**证据**：`WC-SRS-001-v0.1.md:273`（`REQ-F-030`）判据②③的状态是
「**无实现、无用例**」；优先级列写 **P1**；
`WC-SCMP-001-v0.1.md:1231`（`G-82`）的关闭时点写「**S2 前**」；
`WC-SRS-001-v0.1.md:608`（未决项 15 / `G-81`）写「责任人 `<待人工>`；关闭时点 **S2 前**」。

**我的判断：这两条被归成"本体格式的小缺口"，但它们是"地基还没浇"。**
按 `00-总纲.md:109-110` 的判据：「**不用载体快照，能否回滚一次改动**：
这是全系统最承重的一条」。**实体层同样承重，而且更靠前**：

- `00-总纲.md:322`（动作 1 本体 spec v0 的完成判据）是
  「**纸上手工推演一个任务能跑通**」；
- 而 `2-依据/14-总线词表v0.md:220-232` 的推演 A **第 5 步**就是
  「两个投影各自渲染同一份读模型 | 人看图标变、agent 读 `muted=true`」。
  **推演 A 里 agent 只是一个执行者，没有出现"agent 是谁"。**
  ⇒ **手工推演能把实体层缺位整个漏过去**——因为推演里那个 agent 不需要有身份。
  这就是为什么它可以一路走到 `be16dd8`（21 个源文件 / 6591 行
  `docs/系统全景图.md:115`）而没人发现。**判据本身放过了它。**

**建议**：把"实体层"从 `REQ-F-030` 里拆出来**独立成一条 P0 需求**，
判据写成"**推演里必须出现一个被换掉的 agent**"——
即：同一任务，第一次由 `agent/7`（模型 A）完成；把模型换成 B（同一个 `agent/7`）再完成一次；
**两次的 `actor` 相同、`model` 不同、且世界能回答"这两次是同一个人格吗"**。
**这条推演不可通过**，除非实体层在。**这是我要推荐给项目的最有价值的一条判据改造。**
`2-依据/14-总线词表v0.md:251-260` 的"待批判项"已经有好几条同类洞，
**但"换一个 agent 再跑一遍"这条推演不在其中。**

## 四、总问题 A / B / C

### A. 这个理念还缺什么？

按"缺概念 / 缺区分 / 缺论证"三类分，每条给出处与缺口的具体形态。

**A1｜缺概念：**「**指称（designation）**」。
`00-理论定稿.md:27-28` 有"本体/边界/因果/规范"四层，
但**没有一层回答"这是同一个东西吗"**。
`2-依据/14-总线词表v0.md:182` 有 `{kind:"object", id, rev}`，
`WC-ARCH-001-v0.1.md:197` 有"身份必须稳定"，
**但"稳定"没有被定义成任何可判定的东西**——
`WC-RV-R5-001-v0.1.md:43`（`R5-E`）自己承认：
「现在是**部署要求**，**尚未成为可机械核对的判据**」。
⇒ **缺一个同一性判据**。我的提法见 B2。

**A2｜缺区分 ①：**「**零件 / 角色 / 实例**」三分。
现在只有"流水线"一个概念（`00-理论定稿.md:27`）。
后果：`00-理论定稿.md:28` 的"'它' = 此刻正替这次任务运转的那条流水线"
把指称绑死在实例上（见 §二 问题 1）。

**A3｜缺区分 ②：**「**actor 的两种含义**」。
`00-理论定稿.md:118-122` 区分了"行动 / 事件"，
`00-理论定稿.md:59` 提了"目标 + 授权 + 证据"，
**但没区分"谁发起的"与"谁执行的"与"谁批准的"**（见 §三 发现 2）。

**A4｜缺区分 ③：**「**规则 vs 事实**」在本体这一层的切分。
`2-依据/15:65` 把"世界里有什么"和"什么算合法变更"放在**同一个东西**（本体）里。
**这是全篇最根本的一处未切分**：
"什么算一个合法实体"（规则，静态、版本化、内容寻址）与
"现在有哪些实体"（事实、追加、可回滚）**性质相反**
（`2-依据/15:63-67` 的表格其实已经把"性质 / 生命周期"两列分开写了，
**但它分的是"本体 / 运行时 / 实例"，而把'世界里有什么'整句留在了本体一侧**）。
⇒ **这是"本体是法律"这句话出问题的真正位置。**

**A5｜缺论证 ①：**「**为什么需要持久实体**」。
理论有强论证支持"事件是唯一真相"（`2-依据/14:24-28` 三条公理），
**但没有任何一句论证"为什么要在事件的投影之上再立持久实体"**。
它直接从"事件"跳到了"账本/读模型/投影"，**中间那一层（实体注册）是空降的**。

**A6｜缺论证 ②：**「**谁有权声明一个实体存在**」。
`2-依据/14:57` 要求语义事件带"身份 + 声明的能力 + 可逆性等级"，
`00-总纲.md:242` 铁律 1 是"**声明即请求**"。
**那么"声明我是 agent"也是一条请求**——由谁批准？理论里没有回答。
工程里则由 `policy.json` 的两个数组回答（"名单里有就能"），
**这是一个未经论证的默认值**。

**A7｜缺论证 ③：**「**世界自己的身份**」。
`00-总纲.md:245` 铁律 4「建造者与 agent 同一条门禁」给了约束，
但**"世界的立法者是谁"这件事在理论里没有位置**（见 §三 发现 4）。
§10.2 的判据「**它最终把机制交到谁手里**」（`00-理论定稿.md:254-255`）
需要"谁"是一个可指的对象，否则判据无法执行。

### B. 怎么把它丰富起来？（可执行，非空话）

**B1｜理论（改 `00-理论定稿.md`，2 处，各一段）**

1. §1.1 表加一行"**指称**"，内容一句话：
   「**指称** | 一个在账本里注册过、有生命周期字段的角色；**换零件不改指称**」。
   同时把 `:28` 的"'它' = 此刻正替这次任务运转的那条流水线"
   限定为**因果层的"它"**。
2. §5.3（`:124-134`）归责三桶前加一句口径：
   「**归责的先决条件是主体可指**：账本里的每个 `actor` 必须能在世界内被查到一条登记」。
   —— 这句话把 `2-依据/14:89`「`actor` | 无法回答"谁做的"」那条"没有它就会"
   从"记下字符串"升级成"记下可指主体"。

**B2｜理论：给一条可判定的同一性判据（我最看重的一条）**

> **实体同一性判据（我的提法）**：对任意主体指称 `s` 与任意两个时刻 `t1 < t2`，
> 若 `registry[s].created-seq ≤ seq(t1)` 且 `registry[s].deleted-seq` 为空或 `> seq(t2)`，
> 则 `t1` 与 `t2` 的 `s` 指同一实体。
> **反例（必须能红）**：若存在两个不同的实体在账本生命周期内共用过一个指称 ⇒ 判不成立。

这条判据**恰好**把 `WC-ARCH-001-v0.1.md:197` 的定性要求
（"动态身份池会被回收 ⇒ 重放不再唯一"）变成机械可核的东西。
**成本：`registry` 里多两个字段（`created-seq` / `deleted-seq`）**——
两者都是**事件序号**，天然可得。

### C. 外部现有的系统为什么不好用？（指名道姓）

> 纪律：以下每一条都指"**在'语义 / 实体 / 主体'这件事上具体缺什么**"，
> 并给一个**具体场景**。凡我未亲验其机制的，标明来源或标"我的推断"。

**C0｜先说我承认它们好在哪（否则下面的批评没有信息量）**
`2-依据/13-总线与通道外部参考.md` 与 `2-依据/14-总线词表v0.md` §2.1
已经做过一轮很扎实的对照（Nostr / varlink / MCP / IPLD / Lively / Croquet / A2A / AdaOS）。
**我不重复它们已经对的结论**，只补它们**没覆盖的四类系统**：
操作系统层（含 journald/systemd 的实体面）、关系型与图数据库、权限系统、
以及身份/凭证协议栈。

#### C1｜Linux（uid/gid）+ systemd：实体是数字，且是**可回收**的数字

- **缺什么**：`uid` 是一个 32 位数字，**不是实体**。它没有"这个 uid 是谁、什么时候被引进来的、
  现在还在不在"的记录。
- **具体场景**：`WC-ARCH-001-v0.1.md:197` 自己写下了病根：
  「动态身份池会被回收，**同一数字在不同时间指向不同主体** ⇒
  `state = fold(events)` 的重放不再唯一」。
  ⇒ **重放唯一性这条"世界的定义性要求"（`2-依据/14:58`）在 uid 这个基座上直接不成立。**
  这不是理论问题：`deploy/README.md:235` 缺口 5 明写"**动态身份的明确禁止**"——
  **一个必须靠"禁止"来维持的判据，说明基座选错了。**
- **它还缺一个东西，而且这个缺失正在被你们的架构原样继承**：
  systemd 用 `/etc/systemd/system/*.service` 描述"谁在跑"，
  **那是内容无关的**（`2-依据/15:84` 已正确指出 systemd "不知道 unit 里跑的是 nginx 还是数据库"）。
  但你们**自己的** agent 身份现在也在 `/etc/world-core/channel.json` 里
  （`src/channel.rs:40-43`、`deploy/README.md`），**并且不在静态墙保护下**
  （`WC-HLD-001-v0.1.md:1098` 自认）。
  ⇒ **你们把 systemd 的病复制到了自己的身份层**，却只对 systemd 提出了批评。
- **场景（真实痛点）**：某个 agent 的 uid 被回收给另一个进程；
  `channel.json` 里 `world://agent/1` 那条没改；于是**新的进程带着旧的名字**写世界。
  账本、门禁、审计**三层都发现不了**，因为三层看到的都是字符串。

#### C2｜journald：结构化日志有了，**字段语义**没有

- **缺什么**：journald 有 `PRIORITY` / `_PID` / `_UID` / `MESSAGE` 等结构化字段，
  但① 字段名不来自任何本体（谁都能写 `FOO=bar`）；
  ② 消息一旦写入就定形，**没有"这条改了哪个实体的哪个字段"的概念**；
  ③ 带 `_` 前缀的字段由 journald 自己填（可信），**不带 `_` 的由写入者自填（不可信）**——
  但**这个区分只活在文档里，不在类型里**。
- **具体场景**：`2-依据/15:286` 那张表的第三行
  「**留痕可复盘**（谁在何时改了哪个字段）| 本体里的**字段** + 事件账本 |
  ❌ 文件系统只存字节，**没有"字段"这个概念**」——**这句对 journald 同样成立**。
  journald 给你"某进程在某时刻打印了某串字节"，**不给你"`muted` 从 false 变成 true"**。
- **它对你们的用处**：`2-依据/15:67` 把"本体实例"类比成 journald 是准确的，
  **但不要继承它的字段不可信**——你们的 `ontology.json` 正是在补这一层，
  而它现在补得**只到键名**（见 §二 问题 2）。

#### C3｜PostgreSQL / 关系型：实体很强，但真相在**应用私有的 schema** 里，且没有"曾经有过"

- **缺什么**：
  ① 表/列/约束确实是"实体 + 字段"的一等公民——**这一点它比你们现在的
  `objects: BTreeMap<String, BTreeMap<String, Value>>`（`src/readmodel.rs:43`）强得多**；
  ② 但 `UPDATE`/`DELETE` **不是事实**：改了就是改了，
  `xmin`/WAL 是物理机制不是语义事实（谁都能 `VACUUM FULL`）；
  ③ **`NULL` 既表示"从未有过"也表示"设过又被删"**，二者不可区分。
- **具体场景（②③ 合起来）**：`2-依据/15:322`（待定项 9）
  「"**真删**"与不可变账本冲突——总纲 §6 `存` 要求"记忆的条目级权限"，
  删除请求若不留痕破坏账本，留痕又不算真删」。
  **在 Postgres 里这个问题是不可解的**：`DELETE` 之后你永远无法从语义层回答
  "这条记录存在过吗"。你们的方向（追加补偿事件）是对的。
- **还有一条与你们的实体层直接相关**：关系型世界里，
  **"哪个表有哪些行"是 DBA 和应用的私有知识**，不在任何可导出的登记里。
  `2-依据/15:262` 引用 AdaOS 的 `primary_doc.direct_write: false` 时，
  其实是在描述一个**中心化的写入口**——**那正是 Postgres 的权限模型做不到的事**
  （表的所有者可以 `GRANT` 给自己，且这个变更不在数据里）。
  **你们的 `writes`（`policy.json:25-31`）是在做同一件事**，
  但你们的版本有一个好处：**它在文件里、可被比对**；
  也有一个坏处：**它在文件里、所以不在账本里**（见 §二 问题 1、发现 4）。

#### C4｜Neo4j / RDF：**类型**是有的，**值域与生命周期**是没有的

- **Neo4j**：`(:Agent {id:1, model:"m1"})` 看起来就是你们要的东西。
  但① label 与 property **没有类型约束**（property 可以一会是 string 一会是 int）；
  ② 节点没有"状态机"（`status` 只是一个属性，`revoked` 之后仍有完全一样的写权）；
  ③ **没有"谁创建了这个节点"的一等记录**。
- **具体场景**：一个人问"这个 agent 是谁引进的"——Neo4j 答不出，
  除非应用恰好存了那条边，而**那条边的存在与否不受任何约束**。
- **RDF / OWL / SHACL**：**这三样恰恰能补上你们缺的**——
  `@id` 解决同一性（正是 A1 缺的概念）、`rdfs:domain`/`range` 解决值域、
  SHACL 解决"必须有哪些字段"。
  **但你们的判断（`WC-SDP-001-v0.1.md:348` ⑨ 把 RDF/SPARQL 判为锚定）我同意**，
  理由与 `2-依据/14:215-216` 对 IPLD 的处置同构：
  **借形状，不自造编码就够，但采用语义就过头了**——
  `owl:sameAs` 的推理后果不可控，而一个世界核心**不能接受不可控的推理**。
  ⇒ **我的建议是借 SHACL 的"必须有哪些字段"这一条形状，
  用 JSON 写三个断言（存在性 / 类型 / 状态机），十行代码就能落地。**
  这是 A4 与 §二 问题 2 的最小解。

#### C5｜Kafka / CloudEvents / D-Bus / OpenTelemetry：**信封很强，实体很弱**

- **Kafka**：有 topic / key / offset / header。但 **`key` 是不透明字节串**——
  它可以是一个实体标识，**但没有任何东西保证它是**，也没有"这个 key 存在吗"的登记。
  Schema Registry 做 **schema 形状**的演进检查，**不登记实例**——
  "世界里有没有 agent 3"这件事它不回答。
- **CloudEvents**：规范明说 `source` 是**生产者自述**的标识
  （我不引具体条文，标 **我的推断**：这是该规范"生产者自治"设计的必然结果）。
  ⇒ 它把身份交给生产者，与 `src/channel.rs:9-11`
  「身份来源换成**内核**…请求体里若写了别的 `actor`，**直接拒绝**」的正确做法**相反**。
  **你们做对了，而主流总线规范做错了——这一点值得写进对照表。**
- **D-Bus**：`sender` 是**连接名**（形如 `:1.42`），连接一断就没了。
  ⇒ 事件第二天无法回答"谁发的"。这正是 `2-依据/14:89`
  「`actor` | 没有它就会 | 无法回答"谁做的"（内核只有 UID/cgroup 粒度）」
  所要防的，而 D-Bus **正好是这个病**。
- **OpenTelemetry**：`service.name` 是 resource 属性，**允许多个进程共用一个名字**；
  更根本的是**身份在事件之外**（在 resource 里）⇒ **事件被导出后，身份丢了**。
  ⇒ 这与 `2-依据/14:89` 的 `actor` 一等字段设计正好相反，**你们做对了**。
- **具体场景（合起来）**：把这三家任一拼起来，都答不出
  `docs/系统全景图.md:87` 那条真实账本第 3 行的问题：
  「`subject: world://agent/1` 在等批」——**因为"agent 1"从来不是任何一个系统的一等实体**。

#### C6｜MCP：**工具**是一等的，**实体**不是

- **缺什么**：MCP 的 `tools/list` 给出工具名 + 参数 schema，
  **全部在 server 自己的命名空间里**；没有"这个 server 是谁、它属于谁、
  能不能替换、换了之后旧调用还算不算数"的位置。
- **具体场景**：`00-理论定稿.md:27`「零件分属不同所有者」——
  **MCP 让"零件"可发现，但不让"零件的所有者"可发现。**
  于是"越界声明自始无效"（`00-理论定稿.md:116`）在 MCP 里**没有对手方**：
  你无法对着一个 MCP server 声明"你越界了"，因为它是自述的。
- **补充**：`00-总纲.md:335` 明写"不接 MCP / varlink 作为世界协议"，
  `WC-SDP-001-v0.1.md:348` ⑥ 给出理由（锚定）。**我同意结论**，
  但要指出：**拒绝 MCP 不等于拒绝它暴露的问题域**——
  实体层要解决的正是"零件有主"这件事，而 MCP 是所有现有协议里
  **唯一把"零件"做到一等**的，**却仍然没做"主"**。
  这是最值得在文档里点名的一条对照。

#### C7｜A2A：agent card 是**自述**，与你们现在的处境一模一样

- **缺什么**：A2A 的 `AgentCard` 里，agent 声称自己是谁、支持什么技能、端点在哪。
  `2-依据/14:152-159` 已正确借用了 A2A 的 `TaskState` 洞见
  （`working`/`done`/`failed`/`rejected`/…）。
- **但**：`AgentCard` 的字段**全部是自述**，接收方无从核验。
  ⇒ **这正是你们在 CLI 路径上的处境**：
  `src/channel.rs:5-7` 自认「此前唯一入口是 CLI，而 CLI 的 `actor` 是**命令行参数**——
  被管者只要自称 `world://user` 就能冒充最高权主体（`WC-RV-R2-001` **FIND-06** / 假设 `A-06`）」，
  `WC-SRS-001-v0.1.md:268` 判据⑤ 如实承认"**CLI 路径下 `actor` 仍是命令行参数**"。
  ⇒ **你们在通道上修好了，在 CLI 上没修**（`src/guard.rs` 里也没有任何 uid 白名单，
  只有 `--owner-uid` 这个"部署方自证工具"，见 `src/guard.rs:130-131`）。
  **A2A 是你们"如果只修一半会变成什么"的现成反面样本。**

#### C8｜知识图谱那一支：能补的正是你们缺的，代价是推理不可控

- 我已经在 C4 里说了 RDF/SHACL。**这里补一条更具体的**：
  你们 `2-依据/14:66` 说"23 件参考件的「④引用」全缺"、
  "可复盘没有一家提供"——**这个判断在事件溯源阵营里成立，
  在知识图谱阵营里不成立**（图谱的"引用"是 `@id`，`@id` 天生是引用）。
  ⇒ **建议把这条结论的适用范围写明**，
  否则读者会以为"所有外部系统都没有实体引用"，而事实是
  **知识图谱有引用、没有事件；事件总线有事件、没有引用。**
  **你们要的东西是这两者的交集，而目前没有一家同时给。**
  这是你们最准确的生态位陈述，比"没人做可理解 + 可重放"（`2-依据/14:65-66`）更精确。

#### C9｜权限系统：OPA/Casbin/SELinux 都答不出"这个主体还在不在"

- **OPA / Rego**：`input` 是任意 JSON，策略对**形状与字段**做判断。
  ⇒ **"这个主体此刻是否仍在世"不是它能回答的问题**，除非把那个事实喂给它；
  而那个事实从哪来、怎么与账本保持一致，**OPA 不管**。
  这恰好对上 `2-依据/15:315` 的待定项 2「**权限也必须从事件派生**——
  否则权限就是第二本账」。**你们的洞与 OPA 的洞是同一个洞**，
  而你们比 OPA 多一个机会：**因为你们的账本已经在手边**。
- **Casbin / RBAC**：角色是字符串，与 agent 名字同级；
  **模型里没有"实体的生命周期"**。
  ⇒ **具体场景**：`policy.json:20` 的 `ledger.compact` 被标 `reversible: false`，
  门禁靠 `irreversible_actors`（`:32`）白名单裁决。
  **一个 agent 被吊销之后，一条旧 token 仍然会通过判定**——
  因为权限系统不知道它已经死了。
  **Linux 那边你们已经定了正确口径**：`00-总纲.md:260`
  「需接受一个能力天花板：**吊销不能即时生效**（seccomp 不可卸载）→
  语义定为"**吊销 = 勒停重建**"」。
  **这句话正是实体层的需求**：勒停谁、重建谁——**如果 agent 不是实体，"勒停"就没有宾语。**
- **macaroons / Zanzibar**（Google 的授权系统，我不引具体实现细节，标 **我的推断**）：
  Zanzibar 的 relation tuple + `zookie`/snapshot 是**目前最接近"把授权关系当事实存"**的做法,
  **但它的 `user` 仍是字符串，且它把"谁是谁"外包给调用方**。
  ⇒ **它解决了"权限从哪来"，没解决"主体是谁"。**
  这是对你们最有用的一个参照：**Zanzibar 走通了"权限可以是事实"这条路，
  证明你们的方向可行；它没走"主体可以是事实"这条路，说明那是真空白。**
- **SELinux**：type 确实是给进程与文件打的一等标签，**但 type 由策略作者分配、运行时不可改**，
  而且**没有"这个 type 对应哪个实体"的记录**。
  ⇒ 这是"**身份住在配置里**"这个病根**最权威的先例**，
  也是 `WC-ARCH-001-v0.1.md:197` 那条"身份必须稳定"要求的**真正历史来源**。
  **建议把 SELinux 写进对照表**：它证明了"用标签做身份"能撑起一个操作系统，
  也证明了**标签的分配权就是权力**——而那个权力必须可见（正是 `world://core` 的问题）。

**C10｜一句话总结 C**：
现有系统里，**事件总线有事件、无实体**（Kafka / CloudEvents / D-Bus / OTel）；
**知识图谱有实体、无事件**（RDF / Neo4j）；
**数据库有实体、真相在私有 schema 里且删了就没了**（Postgres）；
**权限系统有规则、主体是字符串**（OPA / Casbin / SELinux）；
**操作系统有主体、主体是可回收的数字**（Linux uid）。
**没有一家同时给出"事件是唯一真相 + 主体是一等实体"。**
这比 `2-依据/14:65-66` 现在的表述（"没人做可理解 + 可重放"）**更准确**，
**也正是这个项目真正的空白与机会**。

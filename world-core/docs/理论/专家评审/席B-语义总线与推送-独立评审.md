## 一、评审结论

**一句话：语义层的设计是这个项目最强的地方，传输层的"送达"是整个项目最薄的地方——`11` 篇列出的"订阅"部件在 `14` 篇收缩时无人接手，落进实现后彻底消失，于是 `notice` 成了写进账本就再也出不来的死信，而项目自己把"完工铃优先"立为 `传` 的第一硬约束。**

三到五条要点：

1. **收缩本身大体正确，但漏项真实存在。** "状态降为投影传输形态"对；"`ref` 降为值类型"方向对、执行有三处缺口（见 §二.1）。但 `14` 篇 §三 的三行清单（三家族 / 一个值类型 / 一种投影形态）里**没有任何一行接手"订阅"**，而 `11` 篇 §二 把订阅列为六部件之一——这是**孤儿条款**，不是收缩，是丢失。
2. **`notice` 现在是结构性死信，且不是"忘了做"，是"读模型看不见它"。** `notice` 进账本不改变 fold 出的任何字段（`src/readmodel.rs:109` 只做 `self.notices += 1`），所以**只读投影的人永远不知道发生过通告**；唯一的观察方式是扫日志。这让 `notice` 与 `change` 的传播路径根本不同，而项目从未区分这一点。
3. **推送线不需要新协议，需要的是一条纪律：推送只送"账本位置"，不送"第二份真相"。** 把推送载荷定成账本行的**逐字节副本**（含 `seq` + `chain`），则连续不跳号由 `fold` 的既有 `SeqGap` 判据免费保证、断线补齐由既有 `read_from` 保证、重复投递由 `chain` 逐字节比对检出、多消费者游标天然各放各的——**一条新的一致性协议都不引入**（§五）。
4. **推送给谁做：账本进程（`worldd`）做投递，投影进程只做渲染。** 理由不是"架构好看"，是三条既有事实：唯一写者已经在那里（`src/ledger.rs:142,460`）、`projectd` 物理上不可能写任何东西（`docs/系统全景图.md:47`）、套接字身份（权限即身份）只在 `bind()` 处成立（`src/channel.rs:180-218`）。
5. **通道现在的形态不足以承载推送，且缺口是"阻塞模型"而非"功能缺一个函数"**：`serve_once` 读一行时**无超时**（全仓 `set_read_timeout` 零命中），`serve_n` 是**严格串行的 `for` 循环**（`src/channel.rs:237-242`），所以"长连接等推送"会**把整个总线挂死**——一个不出声的客户端即可造成 DoS。这是本次评审发现的最严重单点。

### 2.1 `11` 篇四类消息 → `14` 篇三家族，丢了什么？

**原文引用**

- `2-依据/11-总线工程规格.md:17-22`：四类消息表——状态（快照/增量）、动作请求/结果、事件（`state.changed` / **完工铃** / 页面报错）、引用（`{content:"sha256:ab3f..."}`）。
- `2-依据/11-总线工程规格.md:26-29`：六部件——"…→ **投影**（界面投影 + 语言投影）→ **订阅**（subscribe 后主动推送，v0.2 已验证）→ **通道**（文件+hash 起步）"。

- `2-依据/14-总线词表v0.md:12-14`：自述"这不是减功能，是去掉了一个假的并列"。
- `2-依据/14-总线词表v0.md:70-81`：**信封（自造）**——`world/kind/id/seq/at/actor/to/trace/flags/body`。
- `2-依据/14-总线词表v0.md:168-176`：`notice` 家族定义 + "**完工铃（`job.done`）第一优先**……长任务零轮询是 `传` 的第一硬约束"。
- `world-core/ontology.json:25-41`：实现里的三家族（`change`/`act`/`notice`），**无 `ref`**。
- `world-core/ontology.json:9-22`：实现的信封 `required = ["world","kind","id","seq","at","actor","flags","body"]`，`optional = ["to","trace"]`，**无单位/量纲**。
- `2-依据/14-总线词表v0.md:257`（待批判项 5）：**"明确不引入 CRDT"**。

**（a）"状态被降为投影的传输形态"——判断对，且是本篇最扎实的一处**

判断：**对**。

理由：状态不是"另一条真相"这个论点在纯事件溯源下是定义性的（`state = fold(events[0..seq])`，`2-依据/14-总线词表v0.md:94-95`），而实现已经兑现——`src/readmodel.rs:109` 对 `notice` 只计数、`State` 字段私有（`src/readmodel.rs:35-44`），丢弃读模型重建是既有验收（`docs/系统全景图.md:145`）。把"状态"从"消息类"降为"传输形态"，本质是**把一个派生量从协议里赶出去**，这在中间件里是正确的方向。

代价：`11` 篇 §二 的"投影"是**一个部件**，`14` 篇把它降成**一种传输形态**——但没有回答"谁来产这个传输形态、什么时候产"。这个空缺后来在实现里变成了"每次调用重算全量并打印"（`docs/系统全景图.md:128` 的 `project language|visual|check`；`src/project/mod.rs:72-80` 的 `last_seq=` 头）。**这是我的推断**：这一降格的真实代价不是概念上的，而是"投影从常驻服务退化成批处理命令"，而这恰好把"推送"的必要性推高了而不是降低了。

**（b）"引用被降为值类型"——判断对，但执行有三处缺口，其中一处是硬缺口**

判断：**方向对**。`14` 篇 §3.0（`:116-118`）的推理无可挑剔：引用不是"发生了什么"，是"某个字段的值"。

但执行层有三处缺口：

| # | 缺口 | 证据 | 后果 |
|---|---|---|---|
| b1 | **实现里 `ref` 完全不存在** | `world-core/ontology.json:25-41` 只有三家族；`src/readmodel.rs:106-116` 的 `match kind` 只认三值 | 大对象外置（`2-依据/15:158-159` "主干道上只放 hash 引用"）**在词表层无法表达**——只能塞进 `after` 的一个匿名 JSON 对象里，失去类型与核验 |
| b2 | **`before` 的逐字节可核验性被严重削弱** | `2-依据/14-总线词表v0.md:132-134` 引 `diff` 的 `{ref, field, before, after}`（即 field **是引用**）；实现落成 `ontology.json:28` 的 `path: string`（`2-依据/14-总线词表v0.md:136` 已自己指出"`path` 是位置，不是身份"） | 重放能复现（`fold` 按 seq），但**"这两个字段指的是不是同一个东西"这件事在词表层不可判**；这正是项目要的"可复盘"里最难的一半 |
| b3 | **单位/量纲没进信封** | `14:260` 自己登记为待批判项 8（"信封里还没写进去"）；`ontology.json:9-22` 实测没有 | 与本次议题直接相关：推送帧里若带 `{"duration":3}`，消费者无法判断单位——**推送线是这条缺口最先咬人的地方** |

判断补充：**把"引用"降为值类型是对的，但把它降成"一个没有名字的 JSON 片段"是错的**。`ref` 应当是一个**有名字的值类型**（词表里可枚举的两层结构，`2-依据/14-总线词表v0.md:180-186` 已经写好了形状），否则 `15` 篇 §5.2 的"运单号 = 内容 hash"在协议上没有落点。

**（c）"订阅/推送"是不是在这次收缩里被漏掉了？——是，而且是本次评审最确定的结论**

判断：**是被漏掉了，且是"无人接手"，不是"有意删除"。**

理由（四条，逐条可核）：

1. **收缩的工程量是"消息类 → 家族"，不覆盖部件。** `11` 篇 §二 的六部件（协议/适配器/治理/投影/**订阅**/通道）与 §一 的四类消息（状态/动作/事件/引用）是**两个不同的轴**：前者是"总线上跑什么"，后者是"总线由哪几块组成"。把四类收缩成三家族，在逻辑上**推不出**"订阅该删"。`14` 篇 §三 的三行清单**没有一行提到订阅**（`:103-114`）——不是论证后删除，是清单里根本没有它的位置。
2. **`14` 篇把订阅的载荷留下了、把订阅本身丢了。** `2-依据/14-总线词表v0.md:110-113` 保留了"快照 / 增量：`{subject, base_seq, snapshot | delta}`"——`delta` 就是推送的**载荷**。**这是我的推断**：作者其实保留了推送要送的东西，只是没写"谁送、怎么送、送给谁"。这是一处**半途而废的收缩**。
3. **上游条例没有随收缩一起改，于是文档之间已经互相打架。** `00-总纲.md:324`（动作 3）的完成判据仍写"**一个订阅者能收到 diff**"；`00-总纲.md:438` 的勾选项仍写"**订阅者不轮询也能收到一次 diff**"；`00-总纲.md:262` 的 `传` 硬约束仍写"四类消息、**订阅推送**、内容寻址"。`14` 篇 §一 自己声明"凡与总纲冲突，以总纲为准"（`:18`）——**按它自己的规则，订阅是活的**。
4. **`12`/`13` 篇均未接手。** `2-依据/12-内核选型对照.md:173` 写"总线 | 四类消息的唯一 IPC；**订阅与推送**"；`2-依据/13-总线与通道外部参考.md:181-184` 有专门一节"**4. 订阅与回放：服务端游标，而不是'订阅那一刻起才有'**"——但那是**外部参考**，不是本项目承诺。全仓检索"订阅/推送"（`.md`，88 命中）里，没有任何一处是**本项目自己要实现的订阅协议规格**；最近的一处是 `world-core/docs/S3-骨架/` 之外的一句"将来的推送面"（`world-core/docs/S2-设计/WC-ARCH-001-v0.1.md:69`、`:386`）。

**改法与代价**

- **改法**：在 `14` 篇 §三 之后新增一节"§三.5 投递（delivery）"，把订阅明确为**第四个部件**（与三家族平行），并给出四条最小规定：订阅的身份来源、首位置语义、帧形态、失败行为。不要新造消息类——订阅是**机制**，不是**家族**，这与 `14` 篇 §4.1"自省不是第四个家族"（`:199-206`）是同一套推理。

### 2.2 "完工铃"现在是坏的

**原文/代码引用**

- `2-依据/14-总线词表v0.md:174`："**完工铃（`job.done`）第一优先**（总纲 §6 `传`）：长任务零轮询是 `传` 的第一硬约束。"
- `world-core/docs/S0-立项/WC-FSR-001-v0.1.md:266`（`REQ-N-001`）：判据 = "一个长任务的**订阅方收到通知的次数 ≥1 且轮询次数为 0**"；`:526` 用例 9：追加 `notice.job.done` → "**订阅方收到推送**"。
- **实测**：`job.done` 在**全部生产代码中零生成点**——全仓命中仅 `tests/perf.rs:102`、`tests/acceptance.rs:64`（测试夹具）与文档。生产里唯一会生成 `notice` 的地方是 `src/lib.rs:291-314` 的 `record_gate_notice`（门禁拒绝/加摩擦的流水）。
- **实测**：门禁拒绝的那条 `notice` 是在 `commit_requested` **返回错误之前**写下的（`src/lib.rs:212` 之后的错误路径 → `:269-285`）——即**同步应答里已经带了 `ok:false` 与原因**，这条 `notice` 对请求者毫无新信息。
- **实测**：`notice` 对读模型不可见——`src/readmodel.rs:109` 只做 `self.notices += 1`；`src/readmodel.rs:111-115` 遇到未知家族直接报错（拒绝猜测）。因此 `project language` / `project visual`（`src/project/*.rs`）**永远不会显示任何通告**。
- **实测**：没有任何送达通道。全仓 `subscribe|notify|push|watch` 的命中全部是 `String::push_str` / `Vec::push` / git `push` / systemd `Type=notify`（`world-core/deploy/README.md:60`）/ 一份 Go 片段里的 `Subscribe()`（`world-core/docs/S0-立项/WC-SCMP-001-v0.1.md:1716`，**不是 Rust 代码**）。
- **实测**：消费者唯一的增量读法是 `Ledger::read_from(from_seq)`（`src/ledger.rs:526-546`），它**每次都从头读文件的前 `valid_len` 字节再过滤**（`:530-531`、`:541-543`）——复杂度 O(整文件字节)，不是 O(增量)。

**我的判断**

1. **"完工铃是坏的"这个说法还低估了：它不是坏了，是不存在。** 词表层有家族、有形状、有语义承诺；**生产层零生成点、零投递、零可见性**。三条链路（产生→投递→被看见）**全部断开**。
2. **`notice` 与 `change` 的传播路径不同，而项目没有区分这一点。** `change` 会进读模型 → 进投影 → 被看见（最终一致，靠重跑投影）；`notice` 不进读模型 → 只存在于日志。**这是我的推断**：这意味着即使做出推送，也仍然要回答"给投影只推 `last_seq` 门牌够不够"——因为投影重算 fold 时**看不见 `notice`**，门牌变了但渲染结果不变，投影会以为"没事发生"。这是本项目特有的一处**推送语义缺口**，我在外部系统里没见过同形（Kafka/NATS 的消费者要自己解 payload，不存在"门牌变了但内容不可见"）。
3. **`REQ-N-001` 现在的可满足性是零，而且它测不出来的原因很微妙**：判据写的是"订阅方收到通知的次数 ≥1 且轮询次数为 0"。轮询次数无法从系统内观测（项目没有计次），所以这条判据**在 v1 只能靠人肉计时记录**（`WC-FSR-001:266` 自己写"计时记录"）。这是"需求写成了无法机械判定的形态"，比"未实现"更值得登记。

**改法与代价**

| 步 | 动作 | 代价 |
|---|---|---|
| 1 | 明确 `notice` 的**送达语义**：`to` 为空 = 广播；非空 = 定投。在 §五 里给出帧与错误码 | 文档 + 约 300 行 Rust |
| 2 | 让"完工铃"有**真实生成点**：`carrier` 长任务结束时追加 `notice{type:"job.done", subject:"world://job/<id>", payload:{exit,...}}`（`carrier/run.rs` 已具备在结果回写后追加第二条事件的位置） | 小，但它依赖 `docs/系统全景图.md:163` 已登记的"载体侧长任务后台等待未做"——**这一条是前置阻塞项** |
| 3 | 把 `REQ-N-001` 的判据改成**可机械判定**的形态（例：订阅端收到 `job.done` 帧的 `seq` ≥1，且订阅端进程的全部 `read_from` 调用次数为 0——后者可用一个计数器或端到端脚本观测） | 小；但**必须先有人裁定"轮询次数怎么算"**，这是人的决定，不是 AI 的 |

### 2.3 顺序与幂等：如何在不引入第二套一致性协议的前提下复用 `seq` 铁律

**原文/代码引用**

- `src/ledger.rs:291-311`：启动时逐行校验 `seq != last + 1` → `ext.world.Ledger.SeqGap`，**拒绝启动**。
- `src/ledger.rs:320-328`：同 `id` 出现两次 → `ext.world.Ledger.DuplicateId`，拒绝启动。
- `src/ledger.rs:405-410`：`append` 要求传入 `seq == next_seq`，否则 `SeqMismatch`。
- `src/ledger.rs:449-458`：`fsync` 失败 → **污染账本**并拒绝后续写入（`Poisoned`）。
- `src/readmodel.rs:92-99`：`apply` 要求 `seq == last_seq + 1`，否则 `ext.world.ReadModel.SeqGap`（"只折叠**连续的账本前缀**，不猜缺口"）。
- `src/ledger.rs:562-577` + `:589-624`：摘要链 `fnv1a64(prev + "\n" + canon(去 chain 的 ev))`，混用/断裂 → 拒绝；`:587-588` **自认边界**："无密钥的链**挡不住'整文件重写'**"，用例名 `c18_chain_cannot_detect_a_full_rewrite`。
- `src/ledger.rs:392-465`：`append` 的成功路径是 **先 `put` + `flush` + `sync_data`，全部成功后才 `next_seq += 1`**（`:449-460`）。

**我的判断：复用是充分的，而且比"够用"更强——这里有一条现成的、可被推送线直接租用的不变量**

> **不变量 P（可租用）：任何消费者只要按 `seq` 严格递增地应用事件，一旦跳号，它就能确定自己坏了。**

这条不变量已经在 `src/readmodel.rs:92-99` 里被实现并被测试守住了。推送线**不需要**发明"至少一次/至多一次/恰好一次"，只需要把 P 租过来：

**三条纪律，一条新协议都不引入**

1. **顺序：由构造保证，而不是由协议保证。** 服务器侧**唯一**取帧事件的路径是 `read_from(last_emitted + 1)`（`src/ledger.rs:526`），而账本本身是 `seq` 严格连续且追加后才推进 `next_seq`（`:460`）。因此"推送序列是否连续"这个问题**不可能被答错**——它要么连续，要么服务器在读文件时就已经报 `Corrupt`。**这是我的推断**：这是"不引入第二套一致性协议"最纯粹的一种兑现方式——**把新问题化成旧问题，而不是把新问题解决掉**。
2. **幂等：用 `chain` 逐字节比对，不用新字段。** 重复投递的判据是 `chain` 值相等（`src/ledger.rs:562-577`）。若消费者收到重复帧，`chain` 相同 ⇒ 丢弃；`chain` 不同 ⇒ **不是重复，是真相分裂**，必须报错并停下（与 `verify_chain` 的 `ChainMismatch` 同族，`:613-620`）。**关键收益**：这笔比对**让推送线免费继承"推送与拉取一致"这条判据**——消费者任何时候都可以 `read_from(seq)` 拉一次，与已收到的帧逐字节比对；这是 §五判据 D3 的来源。
3. **去重不需要在推送层做。** 账本写入侧已拒 `DuplicateId`（`src/ledger.rs:421-426`），启动侧也拒（`:320-328`）。因此**推送线上不会出现"同一个 `id` 的两条不同事件"**——这是账本给的，推送不用管。若消费者应用两次同一帧（比如重启后重放自己的缓冲），`readmodel` 的 `SeqGap`（`src/readmodel.rs:92`）会当场报错——**幂等性问题被转化为可检测的错误**，而非被静默吞掉。

**必须诚实说出的三条边界**

| # | 边界 | 出处 | 对推送线的影响 |
|---|---|---|---|
| A | 摘要链**挡不住整文件重写** | `src/ledger.rs:587-588`；`docs/系统全景图.md:162` | 消费者**无法核验 `N` 之前的历史真实性**。"从 `N` 补齐"这条能力的前提是"N 之前的历史是可信的"——这个前提**当前不由技术提供**，只由文件权限提供（`src/guard.rs` 的静态墙）。**这不是推送线要修的洞，但推送线必须说出来**，否则"补齐"会被误当成"核验" |
| B | `seq` 由**内存里的 `next_seq`** 分配 | `src/ledger.rs:130,344,360-366` | 重启后取号从"读最大 seq + 1"恢复——只要单写者锁有效就没问题（`:170-210`）。但**推送线的"服务器位置"必须来自同一处**，不能另算（否则会出现两个位置口径） |
| C | `at` 是 Unix **秒**且**不决定顺序** | `ontology.json:16`（"顺序由 seq 决定，at 只作辅助"） | 推送线**必须用 `seq` 做超时/退避/去重的唯一键**；用 `at` 会在同一秒内的多条事件上产生并列。且注意 `src/ontology.rs:157-202` 的 `validate` **只查字段存在、不查类型**——`at` 写成字符串不会被拒（`SRS:272` 已登录"`world` 写成字符串被接受"这一族问题） |

### 2.4 投影"不交互"与"主动上报"会不会打架？——推送给谁做

**原文/代码引用**

- `2-依据/15-世界核心的组成与职责.md:232-236`（§7.3）："投影是**出口（叶子节点）**，不是中继节点……'同源'不是靠**商量**达成的，是靠**结构**保证的。"
- `2-依据/15-世界核心的组成与职责.md:244-252`（§7.5 漏水信号）：`"投影 A 要通知投影 B"` / `"让两个投影同步一下状态"` / `"这段状态存在投影里"` **都是真相分裂**。
- `2-依据/15-世界核心的组成与职责.md:199`（§六 例子第 6 步）："运行时 | 由账本**算出读模型** → **推给两个投影**"。
- `world-core/docs/系统全景图.md:45-49`：`world-projectd` —— "**零写权限**……落后了自行全量重算或从检查点续算"。
- `world-core/docs/系统全景图.md:19-35`：内核 `worldd` ="**唯一写者**"；`：34`"通道（总线入口：一个套接字一个身份，权限即身份）"。
- `src/channel.rs:180-218`：`bind()` 是身份的唯一落点（`chmod 0600` + `chown` 到目标 uid）；`:247-305`：`serve_once` 用 `expect.actor` 落笔，**绝不取请求里的字符串**。

**我的判断：不打架，但前提是把"推送"这四个字拆成两件事**

`15` 篇 §7.5 禁的是**"投影之间横向通信"**；`15` 篇 §六 第 6 步要的是**"账本向投影纵向投递"**。这两件事在图上完全不同（一横一纵），**不构成冲突**。冲突只会在一种情况下出现：**把推送队列放进投影进程**——那时"投影 B 落后是因为 A 的队列满了"这种耦合就会长出来，而 §7.5 的漏水信号正是防这个。

因此架构主张是三条，每条都有既有事实支撑：

**主张 1：投递由账本进程（`worldd`）做，不由投影进程做。**
- 理由一（物理的）：唯一写者已经在那里，`next_seq` 就在手里（`src/ledger.rs:130`）。投递者需要"知道现在到第几条了"，这个信息**只有账本进程持有**，别的进程只能读文件猜。
- 理由二（权限的）：`projectd` 是"零写权限"（`docs/系统全景图.md:47`）。让一个零写权限的进程去维护"谁订阅了、投到哪了"，等于把一份**必须可变的状态**放在一个**设计上不可变的位置**——那份状态立刻成为第二本账。
- 理由三（身份的）：订阅者身份只能由套接字权限给出（`src/channel.rs:20-26,180-200`）。一个只读进程**没有能力**开一个"只允许某 uid 连接"的套接字吗？技术上可以（`bind` 不要求写账本），但它就把"谁是谁"的知识复制了一份——**两份身份映射 = 又一个可分裂点**。

**主张 2：投影进程只做渲染，不做投递、不持有推送队列。**
- 投影的输入是**读模型 + 词表 hash**（`src/project/mod.rs:72-80` 的 `#world-core projection=… vocab=… last_seq=… state=…` 头）。推送给投影的应该是**"读模型该重算了"的信号**，而不是读模型本身或事件流。
- **这是我的推断，也是本次评审最想强调的一点**：因为 `notice` 不进读模型（§2.2），所以"事件到了"与"投影该变了"**不是同一件事**。若把推送线做成"事件流 → 投影"，投影会对每条 `notice` 徒劳重算；若做成"位置流 → 投影自己决定要不要重算"，则投影可以只看 `kind` 计数是否变化，代价是一帧的解析。**这正是 `14:253` 那个未决项（"投影是取带 `base_seq` 的快照，还是常驻订阅增量"）的答案方向**：两者都要，但**推送的是"位置 + 增量事件"，不是"状态增量"**——状态增量必须由投影自己从读模型算，否则投影就在自己造状态。

**主张 3：不新增"投递部件"这个进程；投递是 `worldd` 的一个模式，不是第七个部件。**
- 理由：`11:31-33` 的"第一版无中心"已被 `15:168-176` 更正为"**无额外中间件；世界核心即汇接点**"。按这个口径，投递是**汇接点的职责**，不是新中间件。加一个独立的 `busd`/`pushd` 会立刻引入"汇接点有两个"的问题。
- 但**必须新增一个模块**（`src/push.rs`，`M11`），因为 `channel.rs` 现在的职责是"写入口"（`world.commit_requested`，`:289-295`），把推送塞进去会让一个文件同时管两条语义相反的通道。

**一个必须点明的后果（我认为项目目前没有意识到）**

`15` 篇 §7.7 的一处口径其实是**错的**（或者至少是过度乐观的）：`2-依据/15-世界核心的组成与职责.md:199` 写"运行时……算出读模型 → **推给两个投影**"。在 v1 实现里投影是**命令式批处理**（`project language` 每次全量 fold 再打印，`docs/系统全景图.md:128`），**没有常驻进程可推**。所以"推给投影"这句话今天**无处落地**。**这是我的推断**：这句话在文档里活了两轮都没被发现，原因是"投影"在图上画成了叶子节点（看得见）而"投影是个进程还是条命令"从来没被问过。**建议 `15` 篇增一句口径**：投影是"**端口**"，其实现可以是进程也可以是命令；推送的目标是**端口**，不是进程。

**改法与代价**

| 项 | 内容 | 代价 |
|---|---|---|
| 接口 | 新模块 `src/push.rs`（`M11`），暴露 `subscribe(listener, actor, from_seq) -> PushStream`；`worldd serve` 主循环改为 `poll()` 多路复用 | 约 400–600 行 Rust + 一份接口规格；`serve_n` 保留为兼容路径（`src/main.rs:661`） |
| 进程 | `projectd` **不改**（仍是"全量重算 + 打印"）；将来若要常驻，它订阅的是**位置流**，不是事件流 | 0（现在） |
| 文档 | `15` 篇 §7.3 增一句"§7.5 只禁横向；纵向投递由汇接点做"；`15:199` 的"推给两个投影"改述为"推给两个**端口**" | 小；**但这是承重改动**，因为它把一条铁律的适用面写清楚了 |
| 风险 | 新增一条"谁连得上订阅套接字"的配置面（`channel.json` 加 `push: true` 或新增 `subscribers` 段） | 这是**唯一新增的攻击面**，必须与 `bind()` 的目录静态墙同档（`src/channel.rs:183-185`） |

### 2.5 反例检验：推送线做错了会怎样

五条故障场景，每条给"错的行为 / 正确行为 / 判据"。

**F1：消费者落后 10 万条**

- **错的行为**（最常见的错法）：服务器从位置 0 开始补推，**在线程里同步回放**。后果：① 该订阅者把总线占满（参考 §2.6 的阻塞模型）；② 消费者在追平之前看到的都是**历史**，若它按"最新一条"做决策，会做出基于陈旧状态的不可逆动作。
- **正确行为**：**明确区分"补齐"与"直播"**。服务器若判定 `from_seq` 与当前位置的距离超出**在线回放预算**（建议：`max_catchup_events`，默认 4096 或 `max_catchup_bytes`），必须**拒绝流式补齐**，回一个 `ext.world.Push.TooFarBehind`，并在错误正文里给出**当前 `last_seq` 与可用的检查点位置**（`src/checkpoint.rs` 已有 `.base_seq`，`:52`）。消费者收到该码后走"取快照/检查点 + 从 `base_seq+1` 续"的路径。
- **为什么这是正确的**：因为账本支持 O(1) 定位到检查点，而流式补齐是 O(N) 字节。**这与 `Ledger::read_from` 的实现完全一致**（`src/ledger.rs:526-546`，每次全文件读）——**在 `read_from` 变成 O(增量) 之前，任何大跨度补齐都会把服务器拖住**。
- **判据**：D5（§五.6）：一个落后 10 万条的订阅者连接 ⇒ 服务器返回 `TooFarBehind` 且**其余订阅者的帧间隔 P95 不劣化**。

**F2：消费者崩了重启**

- **错的行为**：服务器认为"订阅者还在"（连接没断干净，TCP 半开 / Unix socket 未收 FIN），继续把帧写进一个没人读的缓冲，直到 OOM 或把世界拖死（`deploy/README.md:114` 的 `MemoryMax=2G` 会先杀掉全世界）。
- **正确行为**：三件事。① 服务器**必须把每个订阅者视为可随时消失**，因此不发 ack、不做重投、不维护"未确认队列"（这也正是 §五 方案能做到 O(订阅者数) 内存的原因）；② 断开时**丢弃该订阅者的全部待发帧**，只保留最后一个已发 `seq`（可选落盘到订阅者自己的游标文件）；③ 订阅者**重连时自己带 `from_seq`**（dumb server 原则），服务器不替它记。
- **判据**：D6：`kill -9` 订阅者后，`worldd` 的内存占用回到基线（±1 帧），且 `worldd` 不产生任何错误日志以外的副作用。

**F3：同一事件被推两次**

- **错的行为**：消费者按"帧到达顺序"推进自己的位置，收到重复帧就把同一个 `change` 应用两次。对 `change` 而言是 `before` 比对失败（`src/readmodel.rs:20-23` 的读模型第二道墙会拦住）；但对 `notice` 或 `act`，重复应用会**虚增计数**（`src/readmodel.rs:108-109` 直接 `+= 1`，无幂等保护）——**这是一条真实的、我今天在代码里能指出的缺口**。
- **正确行为**：① 服务器**不主动重投**（不做 ack/重传），因此"推两次"只可能来自服务器 bug 或消费者自己的缓冲重放；② 消费者的应用逻辑**必须以 `seq` 为键**：`seq <= local_seq` ⇒ 丢弃并可选地比对 `chain`；③ **绝不做"按到达顺序应用"**。
- **为什么这条判据能落地而不引入新协议**：因为 `chain` 是逐字节可比的（`src/ledger.rs:562-577`），比对成本是一次字符串相等。
- **判据**：D3 + D4（§五.6）：重放已收到的帧 ⇒ 消费者位置不变、无副作用、无错误（幂等）；篡改一帧的任一字节 ⇒ `chain` 比对必须报错。

**F4：订阅者比生产者慢**

- **错的行为**：无限缓冲（内存无界）或阻塞生产（写完才继续）——前者拖垮世界，后者让"一个慢读者杀死整个总线"。
- **正确行为**：**有界 + 断连**。给每个订阅者一个有界发送缓冲（建议按**帧数**计而非字节数，因为帧大小受 §五 的 `max_frame` 限制）；溢出即 `ext.world.Push.SlowConsumer`，**主动断开该订阅者**，世界继续。
- **为什么"断开"是正确而不是偷懒**：因为推送线**不承担送达责任**（§五.4）。断开一次的成本 = 订阅者重连 + 一次可能的大跨度补齐（被 F1 的预算约束住）。这是把"慢读者"这个不可解问题**转成"可恢复的局部故障"**，而不是假装能优雅降级。
- **明确不做的**：**不抄 NATS queue group 式随机派发**——`2-依据/13-总线与通道外部参考.md:127,184` 已经因"不可逆动作不能随机"拒绝了它，推送线同理（推送不改变执行权归属）。
- **判据**：D7：人为把某一订阅者的读端停住 ⇒ 只断它一个，其余订阅者帧间隔不受影响，且 `worldd` 内存有上界。

**F5：推送队列把世界拖死**

- **错的行为**：把"投递"放进写路径（`world.commit` → append → **同步投递** → 返回）。后果：一个慢订阅者让**所有写请求**变慢；若投递失败还可能导致"落笔了但没投出去"的语义混乱；最坏情况是投递阻塞在 `sync_data` 之后、`next_seq` 推进之前（`src/ledger.rs:449-460`）——**直接破坏"落笔成功 ⇒ seq 已推进"这条不变量**。
- **正确行为**：**投递严格在写路径之外**，且**必须允许"落笔成功但推送未发出"**。具体：`append` 成功后**不做任何 I/O**，只把"位置前移"这个事实暴露给事件循环；投递由 `poll()` 循环在**下一次迭代**取帧（§五.2 的伪码）。这样"世界"与"推送"的耦合只剩**一个整数**（`last_emitted`）。
- **这一条我认为是本次评审最重要的工程结论**：因为 `append` 里那段 fsync-失败即污染的逻辑（`src/ledger.rs:449-458`）极其讲究，任何把它和网络 I/O 混在一起的改动都会让这套精心设计的 fail-loud 语义失效。
- **判据**：D8：让投递路径**全部失败**（订阅者全断）⇒ `append` 的延迟与无订阅者时**无差异**（可测：`tests/perf.rs` 的既有计时框架加一组对照）。

### 2.6 通道现在的形态是否足以承载推送？

**代码引用（逐条实测）**

- `src/channel.rs:31-36`：协议是"**一行请求 → 一行应答**"。
- `src/channel.rs:247-305`：`serve_once` = `accept()` → `read_line`（**无长度上限、无超时**）→ 校验身份 → `commit_requested` → 回一行 → 返回。
- `src/channel.rs:237-242`：`serve_n` 是 `for _ in 0..n { serve_once(...) }`——**严格串行**，注释自述"任一连接处理失败不中止后续"（`:227-228`）。
- `src/channel.rs:211-217`：监听者被 `into_raw_fd` 成裸描述符后**刻意不删套接字文件**（注释 `:201-210` 解释了原因）。
- `src/channel.rs:286-295`：`commit_requested(..., trace, **None**)`——`to`（目的地）**恒为 `None`**。
- `src/event.rs:61-67`：`with_to` 只在 `Some` 且非空时写键。
- **全仓实测**：`set_read_timeout` / `set_write_timeout` / `thread::spawn` / `nonblocking` / `poll` 在 `src/` 下**零命中**。
- `world-core/docs/S1-需求/WC-SRS-001-v0.1.md:269`（`REQ-F-026`）自述："当前实现**四个边界一个都没有**"。

**我的判断：不足以承载，且缺口不是"少一个函数"，是"阻塞模型"**

| # | 缺口 | 严重度 | 为什么推送线非要它 |
|---|---|---|---|
| G1 | **`serve_once` 读一行时无超时** | **致命** | 一个连上就沉默的客户端会让 `worldd` 永远停在 `read_line`。**在推送线存在之前，这只是"通道四边界缺一个"；在推送线存在之后，它是"一条长连接把整个总线挂死"**。今天的 `serve_n` 已经可以被单条沉默连接 DoS（`:237-242` 串行 + `:264` 无超时）——**这是我的推断，但代码路径是确定的** |
| G2 | **`serve_n` 串行** | **致命** | 推送的本质是"一条连接长期不结束"。串行模型下，第一个订阅者一旦连上，后续**所有写请求永久排队**。这不是性能问题，是可用性问题 |

## 三、你发现的、我没问到的问题

**P1（最严重）：Ontology 的 `validate` 只查"字段在不在"，不查"类型对不对"——推送帧会把这个问题放大**

`src/ontology.rs:157-202` 的 `validate` 做四件事：信封必填、版本、家族存在、信纸必填。**它从不检查类型**。所以 `at`（`ontology.json:16` 声称为 integer）写成字符串会被接受，`seq` 写成字符串也不会被拒——`SRS:272` 已经实测登记"`world` 写成字符串**被接受**、缺必填字段 `actor` **被接受**（折叠层不校验）"。

- **这对推送线的意义**：推送线要拿 `seq` 做**唯一的位置键**。今天 `seq` 的类型不由法律保证，只由写入路径保证（`src/lib.rs:195` 取的是 `u64`）。一旦有人手工拼一条账本行（`tools/` 下的多个 probe 脚本就在手工拼行，例：`tools/carrier_acceptance.sh:151`），`seq` 的类型就可能不是整数，而 `Ledger::open` 里 `v.get("seq").and_then(Value::as_u64)`（`src/ledger.rs:300-303`）会**报 MissingSeq**——即"缺号"与"类型错"会被报成同一个错。**这是我的推断**：推送线的错误码设计必须先把这件事分清，否则运维会拿到误导性的错误。
- **建议**：`REQ-F-028`（取值形状，`SRS:271`）标着"已实现"，但实现的只是**文档口径**而非**校验**。这条"已实现"我建议**降级为部分实现**，并在推送线开工前补上类型校验——因为推送线是第一条**把账本字段当协议字段用**的通道。

**P2：`notice` 在读模型里不可见（不只是不投递）**

`src/readmodel.rs:109` 对 `notice` 只 `+= 1`，`State` 的 `objects`（`:43`）从不因 `notice` 变化。所以：

- `15:199` 的"算出读模型 → 推给两个投影"**对 `notice` 无效**；
- 两个投影的"同源"核验（`src/project/mod.rs:121-146` 比较 `last_seq` + `state` 指纹）**对 `notice` 不敏感**——`notice` 到了 `last_seq` 会变（因为 fold 推进了 `last_seq`，`:118`），但 `state` 指纹（若只由 `objects` 决定）不变。**这是我的推断**：一个只订阅 `state` 指纹的人会漏掉全部通告。这正是"完工铃为什么必须走独立推送"的结构性理由，而项目文档里**没有这句话**。

**P3：投影"不新增事实"（`REQ-F-024`）与"推送"之间存在未被识别的张力**

`SRS:267`（`REQ-F-024`）要求投影里出现的每个事实都能在状态源里查到（`P ⊆ S`）。但 `notice` 不在 `S` 里（P2）。于是——

> **一条被推送的 `notice`，如果投影把它渲染出来（"任务 j-A 已完成"），投影就"新增了一个事实"，违反 `REQ-F-024`；如果投影不渲染它，人永远看不见完工铃。**

**这是我的推断**：这是一个**真实的、当前的、未被登记的矛盾**，而且它没有技术解法，只有**口径解法**。三条候选口径，必须由人裁：

| 候选 | 内容 | 代价 |
|---|---|---|
| 甲 | 扩 `S`：让 `notice` 进读模型（新 `notices` 主体，或 `world://notice/<id>` 挂 `seen: true`） | 读模型膨胀；且"通告"变成"状态"，与 `14:178-179` 的"`notice` 说发生了一件事（**可能不对应任何字段变化**）"直接冲突 |
| 乙 | 扩 `P ⊆ S` 的量词：改为"`P ⊆ S ∪ 通告流`"，投影必须能出示"这条来自通告 `id=X`" | 不改读模型；但 `REQ-F-024` 的判据形态要改（可机械判定性下降） |
| 丙 | 投影**不渲染通告**，通告只走语言投影（给程序读），人靠视觉投影从 `job.status: done` 这个 `change` 得知 | 最省，但"完工铃第一优先"就变成"完工铃第二优先"——**且 `job.status` 的 `change` 必须有生成点，而当前 `job.done` 零生成点（§2.2）** |

我倾向**乙**（保住 `notice` 的独立性），但这是口径问题，**不该由 AI 单方面定**。

**P4：`11` 篇 §七 的那条"缺口判断"在收缩后仍然成立，但方向变了**

`11:99-101` 说"没人造的是同一个航站楼"。`13` 篇 §六 红线第 4 条明确"**不抄 MCP / ACP 的'先协商能力再看数据'**"（`13:199`）。但**推送线天然要求协商**（消费者必须告诉服务器"我从哪开始、我要哪些家族"）。

**这是我的推断**：这是一个**真实的设计张力**，且很容易被"先协商再看数据"的禁令误伤。分辨点在于：**协商的必须是"位置"，绝不能是"能力/格式"**。即消费者可以说"我从 `seq=100` 起"，不可以说"我只懂 `world=1` 的格式"——后者就是被禁的"先协商能力"。**建议 `13` 篇红利清单里补一句**，否则实现者会花时间论证"订阅握手是否违规"。

**P5：`REQ-F-023` 的"`to` 是收件人字段"与 `13:190` 的"总线只判传输与名字"从未对齐**

`SRS:266` 说 `to` 的读者是"通道与**将来的订阅方**"；`13:190` 说"**总线只判传输与名字，语义授权下沉服务**"。若 `to` 成为订阅过滤条件，那么**过滤逻辑在哪里**要定：在通道（=总线判名字）还是在订阅者（=消费者自己滤）。

**这是我的推断**：正确做法是**通道不按 `to` 过滤**（广播全部，消费者自滤），理由有三：① 通道过滤需要解析 `body`，那就成了"总线判语义"，违 `13:190`；② 过滤需要维护"主体 → 订阅"的映射，那是身份的第二份拷贝；③ 广播 + 自滤的成本在单机 Unix socket 上可忽略（`docs/系统全景图.md:115` 的体量：内核 6591 行、单机）。
**但这应当由人确认**：如果将来要支持"千人千面的通知扇出"，广播自滤会浪费带宽。v1 不必付这个成本。

**P6：`READ` 的 CLI 把"没有新事件"与"起点超出末尾"合并成同一个结果**

`src/main.rs:422-443`：`read [from]` → `read_from(from)` 返回空 `Vec` → 打印零行 → `ExitCode::SUCCESS`。当 `from > last_seq` 时，结果与"没有新事件"**完全无法区分**。

**这对推送线是硬要求**：§五 的 `PosAhead` 错误码之所以必须存在，就是因为这个区分在 API 层丢了。**这是我的推断**：`read_from` 目前没有"我读到哪了"的返回值概念（签名只有 `from_seq`，靠调用方自己遍历取最大 `seq`），推荐在推送线的 API 里**显式返回"服务器当前位置"**（见 §五.1 的首帧 `pos` 字段），把 `read` 命令的这条缺陷一并收口。

## 四、总问题 A / B / C

### A. 这个理念还缺什么？（理论层面缺的概念 / 区分 / 论证）

缺 **四个概念** 和 **一条论证**。

**A1 缺"投递（delivery）"这个一等概念。**

`14` 篇 §三 用三行定义了"世界上有什么"（三家族 / 值类型 / 传输形态），但**没有一行定义"世界怎么让别人知道"**。结果是"知道"这件事在整个理论里没有位置：它既不是事件（事件是账本里的行），也不是投影（投影是渲染），也不是治理（治理是裁决）。**缺这一层，`notice` 就永远只是账本里的一行字。**

**A2 缺"位置（position）"与"事件（event）"的区分。**

`14:94-95` 有一句极强的话："`seq` 不再是'消息序号'，而是**事件在日志中的位置**……`state = fold(events[0..seq])`"。但理论没有把这句推到底：

> **"位置"是一等公民，"事件"是位置上的内容。**

一旦分开，"订阅"就有了定义（订阅位置，不订阅事件）、"断线补齐"就有了定义（从一个位置走到另一个位置）、"推送丢了算不算丢"就有了答案（位置没丢，内容可以重取）。**这是我认为本项目理论上最值钱的一处未开采的矿**，而且它已经在文档里写了一半。

**A3 缺"可丢弃投递（lossy delivery）"这个概念。**

`14` 篇通篇的强度是"不可伪造、可理解、可重放"，全部围绕**账本**。但没有一句话说**投递可以是可丢的**。于是实现者面对"推送失败怎么办"时只有两种坏选项：要么学 MQ 做重投/确认（把刚扔掉的一致性难题请回来），要么干脆不做（现状）。**理论必须显式授权"投递可丢"**，否则工程上不敢丢。

**A4 缺"谁是订阅者"与"谁是主体"的区分。**

`14:76` 的 `actor` 是"世界内身份"，`policy.json` 的 `subjects.allow` 是主体白名单（`SRS:268`）。但"订阅"这个动作**改变了一个主体能收到什么**——它是一个**权限相关的动作**，却既不是 `act`（没有 `capability`）、也不是 `change`（不改任何字段）、也不是 `notice`。**这是我的推断**：这是本项目特有的一个真实缺口——

> **订阅关系本身要不要留痕？**

按 `15` 篇 §八 的"一个写入口，一个账本"（`:256-264`）和 `15` 篇 §十二 待定项 2（`：`"**权限也必须从事件派生**——否则权限就是第二本账"，`:315`），答案应当是**要**：订阅关系若存在 `channel.json` 里而不进账本，那它**就是第二本账**（与权限同族的问题）。这一条我认为是本项目**理论一致性的真正考验点**，而且现在还没被问出来。

**A5 缺一条论证：为什么"推送"必须是语义总线的一部分，而不是一个外挂。**

`11:99-101` 的论证是"没人造同一个航站楼"。但**推送不推送，与航站楼是不是同一个没有关系**——Kafka 有推送但没有语义，D-Bus 有推送但没有语义。**"要有推送"这件事在本项目里从未被论证过，只被"完工铃第一优先"（`14:174`）当作既定事实引用。** 这是我的推断：**这条论证其实很好写**，就是 A2 —— 因为 `seq` 是位置，而"知道位置变了"这件事**只有账本能回答**，所以"投递"天然属于账本（=语义总线）而不属于外挂。

**如果是外挂**（消费者自己轮询），那 `14:253` 那个待批判项（"投影是取快照还是常驻订阅增量"）就永远答不出——因为"我落后了"这个问题需要一个**权威位置**来回答，而轮询只能回答"我读到哪了"，回答不了"现在到哪了"。

| 系统 | 具体机制（指名） | 在"语义"这件事上缺什么 | 真实痛点场景（具体） |
|---|---|---|---|
| **NATS / JetStream** | 核心 NATS 是 at-most-once 且不重放；JetStream 的 consumer 是**服务端有状态游标**，可取 `beginning/latest/seq/time`，未 ack 重投（`2-依据/13:125`，本篇已亲验引文） | 有**位置**、无**语义**：`subject` 是字符串寻址，事件体是 `[]byte`；没有"哪条是原因、哪条是结果"的字段 | **场景**：`notice.job.done` 推给一个 agent，agent 要回答"这个任务是谁批的"。NATS 的消息里没有 `trace`，agent 只能自己去翻别的 subject 的日志做关联——**而"翻日志做关联"正是本项目要消灭的那个动作**。`14:90` 那句话直接命中：`trace`"⚠ 23 件参考件**无一件有它**" |
| **Kafka** | 同 key 同分区保序；按保留期删除；可重复读；consumer group 的 offset 提交（`2-依据/13:64,141`） | 有**分区序**、无**全局序**；`__consumer_offsets` 是**第二本账**（正是本项目最怕的东西） | **场景一（全局序）**：本项目要求 `state = fold(events[0..seq])`（`14:95`），跨分区的两条事件**没有全序**——`notice.job.done` 与引发它的 `act` 可能在不同 key 的不同分区，消费者可能先看到结果后看到原因。**场景二（第二本账）**：Kafka 的 offset 存放在 broker 内部的 topic 里，而本项目的纪律是"一个写入口，一个账本"（`15:264`）——一旦账本进程崩了，offset 还活着，就会出现"世界回退了但消费者的位置没回退"，消费者**跳过**事件且**没有任何机制能发现**。本项目的回答（§五）是：**位置由消费者自己带，重连时声明，服务器不替它记**——于是"世界回退"必然导致消费者的位置**超出服务器位置**，立刻被 `PosAhead` 抓到 |
| **EventStoreDB** | 每个 stream 单调 `$all` 序号、`$all` 全局流、catch-up subscription、持久订阅、`$maxAge`/`$maxCount` 截断 | **最接近**本项目需求的一件，但仍缺：事件体是**用户自定义的不透明 JSON**，没有"哪个字段变了、旧值是什么"的强制形状 | **场景**：EventStoreDB 完全支持"从 `$all` 的某个位置订阅并补齐"，但订阅者拿到一条事件后**不知道它对应世界里哪个实体的哪个字段**——要回答"静音状态现在是什么"，订阅者必须自己实现一遍 fold，**每个订阅者一份解释规则**。`14:207-216` 的 §4.2（词表必须内容寻址）正是为此：EventStoreDB 保证"读同一份数据"，**不保证"同一套解释规则"**（与 `15:242` 对 Solid/atproto 的批评同形） |
| **D-Bus** | `signal` 类型（`SIGNAL=4`）+ match rule + `BecomeMonitor`；`serial` + `REPLY_SERIAL` 配对；policy 语言"**not well-suited to finer-grained policies**"（`2-依据/13:103,105` 亲验引文） | 二进制头把地址与类型签名**硬绑在帧上**（`13:107`"大模型不可读"）；治理按**进程/用户**而非能力与不可逆性 | **场景**：agent 收到一条 D-Bus signal 要判断"我该不该基于它行动"。signal 只说"某属性变了"，**不说这条变化可逆还是不可逆**——而本项目的门禁是"按不可逆性加摩擦"（`00-理论定稿:97-100`）。D-Bus 的 policy 是**连接级**的，无法表达"这次 `ledger.compact` 需要摩擦，但 `notice.mute` 不需要"（`13:105` 的官方原文：`expressed in terms of D-Bus interfaces and method names, not higher-level domain-specific concepts`） |
| **journald** | `sd_notify`/`Type=notify` 做**就绪与看门狗**；`journalctl -f` 做流式跟随；`_SYSTEMD_UNIT` 等结构化字段 | 日志是**给排障的追加文本流**，没有"事件是真相、状态是它的 fold"这层；没有 `before/after`；没有 `trace` | **场景（本项目已经踩到）**：`world-core/deploy/README.md:73-74,233` 用了 `WatchdogSec=30s` + `Type=notify`，但**进程侧 `WATCHDOG=1` 尚未实现**——`README:233` 自己登记"实装时须先做，否则会被反复重启"。这说明**即使只借 journald 的"就绪/看门狗"这一小块，也要自己实现一半**。更深一层：journald 的"结构化字段"是**写入方自称的**，与账本的可核验性（`chain`）不可比——**日志能告诉你"发生过什么"，不能告诉你"发生过的事没被改过"** |
| **RabbitMQ** | exchange/queue/binding 路由 + ack/nack + 死信队列 + 持久化 | 有**投递保证**、无**真相**：消息 ack 之后就从队列消失；"重启后还能不能重建状态"不在它的语义里 | **场景**：本项目要回答"人离开 24 小时后回来，发生了什么事"（`14:234-247` 的推演 B）。RabbitMQ 的答案取决于**队列是否还被消费过**——若消费者 ack 了，消息就没了；若没 ack，它会重投。**两个都不是"账本"**：一个丢历史，一个重投到消费者可能已经处理过的位置。要拿到"这 24 小时"，必须自己再落一份存储——**那就是两本账**（`15:260`"最糟的情况不是'选错账本'，而是**两本账**"） |
| **MQTT** | QoS 0/1/2、retained message、wildcard topic、last will | 有**投递等级**、无**因果与语义**；`QoS 2` 的"恰好一次"是**昂贵的四次握手**，且只在一个 broker 会话内有效 | **场景**：本项目明确**不引入第二套一致性协议**（`14:257`"明确不引入 CRDT"、第一版用乐观并发 + `seq` 拒绝）。MQTT 的 QoS 2 恰恰就是"第二套一致性协议"的教科书形态——订阅者与 broker 之间维护 packet id 状态机。**本项目不需要它**：因为 `seq` + `chain` 已经给了"重复可检、缺口可检"（§2.3），把"恰好一次"换成"**至少一次投递 + 幂等应用 + 跳号即停**"，代价从四次握手降到一次字符串比较 |
| **WebSocket / SSE** | WS：全双工帧 + ping/pong + 子协议协商；SSE：单向 `text/event-stream` + `Last-Event-ID` 头 + 自动重连 | 只有**传输**：`Last-Event-ID` 是字符串，服务器怎么解释它、断线后补什么，**全在应用层**（无标准语义） | **场景（这一件最值得本项目警惕）**：SSE 的 `Last-Event-ID` 在形状上与本项目的"从 `seq=N` 补齐"**几乎一样**——但它**没有连续性判据**。浏览器自动重连时会带上这个 id，而服务器如果答不出"这个 id 是什么时候的、我还能不能给你补"，就会**静默跳过**中间的事件，且**客户端无从发现**。本项目的 `seq` 连续性判据（`src/readmodel.rs:92-99` 的 `SeqGap`）恰好补上这一刀：**跳号不是"可能出了点问题"，是"我确定我坏了，必须停下"** |
| **ZeroMQ** | PUB/SUB pattern；官方原文"PUB/SUB **无回话**，'加入之前的一切都错过'、**慢订阅者丢消息**"（`2-依据/13:139` 亲验引文） | 丢的是**无声的**——订阅者无法知道自己错过了什么 | **场景**：本项目若照抄 ZeroMQ 语义，`job.done` 可能在订阅者连接建立之前就被丢弃（"加入之前的一切都错过"），而订阅者**永远不会知道**自己是何时错过的。**这一条恰好解释了为什么"按位置订阅"（`14:88` 的 `seq` 断线补齐）不是奢侈品而是必需品**：它把"错过"从**静默**变成**可检测** |
| **MCP / ACP / AG-UI / A2A（agent 侧）** | MCP：`resources subscribe` / `list_changed`，但"**protocol itself cannot enforce these security principles at the protocol level**"（`2-依据/13:75` 亲验引文）；ACP：`session/update` 单向流（`13:85-88`）；A2A：`tasks/{id}:subscribe`，**无 seq**（`13:81`）；AG-UI：有 `STATE_SNAPSHOT`/`STATE_DELTA`，`STATE_DELTA` 用 RFC 6902（`13:91-92`） | 五个协议**全部不满足自描述**（"都要**先协商能力再看数据**"，`13:160`） | **场景**：一个 agent 想在"订阅世界变化"时不读文档就理解一条事件。MCP 的 `notifications/message` 只有 `level` 与 `data`；ACP 的 `session/update` 有 11 种变体但**没有一件带 seq**（`13:85`）——断线后**只能整块重连**（`13:81` 对 A2A 的同一批评）。**与本项目 `14` 篇 §2.1 的八条判据逐条对照，这五件在"重放"与"因果"两行上全空**（`14:58`） |

**C 的结论**：这些系统**没有一件是"不好用"**——它们在各自的问题域里都是最优解。它们**不好用的是"当做语义总线的传输层"这件事**。而本项目的机会恰恰是：

> **账本已经比它们任何一件都更"语义"（`trace`/`before`/`chain`/`seq` 位置语义），但它比它们任何一件都更不"能送达"。**

所以本次评审的结论不是"去抄 Kafka/NATS"，而是：**把它们的传输机制（JetStream 的服务端游标、SSE 的 Last-Event-ID 形状、Kafka 的按位置重放）压到本项目的 `seq` 铁律之下，然后一条投递保证都不抄**。这正是 `13:181-184` 已经写对的方向——只是没有人把它实现，也没有人在 `14` 篇里给它留位置。

## 五、推送线设计草案

### 5.1 概念与帧格式

**三条定义（先把话说清）**

1. **订阅的是位置，不是事件。** 订阅者的语义是"**当服务器的位置大于我的位置时，叫我**"。
2. **推送的载荷是账本行的逐字节副本。** 含 `seq` 与 `chain`；**不重新编码、不改字段、不加包装字段到事件内部**。
3. **一次推送 = 一帧 = 一条账本行。** 帧外只有一种信息：这是事件的规范字节。

**为什么不推"门牌号"（`last_seq` 通知）**：那会**逼所有消费者回到"自己 `read_from`"**（= 轮询），且 `read_from` 目前是 O(整文件)（`src/ledger.rs:526-546`）——等于把现状换了个叫法。

**为什么不推"投影增量/状态差"**：那需要推送线自己去 fold、自己决定"哪里变了"。而 `notice` 不改变 fold 出的任何字段（`src/readmodel.rs:109`）——**推送线要么推不出它，要么必须自己维护一份"通告索引"，那就是第二本账**。

**因此：推事件本体，是唯一能同时满足"零新协议"与"`notice` 可达"的选择。**

**线格式（沿用既有的行分隔 JSON，`src/channel.rs:31-36` 的同族形态）**

```text
握手（订阅者 → 内核，一行）
  {"sub":{"from_seq":100,"filter":["notice","change"],"max_frame":1048576,"ack":false}}

应答 / 首帧（内核 → 订阅者，一行）★ 必须给出服务器当前位置
  {"ok":true,"sub":true,
   "pos":{"from_seq":100,"server_seq":128,"oldest_seq":1},
   "actor":"world://agent/1","vocab":"fnv1a64:…"}

数据帧（内核 → 订阅者，每行一条账本行的规范字节）
  {"seq":101,"kind":"notice","id":"e…","actor":"…","chain":"fnv1a64:…","body":{…}}
  {"seq":102,"kind":"change","id":"…","chain":"fnv1a64:…","body":{…}}

终止帧（内核 → 订阅者，一行，随后关闭）
  {"ok":false,"error":"ext.world.Push.SlowConsumer: …","pos":{"server_seq":151}}
```

**字段裁决（每条给理由）**

| 字段 | 位置 | 理由 |
|---|---|---|
| `seq` | 每帧 | 位置的唯一键（`14:94-95`）。**不得用 `at`**（秒级，同秒并列；`ontology.json:16` 明写"顺序由 seq 决定，at 只作辅助"） |
| `chain` | 每帧 | 幂等与逐字节核验的唯一手段（`src/ledger.rs:562-577`）。**这是"不引入新去重字段"的关键** |
| `kind` | 每帧 | 消费者可用于**本地过滤**（P4：协商位置可以，协商格式不可以）；同时是"要不要重算投影"的判据（`notice` 不改变 fold 结果） |
| `id` | 每帧 | 去重锚点（`14:87`）；账本侧已保证唯一（`src/ledger.rs:320-328,421-426`） |
| `actor` | **只在首帧** | 订阅者身份由套接字给出（`src/channel.rs:180-200`）——**它不会逐帧变化**。逐帧放 `actor` 会诱使 consumer 相信"帧里的 actor"，那正好是 `channel.rs:284-288` 禁止的事 |
| `vocab` | **只在首帧** | 词表 hash（`src/ontology.rs:144`）。消费者可据此核验"我用的是哪一版词表"（`14:207-216`），且**换词表可被检出** |
| `pos.oldest_seq` | **只在首帧** | 让消费者预先知道"还能补多久"（§5.3 的 `TooFarBehind` 可以提前判） |
| `to` | **不用** | 建议**广播自滤**（P5）。若将来要定投，须先裁决"总线是否判语义"（`13:190`） |

**分帧**：沿用**行分隔**（与 `src/ledger.rs:4-6`、`src/channel.rs:31-36` 同族）。两个理由：① 账本行本身天然不含真实换行（`ontology.json` 的既有纪律，`src/ledger.rs:4-6`）；② 一致性——用 `Content-Length` 会引入第二套分帧口径（`13:169-171` 曾建议 `Content-Length`，但那是针对**通道层**的最终决定，**尚未实现**；推送线若先上另一种，就会出现两套）。**这是我的推断**：行分隔在 v1 更安全，`Content-Length` 应在通道层统一改造时再一并考虑。

**帧上限**：`max_frame` 由订阅者声明、服务器取 `min(声明值, 服务器上限)`。超限的处理见 §5.3 的 `FrameTooLarge`。**这条同时也是 `REQ-F-026`（通道资源边界，未实现）的一部分**——建议两件事一起做（§四 B6）。

### 5.2 状态机

**服务器侧（每个订阅连接一个实例）**

```text
        accept
          │  身份 = 套接字（bind 时 chmod 0600 + chown 决定）
          ▼
   ┌──────────────┐   读首行（有超时！）
   │  AwaitSub    │──────────────────────► 非 sub 帧 / 超时  ⇒ 回错误帧 + 关
   └──────┬───────┘
          │ {"sub":{from_seq,…}}
          ▼
   ┌──────────────┐   校验：from_seq vs (oldest_seq, server_seq]
   │   Validate   │──► from_seq > server_seq  ⇒ PosAhead     + 关
   └──────┬───────┘──► from_seq < oldest_seq  ⇒ TooFarBehind + 关
          │ 合法
          ▼
   ┌──────────────┐   发首帧（pos / actor / vocab）
   │  Handshaken  │
   └──────┬───────┘
          ▼
   ┌──────────────┐   while : emit 帧 → 检查发送缓冲
   │    Live      │──► 缓冲超上界          ⇒ SlowConsumer + 关
   └──────┬───────┘──► 读端 EOF/EPIPE      ⇒ 丢弃待发 + 关（无副作用）
          │
          │  每帧：next = last_emitted + 1
          │        若 next > ledger.next_seq() ⇒ 本轮结束，等可读事件
          ▼  下一轮 poll()
```

**关键实现约束（伪码，不含细节语法）**

```text
loop {
    poll(listen_fd, [每个订阅连接], [ledger 的可读通知])
    for s in ready_subscribers {
        while s.buffered_frames < s.max_buffered {      // ← 有界；溢出即 SlowConsumer
            let next = s.last_emitted + 1;
            if next > ledger.next_seq() { break; }       // ← 位置由账本单点裁定
            let ev = ledger.read_from(next)?;            // ← 只取一条；见 B9 的性能注记
            s.send(encode_line(ev));                     // ← 与账本落盘同一字节口径
            s.last_emitted = next;
        }
    }
}
```

> **性能注记（必须同时说）**：`read_from(next)` 目前的实现会**读整个文件**（`src/ledger.rs:526-546`）。逐条调用它会把 O(N) 变成 O(N²)。**两种改法**：① 先把 `read_from` 改成按偏移定位（§四 B9，推荐）；② 或服务器保持一个"已读偏移"的文件句柄，顺序 `read_line`。**这是我的推断**：②更省事且不改变 `read_from` 的公开语义，但它要求服务器自己维护偏移——而那**恰好是消费者该做的事**，所以放在服务器侧需要明确"这是服务器的读优化，不是位置权威"（位置权威仍是 `read_from` 的返回值）。

**订阅者侧（推荐形态，写进规格作为"正确用法"）**

```text
local_seq = 0
loop {
    connect(订阅套接字)
    send {"sub":{"from_seq": local_seq + 1, ...}}
    读首帧 → 核对 server_seq >= local_seq（否则 PosAhead 处理见下）
    for each 数据帧 f:
        若 f.seq <= local_seq:                      # 重复帧
            若 f.chain == chain_of(local_seq): 丢弃（幂等）
            否则: 报错并停（真相分裂）
        否则 若 f.seq == local_seq + 1:              # 唯一合法前进
            apply(f); local_seq = f.seq; 持久化 local_seq
        否则:                                        # 跳号
            报错并停 —— 绝不"跳过继续"
}
```

**订阅者侧的四条硬纪律**：① 位置**必须本地持久化**（这是"多消费者各自游标怎么放"的答案：**放在消费者自己那里**）；② 只能按 `seq + 1` 前进；③ 重复帧必须按 `chain` 判，不能按"我好像见过"判；④ 收到 `TooFarBehind`/`PosAhead` 后**不许重试同一位置**，必须走快照/检查点重建（`src/checkpoint.rs:52` 的 `base_seq`）。

### 5.3 错误码

沿用 `src/error.rs:12-22` 的契约（`ext.world.<域>.<原因>: <人话>`），新增域 `Push`。**七个码，每个都有"谁的错、怎么办"**：

| 错误码 | 触发条件 | 谁的错 | 消费者该怎么办 |
|---|---|---|---|
| `ext.world.Push.TooFarBehind` | `from_seq < oldest_seq`（超出在线补齐预算） | 消费者（落后） | **不许重试**；取最新检查点重建（`checkpoint.rs` 的 `base_seq`），从 `base_seq+1` 重新订阅 |
| `ext.world.Push.PosAhead` | `from_seq > server_seq` | 消费者（游标损坏，或**它连的是另一个世界的账本**） | 停下并人工查；**这是最危险的一类**（可能是账本被换/回退） |
| `ext.world.Push.SlowConsumer` | 发送缓冲超上界 | 消费者（慢） | 重连；服务器**不替它缓冲**——这正是"推送可丢"的落点 |
| `ext.world.Push.FrameTooLarge` | 单帧超 `max_frame` | 双方（配置） | 调大 `max_frame`（但**必须同时调大服务器的账本行上限**，否则是死胡同）；或让生产者把大对象外置为 `ref`（这正是 b1 缺口要补的东西） |
| `ext.world.Push.BadSubscribe` | 首帧不是 `sub` / `from_seq` 非整数 / 字段非法 | 消费者 | 修客户端 |
| `ext.world.Push.NotASubscriberSocket` | 在**写口**发 `sub`，或在**订阅口**发 `commit` | 消费者 | 修客户端；**服务器不得在同一套接字上同时接受两种语义**（否则 `serve_once` 的既有语义被污染） |
| `ext.world.Push.ReadFail` | 读账本出错（`Ledger.Corrupt` 等） | **世界自己的问题** | **必须断开所有订阅者**并让 `worldd` 报错——账本坏了不停下，就是拿坏真相喂所有人 |

**一条纪律**：这七个码全部要**登记进 `WC-IC-001` §三 的错误码清单**（`src/error.rs:21-22` 说明域清单在该处），否则 `code_of`（`:43-54`）能解析但**没有任何文档承诺它**。

### 5.4 "推送丢了算不算丢" —— 唯一答案

**不算丢，且这不是妥协，是设计选择。** 理由是位置与内容的分离（理论缺口 A2）：

> **丢掉的只能是"某次提醒"，不可能是"某个位置"。**

- **判据**：消费者断开期间发生的一切，在它重连后由 `read_from(local_seq+1)` 一字不差地取回（`src/ledger.rs:526`）。**位置没丢 ⇒ 内容没丢。**
- **代价**：消费者**必须**本地持久化自己的位置。这不增加世界的负担（世界不存 offset），代价落在消费者身上——**这正是我们要的方向**（`15:264`"一个写入口，一个账本"：世界不替任何人记第二份状态）。
- **唯一真丢的情形**：`from_seq < oldest_seq`（超出保留窗）。**这必须是显式错误**（`TooFarBehind`），**不许静默跳过**。而"保留窗多久"目前是项目自己登记的未决项（`14:255` 待批判项 3、`15:316` 待定项 3），**推送线不改这个未决项，只是让它的后果变得可见**。
- **一句话口径（建议直接写进 `14` 篇）**：
  > **通告是提醒，账本是事实。提醒可以丢，事实不能丢；丢了提醒的人，回到账本上取。**

### 5.5 一处必须先裁的接口问题：订阅是进程内还是跨进程？

`11:28` 说"订阅（subscribe 后主动推送，v0.2 已验证）"，但没说这个"subscribe"是**进程内 API** 还是**跨进程协议**。**这次必须一次定死**：

| | 进程内订阅 | 跨进程订阅 |
|---|---|---|
| 形态 | `World::subscribe()` 返回一个 channel/回调 | Unix 套接字上的 `sub` 帧（§5.1） |
| 身份 | 不需要（同进程即同信任域） | 由套接字给出（`src/channel.rs:180-200`） |
| 谁能用 | 只有 `worldd` 自己（`lib.rs` 的进程内模块） | `projectd` / `carrier` / 第三方适配器 |
| **结论** | **两者都要，但只有一个是真的** | **跨进程那个是承重的** |

**裁决建议**：**跨进程是规格，进程内是实现细节。** 理由：① 项目的拓扑是"**三方都只跟账本打交道**"（`15:188`）、"**星形，中心就是世界核心**"（`15:170-176`）——所有消费者都在**别的进程**里（`docs/系统全景图.md:38-49` 的两个进程框图）；② `15:20` 的术语表已经说"语言投影 / 视觉投影……**实现可以在核心内或核心外**"——端口是语义，进程不是。**这是我的推断**：先把跨进程协议定死，进程内订阅就只是它的一种裁剪实现；反过来定则会得到一个"只有 `worldd` 自己能用的订阅"，而唯一需要被叫醒的消费者（投影、载体、agent）**全都在外面**。

### 5.6 判据（每条可机械核对）

| # | 判据 | 怎么核 | 反例（必须变红） |
|---|---|---|---|
| **D1** | **订阅者收不到重复 `seq`，也收不到跳号** | 订阅者侧断言"收到的 `seq` 严格 +1" | 服务器跳过一条 ⇒ 必须报错停（不得静默） |
| **D2** | **首帧 `server_seq` ≥ 任何随后帧的 `seq`** | 比对首帧与全部数据帧 | 首帧声称 128，随后收到 `seq=200` ⇒ 必须判不成立 |
| **D3** | **推送 ≡ 拉取（逐字节）** | 消费者对每条已收帧调 `read_from(seq)` 并比对整行字节（含 `chain`） | 任一字节不同 ⇒ 报错（真相分裂） |
| **D4** | **幂等**：重复应用同一帧无副作用 | 重放已收帧全部内容 ⇒ `local_seq` 不变、`state` 指纹不变、无错误 | 应用两次后 `notices` 计数 +2 ⇒ 判不成立（**注意：这是今天 `readmodel.rs:109` 的真实缺口**） |
| **D5** | **`TooFarBehind` 在预算外必现，且不拖累他人** | 造一个落后 ≥ 预算的订阅者 ⇒ 它收到 `TooFarBehind`；同时另一个正常订阅者的帧间隔 P95 不劣化 | 大跨度补齐把总线占满 ⇒ 判不成立 |
| **D6** | **崩溃无副作用** | `kill -9` 订阅者 ⇒ `worldd` 内存回基线、无重投、无残留 | `worldd` 继续为死者缓冲 ⇒ 判不成立 |
| **D7** | **慢消费者只伤自己** | 停住一个订阅者的读端 ⇒ 只断它一个 | 其余订阅者受影响 / `worldd` 内存无界 ⇒ 判不成立 |
| **D8** | **投递不进入写路径** | 全部订阅者断开时，`append` 的延迟与无订阅者时无差异 | 有差异 ⇒ 判不成立 |
| **D9** | **身份不可自称（推送侧）** | 订阅口不接受 `actor` 字段；写口不接受 `sub` | 任一被接受 ⇒ 判不成立 |
| **D10** | **账本坏 ⇒ 立刻停推** | 注入 `Ledger.Corrupt` ⇒ 所有订阅连接收到 `Push.ReadFail` 并断开 | 继续用坏账本喂消费者 ⇒ 判不成立 |

**验收用例建议**（每条判据至少一个"应当失败"的反例，与本项目既有纪律一致）：
- E2E：`channel serve` + 一个订阅客户端 + 一次 `carrier do job.start` ⇒ 订阅者收到 `act`、`act`（结果）、以及（在 `job.done` 生成点落地后）`notice`；
- 反例：把 `read_from` 的返回值人为截断一条 ⇒ D1 必须红；
- 反例：把某帧的 `chain` 改一个字符 ⇒ D3 必须红；
- 反例：让订阅者不持久化游标、重启后从 0 开始 ⇒ D4/D5 必须给出确定行为（而不是静默重放全部历史）。

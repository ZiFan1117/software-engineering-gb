# Fact-check: audit/logging layer & approvals — primary-source verification

Method: only official specs/vendor docs/API schemas (IETF RFCs, W3C, freedesktop/systemd, man7, docs.aws.amazon.com, learn.microsoft.com, GitHub docs + official OpenAPI/docs source, Okta help, Google's official discovery artifact). No blogs/marketing. Where a source was unreachable it is marked UNVERIFIED.

## Group A — audit & logging layer

**A1** TRUE (field list) / missing-fields claim TRUE — RFC 5424 ABNF is exactly `SYSLOG-MSG = HEADER SP STRUCTURED-DATA [SP MSG]` and `HEADER = PRI VERSION SP TIMESTAMP SP HOSTNAME SP APP-NAME SP PROCID SP MSGID`, with `PRI = "<" PRIVAL ">"` (`PRIVAL = 1*3DIGIT ; range 0 .. 191`), `VERSION = NONZERO-DIGIT 0*2DIGIT`, `SD-ELEMENT = "[" SD-ID *(SP SD-PARAM) "]"`, `SD-PARAM = PARAM-NAME "=" %d34 PARAM-VALUE %d34`, `SD-NAME = 1*32PRINTUSASCII` (excluding `=`, SP, `]`, `"`). IANA-registered SD-IDs are only `timeQuality` (`tzKnown`,`isSynced`,`syncAccuracy`), `origin` (`ip`,`enterpriseId`,`software`,`swVersion`), `meta` (`sequenceId`,`sysUpTime`,`language`). RFC 3164 (Informational, obsoleted) has only PRI + TIMESTAMP/HOSTNAME + MSG(CONTENT), with TAG folded into APP-NAME/PROCID/MSGID per RFC 5424 App. A.1 — it defines no structured elements at all. **Absent by design in both:** (1) no acting-human/user field — APP-NAME/PROCID/MSGID identify the *process* (`_PID` analog), RFC 3164's TAG is a program tag, and no SD-ID carries a user; (2) no target object/field field; (3) no before/after value field; (4) no causal-parent field (RFC 5424 §8.7 "Message Integrity"/§8.8 "Message Observation" explicitly provide no integrity or confidentiality). Free-form MSG/SD-PARAM can carry anything, but nothing standard or semantic does. Fetched: https://www.rfc-editor.org/rfc/rfc5424.txt , https://www.rfc-editor.org/rfc/rfc3164.txt

**A2** PARTLY TRUE — Trusted/implicit fields verified from systemd.journal-fields(7): `_PID`,`_UID`,`_GID`,`_COMM`,`_EXE`,`_CMDLINE`,`_CAP_EFFECTIVE`,`_AUDIT_SESSION`,`_AUDIT_LOGINUID`,`_SYSTEMD_CGROUP`,`_SYSTEMD_SLICE`,`_SYSTEMD_UNIT`,`_SYSTEMD_USER_UNIT`,`_SYSTEMD_SESSION`,`_SYSTEMD_OWNER_UID`,`_SELINUX_CONTEXT`,`_SOURCE_REALTIME_TIMESTAMP`,`_SOURCE_BOOTTIME_TIMESTAMP`,`_BOOT_ID`,`_MACHINE_ID`,`_SYSTEMD_INVOCATION_ID`,`_HOSTNAME`,`_TRANSPORT`,`_STREAM_ID`,`_LINE_BREAK`,`_NAMESPACE`,`_RUNTIME_SCOPE`; address fields `__CURSOR`,`__REALTIME_TIMESTAMP`,`__MONOTONIC_TIMESTAMP`,`__SEQNUM`,`__SEQNUM_ID`. **Process tree: NO** — `_CMDLINE` is "the command line of the process the journal entry originates from", and the doc states entries from a forked process's stdout/stderr "will contain credentials valid for a parent process". Tree-wide capture requires a privileged (UID 0) program to pass `OBJECT_PID=`, which then auto-adds `OBJECT_CMDLINE`/`OBJECT_EXE`/`OBJECT_UID`/`OBJECT_SYSTEMD_UNIT`… — explicit opt-in, and documented as UID-0 only. **File content change: NO** — no trusted field names a path or content (`_KERNEL_DEVICE` is a device, not a file); only `_TRANSPORT=audit` records carry kernel-audit text inside `MESSAGE`. **Root can rotate/vacuum: TRUE** — `journalctl --rotate`, `--vacuum-time=`, `--vacuum-size=`, `--vacuum-files=` (combining `--rotate` with vacuum "has the greatest effect"); config `SystemMaxUse=`, `SystemMaxFileSize=`, `MaxRetentionSec=`, `MaxFileSec=`; system-journal access is root plus `systemd-journal`/`adm`/`wheel`. **`Seal=yes` off by default: FALSE as stated** — journald.conf documents `Seal=` as "If enabled (the default)" (i.e. the config default is *on*), but sealing only activates "and a sealing key is available (as created by journalctl's `--setup-keys` command)", and `--setup-keys` is never run by default ⇒ FSS is effectively inactive out of the box even though `Seal=` defaults to yes. Fetched: https://www.freedesktop.org/software/systemd/man/latest/systemd.journal-fields.html , https://www.freedesktop.org/software/systemd/man/latest/journald.conf.html , https://www.freedesktop.org/software/systemd/man/latest/journalctl.html

**A5** TRUE (no cross-system standard) / OTel is opt-in and descriptive — W3C Trace Context defines exactly `traceparent = version "-" trace-id "-" parent-id "-" trace-flags` (`trace-id = 32HEXDIGLC`, `parent-id = 16HEXDIGLC`, `trace-flags = 2HEXDIGLC`, only the `sampled` flag defined) plus the vendor-opaque `tracestate`; `traceparent`/`tracestate` explicitly "MUST NOT" carry "any personally identifiable or otherwise sensitive information", and a vendor is *allowed* to "**Restart trace**: All properties (`trace-id`, `parent-id`, `trace-flags`) are regenerated" for secure-network front gates, and MAY delete any `tracestate` key/value pair. So no identifier is guaranteed to survive process boundaries or a third party. Baggage is fully application-defined: "no key or its value or properties is given semantic meaning by this specification", and a platform MUST propagate only up to **64 list-members and 8192 bytes**, dropping the rest. OTel makes propagation opt-in: "The OpenTelemetry API **MUST use no-op propagators unless explicitly configured otherwise**", and platform defaults are only a "SHOULD" ("`Propagator`s SHOULD default to a composite `Propagator` containing the W3C Trace Context Propagator and the Baggage `Propagator`"); instrumentation "SHOULD call propagators to extract and inject the context on all remote calls", and some libraries may "hardcode the context extraction and injection logic". OTel's own vocabulary is `trace_id`/`span_id` (`TraceId` 16-byte, `SpanId` 8-byte) plus optional `TraceFlags`; in the Logs data model `TraceId`/`SpanId` are optional and "can be set for logs that are part of request processing". **Spans describe the call, not the side effect**: a `Span` "represents a single operation within a trace" and encapsulates span name, immutable `SpanContext`, parent, `SpanKind`, start/end timestamps, `Attributes`, `Link`s, `Event`s, `Status`; the span name "SHOULD be the most general string that identifies a (statistically) interesting *class of Spans*, rather than individual Span instances"; there is no before/after value, no resource-state, and no acting-human field. Recording is lossy by design: when `IsRecording` is false "all this data is discarded right away", and the `sampled` flag is only a recommendation. https://www.w3.org/TR/trace-context/ , https://www.w3.org/TR/baggage/ , https://opentelemetry.io/docs/specs/otel/trace/api/ , https://opentelemetry.io/docs/specs/otel/context/api-propagators/ , https://opentelemetry.io/docs/specs/otel/logs/data-model/

**A6** PARTLY TRUE —
(a) PARTLY TRUE — the syslog protocol itself has no integrity mechanism (RFC 5424 §8.7 "Message Integrity" describes damage/tampering as possible; §5 "Any syslog transport protocol MUST NOT deliberately alter the syslog message" only protects in-transit byte fidelity). rsyslog's `omfile` module documents **no hash-chain parameter** — its parameter list is `asyncWriting`, `addLF`, `closeTimeout`, `compression.driver`, `compression.zstd.workers`, `createDirs`, `cry.Provider`, `dirCreateMode`, `dirGroup`, `dirGroupNum`, `dirOwner`, `dirOwnerNum`, `dynaFile`, `dynaFileCacheSize`, `failOnChOwnFailure`, `File`, `fileCreateMode`, `fileGroup`, `fileGroupNum`, `fileOwner`, `fileOwnerNum`, `followSymlinks`, `flushInterval`, `flushOnTXEnd`, `ioBufferSize`, `rotation.sizeLimit`, `rotation.sizeLimitCommand`, `sync`, `Template`, `veryRobustZip`, `zipLevel` — but it **does** expose `sig.Provider`, with shipped providers "GuardTime Log Signature Provider (gt)", "Keyless Signature Infrastructure Provider (ksi)" and "KSI Signature Provider (rsyslog-ksi-ls12)". So: no built-in hash chain over the log file (TRUE), and not "no signature capability at all" (FALSE) — signing is opt-in, requires an external KSI/GuardTime provider module, and is not part of the syslog protocol or of plain file output. https://www.rsyslog.com/doc/configuration/modules/omfile.html (→ https://docs.rsyslog.com/doc/configuration/modules/omfile.html) , https://docs.rsyslog.com/doc/reference/parameters/omfile-sig-provider.html , https://docs.rsyslog.com/doc/configuration/modules/sigprov_gt.html
(b) TRUE — chattr(1): "A file with the 'a' attribute set can only be opened in append mode for writing. **Only the superuser or a process possessing the CAP_LINUX_IMMUTABLE capability can set or clear this attribute.**" — i.e. root can `chattr -a`. Two further documented caveats: "Setting 'a' and 'i' attributes will not affect the ability to write to already existing file descriptors", and `chattr -R` applies recursively. https://man7.org/linux/man-pages/man1/chattr.1.html
(c) PARTLY TRUE / deployment UNVERIFIED — RFC 5848 "Signed Syslog Messages" exists, Standards Track, May 2010, requiring RFC 5424; it registers SD-IDs `ssign` (`VER`,`RSID`,`SG`,`SPRI`,`GBC`,`FMN`,`CNT`,`HB`,`SIGN`) and `ssign-cert` (`VER`,`RSID`,`SG`,`SPRI`,`TPBL`,`INDEX`,`FLEN`,`FRAG`,`SIGN`), a Signature Block message identified by an SD ELEMENT with SD-ID `ssign`, signer identity = the unique combination of `HOSTNAME`+`APP-NAME`+`PROCID`, recommended `PRI` 110, and IANA registries for Protocol Version (01), Hash Algorithm (1=SHA1, 2=SHA256), Signature Scheme (1=OpenPGP DSA), SG Field, Key Blob Type (C/P/K/N/U). **Wide deployment is UNVERIFIED and unsupported by the evidence found**: rsyslog's official module index (output, input and signature-provider modules) contains no syslog-sign/`ssign` module — its signing story is the external KSI/GuardTime providers — and no other mainstream daemon implementation surfaced in primary sources. The IANA syslog-parameters registry could not be retrieved (HTTP 502) to gauge third-party SD-ID registrations. https://www.rfc-editor.org/rfc/rfc5848.txt , https://docs.rsyslog.com/doc/configuration/modules/index.html

## Group B — approvals / human-in-the-loop

**B1** PARTLY TRUE — GitHub records **who** and an **optional-or-required free-text comment**, but **not** what the approver saw, and documents **no approval timestamp**. Write path: `POST /repos/{owner}/{repo}/actions/runs/{run_id}/pending_deployments` with `environment_ids` (array of integers, required), `state` (required; enum `approved`,`rejected`), `comment` (documented as required, "A comment to accompany the deployment review"); custom-rule path `POST /repos/{owner}/{repo}/actions/runs/{run_id}/deployment_protection_rule` with example body `{"environment_name":"prod-eus","state":"approved","comment":"All health checks passed."}`. Read-back: `GET /repos/{owner}/{repo}/actions/runs/{run_id}/approvals` → `Environment Approval` = `environments[]`(`id`,`node_id`,`name`,`url`,`html_url`,`created_at`,`updated_at`), `state` (`approved`/`rejected`/`pending`), `user` (Simple User: `login`,`id`,…), `comment` (string) — so WHO = `user.login`/`user.id` and `comment` is persisted, not write-only. **WHEN is not documented on the approval object** — `Environment Approval` has no timestamp; the only `created_at`/`updated_at` in that response belong to the nested `environments[]` objects, and deployment/deployment-status timestamps are separate objects. UI contradiction worth flagging: the how-to says "Select the job environment(s) to approve or reject. **Optionally**, leave a comment" while the REST `comment` field is documented as required. **What the approver saw: FALSE** — the approval request payload contains no `sha`/`ref`, and `sha` is documented as "The SHA recorded at creation time" (from `POST /repos/{owner}/{repo}/deployments` body `ref`), i.e. bound at deployment creation, not at approval; the `deployment_protection_rule` webhook's `sha`/`ref` are "Always populated from the check suite, regardless of whether a deployment is created", i.e. outside the persisted approval record. No justification/ticket field beyond free text. Audit log has **no** approval event: `environment.approve` returns zero matches, and the documented `environment.*` events are `add_protection_rule`, `create_actions_secret`, `create_actions_variable`, `delete`, `remove_actions_secret`, `remove_actions_variable`, `remove_protection_rule`, `update_actions_secret`, `update_actions_variable`, `update_protection_rule` — only the last carries approver data and that is configuration (`approvers`, `approvers_was`, `can_admins_bypass`, `prevent_self_review`, `new_value`, `old_value`), not a per-approval record. https://docs.github.com/en/rest/actions/workflow-runs , https://docs.github.com/en/rest/deployments/deployments , https://docs.github.com/en/actions/how-tos/deploy/configure-and-manage-deployments/review-deployments , https://docs.github.com/en/organizations/keeping-your-organization-secure/managing-security-settings-for-your-organization/audit-log-events-for-your-organization

**B2** PARTLY TRUE / mostly FALSE for the granularity claim — **RFC 6749 §3.3** ("Access Token Scope"): "The value of the scope parameter is expressed as a list of space-delimited, case-sensitive strings. **The strings are defined by the authorization server.**" — there is no standard resource-instance or field-level syntax, and the AS "MAY fully or partially ignore the scope requested by the client". **RFC 6750 §3** is explicit that semantics are vendor-defined: "'scope' values are implementation defined; **there is no centralized registry for them**; allowed values are defined by the authorization server." **What a token actually carries:** RFC 6749 §5.1's token response defines only `access_token`, `token_type`, `expires_in`, `refresh_token`, `scope` (an opaque string); `aud`/`sub`/`client_id`/`exp`/`iat`/`nbf`/`iss`/`jti` are **not** RFC 6749 fields — they come from JWT (RFC 7519) and are the RFC 7662 introspection response members (`active`, `scope`, `client_id`, `username`, `token_type`, `exp`, `iat`, `nbf`, `sub`, `aud`, `iss`, `jti`), all OPTIONAL. **RFC 8693** (token exchange, Jan 2020) verified: adds `subject_token`/`subject_token_type`, `actor_token`/`actor_token_type`, `resource`, `audience`, `requested_token_type`, `issued_token_type`, and JWT claims `act` (Actor), `may_act` (Authorized Actor), `scope`, `client_id` — delegation/impersonation only; no resource-instance or field-level restriction field. **RFC 9396 "Rich Authorization Requests" exists** (Standards Track, May 2023) and does add a real fine-grained vehicle: the `authorization_details` request parameter, "an array of objects" each with REQUIRED `type` ("The AS controls the interpretation of the value of the type parameter as well as the object fields that the type parameter allows") and common data fields `locations`, `actions`, `datatypes`, `identifier`, `privileges`; registered by IANA as an OAuth parameter, a JWT claim (`authorization_details` in access tokens) and an introspection response member, with discovery metadata `authorization_details_types_supported` (AS metadata) and `authorization_details_types` (dynamic client registration). Documented examples reach resource-instance granularity (`"identifier":"account-14-32-32-3"`, per-path `permissions` with `path`/`access`) — but this is **API-defined, not standard-defined**, and support is uneven rather than universal: Keycloak ships it (official docs list package `org.keycloak.protocol.oidc.rar` with `AuthorizationDetailsProcessor`, `AuthorizationDetailsProcessorSpi` "as per RAR (Rich Authorization Requests) specification"); no comparable primary evidence was found for other mainstream AS vendors in this pass. https://www.rfc-editor.org/rfc/rfc6749.txt , https://www.rfc-editor.org/rfc/rfc6750.txt , https://www.rfc-editor.org/rfc/rfc7662.txt , https://www.rfc-editor.org/rfc/rfc8693.txt , https://www.rfc-editor.org/rfc/rfc9396.txt , https://www.keycloak.org/docs-api/26.7.2/javadocs/org/keycloak/protocol/oidc/rar/package-summary.html

**B3** TRUE (no such standard) — no mainstream approval mechanism records the information state presented to the approver. Verified negatives: **RFC 9396 §3** imposes a *presentation* obligation only — "When gathering user consent, the AS MUST present the merged set of requirements represented by the authorization request" — while §11.2 leaves "presentation of the authorization details" to deployments; the word "audit" appears exactly once in the whole RFC, in a non-normative appendix describing a field ("This data is provided to facilitate authorization and for auditing purposes"), and nothing requires persisting or exposing what was displayed. **RFC 6749 §4.1.1** defines only the authorization request (`response_type`, `client_id`, `redirect_uri`, `scope`, `state`) — no record of what the user saw. **GitHub's approval record** (B1) stores approver identity + free-text comment with no timestamp, no commit/artifact binding and no audit event. **C2PA 2.1** records content provenance only (assertions `c2pa.hash.data`/`c2pa.hash.boxes`/`c2pa.actions`/`c2pa.ingredient`/`c2pa.metadata`/`c2pa.thumbnail`, the `claim` with `created_assertions`/`gathered_assertions`/`redacted_assertions`, `claim signature`, manifests, ingredients via `hashed_uri{url,alg,hash}`, signer identity and trust list) — it has no approver or UI-state construct. So approval fatigue / rubber-stamping is not detectable from the log: the log records the *decision* and its author, never the *information set* the decision was made on. **UNVERIFIED sub-items:** NIST SP 800-53 Rev.5 AU-3 (and AU-3(1)) content requirements could not be read from a primary source — the OSCAL catalog JSON (raw.githubusercontent.com/usnistgov/oscal-content/main/nist.gov/SP800-53/rev5/json/NIST_SP-800-53_rev5_catalog.json) reaches only the AC family before output truncation, nvlpubs serves a PDF (unsupported), and csrc's control link is a JS catalog; only "AU family = Audit and Accountability" and the existence of AU-02/AU-03 are confirmed, so **do not assert AU-3's field list**. Kantara Consent Receipt v1.1.0 and ISO/IEC 27560:2023 both returned HTTP 403 (kantarainitiative.org, iso.org) — **UNVERIFIED**. https://www.rfc-editor.org/rfc/rfc9396.txt , https://www.rfc-editor.org/rfc/rfc6749.txt , https://spec.c2pa.org/specifications/specifications/2.1/specs/C2PA_Specification.html , https://csrc.nist.gov/pubs/sp/800/53/r5/upd1/final

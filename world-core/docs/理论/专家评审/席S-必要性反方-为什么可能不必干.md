### 1.4 Kubernetes 那一条：本项目最强的外部旁证，本席不隐去，但把它读到底

- ⇒ **正确的类比是：本项目需要的是"给自己的写入路径加一层内容相关的裁判"（一个 admission 层），而不是"造一个语义世界"。** 前者是本席 §六 路线 C 的内容，`席G:761` 逐字估其成本为「**B1–B5 + B9 + B11 + B15 合计约 5–8 人日**」。

### 4.3 作者举的两个真实痛点：是不是"单机单人也照样痛"？——本席逐条判

**痛点一：「Agent 就一遍一遍地截图」**

作者的原始表述被 `席R:302` 逐字抄下：
> 「「现在没有给 Agent 提供相应的接口。以前我们人是使用 system 的，把这个工具用来操控计算机；但是它有一个问题：**我们打进去以后，它的反馈是显示在屏幕上的**，屏幕上的人可以看到。**但是这个 Agent 呢，就一遍一遍地截图**什么的——**它是没有眼睛的，人类没有给它提供眼睛，但是它得模仿人类有眼睛然后再干事**。……」

**判**：**这个痛是单机单人也照样痛的**（本席同意作者）。**但痛的归因不是"缺语义世界"**，`席R` 已把它判到准确的形状：

> `席R:339` 逐字：「⇒ **本席的判（这是我的推断，依据是上引五行）**：**"截图回路"成为主流，机制原因是"**它是唯一不要求应用配合的通道**"**」
> `席R:358-359` 逐字：「**但"它是没有眼睛的"这个修辞要收一收**：**眼睛是有的**（AT-SPI2 的控件树就是眼睛，而且 `01-三者关系论.md:209` 逐字判它"**今天就能做、覆盖一切现有界面**"）。**准确的说法是**：**有眼睛，但每只眼睛都要应用自己长出来**……**agent 用截图，是因为截图是唯一一只不需要应用配合的眼睛，而不是因为它没眼睛。**」

**并且这个痛已经有现成的止痛药，且本项目自己已经登记了**：
> `席R:326-329` 逐字引 `2-依据/06-重复工作审计.md:26`：「\| **CUA**（trycua/cua） \| computer-use 驱动：**AT-SPI/UIA 可访问树 + 输入注入 + 合成光标**；CLI/MCP/SDK 三接口；权限模式 standard/bounded/unrestricted；跨 macOS/Windows/Linux \| ……**Omarchy 已把 `cua-driver-bin` + `cua-hyprland-plugin` 收编进自家打包仓库** \|」；同处引 `2-依据/05-Omarchy机制实证.md:115`：「**不重做**：CUA 回答"agent 怎么操作 GUI"，agentd 回答"agent 能碰什么"——两者是操作层与门禁层的关系，互补不重叠」

⇒ **截图的痛：真痛，但方向是"GUI 操作层"，已有现成实现，且本项目自己写了"不重做"。** 它不构成"造一个语义世界"的理由。

**痛点二：「5 是元还是分」**

这正是当前正文 `:25` 的开篇：
> 「两台机器之间传一句"配额 = 5"。谁都没有看错：一台按自己的协议读，5 就是 5 元；另一台按自己的协议读，5 就是 5 分。**两台都懂自己那一份，可它们说的不是同一件事。**」

**判**：**这个痛点被搬错了场景。**

- **它的原型是跨组织的支付报文**——而正文 `:71` 自己把 `ISO 20022` 列进了"已经通用的东西"那一栏，也就是说**在它真正的战场上，这个问题已经被报文规范解决了**。单位本身的国际标准也不是没有：**[UCUM（Unified Code for Units of Measure）](https://ucum.org/)** 就是干这个的，DICOM 等标准直接指定用它的编码（见 [DICOM PS3.16 变更说明](https://dicom.nema.org/MEDICAL/Dicom/current/output/pdf/part16_changes.pdf)）。
- **在单机单用户下**，"5 是元还是分"的歧义来自**我自己写的两段代码用了两个默认值**。这不是"没有一处能裁"——**在一台机器上，能裁的那一处永远是我自己**。它的解法是**一行 schema 注释 + 一个类型**（或者一个单位字段），不是一本账＋一套词表＋一套门禁＋若干出口。
- 更关键的是：**正文 `:33` 自己已经把这条限定死了**：
> 「**它们之所以能统一，是因为在自己那一套里，值的含义是写死的，而且有一处能裁。**跨过接口、跨过主体，这两样都没有」
  ⇒ **"跨过接口、跨过主体"——单机单人下，主体只有一个，"跨主体"不成立。**

⇒ **本席的推断并合结论**：**这两个痛点里，第一个属 GUI 操作层（有现成方案），第二个属领域 schema（有国际标准）。两个都不足以证明"需要一个新的世界核心"；而《序》用它俩当开篇证据的那套成本结构（平方增长／无权威／归责落空），在单机单人形态下**退化到接近于零**。**

### 4.4 N4 的结论

> **《序》的根是"跨主体的意义不一致"；它的形态是"单机、单用户、不联邦、不多用户"。**
> **这两件事放在一起，等于：一个用来解决多方冲突的东西，被限定在只有一个主体的环境里运行。**
> **本项目自己给出了这个矛盾的三种说法**：正文 `:125`「第二个人不会出现」、正文 `:143`「这需要多方形态，本项目不做」、`WC-PREFACE-LOG-001-v0.2.md:68`「"三方"只指**能力档位**」。
>
> **⇒ 在这个形态里，问题的严重性是被"三方"这个词夸大的。真实的问题规模是："我一个人用几个工具，命名和单位不统一。"**

### 5.5 本席对"替代方案会不会半年后退化"这一条的回答

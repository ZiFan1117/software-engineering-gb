## 一、评审结论

**一句话**：这套系统真正做出来的是**一台高质量的"记账机器"**，而它给自己挂的招牌是"可问责"——**这两者之间差的不是工程量，是制度要素**：v1 交付了"可追溯"，却没有交付"有人必须回答、且回答不足要付代价"。

**要点**：

1. **它的自我定位（§六"把不可追责变成可追责，不把不该做变成不做"）在方向上是对的，但把效力上限划在了一个错误的位置。** 真正的上限不是"能不能判断对错"（那是正当性问题），而是**它只覆盖了主动向世界申请的调用**：一次合规调用内部产生的全部副作用，账本上一片空白（证据见下文 §二.4b / §二.4d）。
2. **"可问责性"的五个要素，它给了一个半。** 可追溯性 ✅（有一处硬伤：`notice` 族完全不过闸）；可归因 ⚠️（记录的是"谁发起了调用"，不是"谁能控制结果"）；**应答性 ❌（v1 明确取消审批通道，`gate.rs:298` 写着"不要等批准，它不会来"）；责任承担 ❌（代码里既无裁决机制也无损失分散机制）；对抗性独立 ❌（单人项目，AI 起草、AI 执行、同一自然人批准与签署，`WC-SDP-001-v0.1.md:18`、`:489`）。** 结论：它的 §六 那句话准确的说法应是"把**无记录**变成**有记录**"。
3. **理论 §4 那条"审计必须区分『人批准』与『人被信息胁迫后批准』"，在实现层面不是"做错了"，而是"被删掉了"——而且删得有文档依据（`WC-R4-DISP-001` E-5 裁定①删 `requires_approval` 字段）。** 但这不是"消除承诺与实现不符"，这是"把承诺本身删掉"。**用一个字段的删除，换掉了一条理论要求**——这是本评审最严重的一条发现。
4. **"判据不在账本里"确实构成理论 §八自己点名的"两本账"危险，而且比它自己描述的形态更隐蔽**：对象与事件不打架（所以它自以为安全），**打架的是"事实"与"裁决事实的法律"**，而这种打架**不报错**，只是让同一本历史账在今天得出与当年不同的裁决结论。**"当时按哪一版法律裁的"必须成为事件。**
5. **日落条款（§六末）在现阶段的口径下是"未检验"，而不是"满足"。** 它的三条判据（审计不集中到厂商 / 世界状态可导出 / 建造者无特权）在单机单人形态下**恰好无法被证伪**——不是因为做到了，是因为还没有厂商、也没有第三方。**而在它自己的死亡判据（§10.2）射程内，有一条已经命中：摘要链是无密钥的 FNV-1a，且整本重写检不出（`系统全景图.md:162` 用例 `c18`）——"审计可篡改"就是"审计不独立"。**

## 二、逐条评审

### 2.1 第 1 问：「把不可追责变成可追责，不把不该做变成不做」这句自我定位准确吗？效力上限划得对吗？

**原文引用**

- `1-理论与哲学/00-理论定稿.md:150`：
  > 所以架构化责任的准确效力是：**把"不可追责"变成"可追责"，不把"不该做"变成"不做"**。
  > 它的上限由此定点：**它能消灭"查无此人"，消灭不了"合法但有害"。**
- `1-理论与哲学/00-理论定稿.md:145-148`：
  > **技术结构能承载"程序"，不能承载"标准"**。……**能**：证明"谁在何时做了什么、有没有越界"——这就是**可问责性**
- `00-总纲.md:243`（铁律 2）：
  > **可问责 ≠ 正确** …… 且证据须**不可否认**——单机审计默认可篡改，须哈希链定期封存别处（07:10）
- `world-core/docs/系统全景图.md:162`：
  > | 7 | 整本重写**检不出** | 摘要链只能检局部篡改；用例名就叫 `c18_chain_cannot_detect_a_full_rewrite` |

**我的判断**

**半准。** 方向对（不把有效性当正当性是好纪律），但**上限划错了位置，且"可追责"这个词用错了**。

**理由**

**(a) 上限划错了：真正的断点在"进入门禁的调用"与"调用造成的世界后果"之间，不在"对错"与"程序"之间。**

理论把上限设在"标准 vs 程序"。但从工程实况看，更紧的一层上限在别处：**账本只记录"有人向世界提出了申请"以及"执行者自报的结果"**。证据：

- `src/carrier/run.rs:209-244`：`undo` 闭包 → `providers::execute(...)` → 结果回写 `inv.result_body(outcome.result, outcome.exit_code, ...)`；`src/carrier/mod.rs:100-116` 说明结果信纸只带 `result`（ok/failed/refused）、`exit_code`、可选 `detail`、可选 `carrier_undo`。
- 全仓 `src/carrier/` 内 **没有** 被执行二进制的哈希、没有 argv 之外的进程身份、没有系统调用级证据（`grep -i 'executable|sha|binary'` 在 `src/carrier/` 下只命中 `command`/`args` 参数名，见 `providers.rs:353-401`）。

所以：**审计粒度 = 一次"能力名 + 动词"**。`job.start` 拿到放行后，那条命令在载体上干了什么，账本里只有执行者自己填的 `exit_code`。**这是我的推断，但推断所依据的字段清单是逐字读来的。** 结论：它连"谁在何时做了什么"里的"做了什么"，在绝大多数动作上都只能给到"申请了什么 + 自报结果如何"。**上限应写成：能消灭"查无此**申请**"，消灭不了"查无此**后果**"。**

**(b) "可问责性"需要五个要素，它给了一个半。** 这是我的专业判断（下同），逐条落地：

| # | 要素（法理上的必要项） | 这套系统给不给 | 依据 |
|---|---|---|---|
| 1 | **可追溯性**：留下可读的、不可否认的记载 | **⚠️ 半**：有记载，但脆弱且有一处结构性破口 | 见下文 (c) |
| 2 | **可归因**：能定位到"当时有控制力的人" | **⚠️ 半**：只到"发起调用的主体"，且主体在 CLI 路径上是自称的 | `src/main.rs:338-341`（`actor` 取自命令行第 4 个位置参数，缺省 `world://user`）；`src/lib.rs:261`（`_ => Ok(())`，即 `notice` 族**完全不过闸**） |
| 3 | **应答性（answerability）**：有一个能要求你解释、你必须回答、回答不足要有后果的对手方 | **❌ 无** | `src/gate.rs:295-303`：`AwaitApproval` 的理由明写"v1 **没有审批通道**（无批准命令、无批准事件）——不要等批准，它不会来" |
| 4 | **责任承担（liability）**：损失落到某个主体、或由机制分散 | **❌ 无**：代码里没有裁决、没有保险池、没有成本承担字段 | `00-理论定稿.md:128-134`（三个归责桶）在 `world-core/src/` 里**零对应物**；`policy.json` 全文 39 行无一处涉及代价承担 |
| 5 | **对抗性独立**：审计不由被审计方独自掌握，且能被非当事人复核 | **❌ 无** | `docs/S0-立项/WC-SDP-001-v0.1.md:18`（技术负责人 `ZiFan`）、`:374`（"执行者 = AI；批准者 = 项目负责人（人）"）、`:489`（批准人 = 项目负责人，"本会话"）；`WC-SQAP-001-v0.1.md:556`（**独立质量部门已被裁剪**，归口由项目负责人兼任） |

**(c) 要素 1 与 2 的两处结构性破口，必须点名：**

- **破口一（审计可伪造）**：`src/lib.rs:261` 的 `_ => Ok(())` 意味着 `commit("notice", 任意 actor, 任意 body)` 不过门禁。这不是我的推测——项目自己的变更台账已经点名：`docs/S0-立项/WC-SCMP-001-v0.1.md:2638`（B-2 高）：
  > **`notice` 家族完全不过门禁**（`lib.rs:191` `_ => Ok(())`）：`world://stranger`/`world://root` 可写账本，**包括伪造的 `gate.rejected`**，事后与真实流水**逐字同形、不可区分**
  我核对了当前源码：`src/lib.rs:260-262` 仍是 `_ => Ok(())`。**一行未加。** 而 `policy.json:26-30` 虽把 `world://agent/*` 的 `writes` 设为 `[]`（这条是后来补上的 S-01 闸，见 `gate.rs:70-76`），`notice` 走的是另一条路，不受它约束。
- **破口二（可归因在 CLI 路径上是自称）**：`src/main.rs:338-341` 由调用者给出 `actor`。`src/channel.rs:169-171` 把身份换成内核（`peer_cred` + `chmod 0600` + `chown`），这是正确的做法——但**只在通道路径上**。CLI 与库 API 两条路径上，`actor` 是自由文本，`main.rs:325` 的用法串甚至没有写上"`[主体]`"这个可选参数的位置。

**(d) "可追责"一词的建议改法**

不建议保留"可追责"，建议改为两句话、并把边界写死：

> **把"无记录"变成"有记录"，把"事后无从查"变成"事后可复核"。**
> 上限：**能消灭"查无此申请"，消灭不了"查无此后果"，也消灭不了"查无此人可担此责"。**

**改法与代价**

| 改法 | 代价 |
|---|---|
| ① `notice` 族必须过 `subject_allowed(actor)`，且 `gate.*` 前缀的类型保留给内核内部主体（`WC-SCMP-001-v0.1.md:2638` 的建议就是这个） | 小。一处 `match` 分支 + 两条用例。**不做的代价：全部审计结论可被一行伪造** |
| ② 账本事件里的 `actor` 与"身份来源"分离：新增 `actor_src`（`kernel` / `cli-self-claimed` / `api-caller`） | 小。但会让"CLI 自称"这个事实**永远留在账上**——这正是审计要的 |
| ③ §六 的定位句改写（见上） | 零工程代价，但有**立场代价**：承认自己交付的是"可追溯"而不是"可问责"，会削弱"架构化责任"作为破局点（`00-理论定稿.md:243-247`）的论证力度 |

### 2.2 第 2 问：「审计必须区分『人批准』与『人被信息胁迫后批准』」——工程上该长成什么样？为什么"取消批准"是逃避？

**原文引用**

- `1-理论与哲学/00-理论定稿.md:102`：
  > - **审计必须区分"人批准"与"人被信息胁迫后批准"**（记录批准的语境）。
- 同篇 `:81`：
  > 3. **反噬**：监督行为本身改变责任结构——**批准即背书**，人批准过的事故反而锁死追责。
- `src/gate.rs:38-43`：
  > 只有一个字段是**刻意的**（`WC-R4-DISP-001` §三 **E-5** 裁定①：删字段）：原先还有一个 `requires_approval`，但它不参与裁决（`decide` 只读 `reversible`），却让 `policy` 子命令打印出"不可逆 → 加摩擦（需批准）"——而 v1 **没有审批通道**……承诺与实现不符 ⇒ 删除该字段
- 全仓核对：`grep -i approval src/**/*.rs` 在 `src/` 下**零命中**（仅 `tests/contract.rs` 与 `docs/` 提及历史字段）。

**我的判断**

**这条理论要求在工程上从未被实现过，而它的"处理方式"是删掉那个提示字段——这是把要求删了，不是把要求做了。** 更严重的是：**当前设计在"批准即背书"这条反噬上，不是减轻，是加重**，因为它把不可逆动作集中给了白名单主体（出厂策略里就是 `world://user`，即"人"），却**不留下任何可用来抗辩"我当时是被信息结构胁迫的"的证据**。

**理由（工程落点：为什么不是"记一句同意"就够）**

"信息胁迫下的批准"在法律上不是"没有批准"，而是**批准有效但可被质疑其意思表示的真实性**。要能在事后做这个区分，审计里必须能重建**当时的"信息环境"**——不只是"谁点了是"。这就决定了记录结构至少要有五个要素：**批的是什么、批的时候看见了什么、有多少时间、有没有别的选项、依据哪一版法律**。

**具体记录结构（字段级建议）**

建议新增一个事件族 `decision`（或复用 `notice` 加 `type=approval.*`，但**不建议**——`notice` 现在不过闸，见 §二.1），并让"批准"成为**一条独立事件**，而不是某个字段：

```jsonc
// ── ① 请求被呈现给人：这是"语境"的锚点 ─────────────────────
{
  "kind": "notice",
  "actor": "world://core",              // 由内核写，非请求方写
  "body": {
    "type": "approval.requested",
    "subject": "world://user",
    "payload": {
      "req_id":        "r-B",                    // 配对键（已有口径）
      "trace":         "e…489-0",                // 指向那条被拦下的 act
      "act_digest":    "fnv1a64:…",              // ★ 被批动作的规范化摘要，防止"批 A 执行 B"
      "capability":    "ledger.compact",
      "verb":          "install",
      "params_digest": "fnv1a64:…",              // ★ 参数也入摘要（现在 params 完全不参与裁决）
      "law":           "fnv1a64:…",              // ★ 当时生效的 policy 内容地址（见 §二.3）

        "redirect":    "file:…",                 //   全文另存（管道，不占主干道）
        "facts": [                               // ★ 结构化事实：人能核，机器也能核

        ],
        "model_claims": ["…"]                    // ★ Agent 对本次动作的自述，原样入账
      },
      "state_fingerprint": "fnv1a64:d55f80…",    // ★ 递交时人看到的世界状态指纹
      "presented_at": 1790000000
    }
  }
}

// ── ② 人的决定：批准 / 拒绝 / 沉默超时 ──────────────────────
{
  "kind": "act",                          // 建议用 act：它必须过闸（notice 不过闸）
  "actor": "world://user",
  "trace": "e…（approval.requested 的 id）",
  "body": {
    "capability": "gate.approve",         // 门禁里声明为 reversible=true（可撤销）→ 免检但留痕
    "verb": "grant",
    "request_id": "r-B",
    "params": {
      "decision":        "granted",       // granted | denied | expired
      "decided_at":      1790000042,
      "latency_secs":    42,              // ★ 决定用了多久——"是否被催促"的第一手证据
      "modality":        "interactive",   // ★ interactive | batch | api | on-behalf
      "decider":         "world://user",
      "decider_auth":    "kernel-peercred", // ★ 与 actor_src 同源；批准尤其不能自称
      "reason":          null,            // 人可留可不留
      "alternatives":    ["deny", "defer"], // ★ 当时有没有"不做"这个选项（见下"必答题"）
      "time_pressure":   null             // ★ 例：{"deadline":…, "consequence":"任务中断"}
    }
  }
}
```

**为什么这五个要素缺一不可（法理上的对应）**

| 字段 | 它防的是什么 | 不记它会怎样 |
|---|---|---|
| `shown.text_digest` + `redirect` | **"我当时看到的不是这个"** | 事后只能拿今天的模板去猜当时显示了什么。**注意**：`src/lib.rs:299-304` 现在**已经**把 `reason` 原文写进 `notice` 了——这是**同一思路的雏形**，但它只覆盖"被拒绝的理由"，不覆盖"被请求批准时呈现的信息" |
| `state_fingerprint` | **"世界的实际状态与当时不同"** | 读模型是 `fold(账本)`，随时可重算；重算用的是**今天的**账本。人不记指纹，就无法证明他当时是基于哪份状态做的判断 |
| `presented_at` / `decided_at` / `latency_secs` | **"我只有三秒钟"** | 这是"信息胁迫"最可操作的代理指标。**当前账本有时间戳**（`src/event.rs:32` `at`），但只有秒级、且**没有任何关于"何时被请求 / 何时被告知"的字段** |
| `alternatives` | **"它没告诉我可以不做"** | 胁迫的核心是"选项集被隐藏"。**这一条是批准语境里最贵也最重要的一项** |
| `act_digest` / `params_digest` | **"批 A、做 B"** | `src/gate.rs:269-307` 的 `decide()` **只读 `capability` 与 `verb`**，从不读 `params`。所以"批准"若只按能力名绑定，**同一个能力下换参数不构成新请求** |

**为什么"干脆取消批准"是逃避，而不是解决**

三层理由，逐层加重：

1. **它把"不可追责"改成了"明文的未授权"**。原来的问题是"人批了，事故反而锁死追责"（`00-理论定稿.md:81` 的反噬）。v1 的处置是**不让任何人批**，于是不可逆动作只剩白名单主体能做。但白名单在出厂配置里就是"世界的主人"（`policy.json:32` `"irreversible_actors": ["world://user"]`）——**这不是取消了责任转移，这是把责任转移**到了唯一那个人身上，并且**不再有任何记录能说明他当时是否被充分告知**。这是我读代码得出的判断。
2. **它让"待批"这件事永远无法闭合**。被拦下的动作会写一条 `gate.awaiting-approval`（`src/lib.rs:305-313`），但**没有任何事件能把这条待批关闭**——没有批准事件、没有过期事件、没有"改由白名单主体执行"的关联事件。于是"待批集"是**只增不减**的。而 `WC-FSR-001-v0.1.md:256`（`REQ-F-012`）写的恰恰是"待批集由日志派生"。**一个只增不减的集合不是一个集合，是一堆流水。**
3. **它在源码注释与拒绝理由里主动引导绕过**：`src/gate.rs:298-299` 逐字写着"**不要等批准，它不会来**"。从制度设计角度看，这句是**反控制的**：它明确告知被管者"此路不通，请另行处置"，而"另行处置"必然发生在**账本之外**（人自己去做、用别的工具做、走没有门禁的路径）。**结果是：需要加摩擦的动作，摩擦把工作推出了审计面。** 这比没有门禁更糟——没有门禁时你至少知道没人管；有了这套之后，账本会呈现一个"世界很干净"的假象。

**改法与代价**

| 改法 | 代价 |
|---|---|
| ① 落地一个**最小**审批通道：`gate.approve` 能力 + `decision` 事件 + `req_id` 配对（**不新增真相源**，批准本身就是一条 `act`） | 中。约等于新增一个事件族 + 一条消费路径。**这是我最强烈建议的一条**，因为它是"应答性"这个要素从 ❌ 变 ⚠️ 的唯一路径 |
| ② 落 `shown.text_digest` 与 `state_fingerprint` | 小-中。需要一个人向端口的呈现记录点。**注意**：若呈现由投影层产生，则必须避免"投影持有状态"（`2-依据/15-世界核心的组成与职责.md:252` 的漏水信号清单）——建议只由内核在递交瞬间落纹 |
| ③ 加 `decided_at` / `latency_secs` / `alternatives` | 小 |
| ④ `params` 参与裁决或至少参与"批准绑定"（`params_digest`） | 中。会碰到 `WC-IC-001-v0.1.md:740` 已登记的未决项 6（"`Policy::decide` 是否纳入 `verb`/`params`"） |
| **不做①-④的代价** | **这套系统在"批准"这件事上不可问责，而在"不批准"这件事上不可用。**它会长期停留在"记账机器"形态 |

### 2.3 第 3 问：判据不在账本里（权限被重算而非被记录）——会不会构成理论自己点名的"两本账"？

**原文引用**

- `2-依据/15-世界核心的组成与职责.md:258-264`：
  > **账本 = 语义事件；本体实例（对象/状态）= 它的投影。任何"直接改对象"的写入路径都不允许存在。**
  > **为什么必须立这条**：最糟的情况不是"选错账本"，而是**两本账**——对象存一份、事件存一份，两边各自演进 → **必然对不上，而且对不上时你不知道信谁**。
- 同篇 `:316`（待定的洞 #2，**项目自己已经看见**）：
  > **权限也必须从事件派生**——否则权限就是第二本账。具体怎么落（挂读模型上？独立权限读模型？）
- 实现实况：
  - `src/event.rs:26-37`（`new_event`）与 `ontology.json:7-23`：信封 = `world, kind, id, seq, at, actor, flags, body` + 可选 `to, trace`。**没有 `law` / `policy` / `vocab` 任何一项。**
  - `src/ontology.rs:129-146`：**本体（词表）有内容寻址** `vocab_hash`（非加密 FNV-1a，`:142-143` 自述"不得用于安全判断"）。
  - `src/gate.rs:109-117`：`policy` 字段只校验 `version == 1`（**硬编码的数字，改它就拒启**），**策略没有内容地址**。
  - `src/gate.rs:309-326`（`summary()`）输出 `policy`、`path`、`capabilities`、`subjects_allow`——**这是打印，不是入账**。
  - `grep 'policy\.change|ontology\.change|law\.change'` 全仓 **零命中**。

**我的判断**

**是，构成"两本账"，而且形态比项目自己描述的那种更隐蔽——它不会"对不上"，只会"悄悄地换个答案"。** "当时按哪一版法律裁的"**必须成为事件**。

**理由**

**(a) 事实与判据现在是分开存储、分开演进的。** 这是"两本账"的定义逐字命中：账本存"发生了什么"，`policy.json` 存"什么算允许"，两边各自演进，**没有任何东西把两者钉在一起**。区别只在于：对象 vs 事件的"两本账"会**打架**（`readmodel.rs:143-153` 会报 `BeforeMismatch`），而事实 vs 法律的"两本账"**不会打架**——所以它不会被任何现有用例发现。

**(b) 三个具体的现实后果：**

1. **历史合法性不可自证。** "上周这个动作合法吗"这个问题，账本本身**答不了**。今天的人只能精算：拿出**今天的** `policy.json`，用**今天的**主体白名单去复核**上周**的事件。如果上周的 `subjects.allow` 与今天不同（比如 agent 前缀规则被收窄），复核结论就是错的，而且**错得没有任何提示**。
2. **法律变更不留痕。** `policy.json:6-9` 自称"本文件是『法律』：改它等于改契约，走 R5 框架变更评审"——但**R5 是文档流程**（`WC-SDP-001-v0.1.md:704`、`:1937`），**不是账本里的事件**。所以"法律被改过"这件事**在世界里没有发生过**。这是最刺的一点：**一个把"事件是唯一真相"当宪法的系统，让它的宪法本身不产生事件。**
3. **重放的确定性丢失。** `2-依据/15-世界核心的组成与职责.md:151-154` 承诺"可复盘 = 读日志；可回滚 = 追加补偿事件"，`00-总纲.md:23-24` 把"事件是唯一真相"当裁决。但"同一本账 + 不同 `policy.json` ⇒ 不同的裁决分配"意味着：**这本账的解释不是账本的函数，还依赖一个账本外、无版本、无痕迹的文件。** 它失去了"唯一真相"这个身份的一半。

**(c) 顺带一处不对称，值得记下来**：**法律的两半，做了寻址的只有"形状"那一半。** 本体（词表）有 `vocab_hash` 并用于投影同源核对（`docs/系统全景图.md:128`）；**门禁策略（权限）没有内容地址**。所以"同一个 `capability` 名，在两版策略下含义不同"这件事，**机器无法发现**。

**最小改法：事件字段草案**

原则：**只加可选字段，不新增真相源，不引入第二个权威。** 改动面 = `event.rs` 的构造器 + `gate.rs` 的加载期算一个内容地址 + `ontology.json` 的 `envelope.optional`。

```jsonc
// 信封新增（与 to / trace 同级；即 2-依据/15 §5.2 的"主干道上只放 hash 引用"）
{
  "law": {
    "policy": "fnv1a64:9c1f…",   // ★ policy.json 的内容地址（沿用 ontology.rs 的 strip_comments + 规范化口径）
    "vocab":  "fnv1a64:4a02…",   // ★ 当时加载的 ontology 内容地址（现只在内存里算，从不入账）
    "world":  1
  }
}
```

**配套的三条口径（缺一条这个字段就白加）**：

1. **`law` 必须由内核在 `commit` 里填，不接受调用方给**——否则它和现在的 `actor` 一样可自称。落点：`src/lib.rs:194-198`（`commit_verbatim` 造信封处）。
2. **`gate.*` 流水（`record_gate_notice`，`src/lib.rs:291-314`）必须同样带 `law`**——拒绝/加摩擦的裁决尤其需要"当时按哪版法律拒的"。
3. **复核/重放时，按事件自带的 `law` 去判定，而不是按当前 `policy.json`**；账本若含多个不同 `law` 值，**必须显式报告"跨法律事件"**，不得静默用单一策略重放。（这与 `WC-CKFMT-001.md` 的"版本不匹配即硬拒、不得猜测"是同一种纪律，`docs/阶段外-待启用/S2-设计/WC-CKFMT-001.md:219`、`:458`。）

**代价（必须诚实说）**

- **字段语义要写死**：`law` 是"裁决时所依据的法律文本"，**不是**"当前法律"。若不写死，将来会有人把它当"法律现在是什么"读——那就是新的误读源。
- **对旧账本**：按项目既有纪律（`WC-CKFMT-001` 的"版本号只增不改、读到旧版即拒绝读取并降级"），无 `law` 的旧账应**允许读、但拒绝用于"当时合法性"的复核**，并把这一点在输出里说清，不得猜。
- **不能解决跨账本问题**：若账本被整体换掉（`c18` 的边界），`law` 也一起被换掉。**这个字段解决的是"法律漂移"，不解决"账本伪造"**——后者见 §二.6 与 §四.C。

### 2.4 第 4 问：五个场景——制度上应该怎样

#### (a) 不可逆动作被白名单主体执行了，事后发现是错的：谁的责任？系统能提供什么证据？

**原文引用**

- `1-理论与哲学/00-理论定稿.md:124-134`：
  > ### 5.3 归责 = 落在把事件组织成行动形状的人
  > 不落在 Agent（事件无归责），落在**设计意图的植入者（厂商）**与**任务的发起者（使用者）**。
  > **场景归责三桶**（不切比例，一桶一个机制）：设计缺陷致错 → 厂商；任务指令致错 → 使用者；分布内随机错 → 谁都没错 → 保险池
- `1-理论与哲学/00-理论定稿.md:267-277`（§10.3 两步判定：可预见 → 厂商；不可预见但已充分告知 → 使用者）
- `policy.json:32`：`"irreversible_actors": ["world://user"]`

**制度上应该怎样**

1. **责任落点**：按它自己的三桶，落在**厂商**（设计缺陷）或**使用者/发起者**（任务指令）。**但必须加一句它没写的**：执行不可逆动作的"白名单主体"，在法律上通常是**控制者本人或其受托人**——在出厂配置里就是 `world://user`。**这是一次自我归责，不是一次责任分配。** 制度语言里，把责任集中到一个自然人身上，且该自然人同时是受益者与批准者，**不构成"可追责"，只构成"可自担"**。这是我的判断，依据是 `policy.json:32` 与 `WC-SDP-001-v0.1.md:374`（执行者 = AI，批准者 = 项目负责人）的同构。
2. **举证责任的分配应当是**：系统主张者证明"动作在授权范围内"（有 `act` + 白名单 + 法律版本）；受害/受损方主张"结果超出合理可预见范围"——而**这一点恰好是账本现在无法支撑的**，因为账本不知道当时的可预见范围。**这是我的推断，但它直接由 §10.3 的两步法推出**：两步法的第 1 步问"是否落在合理可预见的使用范围内"，而"范围"在实现里**没有任何承载物**。
3. **应该提供的证据**（按重要性降序，且区分"能"与"不能"）：

| 证据 | 现在有没有 | 出处 |
|---|---|---|
| 动作意图（能力 + 动词 + 请求号 + 参数） | ✅ | `src/event.rs:82-89` |
| 因果链（结果事件 `trace` 指回意图） | ✅ | `src/event.rs:50-56`；`docs/系统全景图.md:70`、`:76-82` |
| 回退所需旧值（`change` 必带 `before`） | ✅ | `src/event.rs:75-79`；`src/readmodel.rs:143-153` |
| 载体撤销点引用 | ✅ | `src/carrier/mod.rs:100-116`（`carrier_undo`） |
| 动作前后的世界状态指纹 | ⚠️ 需另算（`state` 不含历史时点） | `src/readmodel.rs` 只有折叠后的当前状态 |
| **是谁批准的、他被展示了什么** | ❌ | 见 §二.2；审批通道不存在 |
| **当时依据哪一版法律** | ❌ | 见 §二.3 |
| **被执行的是什么二进制/依赖，其哈希** | ❌ | `src/carrier/` 只记 `command`/`args`（`providers.rs:353-401`） |
| **载体侧实际发生了什么** | ❌ | 结果信纸为自报（`src/carrier/run.rs:232-244`） |
| **独立第三方对上述任何一条的见证** | ❌ | 链无密钥（`src/ledger.rs:562-577`） |

**关键判断**：**它现在能证明"有人申请过并自称成功"，不能证明"实际发生了什么"。** 对(a)这个场景，制度上最需要的恰好是最后两条——**因为"事后发现是错的"中的"错"，通常是对事实的错判，而不是对权限的错判**。

#### (b) 一个动作被门禁拒绝，但请求方改用 `change` 绕过去了——现在的机制拦得住吗？为什么？

**原文引用**

- `src/lib.rs:151-157`：
  > 原实现只裁决 `act`，理由是"`change` 只是记录"。这个理由**站不住**：`change` 恰恰是**唯一真正改状态的写原语**……于是"被拒绝的动作"完全可以用一条 `change` 静默达成——`actor` 与 `subject` 之间约束为零。**"门禁不可绕过"当时是假的**，现在由 `Policy::authorize_write` 补上。
- `src/gate.rs:222-244`（`authorize_write`）：不在 `subjects.allow` → 拒；`writes` 里没有该主体 → 拒；subject 不匹配任何 pattern → 拒。
- `policy.json:25-31`：
  > `"world://user": ["world://*"]`, `"world://core": ["world://*"]`, `"world://agent/*": []`

**我的判断**

**这条路现在堵住了（在出厂配置下），而且是这一轮里质量最高的一处修复。但它只是"这一条路"堵了，另外三条路是敞的。**

**理由——拦得住的证据**

- agent 的 `writes` 是**空数组**（`policy.json:30`），所以 agent 做任何 `change` 都被 `authorize_write` 里 `patterns.iter().any(...)` 判假而拒绝（`gate.rs:233-242`）。**这条设计是对的**：宿主（人）对自己的世界有主权，agent 只能通过 `act` 请求、由世界代它落 `change`（`policy.json:26` 的注释原文）。
- 拒绝时**留痕**：`gate.write-rejected`（`src/lib.rs:250-258`）。"被拒绝也留痕"这条口径落到了 `change` 上。

**为什么它还不算"不可绕过"——三条敞着的路**

1. **`notice` 可伪造（最严重）**：`src/lib.rs:261` `_ => Ok(())`。**一个被拒的 agent 完全可以直接写一条 `notice`，把 `type` 写成 `gate.rejected`——事实上它伪造的"批准痕迹"与真实的拒绝流水逐字同形、不可区分**（`WC-SCMP-001-v0.1.md:2638` 的原话）。审计系统里最不能缺的就是"拒绝的记载"，而这份记载现在是任何人都能印的。
2. **参数不参与裁决**：`gate.rs:269-274` 取 `capability` 与 `verb`，**`params` 从不参与**。所以"换个参数再来一次"永远不需要绕过——它本来就是一次全新的、会被放行的请求。**这是我的推断**，依据是 `decide()` 的取值面，与 `WC-IC-001-v0.1.md:740`（未决项 6：是否纳入 `verb`/`params`）互证。
3. **嵌套执行（最需要立法处理的一条）**：门禁裁决的是"这次能力调用"，而**这次调用内部的副作用不在裁决范围**。`job.start` 是可逆能力（`policy.json:17`），它接受 `command` 与 `args`（`src/carrier/providers.rs:353-401`）。于是：**一次被放行的、可逆的、免检的 `job.start`，可以在载体上执行任意命令**——下载、安装、覆盖文件、连网。账本上它是"一条可逆动作，已放行"。**这是我的推断，依据是能力清单（`policy.json:14-23` 无细粒度动词分类）与 `job.start` 的参数面。** 理论侧对此已有自觉（`00-理论定稿.md:188` "三方之间没有直连……只跟账本对齐"），但**"调用内部"这一层从未被列入裁决面**。

**改法与代价**

| 改法 | 代价 |
|---|---|
| ① `notice` 过闸（同 §二.1 改法①） | 小 |
| ② `params_digest` 入账 + 高摩擦能力的参数进入审批绑定 | 中。需要一套"哪些能力的哪些参数算实质"的规则，而规则本身就是新的裁量面 |
| ③ 嵌套执行的**声明纪律**：需要 `job.start` 之类"能起任意命令"的能力时，把待执行命令的**内容摘要与来源**作为 `act` 的必填 `params`；载体侧执行前核对摘要 | 中-大。这是把门禁从"能力粒度"推到"调用内容粒度"的实质一步。**不做的代价**：门禁的强度等于"最宽松的那条可逆能力"的强度 |

#### (c) 门禁策略被部署方改了，导致上周合法的事今天非法——历史结论怎么办？

**原文引用**

- `policy.json:5-10`：
  > `"本文件是『法律』：改它等于改契约，走 R5 框架变更评审"` / `"策略在启动时一次读入内存，运行中不重读：磁盘上改了要重启才生效"`
- `src/gate.rs:109-117`：策略版本只有 `version != 1` 的硬校验。
- `docs/S0-立项/WC-SDP-001-v0.1.md:704`：R5 是**文档流程**（"框架变更评审"），不是账本事件。

**我的判断**

**历史结论会被静默改写。这不是"以后注意"的问题，是"账本的核心承诺（可复盘）在当前设计下不安全"的问题。**

**理由**

- 今天的复核脚本（人工或机器）拿的是**今天的** `policy.json`。它看到的是一堆 `act` 事件，然后**按今天的法律重新裁决**。结论：**同一本账，两套答案**。
- 两个方向都出错，且都不报警：
  - **收紧型变更**（上周允许、今天不允许）→ 复核把上周**合规**的动作判成**越界**。这是**假不符合项**，会让人对整套审计结论失去信任；
  - **放宽型变更**（上周不允许、今天允许）→ 复核把上周**真实的越界**洗成正常。这是**漏检**，更危险。
- **`00-总纲.md:243`（铁律 2）** 要求"证据须不可否认"。**一个判据会随部署方心情变化的证据体系，不满足"不可否认"。**

**制度上应该怎样（三步，按顺序）**

1. **把"法律"变成账本内的对象**：策略与本体都内容寻址（`law` 字段，见 §二.3），**每条事件带上裁决时的法律地址**。
2. **法律变更本身成为事件**：部署方替换法律时，内核必须写一条 `notice`（建议 `type: "law.changed"`），带旧地址、新地址、变更者、生效时点。**没有这条，"法律改过"在世界里就没有发生过。**
3. **复核必须按事件自带的 `law` 判**，或至少**显式报告"该事件按 X 版法律裁决，当前法律为 Y 版"**，并禁止在跨版本时给出"合法/非法"的单一结论。

**最小改法（与 §二.3 同源，合并实施）**：`law` 字段 + `law.changed` 事件 + 复核输出中的跨版本提示。**改法本身很小；它的意义在于把"法律"从部署方的私有文件，提升为世界自己的历史的一部分。**

#### (d) 出事了要复盘，但**账本之外**的动作（那些没写进账本的、载体侧干的活）怎么交代？

**原文引用**

- `world-core/docs/系统全景图.md:41-42`（载体执行器）：
  > ⚠️ 它对账本**零写权限**；它写世界的唯一通道是上面那条线
  > ⚠️ 它**可以拒绝**（清单没有、连不上内核），**永远不能放行**
- 同件 `:139-151`（已经成立项）：
  > 三进程形态 | 内核唯一可写；适配器连不上内核即**拒绝执行**且**零副作用**
- `src/carrier/run.rs:154-254`（`attempt`）：① 先问内核拿"通过" → ② 才动载体 → ③ 结果回写。
- `docs/系统全景图.md:162`（边界第 7 条）：整本重写检不出；`:158`（边界第 3 条）：静态墙"**只看 mode 位，不看属主**"，属主由部署方 `--owner-uid` 显式断言，**没人传它就不跑**。

**我的判断**

**这个问题要分两半，两半的处境完全不同：**

**前半：同一世界内的动作绕不过门禁——这一半是真的做到了，而且做得漂亮。**

它是**结构性的**，不是承诺：载体执行器先向内核要"通过"，拿不到就一次都不动（`src/carrier/run.rs:154-203`）；载体对账本零写权限（`src/carrier/mod.rs:39-45`）。**这是我在本次评审里唯一愿意说"这是真的"的一项。**

**后半：但那条边界是"进程边界 + 权限位"，而不是"制度边界"。** 三处具体：

1. **它靠部署方不偷懒。** 静态墙只看 mode 位；属主断言要人显式传 `--owner-uid`，"没人传它就不跑"（`docs/系统全景图.md:158`、`src/guard.rs:130-131`；`00-总纲.md:495-496` 自首第 7 条亦承认"当前 `管` 仍靠 agentd 自律"）。**部署方懒一次，整个"不可绕过"就没有了——而账本上不会留下"这次部署没有开属主断言"的痕迹。** 这是我的推断，依据是 `--owner-uid` 只在 `check` 子命令路径内生效（`WC-LLD-001-v0.1.md:28`、`:355`）。
2. **载体内部的副作用，账本不知道。** 账本记的是执行者自报的 `result`/`exit_code`（`src/carrier/mod.rs:100-116`）。一次 `job.start` 内部的下载、安装、写文件，**在账本上就是一条 `act`**。
3. **最强的一处：账本不知道"账本之外还有东西"。** 没有任何机制在报告"本次复盘覆盖了 87% 的动作"或"以下时间段载体侧无观测"。**一个不知道自己在哪漏的审计体系，比一个明确说自己只覆盖 x 的体系更危险。**

**制度上应该怎样**

1. **必须在账本上把"观测面"写清楚**：每条结果事件应带 `evidence: {source: "carrier-self-report" | "kernel-observed" | "third-party"}`，**自报就是自报，不得当作实证**（字段草案见 §二.2 的 `modality` 同源思路）。
2. **被管者不可写域必须由内核自证**：属主断言不该是"部署方工具"，应是**启动的硬条件**；做不到时应**拒绝启动**并留一条事件——`src/guard.rs:27-28` 的"带病运行比不运行更危险"这条纪律，应当同样适用于"没有属主断言的部署"。
3. **回执协议化**：载体的回写不应只有一句自报结果，应至少包含被执行对象的**内容引用**（该二进制/包的哈希）+ 副作用清单（`2-依据/15-世界核心的组成与职责.md:159` 已定的口径："运单号 = 内容 hash"）。

**代价**：②会**破坏当前的安装便利**（部署方必须正确传参，否则世界起不来）。这是一个真实的取舍，但按项目自己的纪律（`policy.json:7`、`src/guard.rs:27-28`），应当选"拒启"。

#### (e) 人不在场 24 小时，事后要回答"发生了什么、哪些在等我批"——现在能答吗？缺什么？

**原文引用**

- `00-总纲.md:29-30`：
  > **常设验收（一条）**：**人离开 24 小时后回来，能答出"发生过什么、哪些在等我批"**——不靠人盯守。
- `world-core/docs/系统全景图.md:156`：
  > | 1 | **v1 没有审批通道** | 不可逆动作只认白名单主体；被摩擦的主体拿到的是"不要等批准，它不会来" |
- `src/lib.rs:291-314`（`record_gate_notice`）：被拦下的动作留一条 `notice`，payload 只有 `capability`/`verb`/`request_id`/`reason`。
- `docs/S1-需求/WC-FSR-001-v0.1.md:256`（`REQ-F-012`）：
  > `act` 结果须覆盖 `rejected` 与 `awaiting-approval`；"待批集"由日志派生

**我的判断**

**不能答，且缺的不是"展示层"，是"事件族"。这是个概念缺口，不是进度缺口。**

**理由——能答的与不能答的，逐条分清**

| 问题 | 现在能不能答 | 依据 |
|---|---|---|
| "发生了什么"（世界内） | ✅ 能 | 账本按 `seq` 只追加；`read` / `state` / `project` 三个只读命令（`docs/系统全景图.md:127-128`） |
| "哪些动作被门禁拒了/加了摩擦" | ✅ 能（但结论可被伪造，见 §二.1(c)） | `gate.rejected` / `gate.awaiting-approval` / `gate.write-rejected` |
| "哪些在等我批" | ❌ **不能** | 见下 |
| "有哪些事在等我，但根本没人问过我" | ❌ **不能** | 门禁只裁决**被请求过**的动作 |
| "哪些是意图发出但结果没回来的" | ✅ 能 | `src/carrier/recover.rs:92-94`（判据：结果信纸带 `params.result`）+ `carrier orphans` 子命令 |

**为什么"哪些在等我批"答不了——三层，一层比一层根本：**

1. **没有"批准"这个事件**：`gate.awaiting-approval` 只证明"某请求被拦了"，**不构成一个等待中的事项**，因为（i）v1 没有审批通道（`gate.rs:298`），（ii）没有任何事件能关闭它。**待批集只增不减**——而"集合"这个概念要求有成员判定，只增不减的流水线不是集合。
2. **即使白名单主体自己做了那件事，也没有任何东西把两件事连起来**：出厂策略下 `irreversible_actors = ["world://user"]`，若主人回来自己执行了它，那是一条**新的 `act`**，与之前那条 `gate.awaiting-approval` **之间没有 `trace`、没有同一个 `request_id` 的配对口径**。所以复盘时你看到的是"有人申请过、被拒了"和"后来有人做了"，**看不出这是同一件事**。
3. **最根本的一层：账本只包含"主动请求过世界的东西"**。24 小时里没进世界的动作（人自己手动做的、别的程序做的、系统更新做的）**在账本上不存在**。所以"发生了什么"这个问题，账本给的答案**系统性地小于**真实发生的事——而**账本不会告诉你它少了什么**。

**缺什么（清单）**

1. **一个待批事件族**：`approval.requested` / `approval.granted` / `approval.denied` / `approval.expired` / `approval.cancelled`（字段草案见 §二.2）。
2. **一个"世界外动作"的登记入口**：至少允许事后补录（`type: "outside.action.recorded"`，带"事后追认"标记与追认人）。**现在完全没有这类事件。** 尺度上可以很薄：只要求"如果它影响了世界状态，就必须有一条 `change` 说明"，也就是把 `2-依据/15-世界核心的组成与职责.md:258` 的"任何直接改对象的写入路径都不允许存在"从**架构纪律**升级为**可核对的账本事实**。
3. **一个"观测面覆盖"的报告**：`check` 或新子命令输出"本次账本覆盖了哪些通道 / 哪些载体能力 / 哪些时间段无观测"。
4. **（制度面，技术上补不了）"人不在场时谁有权批"**：这不是技术选型，是授权链问题。**v1 用"白名单主体"回答了它**（`policy.json:32`），这个回答在单机单人是自洽的，**但一旦有第二个主体，它就退化为"谁拿到主人身份谁就能做不可逆动作"**。这是我的判断。

**改法与代价**：①②需要新事件族与一条消费路径（中等）；③是输出层（小）；④是制度设计，且**不能由建造者单方面定**——按 `00-总纲.md:245`（铁律 4"建造者无特权"），这一条应由使用者自己写进 `policy.json`，而**现在 `policy.json` 里没有表达"谁有权批"的任何字段**（只有"谁能直接做"）。

### 2.5 第 5 问：「产权三档」只做了一档——缺口有多严重？不补会带来什么现实问题？

**原文引用**

- `1-理论与哲学/00-理论定稿.md:110-116`：

| 档 | 区域 | 效力来源 |
|---|---|---|
| 真业主区 | 平台、云端数据 | **许可边界**（能用，墙不能拆） |
| 无业主区 | 开源、协议、公共数据 | **惯例与互惠**（不是"权限有限"，是**谁都够不着**） |
| 全产权区 | 本地文件 | 完整 |

  > **越过产权边界的声明，自始无效**（碰平台权利、碰第三人权利）。
- 实现实况：`policy.json` 全文 39 行，**无任何"场所/产权"字段**；`Capability` 只有一个字段 `reversible`（`src/gate.rs:44-48`）。唯一沾边的是载体侧执行清单里的 `"sandbox"`——而它是"v1 只登记，不实施"（`src/carrier/capd.rs:79-80`），且 `grep -i 'landlock|seccomp' src/**/*.rs` **只命中一句注释**（`src/guard.rs:33` "不做 Landlock / seccomp 自缚"）。

**我的判断**

**缺口的严重性不在工程侧（少写一个字段），而在理论侧：§5.1 的"产权三档"是这套理论里对"效力上限"最诚实、最有价值的一段——而它现在是一个没有实现、没有测试、也没有工程落点的规范断言。** 更麻烦的是，**代码里的实际模型会反向固化一个错误的直觉**："世界内的场所 = 本地文件 = 全产权"。

**严重性分三层：**

1. **理论层**：这是"声明即请求"**唯一**的效力来源（`1-理论与哲学/00-理论定稿.md:108`："它的效力上限是**使用者的受限产权**"）。**效力来源只做了一档，等于效力上限没有被真正确立。**
2. **协议层**：能力（capability）上现在只有一个 `reversible` 布尔。**"产权"永远不是动作的属性，而是场所/对象的属性**——一个动作是否越界，取决于它作用于哪。所以这个缺口**不是"缺个字段"，是缺一个维度**。
3. **合规层**：**账本会在最需要它准确的时候给出一个自信的错误答案。** 因为"我本地有一份副本"（全产权）与"我有权这样使用它"（许可边界）是两件不同的事，而现在的模型把它们合并了。

**不补会带来什么具体的现实问题（三个真实场景）**

- **场景一：平台 API。** Agent 用某平台凭证调接口批量导出数据。在世界里，动作是本地发起的、可逆的、免检的 ⇒ 账本给出"**已合法执行，无需摩擦**"。而**效力边界其实在平台方**：凭证可被随时吊销，条款可随时变，导出规模可能有硬限制。**"世界内合法"与"平台方许可"是两个不同的法域**，账本只记前者。（这是"真业主区"：能用，墙不能拆——`00-理论定稿.md:112`。）**现实后果**：账号被封、数据被要求删除时，账本提供的"合规记录"**在平台侧完全无效**，甚至可能因为"你有完整记录"而更容易被认定为**明知故犯**。**这是我的推断，但推断的依据是"记录的存在会改变过错的认定"这一常规法理。**
- **场景二：开源数据。** 理论说无业主区的效力来源是"惯例与互惠（不是权限有限，是谁都够不着）"（`:113`）。但**robots.txt、爬取频率约定、数据集许可、Depot 条款都不是"够不着"，是"有约束但无权利人"**。一个 agent 批量抓取并用于训练的流程，在账本里是"本地文件、全产权、已放行"。**这类争议（代码/作品被用于训练、爬取与条款）恰好发生在"我本地有副本"与"我有权这么用"的缝隙里。** 缺口在这里不是理论瑕疵，是**把行业里最贵的一类纠纷，排除在可问责范围之外**。
- **场景三：第三方权利。** 把含他人肖像的照片、含 GPL 代码的产物、含个人信息的语料上传/转发。**这不是"我和平台"的关系，是"我和第三人"的关系——而三档模型里第三档压根不存在**（真业主/无业主/全产权，都是"我"与"物"的关系，没有"我"与"他人的权利"这一维）。**后果**：这类事故一旦发生，复盘时账本**既不支持"我不知道"（它记了动作）也不支持"我尽力了"（它没记你查过什么权利状态）**。

**不补的总体代价（一句话）**：**它只在"三档恰好重合"的地方（本地文件）提供可问责性；一旦权利结构变复杂，它就退回"凭据 + 邮件投诉"的旧模式——而旧模式的毛病（`00-理论定稿.md:151`："查无此人"）正是本项目声称要消灭的。**

**改法与代价**

| 改法 | 代价 |
|---|---|
| **① 把"产权"从能力挪到场所**：新增 `place` 对象（`world://local/*`、`world://licensed/<provider>/*`、`world://commons/<source>/*`），能力声明不再带产权 | 中-大。**这是协议级改动**，而按 `WC-SDP-001-v0.1.md:939`（`PR-05`）的纪律，协议级承诺一旦冻结，改动要走 R5 |
| **② 事件里加"依据引用"**：跨越非 `local` 场所的动作，`act` 必带 `basis` 与 `grant_ref` | 小-中 |
| **③ 把三档写进可复算的判据**：对每个 `place` 档给一条"什么样的 `act` 必须带 `grant_ref`"的机器可判规则 | 中 |
| **④ 落一句诚实的范围声明**（若暂不做） | **零工程代价，但需要在 README 与 `policy.json` 顶部写明："v1 只模型化全产权（本地文件）一档；涉及平台许可与第三方权利的动作，本账本不构成合规证据。"** | 

**我的建议顺序**：**先做 ④（今天就能做），再做 ①**。理由：不做 ④ 而只做 ①②③，等于用一个不完整的模型生产"看起来完整"的合规记录——**那比没有记录更危险**。

### 2.6 第 6 问：日落条款——现在这套设计满足"中立/用户主权"吗？可判定的检验方法是什么？

**原文引用**

- `1-理论与哲学/00-理论定稿.md:155-156`：
  > **日落条款**：架构化责任的审计格式必须是**中立 / 用户主权**设计——否则过渡方案会固化为厂商的免责工具（"时序即权力"）。
- `1-理论与哲学/00-理论定稿.md:257-263`（§10.2 判据 + **死亡判据**）：
  > **判据 = 它最终把机制交到谁手里。**
  > | 让**厂商**更容易定型的基础设施（集中审计 / 厂商持有授权 / 状态不可导出） | **伪装中立的定型力量** |
  > | 让**使用者**更容易定型的（本地主权 / 可导出 / 建造者无特权） | **站在使用者一边** |
  > **失效条件（同时是本项目的死亡判据）**：一旦审计集中到厂商、或世界状态不可导出，这条判据**立刻判它输**
- `00-总纲.md:245`（铁律 4）：本体公开且版本化 / 世界状态可导出（退出权）/ **建造者与 agent 同一条门禁** / 世界级不可逆操作走最高级

**我的判断**

**现在这套设计在"形式上"满足（本地纯文本、零依赖、可导出、本体公开），但在"实质上"是未检验的——而且在它自己的死亡判据射程内，已经有一条命中。**

**理由（分三点，第三点最重）**

1. **"满足"是结构的，不是挣来的。** 单机、单人、无厂商、无第三方（`WC-FSR-001-v0.1.md:351`："不处理个人信息（无第三方用户）"）。**在一个没有厂商的场景里，"审计没有集中到厂商"是一句空话**——它不可能不成立。这不是设计胜利，是**检验条件尚未出现**。**这是我的判断，也是本次评审对"最会自我表扬"这句委托说明的正面回应。**
2. **有一条判据已经命中，而且是致命的：`policy.json` 由部署方持有并可替换。** 按 §10.2 的措辞"**厂商持有授权**"，出厂的 `world://user` 与 `irreversible_actors` 是使用者（这是对的）；**但机制上"法律文件可被部署方整个替换、且不产生任何事件"（见 §二.3）意味着：谁控制部署，谁就是实际的立法者。** 当它变成产品（`00-理论定稿.md:141` 的"厂商全责"路径），这条会立刻从"没问题"变成"厂商持有授权"。
3. **第二条命中：审计不可否认性不成立。** 摘要链是**无密钥的 FNV-1a**（`src/ledger.rs:557-577`：`fnv1a64(前值 + "\n" + 规范形式)`），且**整本重写连链重算检不出**（`docs/系统全景图.md:162`，用例 `c18_chain_cannot_detect_a_full_rewrite`）；项目自己也写清了边界：**"不防能写账本目录的对手"**（`docs/阶段外-待启用/S2-设计/WC-CKFMT-001.md:610`）；`00-总纲.md:243`（铁律 2）要求的"哈希链**定期封存别处**"**在实现里不存在**（`grep '封存'` 只命中文档）。**§10.2 的死亡判据问的是"审计集中到谁手里"——而"审计可被单方重写"是同一问题的另一种答法：它把审计交给了**能写那个目录的人**。** 在单机形态下，那个人通常就是使用者（所以还不算判输）；**但它已经不在"使用者主权"这一侧了，它悬在中间，靠部署形态决定落在哪边。**

**可判定的检验方法（六条，都要求：由非作者执行、可机械核对、有反例）**

判据的总原则：**检验运行时事实与所有权，不检验设计者态度。** 每条给"怎么测 / 通过条件 / 现状"。

## 三、你发现的、我没问到的问题

### 3.1 产品化之后，谁承担存量账本的迁移成本？理论没有"中途加入"条款

`00-总纲.md:335`（明确不做）：**"不写机器内核；不接 MCP / varlink 作为世界协议；不做多用户 / 多机 / 联邦。"** 而 `WC-FSR-001-v0.1.md:962`（LA-03）与 `:351` 把"无第三方用户 / 个人自用"作为**合规处境的前提**（"不处理个人信息（无第三方用户）"）。

**问题**：这两条把一个巨大的法域排除在设计之外，而**它们恰恰是"可问责性"问题唯一变难的地方**。更要紧的是一个具体的时序问题：**一个已运行数月、账本里已有几万条事件的单机世界，当它被迫变成多主体（第二个 agent、另一台设备、一个真实的第三方）时，原来的账本怎么办？**

- 若沿用旧账本：里面有大量 `actor: "world://user"` 的事件，**没有身份来源标记**（见 §二.1(c) 破口二）——**新主体上线后，这些历史记录的归属将永远无法与"自称的 user"区分。**
- 若切割账本：**"两本账"当场成立**（`2-依据/15-世界核心的组成与职责.md:258-264` 自己立的红线）。

**我的判断**：**这是理论缺一条"中途加入/主体增补"条款。** 应当在账本设计里现在就把"主体引入"做成事件（`type: "subject.admitted"`，带身份来源与授权依据），并把 `actor_src` 从第一条事件起就写上——**这一条的窗口期很短：等账本里有了真实历史再补，就补不上了。**

### 3.2 时间戳的可采信度：`at` 是秒级、由本机时钟给出，且与 `seq` 并存时会诱导误读

`src/event.rs:96-106`（`unix_secs`，秒级）+ `ontology.json:16`（"顺序由 `seq` 决定，`at` 只作辅助"）+ `00-总纲.md:261`（"登记簿**落盘**：断电重启后能报'上次那个活没跑完'"）。

**问题**：秒级时间戳意味着**同一秒内的多个事件没有可区分的时间序**；理论文档也**明确承认 `at` 只是辅助**。但对外复盘的受众（人、审计者、监管者、法庭）**认的是墙钟时间，不是 `seq`**。当"人离开 24 小时"这条验收（`00-总纲.md:29`）真的被执行时，第一个问题是"**这 24 小时的边界是什么时刻**"——而账本在这个粒度上答不了。更严重的是：**`at` 由本机时钟给出，时钟被改（NTP 跳变、人工改、容器迁移）不留痕**。

**我的判断**：这不是小毛病。**"可问责"的一部分是"可对时"**：证据要能与外部时间轴对齐（邮件到达时间、平台日志时间、门禁刷卡时间）。**建议**：`at` 改用毫秒或更高精度；新增 `clock_monotonic`（不可回退的单调时钟读数，仅用于排序）；并在检测到墙钟回退时写一条 `notice`。**这是我的推断与建议，未在文档或代码里找到任何相关处理。**

### 3.3 项目把"两个系统"当成了"两个真相源"，于是漏掉了同源要求真正难的地方

`2-依据/15-世界核心的组成与职责.md:242` 引用的外部教训是：
> ⚠ 外部教训：Solid 与 atproto 都只保证"读同一份**数据**"，**不保证"同一套解释规则"**。

项目自己把这条教训用在了**投影**上（`vocab_hash` 同源核对，`docs/系统全景图.md:128`）——做得对。**但它没有把同一条教训用在自己身上**：世界核心的"真相"其实是**两个系统**——账本（数据）+ 法律（`ontology.json` + `policy.json`，解释规则）。**它给解释规则的一半（词表）做了内容寻址，另一半（门禁策略）没做**（见 §二.3）。所以：**"读同一份数据、不保证同一套解释规则"这个它明确警惕过的病，正在它自己的核心上发生。**

**为什么值得单列一条**：因为这不是"漏了一个字段"，而是**它已经拥有正确的方法（内容寻址）、已经用它解决过一次同类问题、却没有把它用在最需要的地方**。这类"有工具没用在自己身上"的缺口，比"不知道要做"更难被发现——**因为文档里到处都在讲同源。**

### 3.4 交付物时间戳显示多处文档仍在"滚动修订"，而其中若干条正是本评审引用的口径来源

`docs/系统全景图.md:5`（取数时点 `2026-09-27`，提交 `be16dd8`），而 `WC-SQAP-001-v0.1.md:221-222` 同一日在推进到 `V0.10` 并注明"**本修订须经人批准后生效**"；`WC-R4-DISP-001-v0.1.md:11`（据 `WC-CKFMT-001.md:558` 引述）自述"**本表本身不改变任何规范条款的效力**"；`WC-SDP-001-v0.1.md:178-179` 直接写"**签字栏非空……当前一律留空 ⇒ 本项不成立**"。

**问题**：**我引用为"项目自己承认的边界"的那些句子，有些出自尚未生效的裁定文件。** 例如 `WC-SCMP-001-v0.1.md:2638`（`notice` 不过闸）出自评审记录——**它是"发现"，不是"已生效的规范"；而源码 `src/lib.rs:260-262` 证实该发现当前成立**。

**我的判断**：本评审的所有实现层结论**都以源码为准**（我已逐处核对 `src/`），**不以文档自述为准**。但我必须提醒委托方：**文档里"已关闭 / ✅"的标记密度很高，而源码里这些洞大多仍然敞着**（最典型：B-2 标记为"高"，建议写得很清楚，源码一行未加）。**这是我的观察，也是我对"这套理论最喜欢自我表扬"这一判断的具体证据。**

## 四、总问题 A / B / C

### A. 这个理念还缺什么？（理论层面缺的概念 / 区分 / 论证）

**缺六个概念。前三个是法理上的硬缺口，后三个是把已有直觉变成可用论证的补全。**

**A1. 缺"归责（attribution）"与"追责（liability）"的区分。**
现在 `00-理论定稿.md:124-134`（§5.3 归责三桶）把两者叠在一起：它回答"错该记在谁名下"，不回答"**谁必须赔、赔多少、什么时候赔**"。三桶的第三桶是"保险池"——那是**损失分散机制**，与"归责"是两件事。**缺这个区分的后果**：`4+2 → +3 → 1` 的时序（`:153`）看起来像一个责任体系，实际是**一个记载体系 + 一句关于未来的承诺**。

**A2. 缺"举证责任（burden of proof）"与"证明标准（standard of proof）"。**
`00-总纲.md:243`（铁律 2）说"证据须不可否认"——**"不可否认"是证明标准的一个刻度，但系统没有说明它要达到哪个刻度，也没有说清"谁来证、证到什么程度算够"。** 这一缺口的实际后果：账本提供的是**声明**（`src/carrier/run.rs:232-244` 的自报结果），而不是**证明**。**没有举证责任分配，账本可以被双方各自援引，结论相反。** 这是"可问责"落地时的第一道门槛，也是现在完全空着的一格。

**A3. 缺"'合法但有害'由谁吸收"的论证。**
`:151` 明确承认"消灭不了『合法但有害』"，然后**没有下文**。法理上，"合法但有害"是现代责任法的绝大部分战场（产品责任、危险责任、无过错责任、强制保险、社会补偿基金），**而理论把它一句话让掉了**。**建议补的不只是一句"由保险池兜底"，而是三问**：谁定价？损害阈值谁定？无过错情形下的补偿来源是什么？

**A4. 缺"法的时间性"（法律版本锚定）的概念。** 见 §二.3。理论侧已有原材料（"判据会移动" `:100-101`：**"可逆性必须能被本体记录与重判"**），**但从未推导到"法律本身必须版本化并成为事件"**。这是本评审认为最值得补的一条，因为它同时修好 §二.3 与 §二.6 的 L2。

**A5. 缺把"退出权"写成可判定判据的论证。**
`00-总纲.md:245`（铁律 4）写"世界状态可导出（退出权）"——**这是一条价值，不是一条判据**。已有一条近似判据（`docs/系统全景图.md:141`："跑完全部只读命令后账本 `sha256` 不变"），但那只测"只读不写"，**不测"导出后能否被别人读懂"**。**建议**：把 §二.6 的 L1–L6 直接吸收为理论条目，并明确"退出权 = L1 且 L2 且 L6 同时成立"。

**A6. 缺"谁来问责单数主体"的论证（本理论最深的洞）。**
`1-理论与哲学/00-理论定稿.md:20` 定义了人的四个角色（使用者/被影响者/供给者/规制者）；`:218`（裁决 1）把"监督者角色结构性衰减"定为现行立场。**但整套理论没有回答：当使用者 = 批准者 = 受益者 = 唯一受影响者的可能是同一个人时，"可问责"是问谁？** 现在 `policy.json:32` 就是这个形态（`irreversible_actors = ["world://user"]`）。**我的判断**：**这不是能靠工程补的缺口，而是必须写进理论的"适用域声明"**——即"在单数主体形态下，本机制提供的是**自证式记录**，不是可问责性；可问责性需要**至少两个在法律上互相独立的主体**"。**不写这句，整套理论会长期拿单机演示当多主体结论用。**

### C. 外部现有的系统为什么不好用？（指名道姓）

**总论断（先给判据，再逐个点名）**：这些系统在"可问责"这件事上失败，不是**不够全**，而是**它们全都停在"记录"这一步，且记录本身有一个共同的结构缺陷——它们记的是"身份 + 结果"，不记"依据 + 语境"**。逐条：

**C1. 企业审计 / SIEM（Splunk、QRadar、Sentinel、ELK 的 audit 用例）**

- **缺什么**：**审计的是"身份"，不是"授权"。** 一条 `user=alice action=delete` 的记录，无法回答"**当时 alice 是否被允许 delete**"——因为授权（IAM policy、RBAC binding）是**可变状态**，**改动本身通常不进审计**。
- **真实痛点**：事故复盘时，第一个问题是"她当时有这个权限吗"——答案得去 IAM 快照里翻，而 IAM 往往没有按时间点的历史。**结论只能来自"现在的权限"，然后用它推断过去**——这正是世界核心 §二.3 那个缺口的重演，**只不过在 SIEM 里它已经害了二十年**。
- **第二处**：日志分级与保留策略由**被审计方**掌握。`auditd` 的规则可以改、转发目标可以改、保留期可以缩。事后调证据时发现"**这个时间段没有那个数据源**"——**而这不是出错，是从来没记过。**
- **第三处**：企业审计的**买方是管理层**，不是被影响者。所以它优化的是"可追责到员工"，不是"可追责到组织"。**这是"审计集中到谁手里"的一个成熟样本，也预演了世界核心产品化以后的样子。**

**C2. 云厂商的 CloudTrail / Azure Activity Log / GCP Cloud Audit Logs**

- **缺什么**：**控制面覆盖好，数据面覆盖差**。以 AWS 为例，CloudTrail 默认记录的是**管理事件**（创建桶、改策略）；**数据事件**（`GetObject`/`PutObject` 这类对象级操作）**默认不开、需显式启用，且另计费**（参见 AWS S3 文档中关于用 CloudTrail 记录 S3 API 调用与"启用存储桶对象日志记录"的分辨：[S3 User Guide](https://docs.aws.amazon.com/pdfs/AmazonS3/latest/userguide/s3-userguide.pdf#323#261)）。**"要不要记录某人读走了哪份数据"是一个计费选项**——这是审计面被商业定价决定的最直白证据。
- **真实痛点**：数据泄露调查时发现**只能查到谁调了 API，查不到读了哪个对象**——因为那个层级的事件**从来没打开过**。而**"没打开"这个事实本身也不产生事件**。
- **第二处**：日志可以投递到另一个账号/另一个区域，而**"某段时间没投递"往往只在专门的对账里才看得出来**。

**C3. SaaS 的 activity log（各类"审计日志"页面）**

- **缺什么**：**只记成功的操作，失败与尝试常常不记。** 而**未授权的尝试**恰恰是审计价值最高的部分。
- **真实痛点**：合规要回答"谁尝试访问过受限数据"，而这些日志只能回答"谁成功访问过"。**"没有记录"与"没有人试过"在界面上长得一模一样。**
- **第二处**：导出行为常被当成一次普通读取。**一次把全库导出的动作，与查看一条记录，在日志里可能同样是 `view`。** 这在数据外泄的早期发现上是致命的。

**C4. Kubernetes 的 audit policy**

- **为什么最值得对照**：它和世界核心在**概念上最像**——声明式的规则 + 分级（`None`/`Metadata`/`Request`/`RequestResponse`）+ 一条 API 请求一条记录。规则里甚至可以显式写 `level: None`（例见 AWS EKS 最佳实践文档中的 audit policy 示例：[EKS Best Practices](https://docs.aws.amazon.com/id_id/eks/latest/best-practices/eks-bpg.pdf#aiml-observability#90#13)）。
- **缺什么（三处，每处世界核心都该照镜子）**：
  1. **默认是"不记"**。`level: None` 合法，默认策略由集群管理员定。这与世界核心的"默认拒绝 + 拒绝也留痕"**方向正好相反**；而世界核心的 `notice` 不过闸（`src/lib.rs:261`）在效果上等于给自己开了一个 `level: None` 的口子。**同一个洞，两种实现。**
  2. **审计面 = apiserver 请求**。容器里的进程干什么、节点上 root 干什么、`kubectl exec` 进去之后干什么，**都不在这个审计面里**。**这是"账本之外的动作"最标准的工业界样本**，也正是 §二.4(d) 后半的问题。
  3. **审计策略本身是集群里的一个文件/配置**，谁改谁不留痕（除非另建流程）。**§二.3 的问题，k8s 也有。**

**C5. 数据库的 audit log（Oracle Audit Vault、PostgreSQL `pgaudit`、MySQL audit plugin）**

- **缺什么**：**记 SQL 文本，不记"这条 SQL 依据哪条业务授权"**。应用以 `app_user` 连接、`pgaudit` 记下 `UPDATE customers SET ...`，**但记不下"这是哪个终端用户、依据哪次同意、哪条隐私政策"**。
- **真实痛点**：出了"某人数据被误改"的事，追到 `app_user` 就断了——**责任落在连接池账号上，而那个账号是共享的。** 于是"查无此人"以另一种形态出现了：**不是查不到记录，是记录里的人是假的。**

**C6. 区块链的"不可篡改账本"**

- **它解决什么**：事后**改不了**。
- **它不解决什么（这是本评审最想强调的一条）**：**它完全不解决"谁的责任"。** 上链前的信息可能是错的；钱包私钥的归属完全在系统之外；**"不可篡改"≠"真实"，"公开可验"≠"可归责"。** 这就是为什么绝大多数链上纠纷的最后一步，仍然要靠交易所 KYC、法院冻结与平台合规——**在系统的边界上，制度重新出现，而系统对它一无所知。**
- **对世界核心价值**：**"不可篡改账本"不是"可问责"的近义词。** 世界核心选了本地账本（`docs/系统全景图.md:117`：账本、本体、策略、协议、清单全是纯文本 JSON）而不是链——**这个取舍是对的**，因为它的目标（用户主权）与"公开不可篡改"并不是同一件事。**但它不能在宣传语里借用区块链的"不可篡改"信用**——它的链是无密钥 FNV-1a，且整本重写检不出（`docs/系统全景图.md:162` 的 `c18`）。**在"防篡改"这个维度上，它比区块链弱，而且弱得更多。**

**C7. PKI / 代码签名 / Sigstore / RFC 3161 时间戳**

- **缺什么**：**PKI 与代码签名回答"这个二进制是谁签的"，不回答"这个签名的人当时是否被允许做这件事"。** Sigstore 的透明日志（Rekor）与时间戳服务回答"某段字节**在某个时间存在过**"——这是**存在性证明，不是授权证明**。
- **真实痛点**：签名密钥泄露或 CI 被入侵时，签名是"有效"的，责任却无从落。SolarWinds 一类的供应链事件已经把这个缺口示范过一遍。
- **对世界核心价值——一个正面建议**：**签名/时间戳恰好补上世界核心最弱的两处。** 现在它缺（i）"被执行的是什么"（`src/carrier/` 无二进制哈希）与（ii）"账本不能被单方重写"（无密钥链 + 无外部封存）。**建议**：① 载体回写结果时带被执行对象的内容引用（与 `2-依据/15-世界核心的组成与职责.md:159` 已定的"运单号 = 内容 hash"一致）；② 账本摘要链改为**带密钥**（HMAC）或定期把链头**封存到世界核心不可写的位置**——后者正是 `00-总纲.md:243` 已经写下、但**从未兑现**的那句"须哈希链定期封存别处"。

**C8. OAuth 的 scope / consent**

- **缺什么**：**consent 是一次性的、scope 是无期限的、而"授权"与"具体动作"之间没有绑定。** 用户当时看到的是"这个应用要读你的联系人"，不是"这个应用将在 3 天后读第 128–4301 条联系人"。
- **真实痛点**：出事时，应用说"用户点了同意"，用户说"我不知道它会读这些"，**平台只能按授权协议处理——而那份协议里没有"当时的语境"这一项**。三方各自都有记录，**没有一份记录能让三方对上同一件事**。
- **对世界核心价值**：世界核心的设计**恰好占了这个缺口的正确一侧**——`00-理论定稿.md:102` 的"记录批准的语境"就是在补这一刀。**但它把刀扔了**（v1 无审批通道）。**所以现在的世界核心在这一点上不如 OAuth**：OAuth 至少记录了"谁在何时同意了哪个 scope"，世界核心连这句话都没记。

**C9. Android / iOS 的权限弹窗**

- **缺什么（三条，都是经典缺陷）**：
  1. **按类别授权，不按实例**：允许"访问照片"之后，**读哪一张、读多少张，不再问**。
  2. **一次性、无期限**：授权后长期有效，**没有"用一次批一次"的默认**。
  3. **最重要的一条——弹窗时刻的语境不留痕**：你当时为什么点"允许"？因为应用卡住了主流程、因为你着急、因为弹窗没告诉你它要读多少张。**这些都不进系统。** 学术上也一直在讨论这类许可提示的设计与用户实际决策的关系（例如 USENIX Security 2024 关于 ATT 权限的用户中心设计研究：[Mohamed et al., USENIX Security '24](https://www.usenix.org/system/files/usenixsecurity24-mohamed.pdf#6#5)）——**讨论的焦点正是"提示的时机与语境如何影响同意是否有效"**。
- **这正是世界核心理论最锐利的一刀**：`00-理论定稿.md:102` 的"**人批准 vs 人被信息胁迫后批准**"，说的就是第 3 条。**而现有所有主流系统都没有做这一条**——这是世界核心真正可以说"我看到了别人没看到的"的地方。
- **但也要说清差距**：Android/iOS **至少把"授权"这一层做成了机制**（弹窗、可撤销、可查）。世界核心**现在连这一层都没有**（v1 无审批通道，`src/gate.rs:295-303`）。**所以在这条轴上，它的位置是：概念领先一代，实现落后一代。**

**C10. 一句话的横向结论**

| 系统 | 记什么 | 缺什么 |
|---|---|---|
| SIEM / 企业审计 | 身份 + 动作 + 结果 | **授权依据**（授权变更不留痕） |
| CloudTrail 类 | 控制面 API 调用 | **数据面**（且默认关、另计费） |
| SaaS activity log | 成功的操作 | **失败的尝试**、**规模** |
| k8s audit policy | apiserver 请求（可配为不记） | **apiserver 之外**、**默认不记** |
| 数据库 audit log | SQL 文本 | **真实主体**（连接池账号） |
| 区块链 | 不可篡改的字节 | **真实性、归属、责任** |
| PKI / Sigstore / TSA | 谁签的、何时存在 | **当时是否被允许** |
| OAuth scope/consent | 谁同意了哪个 scope | **语境、与具体动作的绑定** |
| Android/iOS 权限 | 类别级的一次授权 | **实例级、时限、同意的语境** |
| **world-core v1** | **申请的调用 + 自报的结果 + 拒绝的流水** | **批准、依据（法律版本）、后果、真实主体、不可否认性** |

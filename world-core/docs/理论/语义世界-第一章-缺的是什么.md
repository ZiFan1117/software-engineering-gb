# 第一章 · 缺的是什么

> 东西被改了，你多半只能靠"感觉不对"发现。

## 1.1 同一件事，三方不是一个意思

人对 agent 说"把这张照片删了"，agent 收到的是"删除这个文件对象"，机器执行的是"把那块存储标成可用"。三个都对，三件事却不一样。

两台机器之间传一句"配额 = 5"。一台按自己的协议读成 5 元，另一台读成 5 分。两边读得都对，落到两处却不是同一件事。

一次操作成功了，日志里留下一条。可你要问"改的是哪个字段、原来是什么、因为哪一条才发生"，一样都答不上来。

三个例子看上去是三件事：一个是叫法不同，一个是单位不同，一个是记得不全。

**三个都对，合起来却不是一件事。**

## 1.2 三方的"意思"是从哪来的

人靠自己的理解。同一个词指同一件事，因为我们共享身体和经验；理解对不上时，当场说两句就能校正。

机器靠写死的协议。报文怎么编、字段什么含义，都写在规范里；两边照同一份规范解码，得出来的通常是一样的。

agent 靠它被训练出来的经验。它带着一部分人的经验，但它不按任何一份出厂规范运行，行为可以在两次调用之间改变。

三类来源互不相同，而且**互不担保**：一方的理解和另一方对不上时，没有任何一方能拿出凭据说"我这才是对的"。

**三处来源各管各的，谁也不为别人担保。**

## 1.3 承载缺口：意思没有一处由大家共同依赖的地方

今天，一件事的意思寄存在四个地方：人的头脑里、每个软件内部、随软件发布的文档里、各家自己的协议里。

四处都算不上"共同依赖的地方"。软件换了，它内部那份意思跟着换；文档改了，靠文档对齐的约定就断了；文档没改而实现先改了，约定断得更静——没有人会发现。

结果就是：同一件事，谁那里都有一份自洽的解释，合起来却没有一份是大家共用的。

**意思是各存各的，没有一处是共用的。**

## 1.4 判定缺口：起了分歧，没有一处能裁

同一句话经两条路径处理，可能得到两个结果。这件事在今天的工具链里就会发生：一次变更经过一个工具链和经过另一个工具链，落到两处记录上，就成了两件事。

出了事故要复盘时更明显：三方各有一份说得通的叙事，谁也不能证明对方错。**谁说了都不算。**各方没有共同承认过任何一个地方有裁定的资格。

**起了分歧，没有一处能当场裁。**

## 1.5 这两个缺口今天造成什么

两处缺口落到日常，是三件具体的事。

第一件，每见一次面就谈一次。两个系统要对接，先坐下来把"你说的这个字段是什么意思"谈成一份约定；换一个对接方，这份约定重谈一遍。谈成的约定只活在这次合作里，换人、换版本，它跟着作废。

第二件，各家的补丁各补一遍。同一件事的含义，人补一遍、agent 补一遍、机器再补一遍；三份补出来的东西各写在各处，谁也看不见别人补了什么，也没人对得上。

第三件，散场就完。约定谈完了，参会的人散了，就没有一处记着这件事谈过、谈的是什么、还有谁没被告知。下一个人接上来，从头再问一遍。

这三件事的花费不显眼，因为它摊在每一次交接里；把一年的交接加起来，它比任何一次对接本身都贵。

**没有共同的一处，每次交汇都要从头再谈一遍。**

## 1.6 已经统一的那一部分

说"三方没有共同的说法"会被一句反问挡住：HTTP 的方法与状态码、JSON 的数据格式、ISO 8601 的时间写法和 UUID 这几样几十年的成果早就在跑；域名归谁，域名系统说了算；一次提交改了什么，版本库记得清清楚楚。

这四样各自管住了一件事：

- HTTP 统一了"动作与结果的粗糙分类"，没有统一"这次变更改了什么、前值是什么"；
- JSON 统一了"字节怎么解析成结构"，没有统一"结构里每个字段是什么意思"；
- ISO 8601 统一了"时刻怎么写"，没有统一"一件事排在第几位"；
- 域名系统统一了"名字归谁"，没有统一"这个名字底下的东西被改过什么"。

它们各自只在自己的地盘里作数，跨过接口就接不上。四样都还在跑，而它们之间没有一处把话接过去。

换一句话说，它们规定的都是那句话怎么摆、往哪里送。一件事是什么意思，四样都没有接手。

**四样规定的都是话怎么摆。**

## 1.7 别人的做法为什么不够

要的那一处得同时满足三件事：各方都依赖它、它认得出分歧、它把"这件事是什么意思"接过去。照这个条件看现有的几类做法，逐类一句话。

**操作系统（文件系统、shell、服务管理程序、权限位）**擅长把字节稳稳放在盘上、把进程管起来，它记住的是字节、时间和谁能读写；一份配置文档昨天被改过它知道，改的是哪一个设置项、从多少改成多少、谁改的、为什么改，它答不上来。同一个系统里各工具各记一本账，对账时要人工拼。

**日志与审计系统**能吞下大量文本，还能带上时间与来源；它给的是时间线，不是因果：你能看到一件事发生了、另一件事也发生了，看不到后一件是因为前一件。日志是写给人读的散文，程序要拿它做判断只能去匹配字串，措辞一改，所有靠它判断的地方一起失效。

**数据库与版本库**事务与查询都做得很稳，而更新是覆盖：旧值当场消失，前值要留就得应用自己再记一份，于是出现两本账，而应用一定会忘记记。版本库存的是文件快照，它看不出"某个字段由关变开"；对象存储只有键和字节，消息队列有保留期，过期之后历史就没有了。

**Agent 框架**把一次工具调用变成结构化参数，也把对话历史当记忆用；可对话历史可以编辑、可以截断、可以摘要、可以按额度丢弃，会话结束就没了；召回给的是"像什么"，跑了一半的流程没有"补偿"这一说，只能整段重跑。

**权限与治理**管的是"谁能写这个文件"，而出事常常是"某个字段从合法值改成了另一个合法值"；授权一次长期有效，而"该不该做"要看当时的情形；"这件事做完就回不去"这一档它表达不了。粒度粗到只能每次都弹窗问人，弹窗一多，人就闭着眼睛点同意。

这五类都有一个共同的情形：它们各自都有拿手的事，而"这件事是什么意思"落在哪一类的管辖范围之外，谁也答不上来。

**它们各自管得再好，也没有一处管"这句话是什么意思"。**

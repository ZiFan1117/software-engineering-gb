# 01-现状：Agent 今天是怎么碰你的操作系统的（原 01 · 现状）

## 1. 一条命令的真实旅程

当你在 Omarchy 里按 `Super+Shift+Ctrl+A` 说"把屏幕调暗一点"，发生的是：

```
你: "把屏幕调暗一点"
  │
  ▼ LLM 推理（约 2 秒、几百 token —— 全程最贵的一步）
agent 生成文本: "brightnessctl set 60"
  │
  ▼ fork + exec（约 10ms）+ bash 解析
brightnessctl → 打开 /sys/class/backlight/intel_backlight/brightness → 写入 60
  │
  ▼ 返回 stdout 纯文本: "setting backlight to 60%"
agent 解析文本 → 再推理一次"应该成功了"（约 1.5 秒）
```

注意两个事实：

- **真正"干活"的那一步只花了 10 毫秒**，两端各挂了一次秒级的模型推理。
- agent 和驱动之间隔了：LLM → 文本 → bash → coreutils → 库 → 内核，**六层，每层都可能引入歧义**。

## 2. 五个结构性问题（不是 bug，是架构）

| # | 问题 | 具体表现 |
|---|---|---|
| 1 | **文本接口不可靠** | 输出格式随版本/locale 变；SSID 里的 `**` 转义、进度条、颜色码都会让解析跑偏。agent 出错的头号来源 |
| 2 | **权限全有或全无** | 要么普通用户（啥也改不了，sudo 卡密码），要么 root（能 `rm -rf /`）。**没有"只许调亮度"这个档位** |
| 3 | **无审计** | shell history 可删、可绕过；agent 到底改了什么，只能翻聊天记录 |
| 4 | **无资源限制** | agent 起一个 build 吃光 32G 内存，你的桌面会话跟着死 |
| 5 | **无协调** | 开 3 个 agent 同时改 systemd 配置/Nix 通道？互相打架，谁也不知道谁干了什么 |

## 3. Omarchy 现在做到哪一层（全是应用层胶水）

来自其仓库（omacom/omarchy）的真实清单：

| 它做的 | 位置 | 本质 |
|---|---|---|
| 顶栏 agent 用量面板 | `shell/plugins/agents/Main.qml` | Quickshell QML 插件（桌面壳层，不碰系统） |
| 预置 10 个 agent 启动器 | mise stubs：`~/.local/bin/claude`、`opencode`… | 第一次运行才下载的应用包装 |
| 崩溃诊断 | `omarchy agent crash` → 读 `coredumpctl` **文本输出** → 塞给 agent | 胶水：交的是"文本"，不是事件订阅 |
| 系统 skill | `agents/skills/`，软链到 `~/.agents/skills` | 提示词，不是接口 |
| 主题同步 | 换主题时改写各 agent 的配置文件 | 文件替换 |

**结论：OS 内核一行没动、systemd 一个单元没加、权限模型依旧"sudo 或没有"。**
它是把现有零件摆得漂亮——这不丢人（产品上极其成功），但"不彻底"的直觉是对的。

## 4. 这些机制早就存在，缺的只是总装

| 机制 | 年代 | 本来为谁设计 | 对 agent 的意义 |
|---|---|---|---|
| cgroup | 2007 | 容器/服务 | agent 也该被限资源 |
| btrfs 快照 | 2009 | 服务器 | agent 的 Ctrl+Z |
| journald 结构化字段 | 2012 | 系统服务 | agent 动作的可信审计 |
| eBPF | 2014 | 网络/观测 | agent 可生成的"内核插件" |
| varlink | systemd 253+ | 取代 D-Bus 文本面 | 结构化接口，不用解析文本 |
| Landlock | 2021 | 应用自我沙箱 | agent 物理上碰不到白名单外的路径 |

> 零件齐全三十年（ Landlock 最年轻也 5 年了），**缺的从来不是技术，是那个"总装工"**。下一篇就是总装图纸。

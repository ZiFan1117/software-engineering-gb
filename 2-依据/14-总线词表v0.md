# 14-总线词表 v0：**语义事件是唯一真相**

> 一句话：世界的**唯一原语是语义事件**；**状态是它的投影**，快照只是重放的优化。
> 本文件只写词表，不写代码。
>
> **三条公理**（2026-09-26 裁决，本文件的全部前提）：
> ① **我们做的是地基**——载可以买，**通道与总线一律自造**；
> ② **锚定点 = 语义事件**（不是语义对象树，也不是别人的事件格式）；
> ③ 由 ② 推出：**纯事件溯源**——事件是唯一真相，状态是读模型。
>
> **与同日 v0 初稿的差别**（史料纪律：改动记录在此，不假装一开始就对）：
> 初稿把「状态」和「事件」写成**并列的四类消息**；按公理②③收缩为
> **三个事件家族 + 一个值类型 + 一种投影传输形态**（§三）。这不是减功能，
> 是**去掉了一个假的并列**：状态本来就不是"另一条真相"，它是事件的函数。
>
> 上游：[00-总纲](../00-总纲.md) §2.3 / §2.5 / §6 / §9、[11-总线工程规格](11-总线工程规格.md)、
> [13-总线与通道外部参考](13-总线与通道外部参考.md)。
> 性质：**规格**（与 11 篇同档），不是事实、不是立场。凡与总纲冲突，以总纲为准。

## 一、三条公理与它们的推论

| # | 公理 | 直接推论 |
|---|---|---|
| ① | 我们做的是**地基** | 层归属被钉死（§一.1）：**载买 / 通道造 / 总线造**。buzz 那种"四样全进口、只做组合"的路排除 |
| ② | 锚定点 = **语义事件** | 事件必须**可理解**（自解释、自描述），而不只是**不可伪造**；"语义"必须可检验（§二.1） |
| ③ | **纯事件溯源** | 只有一种真相；**状态是投影**；回滚靠**补偿事件**而不是改历史（§三.4） |

### 1.1 层归属（"做地基"的确切含义）

| 层 | 谁提供 | 能不能换 | 本文件 |
|---|---|---|---|
| **载** | **买**（现在 Linux；换轨 Genode） | 能换 | ❌ 不管 |
| **通道** | **自造**（分帧、边界、传输选择、游标、引用编码） | 能换 | ⚠ 只定"必须有什么" |
| **总线** | **自造**（语义事件的定义 + 词表 + 因果） | **不能换** | ✅ **本文件就是它** |

> "从头做"**不等于"全部自己写"**：载体仍然是买的（总纲 §2.1：五件事里唯一可以买的一行）。
> 它的确切含义是：**所有法律都自己立。**

## 二、唯一原语：语义事件

### 2.1 什么叫"语义"——八条判据（与 Nostr 逐条对照）

"语义"不是形容词，是**可检验的清单**。左边是 reference（buzz / Nostr，本会话已核实其源码与文档），
右边是本世界的要求：

| 维度 | Nostr 的事件 | **语义事件（本世界）** |
|---|---|---|
| 类型 | **整数 `kind`**，要查注册表才知道是什么 | **自解释的类型 + 词表版本**；不读文档也能懂 |
| 载荷 | `content` 是**不透明 JSON 字符串** | **结构化的变化**：主体 + 字段路径 + 值 |
| 单位/量纲 | 无 | **在事件里**（"3 秒"还是"3 分钟"不靠猜） |
| 主体 | 靠 tags 约定（`#h` 频道、`#e` 引用） | **一等字段**（`subject` + 字段路径） |
| 因果 | **无**（`#e` 只表示"引用了某条"，语义靠应用层） | **`trace`：引发它的那条事件** |
| 身份与授权 | `pubkey` 签名——**身份有了，能力与不可逆性没有** | 身份 + **声明的能力** + **可逆性等级** |
| **重放** | **规范不管**（relay 存事件，但"重放得到什么"没有定义） | **重放必须得到同一状态**——这是"世界"的定义性要求 |
| 可核验 | 签名 + `id`（**防篡改 ✓**） | 签名 / 哈希链 **+ 状态可回放核验** |

**一句话记住**：

> **Nostr 给了你"不可伪造"，没给你"可理解"和"可重放"。补上后两条，就叫语义事件。**

这也解释了 13 篇里那两处空位：**23 件参考件的「④引用」全缺**、**"可复盘"没有一家提供**——
因为大家都在做"不可伪造"，没人做"可理解 + 可重放"。

### 2.2 一封语义事件的信封（自造）

```
world : 1                      # 词表版本。只加 flags，永不改这个数的含义
kind  : change | act | notice  # 三个家族（§三）
id    : <事件自身身份>           # 去重
seq   : <在日志中的位置，全局单增，由世界分配>
at    : <时间戳>
actor : <世界内身份>             # 不是 pid/uid
to    : <世界内身份 | 空>        # 空 = 广播
trace : <id | 空>               # ★ 因果：引发本条的那条事件
flags : [ ... ]                # 能力旗标；未知旗标必须忽略，永不因它改版本号
body  : { ... }                # 三个家族各自的体
```

| 字段 | 没有它就会 |
|---|---|
| `world` | 词表一改，旧投影无法判断"这条我读不读得懂"（"先协商能力再看数据"的做法已被否） |
| `kind` | 收到事件先要猜家族；三个家族边界消失 |
| `id` | 重传无法去重 |
| **`seq`** | **多适配器并发时无法定序**（[11 篇 §八-1](11-总线工程规格.md) 的洞）；断线后无法说"从第 N 条补给我" |
| `actor` | 无法回答"谁做的"（内核只有 UID/cgroup 粒度） |
| **`trace`** | **无法回答"为什么会变成这样"**；常设验收退化成时间线，不是因果。⚠ 23 件参考件无一件有它 |
| `flags` | 加能力就得改版本号 |
| `body` | — |

> **在纯事件溯源下，`seq` 的地位变了**：它不再只是"消息序号"，而是**事件在日志中的位置**——
> 世界的当前状态**由 `seq` 唯一确定**（`state = fold(events[0..seq])`）。这是本文件最承重的一句话。

## 三、三个家族 + 一个值类型 + 一种投影形态

### 3.0 先给结论（含一条"为什么"）

```
唯一真相：语义事件 × 3 个家族
├── ① change  变更：世界状态发生了变化
├── ② act     动作：请求 → 结果（结果本身也是事件）
└── ③ notice  通告：发生了什么（完工铃等）

不是事件，而是值类型
└── ④ ref     引用：{object:{id,rev}} | {content:{algo,hash}}   ← 作为字段值出现

不是事件，而是投影的传输形态
└── 快照 / 增量：{subject, base_seq, snapshot | delta}
```

**为什么 `ref` 不是事件**：引用不是"发生了什么"，它是**某个字段的值**。
它应当出现在 `change.body.after` 里（如 `after: {kind:"content", hash:"…"}`），而不是自己占一类消息。
——初稿把它当第四类消息，是**把值类型误当成了事件**。

**为什么快照不是真相**：快照是 `fold(events)` 的**缓存**。它必须带 `base_seq` 告诉读者"我对应日志的哪一点"，
否则读者无法判断自己看到的是不是已经过期。**它服务于"boot 进世界"的性能，不承担真相的责任。**

### 3.1 `change` —— 变更

```
subject : <世界内标识，如 world://notice/n-42>
path    : <字段路径，如 muted / items[3].title>
before  : <旧值>          # ⚠ 必带
after   : <新值>
```

- **`before` 必带，这不是偏好是硬要求**：RFC 6902 的 patch **没有逆操作**，
  diff 不记录旧值就**回不去**（13 篇 §八）。形状沿用 `08-transferor/transferor/ir.py` 里**已验证过**的
  `Diff.changed = {ref, field, before, after}`——你们自己已经猜对了这一条。
- **`path` 是位置，不是身份**：并发插入会使位置漂移，所以变更必须绑 `subject` 的对象引用（§3.4）。

### 3.2 `act` —— 动作

```
# 请求
capability : <能力名>          # 世界词表，不是 MCP 的 tool name
verb       : <动词>
params     : { ... }
request_id : <配对用>

# 结果：不作为独立消息类型，而是**追加一条 change 或 notice 事件**
```

**`act` 的结果取值**（借 A2A `TaskState` 的**洞见**，用我们自己的词）：

| outcome | 含义 | 借自 |
|---|---|---|
| `working` | 已受理，还在跑 | A2A `WORKING` |
| `done` | 完成 | `COMPLETED` |
| `failed` | 失败（带类型化 `code`） | `FAILED` |
| **`rejected`** | **被门禁拦下** | `REJECTED` |
| `cancelled` | 被取消 | `CANCELED` |
| **`awaiting-approval`** | **在等人批** | `INPUT_REQUIRED` |
| `awaiting-credential` | 在等凭据 | `AUTH_REQUIRED` |

- **`rejected` 是一等结果**：铁律 1"声明即请求"→ 被拦下是正常结局，不是异常。
- **结果即事件**：`act` 的结果不是"返回给请求方就完了"，它**必须作为事件追加进日志**——
  否则"哪些在等我批"在 24 小时后无处可查（这正是初稿推演 B 暴露的洞，见 §五.2）。
  追加后，"待批集"就只是从日志投影出的一个**读模型**。

### 3.3 `notice` —— 通告（发生了什么）

```
type    : <世界词表，如 notice.muted / job.done（完工铃）>
subject : <挂在哪个主体上>
payload : { ... }
```

- **完工铃（`job.done`）第一优先**（总纲 §6 `传`）：长任务零轮询是 `传` 的第一硬约束。
- `change` 与 `notice` 的分工：`change` 说**哪个实体的哪个字段变成了什么**；
  `notice` 说**发生了一件事**（可能不对应任何字段变化，如"任务跑完了"）。

### 3.4 `ref` —— 引用（**值类型**，两层）

```
# ① 对象引用 —— "同一个对象，我记得它的第几版"
{ kind: "object",  id: <世界内稳定身份 UUID>, rev: <版本号> }

# ② 内容引用 —— "这段字节不可变、可核验"
{ kind: "content", algo: <哈希算法>, hash: <内容 hash>, size, media }
```

- **两层不是重复**：内容 hash 标识**不可变的字节**；对象引用标识**会变的实体的某一版**。
  缺任何一层，"可复盘"都成立不了。
- **先例（本会话核实）**：`lively.next` 的 `lively.serializer2/object-pool.js` 就是
  `{__ref__: true, id: "<UUID>", rev: 0}` + 对象自带 `_rev`；Croquet 的内容 hash 只标**快照**，
  对象级反而靠 `beWellKnownBy(name)`——**这一层 Lively 更强**。
- 内容引用同时是**铁律 2"证据不可否认"**的落点；大对象一律外置为内容引用。

## 四、两条判据（本文件提出）

### 4.1 自省**不是第四个家族**——它是读模型的一个 `subject`

[11 篇 §八-2](11-总线工程规格.md) 问"会不会需要第五类（发现/查询）"。**答：不需要。**

- 在纯事件溯源下更干净：**查询 = 读模型的一个 subject**，如 `world://ontology` / `world://pending`；
- varlink 的 `GetInterfaceDescription` 是**外挂的自省接口**；而"两端都是语义内核"意味着
  **自省不需要外挂**——你问世界"你是什么"，就是读一个读模型。

### 4.2 投影同源 = **词表本身也必须内容寻址**（补总纲 §2.5）

总纲 §2.5 现判据是"投影只能省略，不能添加"，**不够强**：

- 外部教训（13 篇已核实）：Solid 与 atproto 都只保证"**读同一份数据**"，**不保证"同一套解释规则"**——
  两个客户端可以用各自的词表解释同一份数据，于是还是长出"两个世界"；
- 加强为：**词表（含渲染语义）本身也必须内容寻址**，投影要能出示"我用的是哪个 hash 的词表"。
  这样"同源"从口号变成**可核验**（比对两个投影声明的词表 hash）。
- ⚠ 最近的现成形状是 IPLD 的"强链接 schema"，但**直接采用就是把词表锚定在 IPLD 的编码规则上**——
  只可借"对象链接到自己的 schema"这个形状，编码自造。

## 五、手工推演（纸上跑，不写代码——总纲 §9 起手式）

### 5.1 推演 A：人让 agent 静音一条通知

| # | 谁 | 追加什么事件 | 关键字段 |
|---|---|---|---|
| 1 | 界面投影（内核的一种模式） | `act{capability:"notice.mute", params:{notice:"n-42"}, request_id:"r-1"}` | `actor: world://user` |
| 2 | 治理内核（agentd） | 查门禁 → 记 intent → 可逆，不设卡 → 执行 | 可逆性分级决定加不加摩擦 |
| 3 | 治理内核 | `act{request_id:"r-1", outcome:"done"}` | **作为事件追加进日志** |
| 4 | 世界核心 | `change{subject:"world://notice/n-42", path:"muted", before:false, after:true}` | **带 before** |
| 5 | 两个投影 | 各自渲染同一份读模型 | 人看图标变、agent 读 `muted=true` |

**结论：通。** 且 `before` 在第 4 步就在日志里了——回滚所需信息当场留下。

### 5.2 推演 B：人离开 24 小时后回来问"发生过什么 / 哪些在等我批"

这是**常设验收**，也是初稿暴露最多洞的一条。事件溯源后的版本：

| 步 | 需要什么 | 现在够不够 |
|---|---|---|
| 1 | 拿到"这 24 小时的变化" | ✅ `world://log` 读模型支持 `since_seq` 游标（初稿的洞 3 仍在：**回放窗保留多久**未定） |
| 2 | "哪些在等我批" | ✅ **初稿的洞 2 被事件溯源自然解掉**：`act` 结果作为事件追加 → **pending 读模型**由日志派生 |
| 3 | 答"为什么会变成这样" | ⚠ 靠 `trace` 回溯。**洞 1 仍在：trace 链长度与截断策略未定** |
| 4 | 证明两个投影看到的是同一份 | ⚠ 靠 §4.2 的词表内容寻址。**洞 5 仍在** |
| 5 | "坏了我能不能回滚" | ✅ 方向定了：**追加补偿事件，不改历史**（13 篇核实：Azure/Fowler 明确"回滚只追加 compensating event，禁改历史"）；⚠ 具体补偿语义未定 |

**推演 B 的新收获**：事件溯源把"结果必须落进状态"这条**从补丁变成了公理**——
不是"记得把结果也存一份状态"，而是**结果本来就是事件**。这是公理③最实在的收益。

## 六、待批判项（按疼排序）

1. **读模型的新鲜度**：投影是取一份带 `base_seq` 的快照，还是常驻订阅增量？两者混用时怎么判断"我落后了"？
2. **`trace` 链的长度与截断**：24 小时可能几千条，全链回溯成本未估；超过上限降级成什么？
3. **日志保留窗**：保留多久、存哪、代价多少（对比：atproto 主动放弃全量历史；Nix 用代际）
4. **补偿事件的具体语义**：回滚一个 `change` 是发一条反向 `change`，还是发 `notice` 声明放弃？谁来定义"不可补偿"的边界？
5. **并发**：两个投影同时改同一 `subject+path` 怎么办——**明确不引入 CRDT**（13 篇 §六：CRDT 不提供可信的"谁在何时改了什么"）；第一版用乐观并发 + `seq` 拒绝
6. **词表内容寻址的编码**：借 IPLD 的"形状"还是另造？借到什么程度算锚定？
7. **`seq` 由谁分配**（无中心期）：agentd 代发？换中心时怎么不断号？
8. **单位/量纲**：§2.2 的信封里还没写进去（语义类型有了，物理量纲没定）
9. **schema 演进**：事件一旦追加就不能改（不可变），那"字段含义变了"怎么处理（upcasting 的落点在哪）

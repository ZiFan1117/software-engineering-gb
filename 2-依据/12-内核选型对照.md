## 一、先分清两个"内核"：一个是采购问题，一个是自建问题

按 00.9 第一节的三层命名，被叫做"内核"的候选其实是两个不同的问题：

| | 载体层 / 机器内核 | 世界核心（Ontology Runtime） |
|---|---|---|
| 是什么 | 硬件之上的仲裁者：调度 / 虚拟内存 / 文件系统 / 驱动 / IPC / 隔离权限 | 语义本体的存储与持久化 + 总线 + 投影注册 |
| 与语义的关系 | **正交**——语义住在语义层，内核只管秩序（00.8 §3） | **它就是语义本身**——世界的物理定律 |
| 怎么得到 | **采购 + 适配**（选型问题） | **必须自建**（创世的全部内容） |
| 换不换 | 可换（插座），换的是供应商 | 不换（世界的宪法） |
| 失败模式 | 驱动不全、工具跑不起来 | 世界的本体不自洽、持久化不住 |

**由此，"我们要不要自己写一个内核"是个假问题**，因为它的两个读法答案相反且都很干脆：

- 读作机器内核 → **不要**。为造世界而先写驱动、文件系统、网络栈，是拿个人体量去撞
  一个需要多年团队与硬件矩阵的工程；Smalltalk/Genera/Oberon 没有一个是为了做世界先去写内核的
  ——它们要么跑在别人的内核上，要么跑在裸机上但**只驱动一块已知硬件**。
- 读作世界核心 → **必须**，但它不叫内核，也不该叫内核。00.8 阶段 B 原本把它命名为"微内核"，
  这个词会引入特权级、硬件信任、六个职责的错误联想（00.9 第一节已更名）。
  它是**世界核心**：一个跑在载体之上、管理语义对象图与其持久化的运行时。

**一条推论**：创世路线的**全部难度在世界核心与投影**，不在载体层。所以载体层的选择标准
不该是"它有多先进"，而是"**它有多不挡路**"。

## 二、载体层的需求：四行合同漏了第五行

00.8 §3 给下层定的合同是四行：**隔离 / 配额 / 持久化 / 承载**。对照 00.9 第四节新补的
**寄主期**，这四行不够——寄主期要求"世界在宿主内长大，用宿主的编辑器/调试器开发世界，
同时脐带（旧世界进口面）供真流量"。这三件事各自对载体栈提出硬需求：

| 需求 | 来源 | 对载体的要求 |
|---|---|---|
| 跑得动常规开发工具 | 寄主期 | 编辑器 / 构建工具链 / 调试器 / git |
| 跑得动脐带件 | 阶段 B 脐带（00.9 第三节） | 完整网络栈 + 浏览器运行时（transferor 依赖 Playwright 级能力） |
| 世界 image 住得下 | 世界核心 | 事务性、可快照、可导出的文件系统 |
| 世界可迁移 | 立宪四条之退出权（00.9 第六节） | 状态可导出到通用格式，不锁死在私有存储 |

**故合同应为五行**，第五行叫 **可开发（hosted development）**：

```
隔离 / 配额 / 持久化 / 承载 / 可开发
```

**关键限定：合同的乙方是"载体栈"（内核 + 用户态全套），不是内核本身。**
微内核只交付第一、四、五行的**前半**——它把驱动、文件系统、网络栈、用户态全部推给"你自己长"。
在个人体量下，那不是"更纯粹"，是**合同缺货**。这一条是后文判据重排的基础。

## 三、判据重排：能力模型不是选内核的首要理由（修正 00.8 §3）

00.8 §3 的换轨判据以**能力模型**为首（Zircon 是最接近 cap.d 世界观的观念样板，换轨执行首选 seL4）。
这条要修正，三个理由：

**理由一：能力门禁可以纯用户态实现——已经实现了。**
`agentd/internal/capd/capd.go`（145 行）就是能力表的全部：YAML 声明 → 解析 → 校验（名称/provider/
verbs/risk 三档/snapshot/require），`internal/router` 按表放行。**其中没有任何内核模块**。
也就是说，"能力模型"不是一个需要换内核才能获得的东西；它是一个**策略面**的东西，
而策略面本来就是治理层的职责（00.5：治理是服务，不是地基）。

**理由二：能力所需的强制力，载体层已经给了。**
门禁的**声明**是用户态的，但**强制**要靠内核机制——Linux 早就交了：Landlock（5.13+，非特权自锁）、
seccomp、cgroup、namespace。真正欠的只有一件：**跨进程的能力委托原语**
（07 篇 §6 的上游化清单第 1 条）。而"委托逻辑做在 agentd 策略面"本就是 06 篇 §8 的既定结论。

**理由三：02 篇列的"真要改内核的三件"没有一件足以推翻整个载体**（07:59–63）：

| 上游诉求 | 与换轨的关系 |
|---|---|
| 能力委托原语 | 策略面可做（用户态），且局部上游化即可，**不必换内核** |
| GPU 配额与计量 | 是驱动/上游问题，换任何微内核只会**更缺**驱动 |
| 统一结构化事件总线 | 用户态缝合即可（agentd 事件网关已在做），与内核选择无关 |

**故新判据排序**（用于第四节对照）：

| 序 | 判据 | 为什么排这个位置 |
|---|---|---|
| ① | **可开发性** | 寄主期与脐带的阻塞项；缺它世界生不出来 |
| ② | **驱动与硬件覆盖** | 不能用户态自建；微内核的最大短板 |
| ③ | **持久化基座** | 世界 image 的宿主能力（事务/快照/可导出） |
| ④ | 隔离与配额 | 机制齐备度；Linux 已全给 |
| ⑤ | 能力原语 | **可用用户态补足**，是增量而非换轨理由 |
| ⑥ | 命运自主（许可证/治理/活跃度） | 长期风险，不是当期判据 |

一句话：**换轨的理由应该是"载体挡住了世界"，而不是"载体不够优雅"。**

## 四、候选对照

按第三节约定的六项判据逐项对照。**未亲验者一律标 ❌**（本仓库惯例），并注明来源。

| 候选 | ①可开发性 | ②驱动/硬件 | ③持久化基座 | ④隔离/配额 | ⑤能力原语 | ⑥命运自主 | 2026 活跃度 |
|---|---|---|---|---|---|---|---|
| **Genode / Sculpt** | 中上：Sculpt 26.04 起可自托管开发与构建 | **最强**：可把 **Linux 驱动当沙箱组件复用**，PC 驱动跟到 Linux 6.12 | 中：VFS/文件，非对象 image ❌ | 强隔离 / 中配额 | 强：capability 组件模型 | 好：独立项目、多内核后端；**AGPLv3**（另售商业授权） | 高：25.08（2025-08）、26.04（2026-05-28）、26.08 连续发布 |
| **Redox** | 中：Rust 原生、桌面软件少 | 中：smoltcp / RedoxFS / SATA·NVMe·USB·Intel 网卡 | 中：RedoxFS 文件级 | 中：capability 正在做进 IPC 与文件 I/O / 配额弱 | 中：进行中 | 好：MIT | 高：2026-01 首次在自身内编译 Cargo/rustc；NLnet 资助 |
| **seL4** | **弱**：LionsOS/sDDF 属嵌入式范围，x86-64 支持仍在开发，无通用桌面 | 弱：驱动/文件系统/网络栈需自建 | **无**：无对象存储 | 强：形式化验证 | **最强**：纯 capability（CNode/endpoint） | 好：LF 项目、独立基金会 | 高：16.0.0 / Microkit 2.3.0（2026-07）、AArch64 机密性证明（2026-08） |
| **Zircon / Fuchsia** | 不适用（自有整栈） ❌ | 完备（Fuchsia 自身），外部不可用 | 无 ❌ | 强：handle + rights | 强：真 capability | **最差**：2023 裁员、2026-03 媒体称"几乎不可见" ❌ 官方定性未证实 | 低 |
| **HelenOS** | ❌ 未证实 | 中：FAT/tmpfs、AHCI/IDE | ❌ | 中：组件化多服务器，无统一 capability 语义 | 弱 | 好：BSD | 中低：近单主线开发者 |
| **Managarm** | 中上：systemd 可启动、Linux 源级兼容、454 包 | 中上：NVIDIA modeset | ❌ | 中：微内核 + 异步 I/O，非严格 capability | 中 | ❌ 许可证未证实 | 中：2026-01 年度更新 |

**两条必须一起看的观察**：

1. **Genode 是"插座"的现实形态**——它的官方发布说明写明："多亏 Genode 的 Linux 设备驱动环境，
   用户可以**在任何受支持的微内核上**把 Linux 驱动当作沙箱组件使用"，且 PC 驱动跟进到 Linux 6.12；
   seL4 被其列为受支持内核之一（[Genode 25.08 发布说明](https://genode.org/news/genode-os-framework-release-25.08)）。
   也就是说：**00.8 §3 担心的"微内核要自己长驱动/文件系统/网络栈"，已有一个现成解法**，
   而"换内核不换世界"正是 Genode 的产品形态。故 00.8"Zircon 是观念样板、seL4 是执行首选"应修正为
   **"Genode 是插座，seL4 是插座上可选的一个内核"**。
2. **同类尝试已存在，但都极早期**——Aesynx（Rust no_std，capability + **不可变对象图** + "OS world
   service"）方向与本项目最贴，但 2026-09 仅到 v0.37、只跑 QEMU 冒烟、无文件系统与驱动。
   这既印证"语义化世界"这个格子确实空着（14 篇"空白既是机会也是风险"），
   也说明**没有人替我们造好那一半**。

**两种排序的差别（诚实标注）**：本轮内核调研报告给出的首选是 **Redox**，其次 Genode；
本篇按第三节的判据序（可开发性 ①、驱动 ② 优先）得出 **Genode 首选、Redox 次选**。
差别只在权重：若把"个人体量可读、Rust 原生、已达成自举"的权重提高，Redox 居首。
**两种排序在三个结论上一致**：现在不换轨、**不裸用 seL4**、持久化必须自持（见第五节）。

## 五、结论与换轨触发条件

**结论一：现在不换轨。** 理由不是"长大再说"，而是五行合同的硬需求——寄主期要能跑常规开发工具，
脐带要能跑浏览器运行时，两者都要求**完整的载体栈**；没有任何微内核候选今天能按五行交付
（可开发性 ① 与驱动 ② 上，只有 Genode 接近，且它的"能力化桌面"目前仍是路线图草稿 ❌）。

**结论二（最重要，且与 00.9 第五节合流）：换轨的"不拆楼"承诺必须现在就兑现。**
本轮调研给出的一条判断值得单独提出：**"先站 Linux、后换轨"最危险的不是隔离，而是持久化**——
在 Linux 上，世界 image 只能退化成"文件 + 快照"；**语义层一旦依赖这个抽象，换轨时就要重写**。
这正好命中 00.9 第五节的要求：恢复与版本必须建在**本体**里，而不是载体的文件系统里。
否则 00.8"四行合同保证平移不拆楼"这句话，会在**最承重的那一根柱子**上失效。
→ **可检验的判据**：世界核心的持久化层能否在不使用载体快照的前提下完成回滚与检查点。
能，则换轨是"换插座"；不能，则换轨是"拆楼"。

**结论三：换轨目的地重排。**

| 位次 | 候选 | 理由 | 代价 |
|---|---|---|---|
| **第一** | **Genode / Sculpt** | 驱动复用（Linux 驱动当沙箱组件）+ 多内核后端（含 seL4）+ 可自托管构建 | AGPLv3；组件化 API 是新的载体依赖；"能力化桌面"未成熟 ❌ |
| 第二 | Redox | Rust 原生、自举已达成、capability 进行中、MIT、个人体量可读 | 驱动中等、配额弱、桌面软件少 |
| **通过 Genode 使用** | seL4 | 形式化验证 + 纯 capability | **不裸用**：裸用则驱动/文件系统/桌面全自建（个人可行性未证实 ❌） |
| 观念样板 | Zircon | handle + rights 最接近 cap.d 世界观 | 活跃度低、命运捏在谷歌 ❌ |
| 观察对象 | Aesynx | 方向最贴（capability + 不可变对象图 + world service） | v0.37，仅 QEMU，无驱动/文件系统 |

**结论四：换轨触发条件改写。** 00.8 §3 给出的三个条件（能力下沉硬件级 / 绝对自足 / 硬实时认证）
全是**哲学条件**，没有一条会在工程中被自然触发。改为三条**工程条件**：

1. **技术前提**：世界核心稳定 **且** 持久化自持（结论二的判据成立）；
2. **动机条件**：五行合同中某一项在 Linux 上被证明**不可满足**（例如世界级不可逆操作需要
   内核级状态导出，或能力委托的强制力被证明用户态不可靠）；
3. **准入条件**：目标载体通过五行合同的验收——不是"更优雅"，是"挡住了"。

**另设一个自然的重新评估点**：寄主期退出条件达成时（00.9 第四节：世界内工具可自举），
载体层对"可开发性"的依赖下降，此时重估成本最低、收益最大。

## 六、世界核心要造什么（自建的那一半）

载体层可以采购，世界核心没有供应商。以下是**不可外购**的清单（阶段 A/B 的产出）：

| # | 部件 | 内容 | 来源 |
|---|---|---|---|
| 1 | **本体 schema** | 实体 / 状态 / 动作 / 事件 / 引用 / 身份 / 能力权限 **+ 版本历史 + 可逆性标注** | 00.8 阶段 A + 00.9 第五节 |
| 2 | **image 持久化** | 语义对象图的存储、事务、检查点；**不依赖载体的文件系统快照** | 00.9 第五节（恢复能力必须建在本体里） |
| 3 | **总线** | 四类消息的唯一 IPC；订阅与推送 | 00.6 + 00.9 5.1 |
| 4 | **投影注册** | **同源状态上的 N 端口注册表**（v1：视觉 + 语言；听觉等留位），分发与准入校验 | 00.5 §7.2 + 00.9 §7.1 |
| 5 | **能力表与门禁** | 从 agentd 迁移而来（代码与测试直接搬） | 00.8 §4 |
| 6 | **降级模式** | 无 LLM 时世界仍运转（脑干反射） | 00.9 第二节 |
| 7 | **进口面（脐带）** | transferor 的 IR 入口，输出用**世界本体 schema** 表达 | 00.9 第三节 |
| 8 | **元层** | 立宪四条：本体公开版本化 / 退出权 / 建造者特权禁止 / 世界级不可逆操作最高预案 | 00.9 第六节 |

**可复用的现成件（省下阶段 A 的工作量）**：08/11 的 UI-IR 中四类消息、动词化 + 参数 schema、
事件即真相 + 订阅推送、seq + diff、语义合并、hash 焊接——**照抄这部分，重写那部分**
（ref 换持久身份、去掉 surface 四面、拆分类型与 affordance、去掉 focus 层级、
改掉 `browser.*` 命名空间），清单见 00.9 §5.1。

**一句话**：世界核心 ≈ 一个**语义对象图的持久化运行时 + 总线 + 能力门禁**。
它比"写一个内核"小得多，比"写一个应用"大得多——这正是它一直没被任何人造出来的位置。

## 七、现在该做的三件事（按依赖排序）

1. **世界核心的持久化设计**（image 格式 + 事务 + 版本历史 + 检查点）——它与载体选型**解耦**，
   且是阶段 A/B 的真正瓶颈；先做它，载体怎么选都不浪费；
2. **载体适配层**：把五行合同做成一薄层接口（进程/内存/文件/IPC/隔离），
   让换轨成为"换插座"而不是"拆楼"——这是 00.8"四行合同保证平移不拆楼"承诺的**兑现物**，
   目前只停留在承诺层面；
3. **可开发性保障**：寄主期工具链清单 + 退出条件（自举工具可用的判据，00.9 第四节）。

**明确不做**：不写机器内核；不为能力模型换内核；不在世界核心稳定前动载体层。

## 八、待批判项（自首）

1. **"能力可用用户态补足"有安全边界的隐含前提**——当前 cap.d 的强制力依赖 agentd 自己守规矩，
   Landlock 尚未接上（05 篇列为"第二天"）；若用户态强制被证明可绕过，判据⑤的权重需上调，
   本节的结论会朝"更早换轨"偏移。
2. **五行合同的第五行是接口承诺，不是已验证事实**——"可开发性"如何量化（跑得动什么算够）
   未定义，容易变成自我豁免的软条件（00.7 自首②的老毛病）。
3. **候选对照的事实层依赖外部核实**（第四节），凡标 ❌ 者可能是"查不到"而非"不存在"，
   不能当作负面证据使用。
4. **世界核心的工作量未估**——本篇只给了清单，没给体量；"比内核小得多"是相对判断，
   不是估算。

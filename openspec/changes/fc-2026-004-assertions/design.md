# Design

## Context

断言缺口的来源、以及"为什么它们必须与规格同批存在"，见 `fc-2026-002-spec-revisions/design.md`
（那份 change 已把每条的 `audit.md` 编号与规格落点写全）。本件只做"把断言写出来"。

## Goals / Non-Goals

**Goals**：37 条逐条落地；每条都能用**变异**证明会红（改坏实现的一行 ⇒ 该断言红）。
**Non-Goals**：不改规格条文、不改产品行为、不新增能力。

## Decisions

1. **每条断言必须配一个变异点**（"改坏哪一行 ⇒ 它变红"）——否则它可能是恒绿的装饰。
2. **方向已变的两条先重写再补**（`3.3`／`3.4`）：照搬原措辞会写出与实现相反的断言。
3. **归属**：本件是"断言账"，不与 `cover-unimplemented-capabilities`（能力缺口账）混同——
   前者是"规格写了、没测试"，后者是"书要求了、没实现"。

## Risks / Trade-offs

| 风险 | 缓解 |
|---|---|
| 为了把断言写绿而放宽断言 | 决策 1（变异证明）＋ 评审席抽查 |
| 与 `cover-*` 的条目重复 | 决策 3：两边各写"归属"，重复时以"书要求／规格要求"为界 |

## 排除清单

- 不改 `world-core/src/**` 的行为（只允许为了让断言可写而补**测试**）。
- 不动书、不动规格条文。

## Migration Plan

逐组补断言 ⇒ 每组跑 `cargo test --locked` ＋ 变异证明 ⇒ 全绿后归档。

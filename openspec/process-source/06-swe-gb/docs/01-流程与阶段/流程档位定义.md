## 一、为什么要分档

GB/T 8567-2006 的 20 份文档、8 个阶段、4 类评审，是为**大型组织 + 外方审查**设计的。
个人开发或小团队照抄，绝大部分是沉没成本；但完全不要，又会在**第一次交接**时崩盘。

标准本身不区分个人与企业——**ISO 自己就是用 Profile 来解决这个问题的**。
所以本仓库也采用同一思路：**一套标准，两个档位。**

| | **A 档：个人 / 单产品** | **B 档：公司 / 对外交付** |
|---|---|---|
| 典型场景 | 自己用的工具、研究性代码、单人产品 | 有客户合同、多人协作、需移交 |
| 人数 | 1 人 | ≥ 2 人 |
| 交付对象 | 自己 | 客户 / 甲方 / 下一位维护者 |
| 文档量 | **6 份**（清单见下方 §4.1） | 全套（按需引用 `templates/`） |
| 评审 | 自查清单 | 阶段评审 + 记录 + 签署 |
| 追溯 | 需求 ↔ 测试（轻量） | 需求 ↔ 设计 ↔ 代码 ↔ 测试（RTM 门禁） |
| 基线 | Git tag | 需求基线 + 框架基线 + 产品基线 |
| 依据 | GB/T 8567-2006 裁剪条款 | GB/T 8567-2006 + GB/T 38634 系列 |

> **两个档位的规模参照**：ISO/IEC 29110 为"非常小的实体"（≤25 人）定义了四档轮廓，
> 其中 **Entry** 定义 14 个工作产品、**Basic** 定义 22 个。
> 本仓库 A 档的 6 份文档是照 Entry 的切法裁剪的结果。
> 29110 在中国**没有采标**（注意 `GB/T 29110-2012` 是道路交通标准，与软件无关），
> 因此它只作**裁剪参照**，不作法源——法源见 [`../00-标准依据/标准依据.md`](../00-标准依据/标准依据.md)。

## 二、档位判据（唯一的机械规则）

**不要凭感觉选档位。用下面三条判据——任一命中即 B 档。**

| # | 判据 | 为什么这一条 |
|---|---|---|
| 1 | **有第二个人需要交接或接手** | 交接是最贵的事。文档的本质是**异步沟通**，没人接手时它确实没价值 |
| 2 | **有外部交付物或验收责任** | 有验收方 = 有判定标准 = 必须留下可举证的记录 |
| 3 | **失效后果不可接受**（数据丢失、资金、安全、不可回滚） | 风险等级决定证据等级，与人数无关 |

**三条都不命中 → A 档。**

> **判据必须可机械判定。**"项目不大"不是判据，"只有我一个人"才是。
> 模糊判据的结果是每个项目都要重新吵一遍。

### 判据 1 的重要含义

**判据 1 是双向的。** 不只是"有人接手要升档"，也包括：
**如果这个项目永远不会有人接手，那它就该留在 A 档，不要给它套 B 档的流程。**
给单人项目做正式评审记录，是纯粹的浪费——而且会因为"反正没人看"而退化成走过场。

## 三、不可裁剪项（A 档也必须做）

**四条硬红线。这四条之所以不可裁，是因为它们保护的是你自己。**

| # | 不可裁剪项 | 为什么 A 档也躲不掉 |
|---|---|---|
| 1 | **版本控制** | 没有它，你连"上周那版能跑"都回不去。这是**唯一一条零成本的实践** |
| 2 | **需求基线**（哪怕是几条要点） | 没有基线就没有"变更"这个概念，改到哪算哪，最后自己都说不清要做什么 |
| 3 | **至少一个级别的、有记录的系统级测试** | 你自己就是验收方。没记录的测试等于没测——因为你无法复现 |
| 4 | **变更留痕**（哪怕只是 commit message 写清为什么） | 三个月后的你会问"这行为什么这么写"。留痕是给未来的自己看的 |

> 这四条对应 `标准依据.md` 里的三条红线，并额外增加"变更留痕"——
> 因为 A 档没有评审会来兜底，留痕是唯一的记忆载体。

## 四、A 档：个人 / 单产品

### 4.1 交付物（6 份，上限就是上限）

| # | 交付物 | 形式 | 依据 |
|---|---|---|---|
| 1 | **需求要点** | 一页以内，条目化，每条可验证 | GB/T 9385-2008（截取"可验证性"要求） |
| 2 | **设计要点** | 关键决策 + 为什么不选别的；不需要 UML 全套 | — |
| 3 | **测试记录** | 测了什么、结果、怎么复现 | GB/T 38634.3-2020（降级使用） |
| 4 | （按需）**变更说明** | 为什么改、影响什么 | — |
| 5 | （按需）**版本说明** | 这一版和上一版差在哪 | GB/T 12505-90 五要素 |

**超过 6 份就是升档信号，不是"再写一份"信号。**

### 4.2 冒烟门禁（迭代为主，一条命令）

A 档不做阶段评审，但要有**自动化门禁**——这是"迭代为主 + 轻量门禁"的核心：

```
提交 → 一条命令跑通 → 通过则进入下一轮迭代
                    → 不通过则先修，不叠加新功能
```

门禁内容（对应本仓库 `tools/` + `tests/`）：

| 检查 | 工具 | 拦什么 |
|---|---|---|
| 构建/启动 | `skeleton/run_skeleton.py` | 代码根本跑不起来 |
| 单元测试 | `tests/test_module_system.py` | 改坏了已有功能 |
| 依赖方向 | 模块系统环检测 | 结构腐化（低层依赖高层） |
| **需求↔测试追溯** | `tools/trace_matrix.py` | 需求没被测试覆盖 |

> ⚠️ **口径已统一（2026-09-21 修正）**：上一版此处写"A 档不需要 `trace_matrix.py`"，
> 与 `docs/导读本.md` 把它列为 A 档最小可行动作**相冲突**。
> 现已统一为：**A 档照跑 `trace_matrix.py`**。
>
> **代价很小**：该工具要求 RTM 14 列齐备，其中 `设计模块号` 与 `实现代码位置`
> 在 A 档也一并填上即可——A 档模块少，多填两列约几分钟。
> **收益**：导读本的三条命令直接可用，不必记"哪档跑哪个"。
>
> 完整说明与依据见 [`../附件/附件三-评审与门禁.md`](../附件/附件三-评审与门禁.md) §4.3。

**A 档的"轻"体现在文档量与评审形式上，不体现在门禁上**——门禁一律照跑。

### 4.3 A 档主动放弃的部分（显式声明，不装作不存在）

| 放弃项 | 风险 | 补偿方式 |
|---|---|---|
| 正式阶段评审 | 重大设计缺陷可能晚发现 | 靠 S3 骨架跑通**尽早暴露结构错误** |
| 完整 RTM 追溯 | 需求变更时可能漏改 | 靠测试覆盖 + 条目化需求清单 |
| 独立 SQA | 质量靠自检 | 靠自动化门禁替代人工检查 |
| 配置审计 | 交付物可能不齐 | 靠 Git tag + 一条命令可复现 |

> **诚实原则**：A 档是**主动接受**这些风险，不是"因为懒所以没做"。
> 这两者在出问题时的应对完全不同——前者有预案，后者只有慌。

## 五、B 档：公司 / 对外交付

### 5.1 在 A 档四条红线之上增加

| 增加项 | 依据 | 为什么 |
|---|---|---|
| 正式阶段评审 + 记录 | GB/T 8566-2022 | 多人决策需要留痕，否则责任不清 |
| 完整追溯矩阵（RTM） | GB/T 8567-2006 | 交接时"这条需求对应哪段代码"必须可答 |
| 三类基线（需求/框架/产品） | GB/T 12505-90 五要素 | 对外交付点必须有冻结时刻 |
| 配置管理计划 | GJB 438C 已并入开发计划 | 不必独立成文，但内容要覆盖 |
| 需求规格说明（完整） | GB/T 9385-2008 | 验收判定的依据 |
| 接口需求规格说明 | GB/T 8567-2006 | 有外部对接才需要，无则裁剪并留痕 |

### 5.2 文档清单（引用 `templates/`）

B 档不新建模板，直接引用现有 `templates/`，按需裁剪：

| 阶段 | 引用模板 |
|---|---|
| S0 立项 | `01-策划类/02-项目开发计划.md`（含裁剪说明，**必填**） |
| S1 需求 | `02-需求类/01-软件需求规格说明.md`、`03-需求追溯矩阵.csv` |
| S2 框架 | `03-设计类/01-软件概要设计说明.md`、`03-模块接口契约.md` |
| S4 实现 | `03-设计类/04-软件详细设计说明.md`、`05-测试类/03-单元测试记录.md` |
| S5 测试 | `05-测试类/01-软件测试计划.md`、`02-软件测试说明与用例.md` |
| S6 验收 | `05-测试类/04-系统测试报告与准出评审.md` |
| 全阶段 | `06-评审类/01-阶段评审记录.md` |
| S7 交付 | `07-配置与发布类/02-版本说明.md` |

**未引用的模板必须在项目开发计划的「裁剪说明」里写明：裁剪项、理由、补偿措施、批准人。**

## 六、升档与降档

### 6.1 升档触发

| 触发 | 动作 |
|---|---|
| 加入第二个人 | **立即升 B 档**，并补建 RTM 与基线 |
| 签下第一个客户 | **立即升 B 档**，并补齐需求规格说明 |
| 出现不可接受的失效后果 | **立即升 B 档**，并补风险评估 |

> **升档不可逆。** 一旦发生过交接成本，就不存在"回到 A 档"——
> 因为接手的人已经在依赖那些文档了。

### 6.2 A 档 → B 档补齐清单（按优先级）

| 优先级 | 补什么 | 为什么排这个位置 |
|---|---|---|
| 1 | **需求规格说明** | 没有它，B 档的所有追溯都无源头 |
| 2 | **RTM 追溯矩阵** | 交接的核心工具，缺它等于把知识留在原开发者脑子里 |
| 3 | **三类基线** | 建立冻结点，否则后续变更无法判定影响 |
| 4 | **评审记录机制** | 多人决策的责任划分 |
| 5 | 接口需求规格说明 | 仅在有外部对接时 |

### 6.3 降档

**原则上不允许。** 唯一例外：项目整体废弃。
即便是废弃，也要留一份废弃说明（为什么停、资产在哪）。

## 八、⚠️ 与 [`附件二`](../附件/附件二-阶段流程与交付物.md) V1.1 硬条款的关系（本版新增）

**本次修订不改档位**：档位判据（§二）、A 档交付物清单（§4.1）、升档触发（§6.1）**均未变更**。
新增的是**硬条款层**，它对两个档位的适用方式如下。

| 项 | A 档 | B 档 |
|---|---|---|
| **H-01…H-26 硬条款** | **同样不可裁**——理由与四条红线同类：**它们保护的是你自己**（没有它们，A 档连"上周那版能跑"都证明不了） | 不可裁 |
| **门禁形式** | **不开评审会**，但**20 项通用检查单照走**（由本人逐项给结论 + 证据位置），CI 代替人判 | 评审会 + 20 项通用检查单 |
| **H-12 席位与"部分"** | ⚠️ **降级执行**：1 人无法"有几部分设几位专家"；等价要求是"**按部分逐部分独立过判据并分别留痕，不得一次结论覆盖全部部分**"（见 [`附件八`](../附件/附件八-责任时间与阶段分解.md) §6.7） | 照条款执行（有几部分设几位专家） |
| **H-22 辩证处置** | **照执行**（A 档的意见来源通常是自查清单与工具输出；反驳同样要留理由与实测） | 照执行 |
| **评审记录** | `templates/06-评审类/01` 不取用；但**证据 `证据类型` 栏与「本档不能证明的事」两节仍须在自查清单里体现** | 评审记录（**模板待补 `证据类型` 列**，补前手工加列） |

> **本仓库的立场**：**"轻"体现在文档量与评审形式上，不体现在门禁上**（§4.2 末句）。
> 硬条款属于门禁层，因此**不随档位放松**。

# 阶段流程与交付物

> 本文件把 GB/T 8566-2022 的过程框架**裁剪落地**为 S0–S7 八个阶段，每个阶段明确四件事：
> **准入条件 · 核心活动 · 交付物 · 准出门禁**。
>
> 一句话原则：**没有通过门禁，不进入下一阶段。** 门禁不是形式，是风险闸门。

---

## 零、全景图

```
              ┌──────────────── 框架-模块共演化循环（S2 ⇄ S4）────────────────┐
              │                                                              │
 S0 立项 ─→ S1 需求 ─→ S2 框架设计 ─→ S3 骨架跑通 ─→ S4 模块实现 ─→ S5 集成/系统测试 ─→ S6 验收 ─→ S7 交付维护
   │           │            ↑                │              │                  │              │            │
   │           │            └──── 框架缺陷反馈 ─────────────┘                  │              │            │
   │           │                                            └──── 缺陷回归 ─────┘              │            │
   └───────────┴──────────────── 变更控制贯穿全流程（配置管理）────────────────────────────────┴────────────┘
```

阶段编号 S0–S7 是本仓库的**工程约定**，不是国标术语；括号内为标准过程域对应关系。

## S0 立项与策划

| 项 | 内容 |
|---|---|
| **对应标准过程** | 生存周期模型管理、项目管理、质量保证、配置管理（GB/T 8566-2022 管理类过程） |
| **准入** | 有明确的需求来源（合同 / 任务书 / 内部立项单） |
| **核心活动** | 可行性分析；范围与约束界定；风险识别；标准裁剪决策；质量目标量化；配置管理策略确定 |
| **交付物** | ① 可行性研究报告 ② 项目开发计划（含**裁剪说明**）③ 软件质量保证计划 ④ 软件配置管理计划 ⑤ 风险清单 |
| **准出门禁** | **立项评审**通过；范围、约束、质量目标、裁剪说明四项齐备且经批准 |
| **常见失败** | 跳过裁剪说明 → 后续每个阶段都在争论"这个文档要不要写"，反复返工 |

> **质量目标必须可度量。** "系统要稳定"不是目标；"连续运行 72h 无未处理异常，P0 缺陷为 0"才是目标。

## S1 需求工程

| 项 | 内容 |
|---|---|
| **对应标准过程** | 利益相关方需求定义、系统/软件需求分析（GB/T 8566-2022 技术类过程） |
| **准入** | 立项评审通过，项目开发计划已批准 |
| **核心活动** | 需求获取与确认；功能/非功能需求分离；需求**可验证化改写**；接口需求识别；需求编号与属性（优先级、来源、验收准则）；建立需求追溯矩阵 |
| **交付物** | ① 软件需求规格说明（GB/T 9385-2008 结构）② 接口需求规格说明 ③ 需求追溯矩阵（RTM）④ 需求评审记录 |
| **准出门禁** | **需求评审**通过；**需求基线**建立并打标签；每条需求都有唯一编号 + 验收准则；无 TBD 残留（或 TBD 有责任人与关闭日期） |
| **常见失败** | 需求写成愿望（"界面要美观"）→ 到测试阶段无法判定通过与否，返工成本爆炸 |

### 需求可验证化改写：本仓库的硬要求

| ❌ 不可验证 | ✅ 可验证 |
|---|---|
| 界面要美观 | 主流程操作步数 ≤ 5 步；关键操作响应 ≤ 200ms（P95） |
| 系统要稳定 | 连续运行 72h 无未处理异常；MTBF ≥ 200h |
| 支持大数据量 | 单表 1000 万行下，列表查询响应 ≤ 2s（P95） |
| 要安全 | 通过 OWASP Top 10 检查；口令存储 bcrypt(cost≥10)；越权访问用例 100% 拦截 |

**规则：任何写进 SRS 的需求，都必须能推导出至少一条测试用例。写不出测试用例的需求 = 不合格需求。**

## S2 框架设计（第一次框架基线）

| 项 | 内容 |
|---|---|
| **对应标准过程** | 架构设计、设计定义（GB/T 8566-2022 技术类过程） |
| **准入** | 需求基线已建立 |
| **核心活动** | 架构风格选型；分层与边界划分；**模块划分与模块号分配**；模块间接口契约定义；数据模型；错误处理与日志策略；部署视图；**明确标注"当前框架假设"** |
| **交付物** | ① 软件概要设计说明（HLD）② 模块清单与模块号登记表 ③ 模块接口契约 ④ 框架基线 v0.x |
| **准出门禁** | **框架评审**通过；模块边界无循环依赖；每个模块有明确职责与对外契约；**框架假设清单**已成文（这是后续迭代的输入） |
| **常见失败** | 追求"一次设计到位"→ 设计期无限拉长，或用错误抽象锁死实现 |

> **关键心态**：S2 的框架是**假设**，不是**真理**。把假设显式写下来（"假设 A：所有数据源都是同步的"），
> 实现阶段一旦推翻，变更就有据可依、有范围可控。

## S3 骨架跑通（先跑起来）

| 项 | 内容 |
|---|---|
| **对应标准过程** | 实现过程的前置验证（GB/T 8566-2022 技术类过程） |
| **准入** | 框架基线已建立 |
| **核心活动** | 搭建最小可运行骨架：主流程贯通 + 各模块**桩/Mock 实现** + 日志 + 配置 + 构建脚本 + 冒烟测试 + CI 流水线；验证模块装配与依赖解析 |
| **交付物** | ① 可运行骨架（能一条命令跑起来）② 冒烟测试用例与记录 ③ CI 流水线配置 ④ 骨架跑通验证记录 |
| **准出门禁** | **一条命令可跑通**；冒烟测试通过；CI 在干净环境可复现通过；模块注册/依赖解析无环 |
| **常见失败** | 直接进模块实现 → 到集成时才发现构建、装配、依赖全都对不上，返工到怀疑人生 |

> **本仓库的立场**：S3 是**独立阶段**，不是 S4 的一部分。
> "先跑起来"的价值在于：**用最低成本暴露框架的结构性错误**，此时推翻框架的代价最小。
>
> 可直接用 `skeleton/` 作为 S3 的参照实现：`python skeleton/run_skeleton.py`。

## S4 模块实现（框架-模块共演化主战场）

| 项 | 内容 |
|---|---|
| **对应标准过程** | 软件实现、软件单元测试（GB/T 8566-2022 技术类过程） |
| **准入** | 骨架跑通，框架基线 v0.x 已建立 |
| **核心活动** | 逐模块循环：详细设计 → 编码 → 单元测试 → 模块自测 → **框架适配性回判** → 必要时提框架变更 → 更新框架基线 → 继续下一模块 |
| **交付物** | ① 软件详细设计说明（按模块增量）② 模块代码 ③ 单元测试用例与记录 ④ 覆盖率报告 ⑤ **框架变更申请与影响分析**（每次框架变更）⑥ 框架基线 vN |
| **准出门禁** | **模块评审**通过；单元测试全部通过；覆盖率达标（行 ≥ 80%，核心逻辑分支 ≥ 90%，阈值可按裁剪调整但须声明）；无遗留 P0/P1 缺陷；**框架变更已回写设计文档**（文档与代码不得漂移） |
| **常见失败** | 改了框架但不改设计文档 → 文档与代码脱节，下一个接手的人（包括未来的你）直接踩坑 |

### 每个模块的实现循环（标准动作，不可跳步）

```
① 读契约 → ② 详细设计 → ③ 写测试（先测试后实现亦可） → ④ 编码
   → ⑤ 单元测试通过 → ⑥ 模块自测 → ⑦ 框架适配性回判 ─┬─ 适配 → ⑧ 更新文档 → ⑨ 提交 + 评审
                                                      └─ 不适配 → 提框架变更 → 回到 S2 → 更新框架基线 → 重入 ④
```

详见 [`框架与模块共演化.md`](框架与模块共演化.md)。

## S5 集成与系统测试

| 项 | 内容 |
|---|---|
| **对应标准过程** | 软件集成、**验证**（GB/T 8566-2022 §6.4.9）；测试过程（GB/T 38634.2-2020） |
| **准入** | 全部计划内模块通过模块评审 |

| **交付物** | ① 集成测试计划/说明/报告 ② 系统测试计划/说明/报告 ③ 缺陷清单 ④ 覆盖率与追溯矩阵更新 |
| **准出门禁** | **测试准出评审**通过；P0/P1 缺陷为 0，P2 缺陷有明确处置计划；需求覆盖率 100%（每条需求至少一条用例）；用例执行率 100% |
| **常见失败** | 只测正常流程 → 生产环境一遇异常路径就崩 |

## 硬条款速查（H-01…H-26）

> **这些不是"注意事项"，是与准出门禁同级的条款。** 判据、判定人、判不过怎么办、反例见
> [`附件二`](../附件/附件二-阶段流程与交付物.md) §0.2。

| # | 名称 | 一句话 |
|---|---|---|
| H-01 | 阶段外产物 | 超前起草必须**登记 + 带横幅 + 在原阶段重做**；未撤销不得入基线；累计 > 3 份触发复盘 |
| H-02 | 账实对账 | 登记行必须与实存逐行对账，且对账**由会失败的命令执行** |
| H-03 | 判据可判定性 | 每条判据须有**操作定义 + 比对对象 + 期望值/阈值 + 一个反例** |
| H-04 | 门禁自证会红 | 每道门禁**自证会红**；**「未能校验」按「校验不通过」**（fail-closed） |
| H-05 | 判据辖区 | 决定产物**字节/身份**的配置面必须有门禁归属，**不得留无主判据面** |
| H-06 | 单一出处 | 每个事实只有一个权威载体，其它文档**只引用不复述数值** |
| H-07 | 数字三要素 | 凡数字落笔附**复算命令 + 时点 + 对象**；"实测"必须能指向一条命令 |
| H-08 | 引用锚点 | 文档间用**节号 + 锚点原文**；**行号只用于代码与制品（+提交号）** |
| H-09 | 证据四要素 | 实测 = 命令 + 原始输出 + 环境版本号 + 提交号；文档核查 = 路径 + 逐字引用 |
| H-10 | 冻结 | **每完成一份产物即提交**；**评审对象 = 冻结提交的 blob**；摘要以仓库 blob 字节为准 |
| H-11 | 批量操作纪律 | 禁别名同形函数名；绝对路径；**先打印命中集合**；**改后复读断言**；未提交时禁批量操作 |
| H-12 | 席位与部分 | **有几部分技术就设几位专家**；无主部分不可；**不得跨部分下判断**；席位表随部分清单冻结 |
| H-13 | AI 不代签不代裁 | AI 只给**建议值 + 代价**；勾选签字留人；必须写**"建议不等于是"** |
| H-14 | 追认出口 | "先实施后补批"唯一出口 = **事后追认**（时点 + 批准人 + 回退点）；**不得成为默认路径** |
| H-15 | 判据载体 | 每份产物写明**其阶段准出判据由哪份文档承担**；写不出的阶段**不得声称完成** |
| H-16 | 验证面独立 | 验证面**不得用被测实现自身的解析器**；每条判定配**真的会失败的反例** |
| H-17 | 默认值覆盖 | 交付形态有默认值时，用例**至少覆盖一次默认形态** |
| H-18 | 未决项引用 | `TBD-##` 必须写全 `<文档编号> 附录<X> TBD-##`；**裸写视为无效引用** |
| H-19 | 反规模裁剪 | **不得以"现状规模小"为由裁剪或合并文档形态**；**接口类文档必须独立成文** |
| H-20 | 机制有消费者 | 每条机制写明**谁读 / 记在哪 / 不读会怎样**；缺一不得写进流程 |
| H-21 | 承诺可实测 | 每处能力声明都要能指向命令或测试位置；**留着做不到的承诺比没有承诺更坏** |
| H-22 | 辩证处置 | 意见**先复算前提**；处置表四态 + 代价 + 落笔坐标；**反驳是合法输出**；按部分归口 |
| H-23 | 部分清单是一等公民 | 每阶段开工前**冻结技术部分清单**；**按部分设技术官员（1:1）**；席位表与清单**同一提交**；**不得有无主部分** |
| H-24 | 技术评审看内容 | **每阶段必有技术评审（含立项）**；「**格式齐备**」与「**内容已裁定**」**分列两条准出**，**只有前者不算过** |
| H-25 | 反复评审到定案 | **轮次不设上限**直到无保留意见；**分歧不得上抛**：胜负只由**标准条款**或**实测**判定；判不了的**当场做实验** |
| H-26 | 无效轮次判据 | 一轮**无技术内容改动也无明确裁定** ⇒ **无效、须重做**；**立项阶段的中心是"需求与目标口径"**（要什么/给谁/怎么算做成了/目标值多少） |

## 技术评审主链（六环，不可跳）

```
① 部分清单 → ② 席位(1:1) → ③ 技术评审(看内容) → ④ 逐条辩证处置(允许反驳)
                                                            │
   ⑦ 才允许准出 ←─────── ⑥ 反复轮次收敛 ←──── ⑤ 未闭环？回 ③
```

**前六环是准出的承重墙；缺任一环，准出结论没有依据。** 完整说明见
[`附件二`](../附件/附件二-阶段流程与交付物.md) **§0.11**。

> **A 档不设评审会，但六环照走**：技术官员由**本人换身份**担任；
> 第②环的等价要求是"**逐部分独立过判据并分别留痕，不得一次判断覆盖多个部分**"。
> **"轻"体现在会议形式，不体现在这条链上。**

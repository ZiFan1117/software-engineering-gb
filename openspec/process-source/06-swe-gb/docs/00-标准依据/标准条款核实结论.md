2. **12 份的创建时间全部落在 2026-09-21 的 21:38–21:57，共 19 分钟**——这是"批量下载 + 批量打包"，不是逐份取得的正式出版物。
3. **每页恰好一整张 729×1032 的 JPEG**，这个尺寸是典型"在线阅读器一页一图"的输出规格。
4. **全篇没有印刷页码（folio）**：页眉统一为 `GB/T 8567-2006《计算机软件文档编制规范》`，**页脚是整片空白**（已实测：底部 7% × 全宽、底部 4.5% × 右半，两次 OCR 均为空；600 dpi 放大目视亦为白）。
5. **正文标题带彩色**：`7.8 接口需求规格说明(IRS)` 是**橙色**、`说明：` 与 `……格式如下：` 是**蓝色**。GB 正式出版物是黑白印刷，彩色标题说明这是**第三方重排版件**的截图。

### 0.2 由此产生的三条重大限制

| # | 限制 | 后果 |
|---|---|---|
| L1 | **"原图"只有 ≈96 dpi** | 汉字约 12 px 高。任何"300 dpi / 900 dpi 放大"都只是**插值**，不增加信息。**标点级结论（半角/全角括号、`。`/`.`、`：`/`；`）在此分辨率下不可靠判定。** |
| L2 | **没有印刷页码** | 只能引用 **PDF 物理页码**。本文件所有页码均为 PDF 物理页。 |
| L3 | **不是官方件** | 本文件的"已回原图核"= 回**本库所存这一份 PDF 的页面位图**核，**不等于**回官方版本核。凡涉及对外合规声明，**必须另取官方渠道件复核**。 |

> **对 README 两处说法的更正**
> - README 称 `GB/T 8567-2006` "官方公布的 **132 页**，手上这份只有 **100 页**，对不上"。
>   **实测：该 PDF 确为 100 页（`pypdf 6.19.0` 与 `PyMuPDF 1.28.2` 两引擎一致），且它是完整件、不是残件**——
>   首页为封面（`GB/T 8567-2006`、`代替GB/T8567-1988`、`2006-03-14发布`、`2006-07-01实施`），
>   第 100 页为**全篇最后一页**，以 `参考文献`（GB 9385-1988、GB 9386-1988、GB/T 12504-1990、
>   GB/T 12505-1990、SJ/T 11291-2003、SJ 20778-2000、ISO/IEC JTC1/SC7 N2106）结尾。
>   **⇒ "100 vs 132" 不能证明扫描被裁剪**；正确解释是：**该件是第三方重排版的截图打包，其分页与官方印刷分页本就无关**。
> - README 称 `standards/README.md` 是"唯一进 git 的"。**实测：`git ls-files -- standards/` 为空，
>   README 也从未被 `git add`**。即 `standards/` 目前是**零跟踪目录**。**此项不擅自处理，登记为人裁。**

### 0.3 现有 OCR（`_md_mineru/`）有一个致命结构缺陷

**16 份 MD 里 `<!-- page` 出现次数全部为 0**（实测 `GB-T-8567-2006` 版：0 次）。
⇒ **现有 MD 没有任何页码锚点，无法把 MD 行号映射回 PDF 页，也就无法"回原图核"。**
这正是本次必须重建 OCR 的**硬理由**（不是"识别质量"问题，是"可核实性"问题）。

## 4. OCR 局限的如实说明（我们自己的判断）

### 4.1 本次重建 OCR 的方法与耗时（实测）

| 项 | 值 |
|---|---|
| 引擎 | RapidOCR / PP-OCR ONNX（`rapidocr-onnxruntime 1.4.4` + `onnxruntime 1.30.0`），CPU |
| 输入 | **PDF 内嵌位图原始像素**（729×1032，不重采样） |
| 命令 | `.venv-ocr\Scripts\python.exe standards\_md_reocr\reocr_rapidocr.py --only 8567 --native` |
| `GB/T 8567-2006`（100 页） | **465 秒（7.7 分钟）**，产出 4,681 行 / 384,622 B，低置信行 6 行（0.13%） |
| 产物位置 | `standards\_md_reocr\`（**已在 `.gitignore` 中，不入库，随用随弃**） |
| 额外能力 | 每页带 `<!-- page N -->` 页码锚点；**保留原缩进**；**不做段落合并**（合并会凭空造出原文没有的断句）；低置信行标 `<!-- conf=x.xx -->` |

**为什么用"原始像素"而不是 300 dpi 渲染**：源图只有 96 dpi，300 dpi 渲染只是插值放大。
同 8 页（p11–18）对比实测：**原始像素 41 秒 vs 300 dpi 60 秒**，且 300 dpi 版**引入了更多错误**（见 4.3）。

### 4.2 同一页两种渲染，**25.9% 的行互不相同**

在同 8 页（p11–18）、同引擎、同源图上，用 `difflib` 对齐后逐行比较：

```
实质内容行数: A=397  B=397
对齐后: {'equal': 294, 'replace': 103, 'delete': 2, 'insert': 2}
→ 真实内容分歧(replace) = 103 行, 占 A 的 25.9%
→ B 漏掉的行(delete) = 2 行
```

> ⚠️ 直接逐行配对会得到"80.4% 不一致"的**假数字**——那是行切分错位导致的连锁错位。
> **必须先用 `difflib` 做序列对齐**，`replace` 才是真实分歧。此教训已写进 `_diff_paired.py` 注释。

**⇒ 结论：在 96 dpi 源图上，OCR 结果不稳定，约每 4 行就有 1 行随渲染方式而变。**
**因此 OCR 文本绝不能作为逐字引用依据——这不是保守，是实测。**

### 4.3 错误类型与频率（全部为**回原图目视确认**的实例）

| 错误类型 | 实例（图中原文 → OCR 误读） | 出现情况 |
|---|---|---|
| **① 半/全角括号混淆（最高频）** | `(研究)` → `（研究）`；`a)` → `a）`；`(IRS)` → `（IRS)`（**左右不配对的混用**） | 两引擎**都**会犯。重建版 100 页中 `（… )` 混用形式多处（如 p2 L78 `7.8接口需求规格说明（IRS)`、p13 L652、p75 L3713） |
| **② 句末标点混淆** | `；` → `：`；`。` → `.` / `:` | 如 p11 列表项 `c)软件需求规格说明；` 两引擎均误读为 `：` |
| **③ 枚举标号丢失/误认** | `j)操作手册；` → `j操作手册；`；`o)开发进度月报；` → `0）开发进度月报：`；`f)运行与维护阶段。` → `运行与维护阶段。` | **仅 300 dpi 渲染版**，原始像素版正确 |
| **④ 形近字** | `允许` → `充许`；`问题分析图` → `向题分析图`；`目的` → `耳的目的`(MinerU) | 300 dpi 版与 MinerU 版各有；**原始像素版未见这三例** |
| **⑤ 整行漏识别** | p11「在子合同的文档中，文档管理者作为本标准的"需方"而子合同承担者作为"文档管理者"。」整行丢失 | **300 dpi 渲染版**漏；原始像素版正确 |
| **⑥ 双栏/表格阅读顺序错乱** | p11 的 a)–r) 双栏列表：300 dpi 版出现 `c↔1`、`e↔n`、`h↔q` 互换 | 两引擎均有不同程度的栏序漂移 |
| **⑦ 页眉/图表文字处理不一致** | 重建版**逐页读出了页眉** `GB/T 8567-2006《计算机软件文档编制规范》`（正确，图上确有）；MinerU **把页眉剥掉了**。反过来，重建版**读出了「图1 文档编制过程概要」流程图内的文字**，MinerU 只留 `![](base64…)` 图块、**图内文字全丢** | 两者互补，非单纯对错 |

**低置信标记的可靠性：差。** 4,681 行中仅 6 行被标低置信（0.13%），但上文①②类错误
**大量出现在高置信行里**。⇒ **`conf` 分数不能当质量门，只能当"可能有错"的弱提示。**

### 4.4 哪些页不可靠

- **全部 12 份国标，因源图 96 dpi，均处"标点不可判、形近字需人核"的状态**（唯一例外 `GB-T-38634.2-2020`，150 dpi，略好）。
- **双栏排版的页（目录页、a)–r) 类清单、表格页）**：阅读顺序不可信，**必须回原图**。
- **含流程图的页**：文字可能整块丢失（MinerU）或被并入正文（重建版），**引用图内文字必须回原图**。
- **彩色标题（橙/蓝）**：说明该件为第三方重排版，**不能据此判断官方版式**。

# 0) 前置：OCR 必须用仓库自带 venv（系统 python 无 rapidocr）

& $py 'D:\Code\06-swe-gb\standards\_md_reocr\_native_crop.py' `
  'D:\Code\06-swe-gb\standards\GB-T-8567-2006_计算机软件文档编制规范.pdf' 75 0.03 0.53 1.0 0.83 3 out.png

> ⚠️ **`_native_crop.py` 的坑（已踩过）**：jsPDF 生成的 PDF **所有页共用同一个 Resources 字典**，

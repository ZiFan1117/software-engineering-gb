## 一、30 秒上手

> ### ⭐ 本流程**以 B 档为标准**，A 档是它的缩小版
>
> **默认按 B 档做。** 全文所有要求，未特别标注的都是 **B 档要求**。
>
> **A 档**（个人 / 单产品）只在特定情形用，且**不是另一套流程**——
> 它只是"B 档哪些项可以放宽"的一张清单，集中在
> [`附件六-档位与裁剪.md`](附件/附件六-档位与裁剪.md) §五。
> **其余附件不再逐处讲 A 档。**

### 什么时候可以退到 A 档

| 判据 | 档位 |
|---|---|
| **三条全不命中** → 可用 A 档 | |
| ① 有第二个人需要交接或接手 | ❌ 必须 B 档 |
| ② 有外部交付物或验收责任 | ❌ 必须 B 档 |
| ③ 失效后果不可接受（数据/资金/安全） | ❌ 必须 B 档 |

> **反向也成立**：如果这个项目永远不会有人接手、也没有外部交付，
> **那它就该用 A 档**——给单人项目做正式评审记录是浪费，而且会因为"反正没人看"退化成走过场。

### A 档到底放宽了什么

| 项 | **B 档（标准）** | A 档（放宽） |
|---|---|---|
| 文档 | 全套（按需引用 `templates/`） | **6 份** |
| 评审 | **正式评审 + 记录 + 签署** | 换身份自查 + 自动化门禁 |
| 追溯 | 需求 ↔ 设计 ↔ 代码 ↔ 测试 | 需求 ↔ 测试 |
| 基线 | 需求 + 框架 + 产品**三类** | Git tag |
| RACI | **执行者与批准者必须分离** | 一人兼任（须换身份复核） |
| 规模参照 | ISO/IEC 29110 **Basic**（93 页） | Entry（36 页） |

### ⚠️ 四条红线，A 档也不可裁

① 版本控制　② 需求基线　③ 有记录的系统级测试　④ 变更留痕

> 这四条保护的是你自己。尤其版本控制——**唯一零成本的实践**。
>
> **另有九个"异常停"触发条件 A 档同样不可裁**（见 [`附件八`](附件/附件八-责任时间与阶段分解.md) §3.2）——
> 它们是**止损机制**，不是管理负担。

### ⚠️ 提交 GitHub = 按 B 档

**本仓库自身、以及任何走 GitHub PR 流程的项目，一律按 B 档要求。**
PR 即一次正式评审，须有变更请求记录、评审记录与影响分析。
详见 [`附件八`](附件/附件八-责任时间与阶段分解.md) §六。

## 二、八阶段一览

| 阶段 | 干什么 | 交付物 | 准出（门禁） |
|---|---|---|---|
| **S0 立项** | 定范围、约束、质量目标、**裁剪说明** | 项目计划 | **R0** 立项评审 |
| **S1 需求** | 需求获取 + **可验证化改写** | 需求规格说明、需求追溯矩阵 | **R1** 需求评审 + **需求基线** |
| **S2 框架设计** | 架构、模块划分、接口契约 | 设计文档（含**利益相关方与关注点**） | **R2** 框架评审 + 框架基线 |
| **S3 骨架跑通** | 最小可运行骨架（Mock） | 可运行骨架 + 冒烟测试 | **R3** + 一条命令跑通 |
| **S4 模块实现** | 逐模块：详设 → 编码 → 单测 | 模块代码 + 单测 + 覆盖率 | **R4 模块评审**（每模块） |
| **S5 集成/系统测试** | 集成、系统级验证 | 测试说明、测试报告 | **R6 测试准出评审** |
| **S6 验收** | 按 8 个质量特性组织验收 | 验收报告 + 产品基线 | **R7 验收评审** |
| **S7 交付维护** | 发布、回归、变更 | 版本说明、回归报告 | **R8 发布评审** |

> **原则**：**没有通过门禁，不进入下一阶段。**
> **门禁是同步点，不是时间点**——准出条件满足才推进，不看日历。
>
> 评审类型与准出准则见 [`附件三-评审与门禁.md`](附件/附件三-评审与门禁.md)；
> **谁批、何时停、不一致时改哪个**见 [`附件八-责任时间与阶段分解.md`](附件/附件八-责任时间与阶段分解.md)。

## 五、⚠️ 本仓库的边界（必须知道）

### 1. 标准原文只在本地，**不外发、不上传**

`standards/` 下有标准原文 PDF 和转换出的 Markdown，**均已从 git 排除**。

**原因**：国标 / ISO 正文均有**版权**（GJB 另有**密级**）。
推到公开仓库、发给外部，属于**再分发**，有法律风险。

`standards/_md_mineru/` 那 16 份 MD 是**本地检索用**的，**不要外发**。

### 2. 哪些是国标要求，哪些是本仓库强化

本仓库的做法**不全是国标原文要求**。引用时要分清：

| 标记 | 含义 |
|---|---|
| **【国标】** | 标准明文要求，可引条款号 |
| **【本仓库】** | 本仓库自行增加的工程强化项，**可裁剪，须留痕** |

典型区分：
- 【国标】需求可验证性、文档种类、测试记录
- 【本仓库】**S3 骨架跑通**独立成阶段、覆盖率 80% 阈值、`tools/` 自动门禁

### 3. 三个已知的坑

| 坑 | 说明 |
|---|---|
| **别引老标准** | `GB/T 15532-2008`、`GB/T 9386-2008`、`GB/T 12504/12505-90`、`GB/T 29831~29836`（已废止）、`GB/T 16260`、`GB/T 18905` 都**不要引** |
| **`GB/T 29110-2012` 不是软件标准** | 那是**道路交通**标准。中国**没有**采标 ISO/IEC 29110 |
| **文档标准 20 年未更新** | `GB/T 8567-2006` 是现行最新版，其修订计划 2005 年下达至今未完成。**它自己写明"可根据实际情况适当剪裁"** |

## 六、现在从哪开始

```
第 1 步  读本文件，按第一节定档位          → 得到 A 档或 B 档
第 2 步  读附件二，看每个阶段干什么        → 得到任务清单
第 3 步  读附件六，确认每阶段留多少证据     → 得到交付物清单
第 4 步  按附件七的指引，从 templates/ 取模板填
第 5 步  跑 tools/ 门禁验证
```

**最小可行动作（A 档，今天就能开始）**：

```powershell
python skeleton/run_skeleton.py       # ① 骨架能否跑通
python tests/test_module_system.py    # ② 单元测试（42 项）
python tools/trace_matrix.py          # ③ 需求↔测试追溯门禁
python tools/scope_check.py --demo    # ④ 改动是否越界（可选）
```

> **四条门禁 A 档 B 档都跑**——档位只影响**文档量与评审形式**，不影响门禁。
> 唯一要求：RTM 把 `设计模块号` 与 `实现代码位置` 两列也填上。
> （此口径曾与旧文档冲突，已于 2026-09-21 统一，见 [`附件/附件三-评审与门禁.md`](附件/附件三-评审与门禁.md) §4.3）

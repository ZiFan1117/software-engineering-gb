## 一、门禁为什么是硬闸，不是建议

### 1.1 门禁是什么

**评审是过程，门禁是结果。** 开会、走查、看代码都是过程；门禁只有两种取值：**放行**或**不放行**。没有"基本放行""放行但注意"这种第三态。

**门禁 = 一个生存周期阶段的"启动下一步的标准"是否全部满足的二元判定。**

> **【国标】** GB/T 32423-2015 §0.1 定义验证过程：提供客观证据证明产品是否实现——
> "c) 成功完成每个生存周期活动，并满足**启动下一步生存周期活动的所有标准**（即正确生产产品）"。
> 这句话就是门禁的标准出处：门禁就是这个"所有标准"。
>
> **【国标】** GB/T 8566-2022 **6.3.2.3 b) 7)** 把评审制度化了：项目应"进行必要的管理和技术评审、审核和检查"。
> 该条注写明其目的：**"确定转入生存周期的下一阶段或项目里程碑是否已经就绪"**。
> 即：评审是**项目评估与控制过程**的一项任务，不是团队自愿组织的活动。
>

### 1.2 验证 ≠ 确认，两个门禁不能互相顶替

**【国标】** GB/T 32423-2015 §0.1 把 V&V 拆成两条互补的证据链：

| | 验证（Verification） | 确认（Validation） |
|---|---|---|
| 问的问题 | 东西**做对了吗**（符合需求、架构、设计） | **做对的东西**了吗（符合预期用途与用户需求） |
| 证据判据 | 活动遵循需求；满足标准与惯例；**满足启动下一步的所有标准** | 满足分配给产品的系统需求；满足操作环境中的预期用途和用户需求 |
| 本仓库对应 | R1 / R2 / R3 / R4 / R5 / R6 / R8 | **R7 验收评审** |
| 依据 | GB/T 32423-2015 §0.1 a)~c) | GB/T 32423-2015 §0.1 a)~c) |

**落地含义**：测试全过（验证通过）**不等于**验收通过（确认通过）。
"我们内部测都过了"不能替代 R7；R7 的判据是用户的预期用途，不是你的测试用例。

### 1.3 为什么不能通融——四条理由

| # | 理由 | 讲透 |
|---|---|---|
| 1 | **门禁是唯一能主动改变返工成本曲线的时刻** | 缺陷修复成本随阶段单调上升。门禁不是"流程成本"，是**主动选择的拦截点**。跳过门禁不省时间，是把成本推到后面加倍支付。R3 骨架跑通是最极端的例子：此时代码量最小，推翻框架的代价最低；跳过它，代价在 S5 集成时集中爆发 |
| 2 | **门禁是"客观证据"的生产点，不是审批点** | **【国标】** GB/T 8566-2022 **6.4.9.2 e)** 要求验证过程输出"证明所实现的系统满足需求、架构和设计的**客观证据**"；**6.4.11.2 g)** 对确认过程有同样要求。证据必须在**评审对象的那一版**上当场产生。事后补出来的不是证据，是叙述——因为被评审的版本已经不存在了。**这就是"先做着，评审后补"被明令禁止的技术原因** |
| 3 | **门禁是可判定的责任边界** | B 档多人协作，"谁批准的"必须能答。签字栏是责任锚点，不是礼节。出了事能定位到人，流程才有约束力 |
| 4 | **A 档也躲不掉门禁，只是门禁的执行者从人换成了机器** | 人可以对自己通融，CI 不会。A 档放弃的是**评审会**，不是**门禁**。第四章展开 |

### 1.4 三条铁律

> **铁律一：没有准出结论，不进入下一阶段。**
> 下一阶段的一切工作属于**未授权开工**，其产出**不进入基线**。
>
> **铁律二：口头通过等于没通过。**
> 会上说"我觉得可以"、群里回"OK"、口头"大家没意见"——**均不产生门禁效力**。
> 结论以**书面记录 + 签字**为准。未签字的评审记录 = 未评审。
>
> **铁律三：不通过不是失败，是流程在工作。**
> 处置是"退回上一阶段修改 + 重新评审"，不是"降低标准凑合过"。
> **把问题拦在门禁上，是评审最大的价值。**

### 1.5 这些不算门禁通过

| ❌ 不算 | 为什么 |
|---|---|
| "先做着，评审后补" | 事后补的不是证据（见 1.3 理由 2）；且违反铁律一 |
| 群里的"OK"、口头"没问题" | 违反铁律二 |
| "检查单符合率 90%" | 符合率**不是**通过判据。门禁是**一票否决**：关键项（★）不符合即退回，哪怕符合率 99% |
| "条件已在推进中" | 有条件通过的条件**逾期自动降为退回**，不需要任何人再开会确认（见第五章） |
| "时间紧，先上线" | P0/P1 不许带病出厂。确需带病上线，必须由甲方/产品**书面**确认风险并转为"已知问题"，同时登记在版本说明里 |
| "标准说可以裁剪，所以我们不做了" | **【国标】** GB/T 8566-2022 **§4.3 剪裁符合**要求"**剪裁文本是为表明剪裁符合而声明的**"；**附录 A.2** 要求记录剪裁条件、从受影响各方获得输入、并声明删除了哪些输出/活动/任务。**未留痕的裁剪 = 没有裁剪，是漏做** |

## 二、评审类型总表（R0–R8）

> **R0–R8 的编号体系是本仓库的工程约定，不是国标分类。**
> GB/T 8566-2022 规定的是"进行必要的管理和技术评审"这一**任务**（6.3.2.3 b) 7)），
> 不规定评审的编号体系与种类划分。本表是它的落地裁剪。

| 编号 | 评审名称 | 时机 | 主持 | 必参 | 结论形式 | 对应阶段门禁 | A 档 |
|---|---|---|---|---|---|---|---|
| **R0** | 立项评审 | 项目启动前 | 项目负责人 | 甲方/产品、技术负责人、质量 | 批准 / 不批准 / 有条件批准 | **S0 准出** | 不开会 |
| **R1** | 需求评审 | 需求基线建立前 | 技术负责人 | 甲方/产品、设计、测试、开发 | 通过 / 退回 | **S1 准出** | 不开会 |
| **R2** | 框架（概要设计）评审 | 框架基线建立前 | 架构师 / 技术负责人 | 开发、测试、运维 | 通过 / 退回 | **S2 准出** | 不开会 |
| **R3** | 骨架跑通评审 | 骨架可运行后 | 技术负责人 | 开发、测试 | 通过 / 退回 | **S3 准出**（可简化，但**必须执行**） | 不开会 |
| **R4** | 模块评审（详细设计 + 代码） | 每个模块完成时 | 模块负责人 | 1 名同级开发、测试 | 通过 / 有条件通过 / 退回 | **S4 逐模块门禁** | 不开会 |
| **R5** | 框架变更评审 | 每次框架变更申请时 | 技术负责人 | 受影响模块负责人 | 批准 / 驳回 | **S4 内循环门禁** | 降级为留痕 |
| **R6** | 测试准出评审 | 系统测试完成 | 质量负责人 | 开发、测试、技术负责人 | 准出 / 不准出 | **S5 准出** | 不开会 |
| **R7** | 验收评审 | 验收测试完成 | 甲方 / 产品 | 全部干系人 | 验收通过 / 不通过 | **S6 准出** | 不开会 |
| **R8** | 发布评审 | 每次版本发布前 | 技术负责人 | 开发、测试、运维 | 发布 / 不发布 | **S7 准出** | 不开会 |

**"A 档 = 不开会"的准确含义**：门禁条目**一条都不删**，只是判定者从评审会换成 **CI + 自查清单**；
唯一的例外是 **R5**——它在 A 档降级为"变更留痕 + 影响自述"，但**不可取消**（它是四条红线之一）。
详见第四章。

> **R3、R4、R5 是本仓库的强化项** 【本仓库】。传统流程通常只有 R1/R2/R6，
> 导致"框架是否真能跑"和"框架变更是否受控"两个高风险点无人把关——
> 这正是"框架-模块共演化"最容易失控的地方。

### 2.1 评审记录编号

```
<项目代号>-RV-<评审类型>-<序号>-V<主版本>.<次版本>
例：PROJ-RV-R4-M01-003-V1.0
```

类别码 **RV**（ReView）。因评审记录数量多，编号中嵌入评审类型与序号。
空白表见 [`../../templates/06-评审类/01-阶段评审记录.md`](../../templates/06-评审类/01-阶段评审记录.md)，评审结束后归档至 `docs/records/`。

## 三、各评审的准入与准出准则

**读法**：准入不满足 → **评审立即终止**，不开会（B 档）；
准出中带 **★** 的是**关键项**，任一不符合 → 结论**只能是"退回"**，不得用"有条件通过"规避。

### R0 立项评审

| 项 | 内容 |
|---|---|
| **审什么** | 可行性研究报告、项目开发计划（含**裁剪说明**）、软件质量保证计划、软件配置管理计划、风险清单 |
| **准入**（不满足则不开始） | 有明确的需求来源（合同 / 任务书 / 内部立项单）<br>可行性研究与项目开发计划已成稿并标注版本号<br>材料提前 **≥1 个工作日**送达参会人 |
| **准出**（逐项，全满足才通过） | ★ 范围与约束明确且**可界定**<br>★ 质量目标**可度量**（"连续运行 72h 无未处理异常、P0 缺陷为 0"级；"系统要稳定"不合格）<br>★ **标准裁剪说明已声明**：裁剪项 / 理由 / 补偿措施 / 批准人<br>风险清单已建立，每条有责任人与应对措施<br>配置管理策略与版本化方案已确定<br>干系人（含甲方/产品）已识别<br>项目开发计划经批准 |
| **不通过的后果** | 不批准立项，或修改后重评。**未批准即开工 = 未授权开工**，产出不进基线 |

> **常见失败**：跳过裁剪说明 → 后续每个阶段都在争论"这个文档要不要写"，反复返工。

### R1 需求评审

| 项 | 内容 |
|---|---|
| **审什么** | 软件需求规格说明（SRS）、接口需求规格说明、需求追溯矩阵（RTM） |
| **准入** | SRS 已完成评审稿并标注版本号<br>RTM 已建立（每条需求有唯一编号）<br>材料提前 **≥1 个工作日**送达 |
| **准出** | ★ 每条需求**可验证**——能推导出至少一条测试用例<br>★ 每条需求有唯一编号、来源、优先级、验收准则<br>★ **需求基线已打标签**（如 `req-baseline/v1.0`）<br>功能需求与非功能需求分离，非功能需求有**量化指标**<br>接口需求已识别（外部系统、数据格式、异常约定）<br>无未闭环 TBD（若有，必须写明责任人与关闭日期）<br>评审意见全部闭环，或有明确处置结论 |
| **不通过的后果** | 退回 S1 修改后重评；**需求基线不建立**。S2 准入依赖需求基线，故整个项目**在此卡住** |

> **常见退回原因**：需求写成了愿望；缺少异常路径描述；非功能需求无量化；验收准则缺失。
>
> **【国标】可验证性**：需求必须是唯一的、完整的、无歧义的、一致的、可实现的、**可验证的**
> （GB/T 32423-2015 需求分析 V&V 相关任务；GB/T 45802-2025 需求工程过程）。
> **【本仓库】硬规则**：任何写进 SRS 的需求，都必须能推导出至少一条测试用例。**写不出测试用例的需求 = 不合格需求。**

### R2 框架（概要设计）评审

| 项 | 内容 |
|---|---|
| **审什么** | 软件概要设计说明（HLD）、模块清单与模块号登记表、模块接口契约（三件套） |
| **准入** | 需求基线已建立<br>HLD、模块清单、模块接口契约三件套齐备并标注版本 |
| **准出** | ★ 模块划分满足高内聚、低耦合、**无循环依赖**<br>★ 每个模块有唯一模块号、明确职责、对外契约（输入 / 输出 / **异常**）<br>★ **框架假设清单已产出**，每条假设有验证时点<br>架构风格与选型有**理由**（不是"因为流行"）<br>模块清单完整，覆盖全部已基线需求（RTM 正向追溯无缺口）<br>数据模型与关键状态流转已定义<br>错误处理、日志、配置、安全策略已定义<br>框架基线已打标签（`framework/v0.1`） |
| **不通过的后果** | 退回 S2；框架基线不建立，S3 不得开工 |

> **常见退回原因**：模块边界靠"感觉"划；契约只有成功路径没有异常；假设没写下来。
>
> **关键心态**：S2 的框架是**假设**，不是真理。把假设显式写下来（"假设 A：所有数据源都是同步的"），
> 实现阶段一旦推翻，变更就有据可依、有范围可控——这正是 R5 的输入。

### R3 骨架跑通评审

| 项 | 内容 |
|---|---|
| **审什么** | 可运行骨架、构建脚本、冒烟测试用例与记录、CI 流水线配置、骨架跑通验证记录 |
| **准入** | 框架基线已建立<br>骨架代码（含构建脚本）已提交，附提交号 |
| **准出** | ★ **一条命令**能在干净环境跑通骨架<br>★ 全部模块以桩 / Mock 形式**装配成功**<br>★ 模块注册与依赖解析正确、**无环**<br>★ 冒烟测试用例存在且通过<br>★ CI 流水线在**干净环境**可复现通过<br>日志、配置加载路径已验证 |
| **不通过的后果** | 退回 S2 / S3；**不得进入 S4 模块实现**。B 档本评审可简化（书面确认 + CI 记录），但**必须执行** |
| **为什么单独设这道门禁** | 骨架跑通是用**最低成本**验证框架结构正确性的**唯一时机**。此时代码量最小，推翻框架的代价最低。跳过它，代价会在 S5 集成时集中爆发 |

> **【本仓库】** S3 独立成阶段、R3 独立成评审，是本仓库的强化项。
> 可用本仓库 `skeleton/` 作为参照实现：`python skeleton/run_skeleton.py`。

### R4 模块评审

| 项 | 内容 |
|---|---|
| **审什么** | 模块代码 + 单元测试 + 该模块的详细设计章节 |
| **准入** | 模块代码已提交（含单元测试），附提交号<br>详细设计说明中该模块章节已更新 |
| **准出** | ★ 模块行为符合其**接口契约**<br>★ 覆盖率达标：**行 ≥80%，核心逻辑分支 ≥90%**（阈值可按裁剪调整，但**须声明**）<br>★ 覆盖**正常 / 边界 / 异常 / 空值**四类路径<br>★ 无遗留 **P0/P1** 缺陷<br>单元测试全部通过<br>无新增循环依赖（分层方向正确：低层不依赖高层）<br>**框架适配性回判已执行**——若不适配，已提 R5<br>设计文档与代码一致（**无漂移**）<br>至少 1 名同级开发完成代码走查并签字 |
| **不通过的后果** | 该模块不得并入 S5 集成；缺陷回修后重新提交并重评 |

> **落地载体**：R4 的主力不是会议室，是 **PR 模板 + CI**。逐项检查单直接写进 PR 描述，见第六章。
>
> **【本仓库】覆盖率 80% / 90% 阈值**：可裁剪，但裁剪必须在项目开发计划的裁剪说明里写明理由与补偿措施。

### R5 框架变更评审

| 项 | 内容 |
|---|---|
| **审什么** | 框架变更申请单（含触发条件编号 FC-1…FC-6 与**现象证据**）+ 影响分析 |
| **准入** | 变更申请单已完成，含触发条件编号与现象证据<br>影响分析已完成（受影响模块 / 需求 / 需重跑测试 / 工作量估算） |

## 四、A 档怎么办【例外章节】

> ⚠️ **A 档是 B 档的例外，不是另一套流程。**
> **本章只讲"评审这一环"在 A 档怎么落。**
> A 档的**完整放宽清单**（13 项对照）在
> [`附件六-档位与裁剪.md`](附件六-档位与裁剪.md) **§6.2**——那是 A 档的**唯一定义**。
>
> **一句话**：**A 档不开 R0–R8 评审会，但门禁一条都不少——执行者从"评审会"换成了"CI + 自查清单"。**
>
> 如果你只有一个人，却按 B 档准备评审材料、约人开会、写签署记录，
> 那不是严谨，是浪费——而且会因为"反正没人看"退化成走过场。

### 4.1 这不是偷懒，标准本身提供了这条路

| 依据 | 内容 |
|---|---|
| **【国标】** GB/T 32423-2015 **第 5 章「完整性级别」** | V&V 任务的**范围、强度和严格程度**应与完整性级别相当："完整性级别降低，相关的 V&V 任务要求的范围、强度和严格程度也随之降低" |
| **【国标】** 同标准 **6.2** 的 V&V 测试强度表 | 同一张表里，完整性级别 4 是"**实施**"（真做），级别 2 是"**评审**"（只看），级别 1 是"**无动作**"。**"用评审代替实施"是标准写明的合法强度档位** |
| **【国标】** GB/T 8566-2022 **§4.3 剪裁符合** + **附录 A（规范性）剪裁过程** | 允许选择与修改本文件的章条内容；A.2.3 要求识别记录剪裁条件、从受影响各方获得输入、**声明删除了哪些输出/活动/任务**；声明"完全符合"时**不准许**剪裁 |

**推论**：A 档 = 低完整性级别。"不开评审会"对应到标准里的强度是"评审 / 检查"级，
而不是"无动作"——**所以 A 档必须保留一个等效的验证动作，那就是自动化门禁**。
把这个判定写进项目开发计划的「裁剪说明」即可完成留痕。

### 4.2 A 档门禁清单：跑什么命令、看什么结果

> **注意**：下表用本仓库的 `skeleton/`、`tests/`、`tools/` 作为**参照实现**。
> 换到你自己的项目时，把命令换成**你项目的等效命令**，**判据不变**。

| # | 门禁 | 命令 | 通过判据 | 不通过怎么办 | 替代哪个 B 档评审 |
|---|---|---|---|---|---|
| **G1** | 骨架跑通 | `python skeleton/run_skeleton.py` | 退出码 0；模块全部装配成功、依赖解析**无环** | 先修，**不叠加新功能** | **R3**（+ R2 的"无循环依赖"项） |
| **G2** | 单元测试 | `python tests/test_module_system.py`<br>（零依赖模式，无 pytest 也必须能跑） | 退出码 0；全部用例通过 | 先修，不叠加新功能 | **R4** |
| **G3** | 覆盖率 | `python -m pytest tests -q --cov=skeleton --cov-report=term-missing --cov-fail-under=80` | 退出码 0；行覆盖率 **≥80%** | 补测试后再提交 | **R4**（覆盖率 ★ 项） |
| **G4** | 需求 ↔ 测试追溯 | `python tools/trace_matrix.py` | 退出码 0 | 补 RTM 后重跑 | **R1 / R6**（需求覆盖率 100%） |
| **G5** | 改动范围 | `python tools/scope_check.py --base main --scope .scope-declaration.json` | 退出码 0（未越界） | 更新 `.scope-declaration.json`，或按"框架变更"处理 | **R5**（框架变更受控） |
| **G6** | 版本与留痕 | `git tag` + commit message 写清**为什么改** | 每次迭代有 tag；变更能回答"为什么改、影响什么" | 补 tag / 补说明后再继续 | **R5 / R8** |
| **G7** | 干净环境可复现 | 在**新的克隆 / 新机器**上重跑 G1–G3 | 全部通过 | 说明存在环境依赖，先解决 | **R3 / R6** 的"可复现"项 |

**一条命令全跑**（可直接贴进本地脚本或 pre-push 钩子）：

```powershell
# A 档门禁：任一步非 0 即停
python skeleton/run_skeleton.py
if ($LASTEXITCODE -ne 0) { Write-Error "G1 骨架门禁不通过"; exit 1 }

python tests/test_module_system.py
if ($LASTEXITCODE -ne 0) { Write-Error "G2 单元测试门禁不通过"; exit 1 }

python -m pytest tests -q --cov=skeleton --cov-report=term-missing --cov-fail-under=80
if ($LASTEXITCODE -ne 0) { Write-Error "G3 覆盖率门禁不通过"; exit 1 }

python tools/trace_matrix.py
if ($LASTEXITCODE -ne 0) { Write-Error "G4 追溯门禁不通过"; exit 1 }
```

> ⚠️ **PowerShell 不会因为上一条命令非 0 退出码而自动中断**，所以每条后面必须显式判 `$LASTEXITCODE`。
> 漏掉这一步，你的"门禁"会在第一个失败之后继续跑完并返回 0——**等于没有门禁**。

### 4.3 口径（已于 2026-09-21 统一）

**结论：A 档照样跑 `trace_matrix.py`。**

| 曾经的冲突 | 现状 |
|---|---|
| `导读本.md` 把它列为 A 档最小动作之一 | ✅ **以此为准** |
| `流程档位定义.md` §4.2 旧版说"A 档不需要" | 已修正，并注明该工具按实现确属全链门禁 |

**代价**：该工具要求 RTM 14 列齐备，A 档把 `设计模块号` 与 `实现代码位置` 一并填上即可——
模块少，多填两列约几分钟。

**理由**：不新增口径、不新增工具，且自动化门禁在 A 档的价值本来就高于手工核对。
**A 档的"轻"体现在文档量与评审形式上，不体现在门禁上。**

### 4.4 A 档 vs B 档：逐项差异

> **完整对照表见 [`附件六-档位与裁剪.md`](附件六-档位与裁剪.md) §6.2**（13 项）。
> 下表只列**与评审直接相关**的部分。

| 维度 | **A 档：个人 / 单产品** | **B 档：本流程标准** |
|---|---|---|
| **阶段评审** | **不开会**。R0–R8 一律不用组织 | R0–R8 正式评审，有主持人、记录、签署 |
| **门禁怎么判** | **CI 退出码 + 自查清单**（G1–G7） | 评审会逐项结论 + 检查单 + 签字 |
| **准入检查** | 不适用（无会可开） | 材料提前 ≥1 个工作日送达；**关键角色缺席 → 评审无效** |
| **结论形式** | 通过 = 命令返回 0 | 书面结论，**只有三种**：通过 / 有条件通过 / 退回 |
| **角色齐备** | 不适用 | **缺测试参与 → 评审无效**（可测试性是设计质量的核心判据） |
| **证据归档** | 不需要独立归档——**git 历史就是证据** | `docs/records/`，每次评审一份记录 |
| **升档** | 三条判据任一命中 → **立即升 B 档，不可逆** | — |

**升档判据**（任一命中即 B 档，A 档读者请定期自查）：

| # | 判据 | 为什么 |
|---|---|---|
| 1 | **有第二个人需要交接或接手** | 交接是最贵的事。文档的本质是**异步沟通** |
| 2 | **有外部交付物或验收责任** | 有验收方 = 有判定标准 = 必须留下可举证的记录 |
| 3 | **失效后果不可接受**（数据丢失、资金、安全、不可回滚） | 风险等级决定证据等级，**与人数无关** |

> **判据 1 是双向的**：如果这个项目永远不会有人接手，那它**就该留在 A 档**，不要给它套 B 档的流程。
> 给单人项目做正式评审记录是纯粹的浪费——而且会因为"反正没人看"而退化成走过场。

### 4.5 A 档的四条红线（不可裁，也不受"不开评审会"影响）

| # | 红线 | 落在哪条门禁上 | 为什么 A 档也躲不掉 |
|---|---|---|---|
| 1 | **版本控制** | G6（`git tag`） | 没有它，你连"上周那版能跑"都回不去。**唯一一条零成本的实践** |
| 2 | **需求基线**（哪怕只有几条要点） | G4（RTM 的 `需求基线版本` 列） | 没有基线就没有"变更"这个概念，改到哪算哪 |
| 3 | **至少一个级别的、有记录的系统级测试** | G2 / G3 / G7 | 你自己就是验收方。**没记录的测试等于没测**——因为你无法复现 |
| 4 | **变更留痕**（哪怕只是 commit message 写清为什么） | G6 | 三个月后的你会问"这行为什么这么写"。**A 档没有评审会来兜底，留痕是唯一的记忆载体** |

### 4.6 A 档主动放弃什么（显式声明，不装作不存在）

| 放弃项 | 风险 | 补偿方式 |
|---|---|---|
| 正式阶段评审 | 重大设计缺陷可能晚发现 | 靠 **S3 骨架跑通**尽早暴露结构错误 |
| 完整 RTM 追溯 | 需求变更时可能漏改 | 靠测试覆盖 + 条目化需求清单 |
| 独立 SQA | 质量靠自检 | 靠**自动化门禁**替代人工检查 |
| 配置审计 | 交付物可能不齐 | 靠 **Git tag + 一条命令可复现** |

> **诚实原则**：A 档是**主动接受**这些风险，不是"因为懒所以没做"。
> 这两者在出问题时的应对完全不同——**前者有预案，后者只有慌**。

### 4.7 A 档的四种常见误用

| ❌ 误用 | ✅ 正确理解 |
|---|---|
| "我是 A 档，所以不用门禁" | A 档只是不用**评审会**。G1–G7 一条都不能少 |
| "CI 过了就等于需求没问题" | CI 判不了"需求是否写对了"。**机器判不了判断类问题**——A 档靠 S3 骨架跑通尽早暴露结构错误 |
| "我是 A 档，但项目要交付给客户，走 A 档流程就行" | **有验收方就是 B 档（判据 2）**。请立即升档并按第六章补建 RTM 与基线 |
| "我是单人，但为了严谨我按 B 档开评审会" | 单人评审会没有独立视角，必然退化成走过场。**该留 A 档就留 A 档** |

## 五、评审有效性规则（防止评审形式化）

> **形式化的评审比不评审更危险**——它会产生"已经检查过"的虚假信心，而且留下合规的假象。
> 这一章是 B 档评审能不能真正起作用的分界线。A 档读者可跳过本章前半部分，
> 但 **5.6 的反形式化信号对 A 档的自查清单同样适用**。

### 5.1 六条基本规则

| 规则 | 要求 | 违反了会怎样 |
|---|---|---|
| **材料前置** | 评审材料至少提前 **1 个工作日**送达，**会上不做首次阅读** | 未满足送达时限 → 评审结论**不受认可**，须重新组织 |
| **角色齐备** | 必参角色按第二章总表；**缺测试参与的评审无效** | 关键角色缺席 → 评审**无效**，不得产出准出结论 |
| **记录留痕** | 每个评审意见有编号、责任人、闭环状态 | **未闭环的意见不得通过** |
| **结论明确** | **只有三种结论**：通过 / 有条件通过（附条件清单与期限）/ 退回 | 自创选项（"原则通过""基本通过""待补充后通过"）→ **无效结论，门禁不予放行** |
| **时限约束** | 有条件通过的条件必须在**下一阶段门禁前**闭环 | 逾期 → **自动降为退回，无需再开会确认** |
| **反形式化** | 某类评审**连续 3 次"零意见通过"** → 检查是否流于形式并调整检查单 | 零意见通常不代表零缺陷，而代表**检查单太粗**或**参会人未做前置阅读** |

### 5.2 评审无效的五种情形（有效性预检）

> **任一预检项不通过 → 本次评审无效**，须补齐后重新组织。无效评审**不得产出准出结论**。

| # | 情形 | 判据 |
|---|---|---|
| 1 | 材料未提前送达 | 距评审日 < 1 个工作日 |
| 2 | 必参角色不齐 | 对照第二章总表的"必参"列 |
| 3 | **测试角色缺席** | 单项即判无效，无例外 |
| 4 | 评审对象版本不明 | 未标注文档版本号 / 代码提交号 |
| 5 | 准入未核对 | 未按第三章逐条核对准入准则 |

### 5.3 结论与"★ 关键项一票否决"

| 结论 | 含义 | 后续动作 | 门禁效力 |
|---|---|---|---|
| **通过** | 全部 ★ 关键项符合，意见全部闭环 | 进入下一阶段，建立 / 更新对应基线 | ✅ 放行 |
| **有条件通过** | **非关键项**存在待办，不影响主体准出 | 条件清单各项须在**下一阶段门禁前**闭环 | ⚠️ 限期放行 |
| **退回** | 存在 **★ 关键项不符合** | 返回上一阶段修改后**重新评审** | ❌ 不放行 |

> **规则**：存在**任一 ★ 关键项"不符合" → 结论只能为"退回"**，不得以"有条件通过"规避关键项。
>
> **符合率不是通过判据。** 门禁是一票否决式的：关键项不符合时，即使符合率 90% 也必须退回。
> ★ 关键项由项目在裁剪时确定，**关键项的选取属项目风险判断**，模板只提供标注位与判定规则。

### 5.4 有条件通过的时效约束

> **有条件通过的条件必须在下一阶段门禁前闭环，否则自动降为退回。**
> **该降级自动生效，不需要任何人再次开会确认。**
> 条件逾期未闭环时，下一阶段评审主持人**必须**按"退回"处理，
> **不得以"条件已在推进中"为由放行。**

条件清单必须写全四项：**条件内容 / 闭环判据 / 责任人 / 期限**，且**期限必须早于下一阶段门禁日期**。

### 5.5 意见质量要求

| 要求 | 说明 | 反例 |
|---|---|---|
| **具体** | 指出位置与现象 | ❌"文档需要再完善" |
| **可执行** | 明确要做什么 | ❌"注意一下一致性" |
| **可验证** | 能判断是否已闭环 | ❌"提升可读性" |
| **有责任人** | **指定到人，不到组** | ❌"开发组负责" |
| **不接受要写理由** | 记录为何不改 | ❌ 直接删除意见 |

**好差写法对照**：

| ❌ 无法判断是否闭环 | ✅ 具体、可执行、可验证、有责任人 |
|---|---|
| "需求写得不清楚" | "`REQ-F-001` 的验收准则缺量化指标，无法推导出测试用例 `TC-001`；须补齐指标后重新评审（`OP-01`，责任人 `<姓名>`）" |
| "模块质量还行，再看看" | "`M01` 的 `<函数名>` 未覆盖空值路径，缺陷 `BUG-001` 即由此产生；须补测后重新提交（`OP-02`，责任人 `<姓名>`）" |
| "覆盖率有点低" | "`M01` 核心逻辑分支覆盖率为 `<n>%`，低于 90% 阈值；须补齐 `TBD-01` 所列分支（`OP-03`，责任人 `<姓名>`）" |
| "文档注意保持一致" | "`<文档编号>` 第 `<x>` 章仍描述旧接口，与 `IF-007` 契约不一致；须在同一次提交内更新（`OP-04`）" |

### 5.6 评审形式化的七种典型表现

> 这一节是**审计与自查的检查单**。发现任何一种，该次评审的可信度都要打折。

| # | 表现 | 为什么是形式化 |
|---|---|---|
| 1 | 结论栏自创选项（"原则通过""基本通过"） | 三种之外都是无效结论，门禁不予放行 |
| 2 | **用"有条件通过"规避 ★ 关键项不符合** | **最典型、最常见的形式化手法**。把关键问题包装成"条件"即等于放行 |
| 3 | 条件清单不写期限，或期限晚于下一阶段门禁 | 条件永不到期 = 永不闭环 = 有条件通过变成无条件通过 |
| 4 | 意见写"需要再完善""建议优化" | 无法判断是否闭环的意见 = 没有意见 |
| 5 | 准入不满足仍开会并产出结论 | 材料未前置、关键角色（尤其**测试**）缺席的评审**无效** |
| 6 | 检查单合并成一行"整体符合" | 合并填写使评审无法追溯，**无法在后续审计中证明检查确实发生过** |
| 7 | **签字栏空缺就进入下一阶段** | 最严重的违规。**口头通过等于没通过**；未签字的记录不产生门禁效力，下一阶段的产出**不进入基线** |

### 5.7 反形式化的三个预警信号

| 信号 | 说明 | 处置 |
|---|---|---|
| 某类评审**连续 3 次零意见通过** | 零意见 ≠ 零缺陷 | 检查检查单是否太粗、参会人是否做了前置阅读；**调整检查单** |
| 符合率很高但 ★ 关键项"部分符合" | 关键项被稀释成普通项 | 复核 ★ 项的选取；把"部分符合"在关键项上**一律按不符合**处理 |
| 意见**全部**是"改进类"，无一条"缺陷类" | 评审在提建议，不是在找问题 | 检查单中增加可判定的"不符合"触发条件 |
| 有条件通过的**条件清单长期为空** | 说明结论被滥用为"通过"的同义词 | 直接取消该类评审的"有条件通过"选项 |

### 5.8 ⭐ 评审意见的处置表（本版新增；完整结构见 [`../02-评审与门禁/评审门禁与检查单.md`](../02-评审与门禁/评审门禁与检查单.md) §4.2）

> **【本仓库】自定机制，无国标直接对应**——GB/T 8566-2022 只要求"进行必要的管理和技术评审"
> （**6.3.2.3 b) 7)**），**不规定意见如何处置**；GB/T 32421-2015 讲评审怎么做，也不规定处置表形态。
> 本条是为解决两类实际吃过的亏而立的。

**一句话**：**专家的意见我们不一定要采纳**（项目负责人的明确要求）；
**有些时候，他是片面地看问题，不是全部都看问题**。

| 要素 | 规定 |
|---|---|
| **第一步** | **当场复算意见的前提**——前提不成立的，无论提的人是谁、措辞多重，**一律不采纳** |
| **四态** | `采纳` / `部分采纳` / `反驳（给理由与依据）` / `属本项目执行问题（不是条款缺陷）` |
| **三栏必填** | **代价**、**落笔坐标**（文件:节 + **改前改后原文**）、**谁定** |
| **反驳** | **是合法输出**，但必须给理由与依据（标准条款或实测输出）；**"为了显得配合而照抄"明列为反模式** |
| **可核性** | **不接受"已处理""已优化"这类无坐标的说法** |
| **效力** | 处置表**在获批前不改变任何规范条款的效力**——它是**执行计划，不是新法** |
| **两节必列** | ①「**被评审方自己造成的错误**」（不混入"项目问题"）；②「**各评委确认站得住、不得为统一格式而改写**的部分」 |
| **被推翻的判词** | **不得删除**，必须单列一行：原判词 / **复现命令** / **观测到的输出** / 提出人轮次。**同一断言再次出现时，先跑该命令** |
| **按部分归口** | 一位专家**只判他那一部分**；**跨部分的结论必须由该部分的专家出**；汇总人不得替某部分下判断（与 **H-12** 席位一一对应配套） |

**片面看问题的四种典型形态**：① 只看自己那部分却给出影响别部分的结论；
② 把"条件性推论"当成"代码/文档事实"；③ 给出无法判定的判据；
④ 要求改别部分的载体。

> **实际案例（经验来源，本仓库未复现）**：一条"`check.sh` 吞掉失败"的 **P0 判词**，
> 被**两位不同评委先后各提一次**，**两次都被实测推翻**（`set -euo pipefail` 下管道失败**会**传播，`rc=1`）——
> 判词把"**没有 `pipefail` 时的行为**"当成了"**有 `pipefail` 时的行为**"。
> ⇒ 这正是"**先复算前提**"这一步存在的理由。

### 5.9 ⭐ 技术评审：审内容、反复审、无效轮次要重做（本版新增）

> **【本项目自定机制，无国标直接对应】** 国标要求"**进行必要的管理和技术评审**"
> （GB/T 8566-2022 **6.3.2.3 b) 7)**，其注明目的是"**确定转入生存周期的下一阶段或项目里程碑是否已经就绪**"），
> 但**不规定**审到什么程度算够、轮次如何收敛。**ISO/IEC 29110 中国未采标，不得据它论证符合国标。**

**项目负责人的原话**：「**无论什么时候一定要有技术评审**，就是**立项阶段**，那肯定得需要技术评审呀。
每一个技术官员要负责一部分技术内容呀，要**反复地有技术评审做定**呀，
**不能光是形式上文档格式对了，那不行，内容上要有**。」

**① 每阶段必有技术评审，且格式 ≠ 内容。**

| 项 | 规定 |
|---|---|
| 准出条件**分列两条** | `A. 文档格式 / 模板齐备`（必要条件）与 `B. 技术内容已被评审并给出裁定`（必要条件）；**只有 A 不算过** |
| 未裁定的判定 | 格式齐备但无技术裁定 ⇒ 判「**未评审**」（**不是**"待补格式"） |
| 结论须有依据 | 标准条款 或 实测输出；**"综合考虑""经验判断""通常做法"不构成依据** |
| 官员职责 | 一位技术官员**只对他那一部分**下技术判断；**跨部分结论必须由该部分的官员出**；官员**评审文档、不写代码**；**不裁定 = 未评审** |

**反面清单（"格式对但内容是空的"12 种形态，出现任一即判内容未评审）：**
① 判据写成"合理/可接受范围/若干/待定"；② 数字无复算命令/时点/对象却标"实测"；
③ 结论无依据；④ **只填模板不给判断**；⑤ 把"**未落实**"写成"**已落实**"（含"已实施（待批准）"被称"已全部实施"）；
⑥ 假设无验证时点；⑦ 接口契约只有成功路径；⑧ 风险无触发信号；⑨ 能力声明给不出检查/测试位置；
⑩ 关注点↔视角双向覆盖没做；⑪ 逐项勾选但无证据位置；⑫ 评审记录全是"符合/通过"而无一条裁定或反对。

**② 立项阶段的中心是"需求与目标口径"。** 必答四问：**要什么**（含**不做清单**）／**给谁**（具名）／
**怎么算做成了**（指向**判据载体**）／**目标值多少**（数值 + 口径 + **反例**）。
**四问答不出 ⇒ 立项评审不得通过**（无论文档多齐备）。

**③ 轮次机制：反复，直到定案。**

| 规则 | 内容 |
|---|---|
| **轮次不设上限** | 直到**无保留意见**；不得以"已经开过会了"结案 |
| **每轮冻结输入输出** | 每轮开始冻结被评对象（blob + 提交号），结束记录裁定与改动 |
| **分歧不得上抛** | 胜负只由**标准条款**或**实测输出**判定；"我认为/通常做法"不构成理由 |
| **判不了的当场做实验** | 把分歧变成一条可执行的命令，跑它 |
| **未闭环意见逐条回应** | 不是整体回应 |
| **上抛的唯一合法情形** | 需要**人的价值判断**，且必须附「**建议值 + 各选项代价**」 |

**④ 无效轮次判据（可判定，防走过场）：** 一轮评审结束后，
**若既无"技术内容上的改动"、也无"明确裁定"（含明确的不改理由）⇒ 该轮无效，必须重做**。
机器可判部分：比对**本轮前后被评对象的冻结 blob**——无内容变更 **且** 无新增裁定条目 ⇒ 无效。
**注意**：「无变更」只有给出「**为什么不改**」的明确理由时才算裁定。

**⑤ 完整主链（六环，不可跳）——见 [`附件二`](附件二-阶段流程与交付物.md) §0.11：**

```
① 部分清单 → ② 席位(1:1) → ③ 技术评审(看内容) → ④ 逐条辩证处置(允许反驳)
                                                            │
   ⑦ 才允许准出 ←─────── ⑥ 反复轮次收敛 ←──── ⑤ 未闭环？回 ③
```

> **A 档怎么落**：**不设评审会，但六环照走**——技术官员由**本人换身份**担任（"换身份审自己"），
> 第②环的等价要求是"**逐部分独立过判据并分别留痕，不得一次判断覆盖多个部分**"。

### 6.2 PR 模板承载的 R4 检查单

### 6.4 人机分工

| 判定项 | 谁判 | 为什么 |

| 测试是否通过、覆盖率是否达标 | **CI** | 机器可判、可复现、不会累、不会讲情面 |
| 需求追溯是否完整、有无循环依赖、改动是否越界 | **CI** | 同上 |
| **契约是否合理、假设是否成立、测试是否覆盖了真正的风险** | **人** | 需要判断与经验，机器判不了 |
| 准入是否满足、角色是否齐备、意见是否闭环 | **人** | 需要责任归属 |
| **签字与责任归属** | **人** | **不可代签**——AI 可代写，不可代签 |

## 七、标注体系与依据索引

### 7.1 标记的用法与效力

| 标记 | 含义 | 裁剪 | 典型例子 |
|---|---|---|---|
| **【国标】** | 标准**明文要求**，可引条款号 | **不可裁剪**。若确需裁剪，走 GB/T 8566-2022 §4.3「剪裁符合」并声明 | 需求可验证性；文档种类；测试记录；GB/T 25000.51 的 8 个质量特性；评审是项目评估与控制的任务 |
| **【本仓库】** | 本仓库自行增加的**工程强化项** | **可裁剪，须留痕**：裁剪项 / 理由 / 补偿措施 / 批准人，写在 `templates/01-策划类/02-项目开发计划.md` 的「裁剪说明」 | R0–R8 编号体系；S3 骨架跑通独立成阶段；R3/R4/R5 独立成评审；覆盖率 80% / 90% 阈值；A 档自动化门禁；三条铁律；★ 关键项一票否决；评审有效性规则 |

> **裁剪留痕是硬要求**：**【国标】** GB/T 8566-2022 **附录 A.2.3** 要求
> "识别和记录影响剪裁的条件"、"从受剪裁决策影响的当事各方获得输入"、
> "选择需要剪裁的生存周期过程，**删除选定的输出、活动或任务**"。
> 即：**未留痕的裁剪 = 漏做**，不是裁剪。

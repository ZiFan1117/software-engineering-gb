## 一、责任分解（RACI）

### 1.1 角色定义

**A 档一人分饰全部角色**——但**角色仍要分清**，因为"自己审自己"和"换个身份审自己"不是一回事。

| 角色 | 代号 | 职责 | A 档怎么落 |
|---|---|---|---|
| **项目负责人** | PM | 范围、计划、资源、对外接口、裁剪批准 | 本人 |
| **需求负责人** | BA | 需求获取、可验证化、基线、需求变更 | 本人 |
| **架构负责人** | ARCH | 框架设计、契约、框架变更、视角体系 | 本人 |
| **实现者** | DEV | 详细设计、编码、单元测试 | 本人 |
| **测试负责人** | QA | 测试计划、用例、执行、缺陷跟踪 | 本人 |
| **配置管理员** | CM | 版本控制、基线、变更登记、配置审计 | 本人（用 Git 承担） |
| **质量保证** | SQA | 过程合规、门禁执行、不符合项 | 本人（用工具门禁承担） |
| **需求方 / 验收方** | CUS | 提供需求来源、验收签字 | 自己或外部 |
| **评审组** | REV | 评审意见、结论 | 本人 + 工具门禁 |

> **A 档的关键纪律**：**换身份审自己**。
> 写完需求后，隔一天以上、以"测试负责人"的身份读一遍——
> **问"这条我怎么判它过了？"**。这比当场自审有效得多。

| 阶段 | 交付物 | PM | BA | ARCH | DEV | QA | CM | 客户 |
|---|---|---|---|---|---|---|---|---|

### 1.3 三条责任铁律

| # | 铁律 | 为什么 |
|---|---|---|
| 1 | **执行者不能是唯一批准者**（B 档） | 自己批自己 = 没有评审 |
| 2 | **需求变更必须由 BA 登记，不能直接改** | 否则 RTM 断裂，门禁失败 |
| 3 | **框架变更必须由 ARCH 提，且走 R5** | 否则"静默改框架"——最贵的技术债 |

## 二、时间分解

### 2.1 门禁是同步点，不是时间点

**阶段划分的依据是"门禁通过"，不是"日历到了"。**

```
❌ 错误理解：S1 计划 2 周，2 周后进 S2
✅ 正确理解：S1 的准出条件全部满足，才进 S2（可能 3 天，也可能 6 周）
```

> **这条很重要**：按日历推进是"进度驱动"，按门禁推进是"质量驱动"。
> 本流程选后者——**因为门禁没过的阶段，后面的工作会成倍返工。**

### 2.2 三条时间线

| 时间线 | 频率 | 载体 | 谁看 |
|---|---|---|---|
| **每次提交** | 每次 commit | 自动化门禁（4 条命令） | 机器判 |
| **每个模块完成** | 按模块 | R4 模块评审 | 模块负责人 |
| **固定周期** | 周 / 双周 / 月 | **进度状态记录（PSR）** | 项目负责人 + 需求方 |

**PSR 频率**（在项目开发计划里声明）：

| 项目周期 | 频率 |
|---|---|
| < 1 个月 | 每周 1 次 |
| 1–6 个月 | 每两周 1 次 |
| > 6 个月 | 每月 1 次，**里程碑处加记 1 次** |

### 2.3 时间上的"必停点"

```
S0 ──[必停①]── S1 ──[必停②]── S2 ──[必停③]── S3 ──┐
                                                      │
        ┌─────────────────────────────────────────────┘
        ↓
       S4 ──[必停④ 每模块]── S5 ──[必停⑤]── S6 ──[必停⑥]── S7 ──[必停⑦ 每次发布]
```

| 必停点 | 时机 | 不批的后果 |
|---|---|---|
| **①** | S0 结束，写需求前 | 范围没定 → 需求无限膨胀 |
| **②** | 需求写完，**基线化前** | 不合格需求冻结进基线 → 后面全返工 |
| **③** | 框架定完，**写代码前** | 结构错误留到实现期 → 推翻代价最大 |
| **④** | **每个模块**写完 | 缺陷堆积到集成期 → 定位成本指数上升 |
| **⑤** | 系统测试做完 | 带缺陷进验收 → 验收变扯皮 |
| **⑥** | 验收通过，**产品基线冻结前** | 交付后还能改 → 交付物与验收物不一致 |
| **⑦** | **每次发布前** | 未回归的版本流出 |

> **④ 是最容易被跳过的一环**——"模块这么小，不用审吧"。
> 跳过它的代价在 S5 集中爆发：**多个模块的缺陷互相纠缠，定位成本远超逐个审的成本。**

## 三、什么时候必须停下来让人看

### 3.1 两类停机：计划停 vs 异常停

| 类型 | 触发 | 谁决定停 | 怎么恢复 |
|---|---|---|---|
| **计划停** | 走到 §2.3 的必停点 | 流程自动 | 门禁通过 |
| **异常停** | 命中 §3.2 任一条件 | **任何参与者都有权叫停** | 问题关闭 + 复评 |

> **"任何参与者都有权叫停"是本流程的硬规定。**
> 尤其 SQA 有**停工权**（见 `templates/01-策划类/03-软件质量保证计划.md`）——
> 发现不可裁剪项缺失时，有权提请暂停阶段门禁。

### 3.2 异常停的九个触发条件（命中即停）

| # | 触发条件 | 为什么必须停 |
|---|---|---|
| 1 | **需求基线被改动，但没有变更请求** | 追溯链断了，后面全不可信 |
| 2 | **代码改了，对应设计/需求文档没在同一次提交里改** | **文档漂移**——配置管理失效的头号征兆 |
| 3 | **框架契约被改动**（模块接口、分层、公共接口） | 静默改框架是最贵的技术债 |
| 4 | **测试发现 P0 缺陷** | 继续叠加功能会掩盖根因 |
| 5 | **需求覆盖率 < 100%**（有需求没有对应用例） | **写不出用例的需求 = 不合格需求** |
| 6 | **出现 P0/P1 缺陷且无处置计划** | 缺陷不会自己消失 |
| 7 | **发现两条需求互相冲突** | 需求集不一致（违反 GB/T 45802-2025 §5.2.6） |
| 8 | **进度偏差 > 5 个工作日且无纠正措施** | 见 `templates/04-实现类/04-进度状态记录.md` §3 |
| 9 | **文档与已交付版本对不上** | 交付物不可信 |

### 3.3 停机后怎么恢复（四步，不可跳）

```
① 定性质：是文档错、代码错、还是两者都错？（见第四章判定规则）
② 定范围：这次不一致影响了哪些需求 / 设计 / 用例 / 文档？
③ 定动作：写变更请求（CR）或缺陷记录，指定责任人与截止日
④ 复评：问题关闭后，由原门禁重跑一次；重跑通过才恢复
```

> **不允许"先继续，回头再补"**——回头补的从不补。

## 四、⭐ 软件与文档对不上，改哪个？

**这是本附件最核心的一节。** 之前仓库里没有统一规则，
只有 `02-模块清单与模块号登记表.md` 顺带提了一句"以代码注册表为事实"。

### 4.1 判定原则：**文档是意图，代码是现实，基线是裁判**

```
        基线（需求基线 / 框架基线 / 产品基线）
                    ↓  谁跟基线一致，谁是对的
        ┌───────────┴───────────┐
     文档                      代码
  （描述了意图）            （实现了现实）
```

**判定三步**：

| 步 | 问什么 | 依据 |
|---|---|---|
| **①** | **基线怎么规定的？** | 需求基线、框架基线、产品基线里的冻结内容 |
| **②** | **代码是否按基线意图实现？** | 若代码偏离基线 → **代码错**（除非有批准的变更请求） |
| **③** | **文档是否准确描述了基线？** | 若文档偏离基线 → **文档错** |

> **一句话**：**谁偏离基线，谁错。**
> 若**两者都偏离**，说明基线本身该改 → 走变更请求，改基线。

### 4.2 六种场景与处置（照表执行）

| # | 场景 | 谁错 | 处置 | 走什么流程 |
|---|---|---|---|---|
| **1** | 代码改了**有意为之**，且更符合需求 | **文档错** | 更新文档 | **补 CR** → 更新文档 → 回写 RTM |
| **2** | 代码改了**有意为之**，但偏离了需求 | **代码错**（除非需求该改） | 改回代码，或提需求变更 | **补 CR** → 二选一：改代码 / 改基线 |
| **3** | 代码改了**无意为之**（手误、重构副作用） | **代码错** | 改回代码 | 记缺陷 → 修复 → 回归 |
| **4** | 文档改了，代码没跟上 | **实现未完成** | 排期实现 | 记 CR → 进 S4 待办 |
| **5** | 测试结果与需求不符 | **看哪边符合业务意图** | 若代码不合需求 → 改代码；若需求写错 → 改需求 | 缺陷 or CR |
| **6** | 两者都与基线不符 | **基线该改** | 提基线变更 | **CR + 走 R5（若涉框架）** |

### 4.3 ⚠️ 三个反直觉但重要的规定

#### 规定 1：**"代码能跑"不是"代码对"的理由**

最危险的一句话是"**代码都跑通了，肯定是文档写错了**"。

**为什么危险**：代码跑通只证明它**自洽**，不证明它**符合需求**。
代码可能一直跑得通，但一直在做错的事——**这正是缺陷最晚被发现的原因**。

**正确做法**：**看基线**，不看"能不能跑"。

#### 规定 2：**不许"以代码为准"批量刷文档**

有时会出现"文档落后太多，干脆照代码重写文档"。**这等于让需求被实现反向定义**——
需求基线失去约束力，整个追溯体系作废。

**允许的例外**：只有当**逐条确认过"代码是对的"**、且每条都有 CR 支撑时，才可以批量更新。
**"批量"是结果，不是起点。**

#### 规定 3：**不一致本身就是缺陷，必须登记**

不管最后判定是文档错还是代码错，**"不一致"这件事必须有一条记录**（CR 或缺陷）。

**为什么**：它回答"这行为什么这么写"。
没有记录的不一致，三个月后无法判断是"有意设计"还是"忘了改"。

### 4.4 判定记录表（照填，不要只在脑子里判）

| 项 | 内容 |
|---|---|
| 发现时间 / 发现人 | `<YYYY-MM-DD>` / `<姓名>` |
| 不一致的具体位置 | 文档：`<SRS §4.2 REQ-F-001>` vs 代码：`<src/m20/service.py:45>` |
| **基线怎么规定的** | 引基线版本：`req-baseline/v1.0` 第 `<...>` 条 |
| **判定结论** | ☐ 文档错 ☐ 代码错 ☐ 基线该改 ☐ 实现未完成 |
| **判定依据** | `<引用基线条文 / 需求方确认记录>` |
| 处置动作 | `<改文档 / 改代码 / 提 CR>` |
| 责任人 / 截止日 | `<姓名>` / `<YYYY-MM-DD>` |
| 关联记录 | `<CR-003>` / `<BUG-007>` |
| RTM 是否已回写 | ☐ 是 |

> **A 档简化**：可只填「位置 / 判定结论 / 判定依据 / 处理」四栏，但**判定依据一栏不能省**——
> 它是防止"随手挑一个改掉"的唯一约束。

## 五、门禁 × 阶段 × 责任 对照总表

| 门禁 | 阶段 | 审什么 | 依据 | 谁批 | A 档替代 |
|---|---|---|---|---|---|
| **R0** | S0 准出 | 范围、约束、质量目标、**裁剪说明** | GB/T 8566-2022 管理类过程 | PM | 自查清单 |
| **R1** | S1 准出 | **需求质量 9+5 特性**、RTM、TBx 清零 | **GB/T 45802-2025** §5.2.5/§5.2.6 | PM + CUS | 自查 + `trace_matrix.py` |
| **R2** | S2 准出 | **关注点—视角覆盖度**、无环依赖、契约完备 | **GB/T 45630-2025** §6.9；GB/T 8566-2022 §6.4.4 | ARCH | 自查 + 环检测 |
| **R3** | S3 准出 | 一条命令跑通、冒烟过 | 【本仓库】 | DEV 自查 | 同左（本即自动） |
| **R4** | S4 每模块 | 单测过、覆盖率、**文档与代码同提交** | GB/T 38634.3-2020 | 模块负责人 | `tests/` + `trace_matrix.py` |
| **R5** | 框架变更时 | 契约合理性、影响分析、假设是否被推翻 | GB/T 8566-2022 配置管理过程 | ARCH + PM | 自查 + `scope_check.py` |
| **R6** | S5 准出 | **需求覆盖 100%**、P0/P1=0、追溯双向完整 | GB/T 38634.2-2020 | QA | `trace_matrix.py` |
| **R7** | S6 准出 | **8 个质量特性逐项结论** | **GB/T 25000.51-2016** | CUS + PM | 验收用例表 |
| **R8** | S7 每次发布 | 回归过、版本号规范、无文档漂移 | GB/T 8566-2022 | PM | 自查 + 门禁 |

> **R5 特殊**：它不是阶段门禁，而是**事件触发门禁**——
> 任何框架契约变更都会触发它。**A 档也必须走**，代价是自查 + 跑 `scope_check.py`。
>
> 以上均为 **B 档（本流程标准）** 的要求。A 档的放宽项集中在
> [`附件六-档位与裁剪.md`](附件六-档位与裁剪.md) §6.2，本附件不重复。

## 六、⚠️ 提交 GitHub = 按 B 档

**本仓库自身，以及任何走 GitHub PR 流程的项目，一律按 B 档要求。**

理由很简单：**提交到 GitHub 就已经满足了 B 档判据**——
改动有了外部可追溯性，且必然会有第二个人（或未来的自己以外的人）看到。

### 6.1 PR 即一次正式评审

| B 档要求 | 在 GitHub 上如何落地 |
|---|---|
| **正式评审 + 记录 + 签署** | PR 的 Review + Approve；**评审记录写进 PR 描述或链接到 `01-阶段评审记录.md`** |
| **变更请求（CR）** | PR 描述须回答 CR 的核心两问：**① 为什么改（不改的后果）② 影响哪些配置项** |
| **完整 RTM** | PR 涉及需求改动时，必须同 PR 更新 `03-需求追溯矩阵.csv` |
| **三类基线** | 用 Git tag：`req-baseline/vX.Y`、`framework/vX.Y`、`vX.Y.Z` |
| **RACI 分离** | **作者不能自己 Appove 自己的 PR** |
| **配置审计** | CI 门禁 + PR 检查单 |

### 6.2 PR 必须满足的六条（缺一不可）

```
[ ] 1. 变更说明写清「不改的后果」——不是"优化""完善"
[ ] 2. 变更类型正确标注（feat / fix / framework / refactor / docs / test / chore）
[ ] 3. 追溯信息：关联的需求编号 / 变更请求编号
[ ] 4. 变更范围声明：本次改动的路径范围（与 .scope-declaration.json 一致）
[ ] 5. R4 检查单逐项确认（契约/测试/追溯/评审四组）
[ ] 6. 触及框架或敏感路径时，附影响分析与 R5 结论
```

> **第 6 条的"敏感路径"**：`skeleton/module_system.py`、`skeleton/modules.py`、
> `tools/`、`.github/workflows/`、`docs/02-评审与门禁/`
> （见 `tools/scope_check.py` 的 `SENSITIVE_PATHS`）。
>
> **改这些文件必须走 R5**——否则"放宽门禁"会成为最容易的作弊路径。

### 6.3 CI 门禁是硬闸，不是提示

`.github/workflows/gate.yml` 四个作业**全部阻断式**：

| 作业 | 命令 | 拦什么 |
|---|---|---|
| `smoke` | `python skeleton/run_skeleton.py` | 骨架跑不起来 |
| `unit-test` | `pytest --cov-fail-under=80` | 测试失败 / 覆盖率不足 |
| `traceability` | `python tools/trace_matrix.py` | 追溯断裂 |
| `scope` | `python tools/scope_check.py` | 改动越界 |

> ⚠️ **2026-09-21 修正**：`scope` 作业此前带 `continue-on-error: true`，
> 导致**无论退出码为何都不阻断**，受控变更实际无门禁。**已移除该选项。**
> 现在退出码 0 通过、1 越界阻断、2 环境不可用也阻断
> （**「未能校验」不等于「校验通过」**）。

### 6.4 分支与提交约定

| 项 | 约定 |
|---|---|
| 分支模型 | `main`（受保护，仅经 PR 合入）/ `develop` / `feat/*` `fix/*` |
| 提交信息 | Conventional Commits：`<type>(<scope>): <subject>` |
| 合并方式 | Squash merge（保持主线历史清晰） |
| 禁止 | **直接推 `main`**；**自审自合**；**跳过 CI** |

详见 [`附件五-配置与版本.md`](附件五-配置与版本.md) §七。

### 6.5 A 档项目提交 GitHub 怎么办

**升级到 B 档。** 这是 §6.6 升档触发的第三条：

| 触发 | 动作 |
|---|---|
| 提交到 GitHub / 走 PR 流程 | **立即升 B 档** |

**补齐清单（按优先级）**：① 需求规格说明 ② 完整 RTM ③ 三类基线
④ 评审记录机制 ⑤ 接口需求规格说明

> **不想升档的唯一合法做法**：保持在本地私有仓库，不走 PR 流程。
> **一旦公开或走 PR，就等于接受了外部可追溯性，即 B 档。**

### 6.6 ⚠️ 门禁"正确"不等于门禁"被强制"（本版新增）

**这是本附件必须说清的一件事**，因为经验来源项目实测过：**免费私有仓库无分支保护，
CI 红了仍可直接推主线**。

| 概念 | 含义 | 谁保证 |
|---|---|---|
| **门禁正确** | 门禁判得对：会红、红得有意义、判据可判定 | 门禁自证（[`附件二`](附件二-阶段流程与交付物.md) §0.2 **H-04**） |
| **门禁被强制** | 红了**推不进去** | 分支保护 / 必需状态检查 / **打标签前置动作** |

**本流程的立场**：

1. 无分支保护时，必须在**项目开发计划里明文写出这一残余风险**（不得默认"有 CI 就等于有门禁"）；
2. **用"打标签前置动作"补强制力**：打任何基线标签**之前**必须跑一次对账 / 门禁，
   并**把输出贴进基线记录**；**输出缺失即视为基线未建立**——
   这样在有无分支保护的环境里**都会红**（红在"记录缺输出"这一条上）；
3. **评审记录里必须区分**"CI 通过"与"CI 有强制力"——前者是证据，后者是制度。

### 6.7 ⭐ 技术部分清单与席位：一等公民（本版新增，与 [`附件二`](附件二-阶段流程与交付物.md) H-23 配套）

**项目负责人的直接要求**：**每一个技术官员要负责一部分技术内容**；
**有几部分技术就设几位专家**；不得出现"无主的部分"。

本附件的 RACI 表（§1.2）按**交付物**分责任，**不足以回答"谁有资格判这一部分技术内容"**——
所以必须另有一张「**本阶段技术部分清单**」。

| 要求 | 判据 | 判不过怎么办 |
|---|---|---|
| **每阶段开工前先冻结"技术部分清单"** | 清单每部分有**编号、名称、边界描述**（建议按**框架分层 + 接口契约边界**划分，使每部分都有明确契约面） | 无清单 ⇒ 该阶段**不得开工**；已开工的按"阶段外产物"处理 |
| **按部分设技术官员（1:1）** | 每个部分至少一位**具名**技术官员；一位官员**只管一部分技术内容** | 存在无主部分 ⇒ 评审**无效** |
| **席位表与部分清单同时冻结**（同一提交） | `git show --stat <commit>` 中两者**同时出现**；数量相等、覆盖完备 | 对不齐 ⇒ 评审无效，重新组会 |
| **不得一位专家跨部分下判断** | 评审记录里每条结论能指向**该部分的**官员 | 跨部分结论 ⇒ **该条结论无效**，须由该部分官员重新出具 |
| **技术官员评审文档、不写代码** | 评审人不是同一交付物的实现者 | 同人 ⇒ 回避，换人 |
| **部分清单变更走变更** | 部分清单变更 ⇒ 席位表**同一次**跟着改 | 会后临时调整 ⇒ 无效 |

> **A 档（1 人）怎么落**：「有几部分设几位专家」在 1 人项目里无法字面满足，
> 但"**无主的部分**"要求仍然适用：**本人必须按部分逐部分独立过一遍判据并分别留痕**，
> **不得用一次结论覆盖全部部分**。"跨部分下判断"在 A 档的等价禁令是"**一次判断覆盖多个部分**"。

**为什么这条是一等公民（真实教训——三个"长期没有主"的东西）**：

| 没有主的东西 | 后果 | 出处 |
|---|---|---|
| **门禁工具链** | 三项观察项**没有消费者**（没有条款说谁读 `[OBS]`、记在哪） | `WC-CR-005 §九` |
| **`.gitattributes`** | 决定**全仓每个文件的检出字节**，却被判 `[另属他门]`，而**没有别的门** | `WC-SCMP-001 §4/8.4 G-07` |
| **五份新载体 / 登记面** | 框架基线清单"只寄生在另一文档、未进本台账"；`AC-07` 判据存在但**审计面不含任何文档** ⇒ 装饰 | `G-21`、`G-27` |

> **完整主链（六环，不可跳）**：**部分清单 → 席位(1:1) → 技术评审(看内容) → 逐条辩证处置 → 反复轮次收敛 → 才允许准出**，
> 见 [`附件二`](附件二-阶段流程与交付物.md) **§0.11**。

### 6.8 ⭐ 评审意见的辩证处置（本版新增，与 [`附件二`](附件二-阶段流程与交付物.md) H-22 配套）

**原则（项目负责人明确要求）**：**专家的意见我们不一定要采纳**——要结合实际情况和他辩论。
**有些时候，他是片面地看问题，不是全部都看问题。**

| 纪律 | 内容 |
|---|---|
| **先复算前提** | 收到意见后**第一件事是当场复算它的前提**；前提不成立的意见**一律不采纳**，并记入处置表"反驳"态 |
| **四态 + 代价 + 坐标 + 谁定** | 逐条给 `采纳 / 部分采纳 / 反驳 / 属本项目执行问题`，并给代价、**落笔坐标（文件:节 + 改前改后原文）**、谁定 |
| **反驳是合法输出** | 但**必须给理由与依据**（引标准条款或引实测输出）。**"为了显得配合而照抄"是反模式**——它与"降低标准"是同一后果的两种外观 |
| **必须可核** | **不接受"已处理""已优化"这类无坐标的说法** |
| **获批前不改变效力** | 处置表是**执行计划**，不是新法；据此产生的改动标注"**本修订须经人批准后生效**" |
| **按部分归口** | 一位专家只判他那一部分；**跨部分结论必须由该部分的专家出**；汇总人不得替某部分下判断 |

**片面看问题的四种典型形态**（当场识别用）：
① 只看自己那部分、却给出影响别部分的结论；
② 把"条件性推论"当成"代码/文档事实"陈述；
③ 给出无法判定的判据（"合理""可接受范围"）；
④ 要求改别部分的载体。

> **处置表的完整结构、填写方式与"被推翻的判词"记录位置**见
> [`附件三-评审与门禁.md`](附件三-评审与门禁.md) **§5.8**。

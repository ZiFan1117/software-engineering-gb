# 附件五 · 配置与版本

> **本附件回答**：什么东西必须纳入版本控制、什么时候冻结成基线、版本号怎么涨、
> 变更怎么走流程、A 档与 B 档各做到什么程度。

> 上游：[`../导读本.md`](../导读本.md) ｜ 依据核验日期：**2026-09**
> 同源文档：[`../04-配置与版本/配置管理与版本化.md`](../04-配置与版本/配置管理与版本化.md)（仓库权威定义，本附件与其同口径）

**四条硬结论（先用后读）**

| # | 结论 |
|---|---|
| 1 | **没有纳入版本控制的东西，等于不存在。** 交付物放在 U 盘、共享盘、本机目录里，配置审计一律判为不存在 |
| 2 | **没有基线的迭代，等于失控。** 基线是"经过批准、不可静默修改"的快照；没有它，"这次改动影响了什么"只能靠回忆 |
| 3 | **文档与代码必须同一次提交。** 文档漂移是配置管理失效的头号征兆 |
| 4 | **框架版本与产品版本分离，框架从 `v0` 起。** 不要过早宣布框架 `v1.0` |

## 一、依据与三个标准状态（必读）

| 标准 | 状态 | 本附件怎么用它 |
|---|---|---|
| **GB/T 8566-2022**《系统与软件工程 软件生存周期过程》 | 现行（等同采用 ISO/IEC/IEEE 12207:2017） | **配置管理要求的现行依据**。该标准含**配置管理过程**（OCR 提取显示为 `6.3.5`）与**信息管理过程**（OCR 提取显示为 `6.3.6`） |
| **GB/T 8567-2006**《计算机软件文档编制规范》 | 现行（中国自主制定，非采标） | **文档种类与章节骨架**。其文档种类含《软件配置管理计划（SCMP）》（OCR 目录标注为 `7.17`）；其 SCMP 编写格式把配置管理活动分为**配置标识、配置控制、配置状态记录与报告、配置检查与评审**四方面 |
| **GB/T 20158-2006**《信息技术 软件生存周期过程 配置管理》 | ⚠️ **已废止** | **不作为依据。** 见下方"引用口径" |
| **GB/T 12505-90**《计算机软件配置管理计划规范》 | 1990 年老标准，**不作为执行依据** | 只采其**五要素概念**：配置项标识、基线、变更控制、状态记录、配置审计。实现方式按现代工程实践（Git + CI + 制品版本化） |

### 1.1 ⚠️ `GB/T 20158-2006` 的引用口径（正式文件必须照此写）

**事实**：`GB/T 20158-2006` **已废止**。其配置管理内容现由 **`GB/T 8566-2022`** 覆盖，
但**官方未标注直接替代标准**。

| 写法 | 判定 |
|---|---|
| "该标准已废止，配置管理要求现参见 **GB/T 8566-2022**。" | ✅ **唯一正确写法** |
| "`GB/T 20158-2006` 由 `GB/T 8566-2022` 代替。" | ❌ **禁止**。官方未标注直接替代关系 |
| 在"依据标准"清单里列 `GB/T 20158-2006` | ❌ **禁止**。已废止标准不进依据清单 |

### 1.2 `GB/T 12505-90` 的引用口径

该标准发布于 1990 年，其**五要素框架**今天依然成立，但其实现方式描述已过时——
没有持续集成、没有制品仓库、没有分布式版本控制的概念。

| 允许 | 禁止 |
|---|---|
| "概念要素参照 `GB/T 12505-90` 的**五要素框架**" | 把 `GB/T 12505-90` 当作变更流程、审计方式的执行依据 |
| 引用其五要素名称 | 引用其人工台账、物理介质、纸质签发类具体做法 |

> `GB/T 8567-2006` 的**参考文献**中也列有 `GB/T 12505-1990`（OCR 提取）——
> 即文档标准本身也只把它当参考件，而非规范性引用文件。

## 二、配置管理五要素在本仓库怎么落地

### 2.1 五要素 → 工具与文件

| 要素 | 国标落点【国标】 | 本仓库落地方式【本仓库】 | 校验手段 |
|---|---|---|---|
| **① 配置项标识** | `GB/T 8566-2022` 配置管理过程"执行配置标识"活动（OCR：`6.3.5.3 b)`）——唯一标识受控项、识别属性、定义全生存周期基线 | 仓库路径为唯一权威 + 统一编号规则（§三）+ Git 追踪 | CI 校验编号格式（如 `M01` 号段归属、`REQ-F-NNN` 三位） |
| **② 基线管理** | 同上"定义全生存周期的基线"（OCR：`6.3.5.3 b) 3)`）；"执行发布控制"（OCR：`6.3.5.3 d)`） | Git **附注标签**：`req-baseline/v1.0`、`framework/v0.x`、`product/vX.Y.Z`（§四） | 标签命名正则 + 标签不可移动（仓库保护规则） |
| **③ 变更控制** | "执行配置变更管理"（OCR：`6.3.5.3 c)`）——变更请求与差异请求的识别、评价、处置，通常由 **CCB（配置控制委员会）** 控制 | 变更申请单 + **R5 / R8** 评审 + PR 流程（§六） | PR 检查单；提交信息必须含变更编号 |
| **④ 状态记录** | "执行配置状态纪实"（OCR：`6.3.5.3 e)`）——维护元素、基线与版本的 CM 状态信息 | Git 提交历史 + `CHANGELOG` + `docs/records/` 归档 + 制品台账 | `CHANGELOG` 由提交信息生成，不靠回忆补 |
| **⑤ 配置审计** | "执行配置评价"（OCR：`6.3.5.3 f)`）——含**功能配置审核（FCA）**与**物理配置审核（PCA）** | CI 门禁 + 配置审计检查单（§2.3）+ 追溯矩阵校验 | `tools/trace_matrix.py`、`tools/scope_check.py`、`tests/test_module_system.py` |

> **术语对齐**：`GB/T 8566-2022` 用"配置审核 / 配置评价"，
> `GB/T 12505-90` 与 `GB/T 8567-2006` 用"配置审计 / 配置检查与评审"，
> 指同一件事。**本仓库统一用"配置审计"**，不因用词不同而重复建流程。

### 2.2 五要素的失效判定（出现即视为配置管理失效）

| 要素 | 失效征兆 | 后果 |
|---|---|---|
| ① 标识 | 出现无编号模块、编号复用、同一对象两个编号 | 历史文档/旧测试/旧缺陷单全部指错方向 |
| ② 基线 | 口头冻结、标签乱打、标签可移动 | 无法回退到已知良好状态 |
| ③ 变更 | 改完再补审批；驳回的变更直接丢弃 | 未授权变更；同类问题反复出现 |
| ④ 状态 | 文档改了代码没改（或反之） | 追溯体系失效，文档不再可信 |
| ⑤ 审计 | 勾选而无证据；审计人 = 被审计项作者 | 审计变成走过场，账实不符 |

### 2.3 配置审计检查单（R8 发布评审前执行）

| # | 检查项 | 判定方式 | A 档 | B 档 |
|---|---|---|---|---|
| 1 | 所有配置项均已纳入版本控制（无游离文件） | 配置项清单 ↔ 仓库实际 | ✅ | ✅ |
| 2 | 无密钥/凭据入库（含历史提交扫描） | secret 扫描 + `.gitignore` | ✅ | ✅ |
| 3 | 依赖锁定文件已更新且可复现构建 | lock 文件 + 干净环境构建 | ✅ | ✅ |
| 4 | 所有基线标签符合命名规范且指向正确提交 | 标签正则 + 指向校验 | ✅ | ✅ |
| 5 | 变更申请与影响分析齐全，均已批准 | 变更台账 | 简化 | ✅ |
| 6 | 每次变更都有对应的回归测试记录 | 回归记录 ↔ 变更编号 | ✅ | ✅ |
| 7 | 文档与代码版本一致（无漂移） | 同提交检查 | ✅ | ✅ |
| 8 | 追溯矩阵完整（需求→设计→代码→测试 双向可查） | `python tools/trace_matrix.py` | 降级 | ✅ |
| 9 | 版本说明含变更内容、已知问题、升级与回滚注意 | 文档检查 | 按需 | ✅ |
| 10 | 制品哈希已记录，可校验 | 制品台账（SHA-256 / 镜像 digest） | 按需 | ✅ |

> **勾选而无证据的审计记录视为无效。** 审计执行人**不得**是本次被审计配置项的作者。
> B 档的完整检查单见 [`templates/07-配置与发布类/01-软件配置管理计划.md`](../../templates/07-配置与发布类/01-软件配置管理计划.md) 第九章。

## 三、配置项清单：什么必须入库

### 3.1 入库判定表

| 类别 | 具体项 | 入库 | 说明 |
|---|---|---|---|
| **需求类** | SRS、接口需求规格、RTM、需求评审记录 | ✅ | 需求基线载体 |
| **设计类** | HLD、LLD、模块清单、接口契约、**框架假设清单** | ✅ | 框架基线载体 |
| **代码** | 源码、SQL 脚本、配置模板（**非真实密钥**） | ✅ | 用 `.gitignore` 排除构建产物与密钥 |
| **测试类** | 测试计划/说明/用例/报告、测试数据生成脚本 | ✅ | 测试资产可复用 |
| **脚本与工具** | 构建脚本、CI 配置、门禁工具 | ✅ | 环境可复现的前提 |
| **文档** | 用户手册、部署说明、版本说明、`CHANGELOG` | ✅ | 交付物 |
| **构建产物** | 二进制包、容器镜像 | ❌ **不入源码库** | 走制品库 / Release 附件，**必须记录版本标签与哈希** |
| **密钥与凭据** | 口令、Token、证书私钥 | ❌ **严禁入库** | 用环境变量 / 密钥管理；**一旦误提交必须立即吊销轮换** |
| **第三方依赖** | 依赖清单与锁定文件 | ✅ | `requirements.txt` / `package.json` + lock 必须入库，保证可复现构建 |

> **"源码在 Git 里就够了"是本仓库明确否定的做法。** 无法证明发布出去的制品
> 就是某次提交构建出来的，追溯链会在最后一步断裂。

### 3.2 编码规则：唯一性 + 永不复用

**三条铁律【本仓库】**

| # | 规则 | 落地动作 |
|---|---|---|
| 1 | **编号一经分配，永不复用** | 对象废弃后编号作废，不回收、不递补 |
| 2 | **废弃对象保留登记行，不删** | 保留行是"永不复用"的**证据**；删除行等于允许复用 |
| 3 | **写全、左补零** | 写 `M01` 不写 `M1`；写 `REQ-F-012` 不写 `REQ-F-12` |

**占位符约定（全仓库统一）**

| 占位符 | 含义 | 用在哪 |
|---|---|---|
| `<项目名称>` | 项目**全称** | 产品名称、封面、正文叙述 |
| `<项目代号>` | 项目**短代号** | **文档编号**中（如 `<项目代号>-SRS-001-v1.0`） |
| `<REQ-F-001>` / `<REQ-N-001>` | 功能 / 非功能需求编号 | RTM、SRS、测试用例 |
| `<M01>` | 模块号 | 设计文档、模块清单、代码 |
| `<IF-001>` | 接口编号 | 接口需求规格、契约 |
| `<TC-001>` | 测试用例编号 | 测试说明、测试记录、RTM |
| `<BUG-001>` | 缺陷编号 | 缺陷清单、版本说明 |
| `<TBD-01>` | 待决事项 | 任何文档；**必须写明责任人与关闭日期** |
| `<YYYY-MM-DD>` / `<姓名>` | 日期 / 人名 | 签字、批准、执行记录 |

> **为什么编号用短代号而不用全称**：全称含空格与中文，放进编号后无法稳定引用、
> 无法做正则校验、也无法作为文件名。短代号是编号体系可机械校验的前提。

**业务对象编码【本仓库】**

| 对象 | 格式 | 示例 | 规则 |
|---|---|---|---|
| 功能需求 | `REQ-F-` + 3 位 | `REQ-F-012` | 一经分配永不复用 |
| 非功能需求 | `REQ-N-` + 3 位 | `REQ-N-004` | 同上 |
| 接口 | `IF-` + 3 位 | `IF-007` | 同上 |
| 模块 | `M` + 2 位（分层分带） | `M01`、`M45` | 模块废弃后编号作废不回收 |
| 测试用例 | `TC-` + 3 位 | `TC-003` | 全域唯一，不复用 |
| 缺陷 | `BUG-` + 3 位 | `BUG-021` | 全域唯一 |
| **框架变更** | `FC-` + 年 + 3 位 | `FC-2026-007` | 触发条件必须引用 `FC-1`…`FC-6` |
| **其他变更** | `CHG-` + 年 + 序号 | `CHG-2026-014` | 非框架类变更（需求/文档/脚本/构建方式） |
| 技术债 | `DEBT-` + 3 位 | `DEBT-011` | 已知不做但记录在案 |

> **两类变更编号并存，用途不同**：`FC-` 是**框架变更**专用（触发条件必须可归到 `FC-1`…`FC-6`，
> 见 [`../01-流程与阶段/框架与模块共演化.md`](../01-流程与阶段/框架与模块共演化.md)）；
> `CHG-` 承载其余变更。框架变更**同时**是一次变更，走同一条八步流程，只是编号前缀与评审级别不同。

### 3.3 模块号规则（`M01`–`M99` 分层分段）【本仓库·强化项】

GB/T 8567-2006 **未规定**模块编号格式。下表是本仓库为"框架—模块共演化"与自动化门禁增加的工程约定。

| 分层 | 号段 | 允许依赖 | 禁止 |
|---|---|---|---|
| 表现层 | **`M01`–`M19`** | 业务层、公共/工具层 | 禁止直连数据访问层与基础设施层 |
| 业务层 | **`M20`–`M39`** | 数据访问层、基础设施层、公共/工具层 | 禁止反向依赖表现层 |
| 数据访问层 | **`M40`–`M59`** | 基础设施层、公共/工具层 | 禁止包含业务规则 |
| 基础设施层 | **`M60`–`M79`** | 公共/工具层 | 禁止依赖业务层与表现层 |
| 公共/工具层 | **`M80`–`M99`** | **不依赖任何其他层** | 禁止依赖任何业务/技术模块 |

**分配与回收规则**

| 编号 | 规则 |
|---|---|
| MR-1 | 在**所属分层号段内**取下一个未使用的号 |
| MR-2 | **编号一经分配，永不复用**。`M20` 废弃后，下一个业务层模块取 `M27`，**不是** `M20` |
| MR-3 | 号段用尽即**停止在该层新增模块**，应重新审视架构（提 R5），不得挤占其他层号段 |
| MR-7 | **换层 = 换号**。模块从业务层移到基础设施层，必须取新号，并把旧号登记为「已废弃」 |

> **依赖方向由模块号段位可读地表达出来**，CI 据此校验（无环、无反向、无跨层跳跃）。
> 完整规则与校验项见 [`../../templates/03-设计类/02-模块清单与模块号登记表.md`](../../templates/03-设计类/02-模块清单与模块号登记表.md)。

## 四、三类基线

### 4.1 三类基线对照

| 基线 | 标签 | 何时建立（门禁） | 冻结什么 | 谁能改 | 变更走哪 |
|---|---|---|---|---|---|
| **需求基线** | `req-baseline/v1.0` | **R1 需求评审通过**后立即打标签 | SRS + 接口需求规格 + RTM | 批准人：技术负责人；涉范围变更须甲方/产品确认 | 需求变更申请 → 影响分析 → **R1 复评** → 升 `v1.1`/`v1.2` |
| **框架基线** | `framework/v0.1`（首次，**从 v0 起**）<br>`framework/v0.N`（迭代） | **R2 框架评审通过**（首次）<br>每次 **R5 框架变更批准 + 回归通过**后 | HLD + 模块清单与模块号登记表 + 模块接口契约 + **框架假设清单** | 批准人：技术负责人（R5 主持） | **只能走 R5 框架变更评审**，八步流程不可跳 |
| **产品基线** | `product/v1.0.0` | **R7 验收评审通过**后立即打标签 | **全部交付物** + 制品 + **制品哈希** + 用户手册 + 版本说明 | 批准人：甲方/产品（R7 主持） | **只能通过新版本发布演进**（`v1.0.1` / `v1.1.0` / `v2.0.0`），不得静默修改 |

> **补充（可选强化项）**：`templates/07-配置与发布类/01-软件配置管理计划.md` 另定义了
> **测试基线 `test-baseline/v1.0`**（R6 测试准出通过后建立，冻结测试计划/说明/用例/报告）。
> 它**不属于**三类基线，B 档可选用；A 档不建。

### 4.2 基线三律

| # | 律 | 落地动作 |
|---|---|---|
| 1 | **打标签之前的集合不是基线** | 口头冻结不算数，必须是**附注标签**（`git tag -a`），且标签不可移动 |
| 2 | **基线冻结后不得原地修改** | 修正只能是"新版本 + 变更记录" |
| 3 | **每次打标签必须同时记录"包含哪些配置项"** | 否则无法回答"这个版本到底发了什么" |

### 4.3 建基线与冻结操作规程

| 步骤 | 动作 | 产出 | 责任人 |
|---|---|---|---|
| 1 | 确认门禁已通过（**R1 / R2 / R5 / R7**） | 评审记录编号 | 配置管理员 |
| 2 | 核对本基线应含配置项是否全部就位、版本一致 | 基线内容清单 | 配置管理员 |
| 3 | 在受保护分支打**附注标签**并推送 | Git 标签 | 配置管理员 |
| 4 | 保护标签：禁止强推、移动、删除 | 仓库保护规则 | 配置管理员 |
| 5 | 归档构建产物，标注对应提交号与产品版本号 | 制品记录（含哈希） | 配置管理员 |
| 6 | 更新状态记录与基线条目 | 状态报告 | 配置管理员 |
| 7 | 通知全体成员 | 通知记录 | 配置管理员 |

### 4.4 与 `GB/T 8566-2022` 三种基线的关系（不要把两者混为一谈）

`GB/T 8566-2022` 配置管理过程提到，**系统级基线通常有三种：功能基线、分配基线、产品基线**（OCR 提取）；
`GB/T 8567-2006` 的 SCMP 编写格式中也有同样表述（OCR 提取，显示为 `4.1.1` 条）。

**本仓库的三类基线是按迭代节奏重构的落地形式，不是那三种基线本身。**

| 本仓库基线 | 大致对应 | 差异（必须知道） |
|---|---|---|
| 需求基线 | 功能基线 | 本仓库冻结的是 SRS + IRS + RTM，不含系统级功能分配 |
| 框架基线 | 分配基线（部分） | 本仓库把"模块划分 + 接口契约 + 假设清单"当独立冻结点，**并允许它反复演进（`v0.1→v0.2→…`）** |
| 产品基线 | 产品基线 | 一致：交付物 + 制品 + 哈希 |

> **写法要求**：对外交付文档里若要提"三种基线"，
> **引用标准时写标准的三种，描述本仓库时写本仓库的三种**，
> 不要写"本仓库的框架基线即标准的功能基线"这类等同表述。

## 五、版本号规范

### 5.1 语义化版本（产品与模块）

| 位 | 名称 | 递增条件 | 示例 |
|---|---|---|---|
| **MAJOR** | 主版本 | **不兼容**的接口 / 数据 / 行为变更 | `1.4.2` → `2.0.0` |
| **MINOR** | 次版本 | **向后兼容**的功能新增 | `1.4.2` → `1.5.0` |
| **PATCH** | 修订号 | **向后兼容**的缺陷修复 | `1.4.2` → `1.4.3` |

**附带规则**

| 规则 | 说明 |
|---|---|
| MAJOR 递增时 MINOR 与 PATCH 归零 | `1.4.2` 的破坏性变更结果是 `2.0.0`，不是 `2.4.2` |
| `0.y.z` 表示开发期 | 该阶段允许破坏性变更；**未稳定的框架不得宣布 `v1.0`** |
| 预发布后缀 | `-alpha.N` → `-beta.N` → `-rc.N`；`-rc.N` 不得作为正式发布版本 |
| 构建元数据 | `+build.NNN`，**不参与版本比较** |
| 版本号唯一 | 同一版本号不得对应两份不同内容的制品 |

> **语义化版本是本仓库既定工程约定，不声称来自国标。**
> `GB/T 8566-2022` 规定配置管理过程，但**不规定版本号格式**。

### 5.2 框架版本：独立编号，从 `v0` 起

| 位 | 递增条件 |
|---|---|
| **MAJOR** | 模块划分 / 契约**不兼容**变更 |
| **MINOR** | 契约**兼容性扩展**、新增框架能力 |

格式 `vMAJOR.MINOR`（两位），例：`v0.4`。

> **不要过早宣布框架 `v1.0`。** `v0.x` 明确表达"框架尚未稳定，允许破坏性调整"。
> 一旦 `v1.0`，契约冻结，任何破坏性变更都要通知**全部**使用方并走完整流程。

**为什么框架版本与产品版本必须分离**：框架的"稳定"与产品的"可用"是两个独立维度。
框架 `v0.1` 完全可以支撑产品 `v1.0.0` 的发布——**框架版本号表达的是契约稳定性，不是产品质量等级**。
混为一个版本号会导出两种错误：要么为了"版本号好看"过早冻结框架，
要么每次框架微调都强制产品升 MAJOR。

### 5.3 版本递增决策表（照表判定，不凭感觉）

| 变更性质 | 产品版本 | 框架版本 |
|---|---|---|
| 修 bug，契约不变 | PATCH | 不变 |
| 新增模块（不改既有契约） | MINOR | 可能 MINOR（若框架新增装配点） |
| 契约扩展字段（兼容） | MINOR | MINOR |
| 契约语义变更（不兼容） | **MAJOR** | **MAJOR** |
| 数据模型不兼容变更 | **MAJOR** | 可能 MAJOR |
| 仅文档 / 日志 / 配置默认值 | PATCH | 不变 |

### 5.4 各对象版本号对照

| 对象 | 版本格式 | 示例 | 批准人 |
|---|---|---|---|
| 需求基线 | `req-baseline/vMAJOR.MINOR` | `req-baseline/v1.0` | 技术负责人（涉范围含甲方/产品） |
| 框架基线 | `framework/vMAJOR.MINOR` | `framework/v0.4` | 技术负责人（R5） |
| 模块 | `MAJOR.MINOR.PATCH` | `1.3.2` | 模块负责人 |
| 产品发布 | `MAJOR.MINOR.PATCH` | `2.1.0` | 技术负责人（R8） |
| 文档 | `vMAJOR.MINOR` | `v1.1` | 文档责任人 |

### 5.5 标签命名规范（可机械校验）

| 对象 | 命名正则 |
|---|---|
| 需求基线 | `^req-baseline/v\d+\.\d+$` |
| 框架基线 | `^framework/v\d+\.\d+$` |
| 产品基线 | `^product/v\d+\.\d+\.\d+$` |
| 测试基线（可选） | `^test-baseline/v\d+\.\d+$` |

**标签硬要求**：必须是**附注标签**（`git tag -a`），必须带说明，**禁止移动、强推覆盖、删除**。

## 六、变更控制流程（八步，不可跳）

### 6.1 流程图

```
① 提出变更申请 ─→ ② 影响分析 ─→ ③ 变更评审 ─→ ④ 批准/驳回
                                                    │
       ⑧ 归档与状态记录 ←─ ⑦ 新基线冻结 ←─ ⑥ 回归验证 ←─ ⑤ 实施变更
```

### 6.2 八步明细

| 步骤 | 内容 | 产出 | 门禁 | 责任人 |
|---|---|---|---|---|
| ① 申请 | 变更内容、动机、**触发条件** | 变更申请单（`FC-` 或 `CHG-`） | **字段完整**（禁止"我觉得更好"） | 提出人 |
| ② 影响分析 | 受影响模块 / 需求（**RTM 反查**）/ 接口 / 数据 / 测试范围 / 工作量 | 影响分析表 | **影响范围可推导回归范围** | 提出人 + 设计者 |
| ③ 评审 | 方案对比（**≥2 案，含"不改"案**），判定变更等级 | 评审记录 | 按变更级别选 **R5** 或 **R8** | 评审组 / CCB |
| ④ 批准 | 批准则**定新版本号**；驳回记入技术债 | 批准记录 | **批准人签字** | 按 §6.4 权限 |
| ⑤ 实施 | 代码 + **同步更新设计文档** | 提交 | **文档与代码同提交** | 实施人 |
| ⑥ 回归 | 按影响分析执行回归（**R-A/B/C/D**，见 [`../03-测试与回归/测试体系与缺陷管理.md`](../03-测试与回归/测试体系与缺陷管理.md)） | 回归测试报告 | **回归通过** | 测试 |
| ⑦ 基线 | 打标签、更新版本说明 | Git 标签 + 版本说明 | **标签规范**（§5.5） | 配置管理员 |
| ⑧ 归档 | 更新 `CHANGELOG`、状态记录、通知相关方 | `CHANGELOG` + 状态报告 | **可追溯** | 配置管理员 |

> **红线：文档与代码必须同一次提交。** 文档漂移是配置管理失效的头号征兆——
> 一旦文档不可信，整套追溯体系就归零了。
>
> **③ 与 ④ 不得后置到 ⑤ 之后。** "先改完再补审批"在本仓库视为**未授权变更**。

### 6.3 变更申请最小字段集

```yaml
变更编号: FC-2026-007          # 框架变更用 FC-；其余用 CHG-
变更类型: 代码 / 设计 / 需求 / 脚本 / 构建方式 / 基线定义
变更等级: 重大 / 一般 / 轻微 / 紧急
触发条件: FC-1 契约不足        # 框架变更必须引用 FC-1…FC-6；FC-6 应驳回
现象证据: M03 需要向 M05 传递带优先级的任务，现有 Msg 契约无优先级字段，
          当前用 payload 强转字符串 hack，已在 3 处出现
受影响配置项: [M03, M05, M07]  # 引用配置项编号
受影响需求: [REQ-F-012, REQ-F-019]   # RTM 反查
需重跑测试: 单元(M03,M05,M07) + 集成(IT-004) + 冒烟
方案A: 扩展 Msg 契约增加 priority 字段（低成本，1 人日）
方案B: 引入独立优先级队列层（高成本，5 人日，但 FC-4 也会受益）
决策: 采纳方案A；方案B记入技术债 DEBT-011
版本影响: 框架 v0.4；产品 PATCH
批准人: <姓名>  日期: <YYYY-MM-DD>
```

### 6.4 变更分级与审批权限

| 等级 | 判定标准 | 评审 | 批准人 | 回归范围 | 版本影响 |
|---|---|---|---|---|---|
| **重大** | 破坏性接口变更；需求范围变更；基线定义变更；数据结构不兼容 | R5（框架）/ R1（需求） | 技术负责人 + 甲方/产品（涉需求时） | 全量或按影响分析的全回归 | 框架 MAJOR / 产品 MAJOR |
| **一般** | 兼容性扩展；模块内实现调整；新增非破坏性能力 | R5 或 R4 | 技术负责人 | 受影响模块 + 集成测试 | 框架 MINOR / 产品 MINOR |
| **轻微** | 缺陷修复；文案；不改契约的重构 | R4（可简化） | 模块负责人 | 定向回归 + 冒烟 | 产品 PATCH |
| **紧急** | 生产环境 P0 故障修复 | **事后评审**（48 h 内补） | 技术负责人（事后补批） | 定向 + 冒烟，24 h 内补全回归 | 产品 PATCH |

> **紧急变更不是免流程通道，只是流程顺序后置。** 缺少补审、补回归、复盘的紧急变更，
> 在 R8 发布评审中一律判为不通过。

### 6.5 变更记录实例（本仓库真实发生过的两次框架变更，供参照写法）

| 字段 | **FC-2026-001** | **FC-2026-002** |
|---|---|---|
| **触发条件** | FC-1 契约不足 | FC-1 契约不足 |
| **现象证据** | `templates/03-设计类/02-模块清单与模块号登记表.md` 明令"禁止跨层跳跃"，但 `skeleton/module_system.py` 只校验了分层倒置——**规范说了而机器不查，必然漂移** | `docs/demo/需求追溯矩阵.csv` 的多值字段写作未加引号的 `M01,M20`，裸逗号被 CSV 解析器当作列分隔符，**整行右移一列**；而门禁工具在此情况下仍报"通过"（退出码 0）——**门禁静默失效** |
| **受影响模块** | 全部（校验规则属框架层能力） | 无（工具层修正） |
| **受影响需求** | 无（不改变业务行为） | 无（不改变业务行为） |
| **需重跑测试** | 全部单元测试 + 骨架冒烟 | 追溯门禁全部模式 + 构造错位用例验证 |
| **方案对比** | A 仅修分层语义（低成本，但规范与代码仍不一致）；**B 补齐跨层跳跃校验**（成本略高，消除漂移）→ 采纳 B | A 只改数据（下次还会踩）；**B 改数据 + 加结构完整性校验**（根治）→ 采纳 B |
| **框架新版本** | 框架校验能力增强，MINOR | 同左 |
| **回归验证** | 单元测试 34/34、骨架 15/15 | 错位 CSV 实测报错返回 1；`--strict` 全绿 |
| **教训** | **规范里写了但工具不查的规则，等于没有规则** | **门禁的失败模式不是"报错太多"，而是"该报错时不报错"**；数据错位类缺陷必须用结构校验兜住，不能依赖人工核对 |

> FC-2026-002 值得特别注意：发现它的不是自动化门禁，而是**评审中的人**。
> 自动化门禁与人工评审是互补关系——机器负责确定性的规则，
> 人负责发现"规则本身没想到的情况"。

## 七、分支与提交策略

### 7.1 分支模型（简化 Git Flow，够用且不重）

| 分支 | 用途 | 规则 |
|---|---|---|
| `main` | 稳定可发布 | **只接受来自 PR 的合并**；每次合并打标签；禁止强推 |
| `develop` | 集成主线 | 模块开发汇入此处；CI 全量跑 |
| `feature/M<模块号>-<简述>` | 模块开发 | 从 `develop` 切出，完成后 PR 回 `develop` |
| `fix/BUG-<编号>` | 缺陷修复 | **必须关联 BUG 编号** |
| `hotfix/<版本>` | 紧急修复 | 从 `main` 切出，回并 `main` 与 `develop` |

**A 档可裁剪**：单人项目可只用 `main` + 短生命周期分支，但**不得直接向已打基线标签的提交强推**。

### 7.2 提交信息规范（Conventional Commits）

```
<类型>(<范围>): <简述>

[正文：为什么改，而非改了什么]

[追溯：REQ-F-012 / M03 / BUG-021 / FC-2026-007]
```

| 类型 | 含义 | 版本影响 |
|---|---|---|
| `feat` | 新功能 | MINOR |
| `fix` | 缺陷修复 | PATCH |
| `refactor` | 重构（不改行为） | 无 |
| `docs` | 文档 | 无 |
| `test` | 测试 | 无 |
| `chore` | 构建 / 工具 | 无 |
| **`framework`** | **框架变更** | 框架 MINOR / MAJOR |
| `BREAKING CHANGE`（脚注） | 不兼容变更 | MAJOR |

> **`framework` 类型是本仓库的强化项【本仓库】**：让框架变更在提交历史里一眼可辨，
> 便于统计"**框架变更次数 / 已实现模块数**"这个健康度指标（健康值 < 0.5）。

**示例对照**

| 写法 | 判定 |
|---|---|
| `framework(contract): Msg 契约增加 priority 字段` + 正文写动机 + `FC-2026-007` | ✅ |
| `feat: 加了个优先级` | ❌ 无范围、无追溯、没说为什么 |
| `fix(M40): 修复分页越界` + `BUG-021 / REQ-F-012` | ✅ |
| `update` | ❌ 类型缺失 |

### 7.3 合并门禁

| 门禁 | 内容 | A 档 | B 档 |
|---|---|---|---|
| CI 通过 | 构建 + 测试 + 覆盖率 | ✅ | ✅ |
| 追溯矩阵校验 | `python tools/trace_matrix.py` | 降级 | ✅ |
| 改动范围校验 | `python tools/scope_check.py` | 按需 | ✅ |
| 依赖方向校验 | 模块系统环检测 / 跨层校验 | ✅ | ✅ |
| 人工评审 | 至少 1 人评审通过 | 自查 | ✅ |

## 八、A 档 / B 档差异

### 8.1 配置与版本维度的对照

| 维度 | **A 档：个人 / 单产品** | **B 档：公司 / 对外交付** |
|---|---|---|
| **版本控制** | ✅ **不可裁剪**（唯一零成本实践） | ✅ 不可裁剪 |
| **基线** | **Git tag 就够**——至少一个需求基线标签 | **三类基线齐全**：需求 + 框架 + 产品，各自有内容清单 |
| **变更流程** | **变更留痕即可**：commit message 写清"为什么改"；重大改动写一份变更说明 | 八步流程 + 变更分级审批 + CCB + 影响分析表 |
| **配置项清单** | 一张简表：代码 / 需求要点 / 设计要点 / 测试记录 / 版本说明 | 四类配置项（文档/代码/脚本/构建产物）全表 + 责任人与基线归属 |
| **配置审计** | ❌ 不做独立审计；靠"一条命令可复现" | ✅ 每次 R8 前执行 §2.3 全量检查单 |
| **制品管理** | 本地制品 + 版本说明里写清版本与来源 | 制品库 + **SHA-256 哈希** + 提交号对应 |
| **追溯** | 需求 ↔ 测试（轻量） | 需求 ↔ 设计 ↔ 代码 ↔ 测试（**RTM 门禁**） |
| **分支** | 可只用 `main` + 短分支 | PR 流程 + 受保护分支 + 至少 1 人评审 |
| **依据** | `GB/T 8567-2006` 裁剪条款 | `GB/T 8567-2006` + `GB/T 38634` 系列 + 三类基线 |

### 8.2 A 档最小可执行动作（今天就能做）

| # | 动作 | 验收 |
|---|---|---|
| 1 | 把全部源码与文档纳入 Git，`.gitignore` 排除构建产物与密钥 | 无游离文件；无密钥入库 |
| 2 | 需求要点条目化（每条可验证），打一个 tag：`req-baseline/v1.0` | `git tag -a` 附注标签存在 |
| 3 | 提交信息按 §7.2 写，正文写"为什么改" | 随机抽 5 条提交，都能看出动机 |
| 4 | 发版前写一份版本说明（这一版和上一版差在哪） | `RN` 文档存在 |

> **A 档主动放弃的部分（显式声明，不装作不存在）**：正式阶段评审、完整 RTM 追溯、
> 独立 SQA、配置审计。放弃的风险与补偿方式见
> [`../01-流程与阶段/流程档位定义.md`](../01-流程与阶段/流程档位定义.md) §4.3。

### 8.3 A 档 → B 档：配置与版本维度先补什么

| 优先级 | 补什么 | 为什么排这个位置 |
|---|---|---|
| 1 | **需求规格说明 + RTM** | 没有它，B 档的所有追溯都无源头 |
| 2 | **三类基线** | 建立冻结点，否则后续变更无法判定影响 |

> **升档不可逆。** 一旦发生过交接成本，就不存在"回到 A 档"。

## 九、标注体系

### 9.1 两类标记

| 标记 | 含义 | 引用规矩 | 可裁剪 |
|---|---|---|---|
| **【国标】** | 标准**明文**要求 | **必须写清标准号**；条款号仅在核对过原文后引用 | ❌ 不可随意裁剪，裁剪须留痕 |
| **【本仓库】** | 本仓库自行增加的工程强化项 | 可写"本仓库约定"，**不得声称来自国标** | ✅ 可裁剪，**须留痕** |

### 9.2 本附件中的典型划分

| 【国标】 | 【本仓库】 |
|---|---|
| 配置管理过程的六项输出：识别并管理配置项、**建立配置基线**、控制变更、配置状态信息可用、完成配置审核、控制和批准发布与交付（`GB/T 8566-2022` 配置管理过程，OCR 提取） | `M01`–`M99` **分层分段**模块号与"换层=换号" |
| 变更请求与差异请求由 **CCB** 控制（同上，OCR 提取） | 编号**永不复用**、废弃保留登记行 |
| **FCA / PCA** 两类配置审核（同上，OCR 提取） | `framework` 提交类型 + 健康度指标"框架变更次数 / 已实现模块数" |
| 配置管理计划文档种类与四方面活动（`GB/T 8567-2006`，OCR 提取） | 八步变更流程、版本递增决策表、§6.5 的 FC 实例 |
| 文档与配置项的**可追溯性**要求 | `tools/` 自动门禁、CI 拦截、基线标签命名正则 |
| —— | 语义化版本规则（**不声称来自国标**，国标不规定版本号格式） |

> **裁剪留痕三件套**：裁剪项、理由、补偿措施——外加**批准人**。

## 附录 A · 常见失效征兆（出现即需干预）

| 征兆 | 后果 | 处置 |
|---|---|---|
| 文档改了代码没改（或反之） | 追溯体系失效 | 强制同提交；PR 检查单加一项 |
| 基线标签乱打 | 无法回退到已知良好状态 | 统一标签规范（§5.5）+ CI 校验 |
| 密钥入库 | 安全事故 | **立即吊销轮换**；引入 secret 扫描 |
| 版本号随手起 | 无法判断兼容性 | 语义化 + CI 校验标签格式 |
| 只有 `main` 分支、直接提交 | 无评审、无隔离 | 引入 PR 流程 |
| `CHANGELOG` 靠回忆补 | 版本历史不可信 | 从提交信息自动生成 |
| 模块号复用 | 历史文档/旧测试/旧缺陷单全部指错方向 | 恢复废弃行；新对象取新号 |
| 规范里写了但工具不查 | 必然漂移（见 FC-2026-001） | 规则落地为校验，否则删掉这条规则 |

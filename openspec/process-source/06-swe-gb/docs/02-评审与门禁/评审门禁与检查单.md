# 评审与门禁

> 评审不是"大家坐一起看看文档"，门禁也不是"走个流程"。
> 本文规定：**每种评审什么时候开、谁参加、看什么、什么算通过、不通过怎么办。**
>
> 依据：GB/T 8566-2022（技术评审与管理评审过程）、GB/T 8567-2006（文档评审要求）。

---

## 一、门禁的三个铁律

1. **没有准出结论，不进入下一阶段。** "先做着，评审后补"是本仓库明令禁止的做法。
2. **评审结论必须书面化。** 口头通过 = 没通过。结论写入 `templates/06-评审类/01-阶段评审记录.md`。
3. **不通过不是失败，是流程在工作。** 评审不通过的处置是"退回上一阶段修改 + 重新评审"，不是"降低标准凑合过"。

---

## 二、评审类型总表

| 编号 | 评审名称 | 时机 | 主持 | 必参 | 结论形式 | 对应阶段门禁 |
|---|---|---|---|---|---|---|
| **R0** | 立项评审 | 项目启动前 | 项目负责人 | 甲方/产品、技术负责人、质量 | 批准/不批准/有条件批准 | S0 准出 |
| **R1** | 需求评审 | 需求基线建立前 | 技术负责人 | 甲方/产品、设计、测试、开发 | 通过/退回 | S1 准出 |
| **R2** | 框架（概要设计）评审 | 框架基线建立前 | 架构师/技术负责人 | 开发、测试、运维 | 通过/退回 | S2 准出 |
| **R3** | 骨架跑通评审 | 骨架可运行后 | 技术负责人 | 开发、测试 | 通过/退回 | S3 准出（可简化，但**必须执行**） |
| **R4** | 模块评审（详细设计+代码） | 每个模块完成时 | 模块负责人 | 1 名同级开发、测试 | 通过/有条件通过/退回 | S4 逐模块门禁 |
| **R5** | 框架变更评审 | 每次框架变更申请时 | 技术负责人 | 受影响模块负责人 | 批准/驳回 | S4 内循环门禁 |
| **R6** | 测试准出评审 | 系统测试完成 | 质量负责人 | 开发、测试、技术负责人 | 准出/不准出 | S5 准出 |
| **R7** | 验收评审 | 验收测试完成 | 甲方/产品 | 全部干系人 | 验收通过/不通过 | S6 准出 |
| **R8** | 发布评审 | 每次版本发布前 | 技术负责人 | 开发、测试、运维 | 发布/不发布 | S7 准出 |

> **R3、R4、R5 是本仓库的强化项**：传统流程往往只有 R1/R2/R6，导致"框架是否真能跑"
> 和"框架变更是否受控"两个高风险点无人把关。这正是"框架-模块共演化"最容易失控的地方。

## 三、各评审的准入与准出准则

### R1 需求评审

**准入（Entry）**
- SRS 已完成评审稿，版本号已标注；
- 需求追溯矩阵已建立（每条需求有唯一编号）；
- 需求评审材料在评审前 **≥1 个工作日**发给参会人。

**准出（Exit）**
- [ ] 每条需求**可验证**（能推导出至少一条测试用例）；
- [ ] 每条需求有唯一编号、来源、优先级、验收准则；
- [ ] 功能需求与非功能需求分离，非功能需求有量化指标；
- [ ] 接口需求已识别（含外部系统、数据格式、异常约定）；
- [ ] 无未闭环的 TBD（若有，必须写明责任人与关闭日期）；
- [ ] 评审意见全部闭环，或有明确处置结论；
- [ ] **需求基线已打标签**（如 `req-baseline/v1.0`）。

**常见退回原因**：需求写成了愿望；缺少异常路径描述；非功能需求无量化；验收准则缺失。

---

### R2 框架（概要设计）评审

**准入**
- 需求基线已建立；
- HLD、模块清单、模块接口契约三件套齐备。

**准出**
- [ ] 架构风格与选型有**理由**（不是"因为流行"）；
- [ ] 模块划分满足：高内聚、低耦合、**无循环依赖**；
- [ ] 每个模块有唯一模块号、明确职责、对外契约（输入/输出/异常）；
- [ ] 模块清单完整，覆盖全部已基线需求（RTM 正向追溯无缺口）；
- [ ] 数据模型与关键状态流转已定义；
- [ ] 错误处理、日志、配置、安全策略已定义；
- [ ] **框架假设清单已产出**，每条假设有验证时点；
- [ ] 框架基线已打标签（`framework/v0.1`）。

**常见退回原因**：模块边界靠"感觉"划；契约只有成功路径没有异常；假设没写下来。

---

### R3 骨架跑通评审

**准入**
- 框架基线已建立；
- 骨架代码已提交，含构建脚本。

**准出**
- [ ] **一条命令**能在干净环境跑通骨架；
- [ ] 全部模块以桩/Mock 形式装配成功；
- [ ] 模块注册与依赖解析正确，无环；
- [ ] 冒烟测试用例存在且通过；
- [ ] CI 流水线在干净环境可复现通过；
- [ ] 日志、配置加载路径已验证。

**为什么单独设这道门禁**：骨架跑通是用**最低成本**验证框架结构正确性的唯一时机。
此时代码量最小，推翻框架的代价最低。跳过它，代价会在 S5 集成时集中爆发。

---

### R4 模块评审

**准入**
- 模块代码提交，含单元测试；
- 详细设计说明（该模块章节）已更新。

**准出**
- [ ] 模块行为符合其**接口契约**；
- [ ] 单元测试全部通过；覆盖率达标（行 ≥80%，核心分支 ≥90%）；
- [ ] 覆盖了正常、边界、异常、空值四类路径；
- [ ] 无新增循环依赖；
- [ ] **框架适配性回判已执行**（若不适配，已提 R5）；
- [ ] 设计文档与代码一致（无漂移）；
- [ ] 无遗留 P0/P1 缺陷；
- [ ] 至少 1 名同级开发完成代码走查并签字。

---

### R5 框架变更评审

**准入**
- 变更申请单已完成，含触发条件编号（FC-1…FC-6）与现象证据；
- 影响分析已完成（受影响模块/需求/需重跑测试/工作量估算）。

**准出**
- [ ] 触发条件成立（**FC-6 个人偏好类一律驳回**）；
- [ ] 至少给出 **2 个方案对比**（含"不改"或"最小改"案）；
- [ ] 影响范围明确，回归范围可推导；
- [ ] 若为破坏性变更，已通知全部使用方；
- [ ] 批准后有确定的新框架版本号；
- [ ] 驳回的变更已记入**技术债清单**（不是丢弃）。

---

### R6 测试准出评审

**准入**
- 系统测试执行完毕；
- 缺陷清单已更新至最新状态；RTM 已更新。

**准出**
- [ ] P0/P1 缺陷 **为 0**；P2 缺陷有明确处置计划与责任人与期限；
- [ ] 需求覆盖率 100%（每条需求至少一条对应用例）；
- [ ] 用例执行率 100%（未执行用例必须有说明与批准）；
- [ ] 测试报告含环境、版本、数据、结论，可复现；
- [ ] 未通过用例的处置结论明确（修复 / 降级 / 转为已知问题并批准）。

---

### R7 验收评审

**准入**：测试准出已通过；用户文档齐备。

**准出**
- [ ] 验收用例全部通过；
- [ ] 按 GB/T 25000.51-2016 的 8 个质量特性逐项给出结论；
- [ ] 交付物清单齐备（代码、文档、手册、部署说明）；
- [ ] **产品基线已打标签并冻结**；
- [ ] 遗留问题清单与处置达成一致。

---

### R8 发布评审

**准出**
- [ ] 变更申请与影响分析已批准；
- [ ] 回归测试按影响范围执行完毕且通过；
- [ ] 版本号符合语义化规范；
- [ ] 版本说明（含变更内容、已知问题、升级注意）已完稿；
- [ ] 回滚方案已确认可行。

## 四、评审有效性规则（防止评审形式化）

| 规则 | 说明 |
|---|---|
| **材料前置** | 评审材料至少提前 1 个工作日送达，会上不做首次阅读 |
| **角色齐备** | 缺测试参与的评审无效（可测试性是设计质量的核心判据） |
| **席位与部分一一对应** | **有几部分技术就设几位专家**；不得出现"无主的部分"；**不得一位专家跨部分下判断**；专家**评审文档、不写代码**；席位表随部分清单**一起冻结**（见 [`附件八`](附件八-责任时间与阶段分解.md) §6.7） |
| **记录留痕** | 每个评审意见有编号、责任人、闭环状态，未闭环不得通过 |
| **结论明确** | 只有三种结论：通过 / 有条件通过（附条件清单与期限）/ 退回 |
| **时限约束** | 有条件通过的条件必须在下一阶段门禁前闭环，否则自动降为退回 |
| **反形式化** | 若某类评审连续 3 次"零意见通过"，需检查是否流于形式并调整检查单 |
| **意见要辩证处置** | 专家意见**先复算前提**再决定采纳与否；**反驳是合法输出**（须给理由与依据）；**"为了显得配合而照抄"是反模式**。见 §4.2 |
| **每阶段必有技术评审** | **含立项阶段**。**没有技术评审的阶段不存在"准出"**。审的是**技术内容**，不是文档格式。见 §4.3 |
| **不得用"格式合规"冒充内容评审** | 准出条件里「格式/模板齐备」与「技术内容被评审并裁定」**分列两条**，**只有前者不算过**。见 §4.3 反面清单 |
| **评审必须反复，直到定案** | **轮次不设上限**直到无保留意见；**分歧不得上抛**（胜负只由**标准条款**或**实测**判定，判不了的**当场做实验**）。见 §4.4 |
| **无效轮次须重做** | 一轮评审**未产生任何技术内容改动、也未产生任何明确裁定** ⇒ **该轮无效、须重做**。见 §4.4 |

### 4.1 门禁通过前必过的 20 项通用检查单

每道门禁（R0–R8）组会时，除本门禁的专项检查单外，**必须逐项走一遍**
[`附件二`](../附件/附件二-阶段流程与交付物.md) **§0.10「每道门禁通用检查单（20 项）」**，
并在评审记录里逐项给出**结论 + 证据位置**。

> **勾选而无证据的审计记录视为无效。** 勾不出来的一律**不勾**——
> **不勾不是失败，假装勾了才是**（宁可有名无实被看见，不可无声消失）。

### 4.2 评审意见的处置表（⭐ 本版新增，**不是"意见汇总"，是"逐条可核的执行计划"**）

**为什么要单立一张表。** 本项目吃过两种亏：
① 把专家意见当成必须照抄的指令 ⇒ **规范越改越多、执行的还是那几条**；
② 一条被两位评委先后提出的 P0 判词，**两次都被实测推翻**（判词把"没有 `pipefail` 时的行为"
当成了"有 `pipefail` 时的行为"）。
⇒ 所以：**先复算前提，再决定采纳与否**；**反驳是合法输出**。

**处置表结构**（每位/每轮意见合并成一张表）：

| # | 意见原文（逐字，标出处：哪位评委 / 哪条判词） | **前提复算**（命令 + 观测到的输出） | **处置（四态）** | 代价 | **落笔坐标**（文件:节 + 改前原文 → 改后原文） | 谁定 | 状态 |
|---|---|---|---|---|---|---|---|
| 1 | `<逐字原文>` / `<评委 A 第 3 轮>` | `<命令>` ⇒ `<输出>`（**前提成立 / 不成立**） | `采纳` / `部分采纳` / `反驳` / `属本项目执行问题` | `<代价>` | `<文件> §<节>：「<改前>」→「<改后>」` | `<角色>` | `<待批 / 已落笔 / 已否决>` |

**四态的判读纪律：**

| 态 | 什么情况用 | 必须附什么 |
|---|---|---|
| **采纳** | 前提成立且与实际情况相符 | **落笔坐标**（改前改后原文） |
| **部分采纳** | 方向对但范围过头 / 会静默删数 | 采纳哪部分、不采纳哪部分、**各自的理由** |
| **反驳** | **前提不成立**、或与国标/实际情况冲突、或改了会降低标准 | **理由 + 依据**（标准条款 或 实测输出）；**禁止只写"不适用"** |
| **属本项目执行问题** | 条款已写对，是**没执行** | 责任人 + 时点；**不得把它改写成新条款**（否则等于用改条款掩盖不执行） |

**三条硬纪律：**

1. **逐条可核**：`落笔坐标` 必须能指向**具体位置与改前改后原文**；
   **不接受"已处理""已优化"这类无坐标的说法**；
2. **获批前不改变效力**：处置表是**执行计划，不是新法**；据此产生的改动一律标注
   「**本修订须经人批准后生效**」；
3. **必须单列两节**：
   - 「**被评审方自己造成的错误**」（不混入"项目问题"）——这是本项目已经用出来、被证明有效的形态；
   - 「**各评委确认站得住、不得为统一格式而改写**的部分」——**防止"为了整齐"把对的东西改坏**。

**必须留痕的第三件事：「被推翻的判词」行。** 前提被推翻的意见**不得删除**：

| 原判词 | **复现命令** | **观测到的输出（与判词不符）** | 提出人 / 轮次 | 复跑结论 |
|---|---|---|---|---|
| `<逐字原文>` | `<命令>` | `<输出>` | `<评委> / 第 <n> 轮` | `<前提不成立，判词撤销>` |

> **纪律**：**同一断言再次出现时，先跑这张表里的复现命令，不得直接采信。**
> 经验来源的原话：「"`check.sh` 吞掉失败"这一断言，**凡再出现，必须先复跑 A–E 五个实验**」。

**按"部分"归口**：一位专家**只判他那一部分**；**跨部分的结论必须由该部分的专家出**；
汇总人**不得替某部分下判断**（承 §四 的"席位与部分一一对应"）。

**片面看问题的四种典型形态（当场识别）：**

| # | 形态 | 识别问句 |
|---|---|---|
| 1 | 只看自己那部分，却给出影响别部分的结论 | "这条结论落在哪一部分？该部分专家是谁？" |
| 2 | 把"条件性推论"当成"代码/文档事实"陈述 | "这一步是事实，还是需要额外前提的推论？前提是什么？" |
| 3 | 给出无法判定的判据（"合理""可接受范围"） | 按四要素逐条判，缺一即退回（[`附件二`](../附件/附件二-阶段流程与交付物.md) H-03） |
| 4 | 要求改别部分的载体 | "这份载体的所有者是谁？"——改它要走该部分的评审 |

### 4.3 ⭐ 技术评审：审内容，不审格式（**不得用"格式合规"冒充**）

**项目负责人的原话**：「**无论什么时候一定要有技术评审**，就是**立项阶段**，那肯定得需要技术评审呀。
每一个技术官员要负责一部分技术内容呀，要**反复地有技术评审做定**呀，
**不能光是形式上文档格式对了，那不行，内容上要有**。」

**两条准出必须分列：**

```
[ ] A. 文档格式 / 模板齐备          ← 必要条件
[ ] B. 技术内容已被评审并给出裁定    ← 必要条件（缺此则"未评审"，不是"待补格式"）
```

**反面清单（"格式对但内容是空的"12 种典型形态）——出现任一形态即判「内容未评审」：**

| # | 反面形态 | 为什么它是空的 |
|---|---|---|
| 1 | 判据写成"合理 / 可接受范围 / 若干 / 待定" | 没有阈值就没有判定点 |
| 2 | 数字无复算命令 / 时点 / 对象，却标"实测" | "实测"两字指不到命令 |
| 3 | 结论无依据（"综合考虑""经验判断""通常做法"） | 无法复核，等于没判 |
| 4 | **只填模板不给判断**（表填满但没有"为什么选 A 不选 B"） | 模板是骨架，不是判断 |
| 5 | 把"**未落实**"写成"**已落实**"（含"已实施（待批准）"被称"已全部实施"） | 承诺与实现不符，比留白更坏 |
| 6 | 假设清单没有**验证时点** | 没有验证时点的假设是定时炸弹 |
| 7 | 接口契约**只有成功路径** | 异常语义到集成时靠猜 |
| 8 | 风险清单没有**触发信号** | 写不出触发信号说明没想清楚 |
| 9 | 能力声明给不出**检查 / 测试位置**（"已防护""已堵"） | 没有检查在守它 |
| 10 | 关注点 ↔ 视角**双向覆盖没做**（孤儿项） | 架构描述没回应关切 |
| 11 | 表格**逐项勾选但无证据位置** | 勾选而无证据的记录视为无效 |
| 12 | 评审记录里**全是"符合""通过"**，没有一条裁定或反对 | 该轮很可能是**无效轮次**（见 §4.4） |

**技术官员的职责边界（与 §四 的"席位与部分一一对应"配套）：**

- **一位技术官员只对他那一部分下技术判断**；**跨部分结论必须由该部分的官员出**；
- 官员**评审文档与内容、不写代码**；同一交付物的实现者不得担任其评审人；
- 官员在自己的部分内**必须给出明确裁定**（选哪个方案、为什么、代价是什么）——**不裁定 = 未评审**。

**立项阶段的中心是"需求与目标口径"**（不是格式）：

| 必答四问 | 判据 |
|---|---|
| **要什么** | 范围含**不做清单**且非空 |
| **给谁** | 用方与验收方**具名** |
| **怎么算做成了** | 指向**判据载体**（哪份文档的哪一节） |
| **目标值多少** | 有**数值 + 口径 + 反例** |

> **四问答不出 ⇒ 立项评审不得通过**（无论文档多齐备）。
> **次之**：可行性技术面（候选方案与淘汰理由）、初步模块划分与关键技术风险；
> **再次之**：计划、资源、格式。

### 4.4 ⭐ 轮次机制：反复评审，直到定案

```
一轮结论 ──→ 对方复算前提并反驳 ──→ 再一轮 ──→ …… 直到「无保留意见」
                     │
                     └─ 判不了的 ⇒ 当场做实验（把分歧变成一条可执行的命令）
```

| 规则 | 内容 |
|---|---|
| **轮次不设上限** | 直到**无保留意见**为止；不得以"已经开过会了"结案 |
| **每轮冻结输入输出** | 每轮开始冻结被评对象（blob + 提交号），结束记录本轮裁定与改动——否则第 3 轮时已无人知道第 1 轮判的是什么 |
| **分歧不得上抛** | 胜负只由 **①标准条款** 或 **②实测输出** 判定；**"我认为""通常做法""外部都这么做"不构成理由** |
| **判不了的当场做实验** | 把分歧转成一条可执行的命令，跑它，看输出 |
| **未闭环意见逐条回应** | 上一轮的保留意见，下一轮必须**逐条**回应（不是整体回应） |
| **上抛的唯一合法情形** | 需要**人的价值判断**（范围取舍、风险承受度），且必须附「**建议值 + 各选项代价**」 |
| **无效轮次的判据** | 一轮结束后，**若既无技术内容改动、也无明确裁定**（含明确的不改理由）⇒ **该轮无效，须重做**；重做 = 换材料 / 换问法 / 补证据后重评，不是"再念一遍" |

> **机器可判部分**：比对**本轮前后被评对象的冻结 blob**——无内容变更 **且** 无新增裁定条目 ⇒ 无效。
> **注意**：「无变更」只有在给出「**为什么不改**」的明确理由时才算裁定。

**成功范例（经验来源，本仓库未复现）**：一条"`check.sh` 吞掉失败"的 **P0 判词**被**两位评委先后各提一次**，
最终由 **五组 bash 实验（A–E）定案并推翻**——判词把"没有 `pipefail` 时的行为"当成了"有 `pipefail` 时的行为"；
并立纪律：**该断言凡再出现，必须先复跑 A–E**。
**反面范例**：同一批里 AI 的复核意见把"**条件性推论**"当成"**代码事实**"陈述，
被被复核方用代码逐字定位反驳并纠正 ⇒ **复核意见同样必须标出"哪一步是事实、哪一步是推论"**。

### 4.5 技术评审主链（六环，不可跳）

```
① 部分清单 → ② 席位(1:1) → ③ 技术评审(看内容) → ④ 逐条辩证处置(允许反驳)
                                                            │
   ⑦ 才允许准出 ←─────── ⑥ 反复轮次收敛 ←──── ⑤ 未闭环？回 ③
```

**完整说明见 [`附件二`](../附件/附件二-阶段流程与交付物.md) [§0.11](../附件/附件二-阶段流程与交付物.md)。**
**前六环是准出的承重墙**；缺任一环，准出结论没有依据。

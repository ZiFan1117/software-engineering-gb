## 一、架构确认

```
治理（agentd）+ 货运（通道）+ 骨干（总线）
        │
        ├── UI 投影（语义 shell）      ← 从零开发，先行
        └── 浏览器投影（语义浏览器内核）← 从零开发，殿后
        （transferor：存量 web 的过渡桥，全程服役至阶段 3 接棒）
```

## 二、任务表（六件大事 × 四阶段）

### 阶段 0：总线协议 v1 定稿（地基，纯设计）

- 合并 transferor 的 UI-IR 与 agentd 的能力协议为**统一 schema**（四类消息：
  状态/动作/事件/引用）；
- 定内容寻址规则（hash 引用即证据）；
- 产出：协议文档 + JSON Schema + 两个现有部件的兼容改造清单。

### 阶段 1：让总线先活起来（治理+桥，现有资产大半就位）

- agentd 真机验证（WSL2/Linux）：把"逻辑全绿"升级为"真机验证"（批判清单头号欠账）；
- transferor 加 **MCP 方言**（snapshot/act/events 暴露为 MCP 工具），接入 MCP 网关
  生态（身份/审计/路由白拿）；
- 价值：边造新房边住旧房——总线有真流量、真审计、真事件，后续开发有实数据可依。

### 阶段 2：UI 投影从零开工（第一个语义内核，主战场）

- 目标：**语义 shell v0**——语义树为文档本体的桌面环境（顶栏/通知/启动器最小集）；
- 渲染是投影、总线是原生 IPC、agentd 是内置海关；
- 技术起点：AccessKit 语义树 schema（14 篇已核）+ Rust/Qt Quick 选型评估；
- 自举：自家 shell 当自家第一个用户（agentd 部署其上）。

### 阶段 3：浏览器投影从零开工（最后的堡垒）

- 语义浏览器内核：语义模型为文档本体、渲染为投影、DOM 转译层养活存量 web；
- **开工条件**（不满足不动工）：shell 稳定（IR/协议实战检验过）、DOM 转译层在
  transferor 上练熟、A2UI/WebMCP 页面生态初具；
- 方法论照 Ladybird：Web Platform Tests 驱动、小步啃存量；
- transferor 服役至语义内核接棒。

### 贯穿常设件

通道（文件+hash 起步）；语言投影（语义→人话，阶段 2 后补）；
每阶段批判-修订循环（本系列既有纪律）。

## 三、次序三铁律

1. **协议最先**：不定协议，六件东西各说各话；
2. **真流量先热**：从零开发最怕没有真数据喂——先用现成部件把总线跑热再开新工地；
3. **最难的堡垒最后攻**：shell 先行（14 篇：产房）、浏览器殿后（终点）。

## 四、待批判项

1. 四阶段的时长/资源未估（个人体量 vs Ladybird 级工程，阶段 3 可能需要团队/多年）；
2. "开工条件"是自制标准，存在自我豁免风险（条件可以一直"不满足"或被降低）；
3. transferor 的角色从"产品"滑为"过渡桥"，其维护投入与阶段 3 的启动时点之间
   存在博弈（桥修太好可能反而拖延内核开工）。

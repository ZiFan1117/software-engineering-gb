# 配置管理与版本化

> 依据：**GB/T 8566-2022**（配置管理过程）+ **GB/T 8567-2006**（配置管理计划文档要求）。
>
> ⚠️ **GB/T 12505-90《计算机软件配置管理计划规范》是 1990 年老标准**，本仓库只采其**五要素框架**
> （配置项标识、变更控制、状态记录、配置审计、基线管理），实现方式按现代工程实践（Git + CI + 制品版本化）。

---

## 一、配置管理五要素在本仓库的落地

| 要素 | 国标含义 | 本仓库落地方式 |
|---|---|---|
| **配置项标识** | 唯一标识每个受控项 | 文件路径 + Git 追踪 + 模块号/需求号/用例号编码规则 |
| **基线管理** | 在特定时点冻结配置 | Git 标签：`req-baseline/v1.0`、`framework/v0.1`、`product/v1.0.0` |
| **变更控制** | 变更须申请、评审、批准 | 变更申请单 + R5/R8 评审 + PR 流程 |
| **状态记录** | 记录变更历史与状态 | Git 提交历史 + CHANGELOG + 评审记录归档 |
| **配置审计** | 验证配置与基线一致 | CI 门禁 + 配置审计检查单 + 追溯矩阵校验 |

## 二、配置项清单（什么必须纳入版本控制）

| 类别 | 具体项 | 是否入库 | 说明 |
|---|---|---|---|
| **需求类** | SRS、接口需求规格、RTM、需求评审记录 | ✅ | 需求基线载体 |
| **设计类** | HLD、LLD、模块清单、接口契约、框架假设清单 | ✅ | 框架基线载体 |
| **代码** | 源码、SQL 脚本、配置模板（非真实密钥） | ✅ | 用 `.gitignore` 排除构建产物与密钥 |
| **测试类** | 测试计划/说明/用例/报告、测试数据生成脚本 | ✅ | 测试资产可复用 |
| **脚本与工具** | 构建脚本、CI 配置、门禁工具 | ✅ | 环境可复现的前提 |
| **文档** | 用户手册、部署说明、版本说明、CHANGELOG | ✅ | 交付物 |
| **构建产物** | 二进制包、容器镜像 | ❌ 不入库 | 用制品库/Release 附件，**必须记录版本标签与哈希** |
| **密钥与凭据** | 口令、Token、证书私钥 | ❌ **严禁入库** | 用环境变量/密钥管理；一旦误提交必须立即吊销轮换 |
| **第三方依赖** | 依赖清单与锁定文件 | ✅ | `requirements.txt` / `package.json` + lock 必须入库，保证可复现构建 |

### 编码规则（唯一性 + 永不复用）

#### 占位符约定（全仓库统一）

| 占位符 | 含义 | 用在哪 |
|---|---|---|
| `<项目名称>` | 项目**全称** | 产品名称、封面、正文叙述 |
| `<项目代号>` | 项目**短代号** | **文档编号**中（如 `<项目代号>-SRS-001-v1.0`） |
| `<REQ-F-001>` / `<REQ-N-001>` | 功能 / 非功能需求编号 | RTM、SRS、测试用例 |
| `<M01>` | 模块号 | 设计文档、模块清单、代码 |
| `<IF-001>` | 接口编号 | 接口需求规格、契约 |
| `<TC-001>` | 测试用例编号 | 测试说明、测试记录、RTM |
| `<BUG-001>` | 缺陷编号 | 缺陷清单、版本说明 |
| `<TBD-01>` | 待决事项 | 任何文档；**必须写明责任人与关闭日期** |
| `<YYYY-MM-DD>` / `<姓名>` | 日期 / 人名 | 签字、批准、执行记录 |

> **为什么编号用短代号而不用全称**：全称含空格与中文，放进编号后无法稳定引用、
> 无法做正则校验、也无法作为文件名。短代号（如 `PRJ`）是编号体系可机械校验的前提。

## 三、基线定义

| 基线 | 标签 | 何时建立 | 冻结内容 | 变更要求 |
|---|---|---|---|---|
| **需求基线** | `req-baseline/v1.0` | R1 需求评审通过 | SRS + 接口需求 + RTM | 需求变更申请 → 影响分析 → R1 复评 |
| **框架基线** | `framework/v0.1` | R2 框架评审通过 | HLD + 模块清单 + 接口契约 + 假设清单 | **R5 框架变更评审**（本仓库强化项） |
| **测试基线** | `test-baseline/v1.0` | R6 测试准出通过 | 测试计划/说明/用例/报告 | 测试资产变更需说明 |
| **产品基线** | `product/v1.0.0` | R7 验收通过 | 全部交付物 + 制品哈希 | 只能通过新版本发布演进 |

> **基线的意义**：基线是"经过批准、不可静默修改"的快照。有了基线，
> "这次改动影响了什么"才能被机械地推导出来，而不是靠回忆。

## 四、版本号规范（语义化，框架版本与产品版本分离）

### 产品与模块版本

| 位 | 名称 | 递增条件 | 示例 |
|---|---|---|---|
| MAJOR | 主版本 | **不兼容**的接口/数据/行为变更 | 1.4.2 → 2.0.0 |
| MINOR | 次版本 | **向后兼容**的功能新增 | 1.4.2 → 1.5.0 |
| PATCH | 修订号 | **向后兼容**的缺陷修复 | 1.4.2 → 1.4.3 |

可选后缀：`-alpha.N`、`-beta.N`、`-rc.N`（预发布）；`+build.NNN`（构建元数据）。

### 框架版本（独立编号，从 v0 起）

| 位 | 递增条件 |
|---|---|
| MAJOR | 模块划分/契约**不兼容**变更 |
| MINOR | 契约**兼容性扩展**、新增框架能力 |

> **不要过早宣布框架 v1.0。** v0.x 明确表达"框架尚未稳定，允许破坏性调整"。
> 一旦 v1.0，契约冻结，任何破坏性变更都要通知全部使用方并走完整流程。

### 版本递增决策表

| 变更性质 | 产品版本 | 框架版本 |
|---|---|---|
| 修 bug，契约不变 | PATCH | 不变 |
| 新增模块（不改既有契约） | MINOR | 可能 MINOR（若框架新增装配点） |
| 契约扩展字段（兼容） | MINOR | MINOR |
| 契约语义变更（不兼容） | MAJOR | MAJOR |
| 数据模型不兼容变更 | MAJOR | 可能 MAJOR |
| 仅文档/日志/配置默认值 | PATCH | 不变 |

## 五、变更控制流程（八步，不可跳）

```
① 提出变更申请 ─→ ② 影响分析 ─→ ③ 变更评审 ─→ ④ 批准/驳回
                                                    │
       ⑧ 归档与状态记录 ←─ ⑦ 新基线冻结 ←─ ⑥ 回归验证 ←─ ⑤ 实施变更
```

| 步骤 | 内容 | 产出 | 门禁 |
|---|---|---|---|
| ① 申请 | 变更内容、动机、触发条件 | 变更申请单 | 字段完整 |
| ② 影响分析 | 受影响模块/需求（RTM 反查）/接口/数据/测试范围/工作量 | 影响分析表 | 影响范围可推导回归范围 |
| ③ 评审 | 方案对比（≥2 案，含"不改"案） | 评审记录 | 按变更级别选 R5 或 R8 |
| ④ 批准 | 批准则定新版本号；驳回记入技术债 | 批准记录 | 批准人签字 |
| ⑤ 实施 | 代码 + **同步更新设计文档** | 提交 | 文档与代码同提交 |
| ⑥ 回归 | 按影响分析执行回归 | 回归测试报告 | 回归通过 |
| ⑦ 基线 | 打标签、更新版本说明 | Git 标签 + 版本说明 | 标签规范 |
| ⑧ 归档 | 更新 CHANGELOG、状态记录 | CHANGELOG | 可追溯 |

> **红线：文档与代码必须同一次提交。** 文档漂移是配置管理失效的头号征兆——
> 一旦文档不可信，整套追溯体系就归零了。

## 六、分支与提交策略

### 分支模型（简化 Git Flow，够用且不重）

| 分支 | 用途 | 规则 |
|---|---|---|
| `main` | 稳定可发布 | 只接受来自 PR 的合并；每次合并打标签 |
| `develop` | 集成主线 | 模块开发汇入此处；CI 全量跑 |
| `feature/M<模块号>-<简述>` | 模块开发 | 从 develop 切出，完成后 PR 回 develop |
| `fix/BUG-<编号>` | 缺陷修复 | 必须关联 BUG 编号 |
| `hotfix/<版本>` | 紧急修复 | 从 main 切出，回并 main 与 develop |

### 提交信息规范（Conventional Commits）

```
<类型>(<范围>): <简述>

[正文：为什么改，而非改了什么]

[追溯：REQ-F-012 / M03 / BUG-021 / FC-2026-007]
```

| 类型 | 含义 | 版本影响 |
|---|---|---|
| `feat` | 新功能 | MINOR |
| `fix` | 缺陷修复 | PATCH |
| `refactor` | 重构（不改行为） | 无 |
| `docs` | 文档 | 无 |
| `test` | 测试 | 无 |
| `chore` | 构建/工具 | 无 |
| `framework` | **框架变更** | 框架 MINOR/MAJOR |
| `BREAKING CHANGE`（脚注） | 不兼容变更 | MAJOR |

> **`framework` 类型是本仓库的强化项**：让框架变更在提交历史里一眼可辨，
> 便于统计"框架变更次数 / 已实现模块数"这个健康度指标。

## 七、配置审计检查单

每次发布评审（R8）前执行，可自动化项交给 CI。

- [ ] 所有配置项均已纳入版本控制（无游离文件）
- [ ] 无密钥/凭据入库（含历史提交扫描）
- [ ] 依赖锁定文件已更新且可复现构建
- [ ] 所有基线标签符合命名规范且指向正确提交
- [ ] 变更申请与影响分析齐全，均已批准
- [ ] 每次变更都有对应的回归测试记录
- [ ] 文档与代码版本一致（无漂移）
- [ ] 追溯矩阵完整（需求→设计→代码→测试 双向可查）
- [ ] 版本说明含变更内容、已知问题、升级与回滚注意
- [ ] 制品哈希已记录，可校验

## 八、常见失效征兆（出现即需干预）

| 征兆 | 后果 | 处置 |
|---|---|---|
| 文档改了代码没改（或反之） | 追溯体系失效 | 强制同提交；PR 检查单加一项 |
| 基线标签乱打 | 无法回退到已知良好状态 | 统一标签规范 + CI 校验 |
| 密钥入库 | 安全事故 | 立即吊销轮换；引入 secret 扫描 |
| 版本号随手起 | 无法判断兼容性 | 语义化 + CI 校验标签格式 |
| 只有 main 分支、直接提交 | 无评审、无隔离 | 引入 PR 流程 |
| CHANGELOG 靠回忆补 | 版本历史不可信 | 从提交信息自动生成 |

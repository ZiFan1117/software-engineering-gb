# 测试体系、缺陷管理与回归测试

> 依据：**GB/T 38634.1/.2/.3/.4-2020《系统与软件工程 软件测试》**（概念定义 / 测试过程 / 测试文档 / 测试技术）、
> **GB/T 25000.51-2016**（RUSP 质量要求与测试细则）、GB/T 41905-2022（测试工具能力）。
>
> ⚠️ **不要以 GB/T 15532-2008 为主要依据**——那是 2008 年的老标准，网上引用最广但已被 38634 系列实质覆盖。

---

## 一、测试级别（五级，骨架冒烟是本仓库的强化项）

| 级别 | 目标 | 对象 | 准入 | 准出 | 责任人 | 依据 |
|---|---|---|---|---|---|---|
| **L0 骨架冒烟** | 证明框架能装配、能跑通 | 骨架 + 桩模块 | 框架基线建立 | 一条命令跑通；冒烟用例通过；CI 干净环境复现通过 | 开发 | 本仓库强化项 |
| **L1 单元测试** | 证明模块内部逻辑正确 | 单个函数/类/模块 | 模块代码完成 | 全部通过；行覆盖率 ≥80%，核心分支 ≥90%；覆盖正常/边界/异常/空值 | 开发 | GB/T 38634.2-2020 |
| **L2 集成测试** | 证明模块间接口与协作正确 | 模块接口、数据流 | 相关模块通过 L1 | 接口用例全通过；异常传递正确；无循环依赖 | 开发+测试 | GB/T 38634.2-2020 |
| **L3 系统测试** | 证明系统整体满足需求 | 完整系统 | 集成测试通过 | P0/P1=0；需求覆盖率 100%；用例执行率 100% | 测试 | GB/T 38634.2/.4-2020 |
| **L4 验收测试** | 证明满足用户与合同要求 | 交付形态 | L3 准出通过 | 八项质量特性逐项结论；验收用例全通过 | 甲方/产品+测试 | GB/T 25000.51-2016 |

> **L0 为什么必须独立**：它是唯一能在"代码量最小、推翻框架代价最低"时点暴露框架结构性错误的环节。
> 跳过 L0 直接写模块，框架缺陷会被推迟到 L2/L3 集中爆发，那时修复成本是 L0 的数倍。

## 二、测试类型（按维度，不是按级别）

| 类型 | 关注点 | 何时做 | 常用技术（GB/T 38634.4-2020） |
|---|---|---|---|
| **功能测试** | 需求是否被正确实现 | L1–L4 | 等价类划分、边界值分析、判定表、场景法 |
| **性能测试** | 响应时间、吞吐量、资源占用 | L3 | 负载测试、压力测试、稳定性（浸泡）测试 |
| **并发测试** | 竞态、死锁、资源争用 | L2–L3 | 多线程/多进程并发、锁竞争探测 |
| **异常与容错** | 依赖失效、超时、断网、脏数据 | L2–L3 | 故障注入、错误推测 |
| **边界测试** | 极值、空值、超长、0 与 null | L1–L3 | 边界值分析 |
| **恢复测试** | 崩溃后能否恢复、数据是否一致 | L3 | 杀进程、断电模拟、事务回滚验证 |
| **安全性测试** | 鉴权、越权、注入、敏感信息 | L3–L4 | OWASP Top 10 对照、越权用例矩阵 |
| **兼容性测试** | 环境、版本、浏览器、终端差异 | L3–L4 | 环境矩阵组合 |
| **可维护性验证** | 可读性、可测性、可部署性 | L4 | 静态检查、代码走查、部署演练 |

### 非功能需求的量化底线（SRS 必须给，测试必须验）

| 维度 | 可验证指标示例 |
|---|---|
| 性能 | 关键操作响应 ≤ 200ms（P95）；列表查询在 1000 万行下 ≤ 2s（P95） |
| 并发 | 支持 500 并发用户，错误率 < 0.1% |
| 稳定性 | 连续运行 72h 无未处理异常；内存无持续增长（泄漏 < 1%/24h） |
| 安全 | OWASP Top 10 检查通过；口令 bcrypt(cost≥10)；越权用例 100% 拦截 |
| 恢复 | 进程被杀后 30s 内自动恢复；数据零丢失（事务级） |

## 三、测试用例的写法（卡片式，强制格式）

用例必须能**独立复现**。看到用例的人不看代码也能执行。

```markdown
#### TC-003 订单金额边界——超出上限
- 对应用户需求: REQ-F-012
- 测试项: 订单提交金额校验
- 级别/类型: L3 系统测试 / 边界测试
- 前置条件: 已登录，账户余额充足，单笔上限为 100000.00
- 测试数据: 订单金额 = 100000.01
- 测试步骤:
  1. 进入下单页，输入金额 100000.01
  2. 点击提交
- 预期结果: 提交被拒绝；提示"单笔金额不得超过 100000.00"；无订单产生；日志记录 WARN
- 实际结果: <执行时填写>
- 判定: <通过/不通过>
- 执行人/日期: <姓名> / <YYYY-MM-DD>
```

**规则**：
1. 一条用例只验一个判定点；
2. 预期结果必须**具体到文案/状态码/数据变化**，禁止"显示正确"；
3. 每条用例必须挂到至少一条需求编号（RTM 反查）；
4. 用例编号全域唯一，一旦分配永不复用。

## 四、缺陷管理

### 严重级别定义（必须与项目约定一致，下面是本仓库默认值）

| 级别 | 定义 | 示例 | 准出要求 |
|---|---|---|---|
| **P0 致命** | 系统不可用、数据丢失/损坏、安全漏洞 | 服务无法启动；下单后金额丢失；SQL 注入可读全库 | **必须为 0** |
| **P1 严重** | 核心功能不可用、无临时绕过方案 | 支付流程中断；关键页面 500 | **必须为 0** |
| **P2 一般** | 非核心功能异常，有绕过方案 | 导出格式错乱；次要校验缺失 | 有明确处置计划（责任人+期限） |
| **P3 轻微** | 体验问题、文案、样式 | 按钮错位；提示语有错别字 | 可延至下版本，登记即可 |
| **P4 建议** | 优化建议、技术债 | 重构建议；日志级别调整 | 记入技术债清单 |

> **P0/P1 不许带病出厂**——这是硬闸，不接受"时间紧先上线"。若确需带病上线，
> 必须由甲方/产品书面确认风险并转为"已知问题"，同时登记在版本说明的"已知问题"章节。

### 缺陷生命周期

```
新建 → 确认（复现/判定级别） → 分派 → 修复中 → 待验证 → 验证通过 → 关闭
                                    │                    │
                                    └── 拒绝/延后 ────────┴── 验证不通过 → 重新打开
```

**规则**：
- 缺陷必须能**复现**，附复现步骤、环境、数据、日志；不可复现的缺陷必须有排查记录后才可关闭；
- 修复缺陷必须**关联回归测试**（见下）；
- 缺陷编号全域唯一（`BUG-001`），关联到需求编号与用例编号。

## 五、回归测试策略（按影响范围选，不搞"要么全测要么不测"）

回归范围**必须由变更影响分析推导**，不能凭"感觉没影响"。

| 策略 | 适用场景 | 范围 | 成本 |
|---|---|---|---|
| **R-A 冒烟回归** | 仅文案、日志、配置默认值等无逻辑变更 | L0 冒烟 + 受影响模块 L1 | 极低 |
| **R-B 模块回归** | 单模块内部修改，接口契约未变 | 该模块 L1 + 直接依赖方 L2 | 低 |
| **R-C 契约回归** | 接口契约变更（= 框架变更） | 全部使用该契约的模块 L1 + 相关 L2 + 关键 L3 | 中 |
| **R-D 全量回归** | 框架结构性变更、数据模型变更、发布前 | L0+L1+L2+L3 全量 | 高 |

### 回归范围决策表（必须填进变更申请）

| 变更内容 | 是否改契约 | 是否改数据模型 | 建议回归策略 | 必须重跑的用例编号 |
|---|---|---|---|---|
| 修 bug（模块内） | 否 | 否 | R-B | `<TC-xxx, TC-yyy>` |
| 新增模块 | 否 | 否 | R-B + 新模块 L1/L2 | `<...>` |
| 扩展契约字段 | 是（兼容） | 否 | R-C | `<...>` |
| 修改契约语义 | 是（不兼容） | 可能 | R-C 或 R-D | `<...>` |
| 调整表结构 | 否 | 是 | R-D | `<...>` |
| 更换框架组件 | 可能 | 可能 | R-D | `<...>` |

> **自动化价值最高的地方就是回归。** 手工回归会因成本压力被舍弃，自动化回归才可能"每次都跑"。
> CI 中把 L1 + 关键 L2 设为"每次提交必跑"，是全流程性价比最高的一项投资。

## 六、测试门禁的自动化落点

| 门禁项 | 自动化方式 | 工具 |
|---|---|---|
| L1 全部通过 | CI 运行测试 | `pytest` / 项目测试框架 |
| 覆盖率达标 | CI 覆盖率检查 | `coverage` / `pytest-cov` |
| 需求覆盖率 100% | 追溯矩阵校验（每条需求至少一条用例） | `tools/trace_matrix.py` |
| 无循环依赖 | 依赖解析校验 | `skeleton` + `tools/trace_matrix.py` |
| 改动范围越界 | 相对基线的文件范围检查 | `tools/scope_check.py` |
| 冒烟通过 | CI 首步执行 | `skeleton/run_skeleton.py` |

**原则**：机器能判的不交给人。把人的评审注意力留给"契约是否合理""假设是否成立""测试设计是否覆盖了真正的风险"。

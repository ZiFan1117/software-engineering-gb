# 框架与模块共演化

> 这是本仓库**最核心的一篇**。它把"框架 → 模块 → 发现框架不对 → 改框架 → 再模块"这条
> 看起来像返工的路径，变成一条**受控的、可追溯的、成本可预测的**工程主线。

---

## 一、核心论断

**框架不是设计出来的，是演进出来的。** 但"演进"不等于"随时改"。

二者差别只在一点：**有没有受控的变更记录与基线。**

| 失控的迭代 | 受控的迭代 |
|---|---|
| 谁想改就改，口头同步 | 每次框架变更走变更申请，写明动机与影响范围 |
| 改了代码没改设计文档 | 文档与代码同版本提交，同基线冻结 |
| 不知道这次改动影响了哪些模块 | 变更申请强制列出受影响模块 + 受影响需求 + 需重跑的测试 |
| 回归靠"感觉没影响" | 回归范围由影响分析推导，有记录 |
| 版本号随便起 | 版本号语义化，框架版本与产品版本分离 |

## 二、双螺旋模型

```
    框架线（结构性资产）                模块线（功能资产）
    ─────────────────                  ─────────────────
        框架 v0.1
        （骨架跑通）
             │
             ├───────────→  模块 M01 实现
             │                    │
             │              ┌─────┴─────┐
             │              │ 适配？     │
             │              └─────┬─────┘
             │              不适配 │
        ┌────┴────┐               │
        │ 框架变更 │←──────────────┘
        │ 影响分析 │
        └────┬────┘
             │
        框架 v0.2  ←── 新基线（冻结）
             │
             ├───────────→  模块 M02 实现
             │                    │
             │              适配 ─┴─→ 模块 M02 完成
             │
        框架 v0.3 …… 直至收敛
```

**关键观察**：框架变更的频率应当**递减**。如果到第 5 个模块还在频繁推翻框架，说明 S2 阶段的
抽象层次选错了（不是"迭代正常"，是"设计返工"）。这是一个可用的**健康度信号**。

## 三、框架变更触发条件（什么时候才该改框架）

不是所有"写起来别扭"都要改框架。只有命中以下任一条，才提框架变更：

| 编号 | 触发条件 | 说明 | 建议处置 |
|---|---|---|---|
| **FC-1** | **契约不足** | 模块间接口无法表达真实数据流，只能靠 hack 传递 | **必须改**：这是结构性缺陷 |
| **FC-2** | **职责错位** | 某功能在现有模块划分下无处安放，或必然造成双向依赖 | **必须改**：会导致循环依赖 |
| **FC-3** | **假设被推翻** | S2 写明的"框架假设"被实现证伪（如假设同步、实为异步） | **必须改**：且要复盘假设为何错 |
| **FC-4** | **重复实现** | 第 3 个模块出现同一段逻辑的第 3 次复制 | **应该改**：抽取公共能力到框架层 |
| **FC-5** | **测试不可达** | 模块无法被独立测试（依赖写死、不可注入） | **应该改**：影响可验证性 |
| **FC-6** | **个人偏好** | "我觉得这样更优雅" | **不改**：记入技术债清单，留给下个大版本 |

> **判定规则**：改框架的成本 = 影响模块数 × 单模块改造成本 + 回归成本。
> 如果**不改**导致的持续成本（每个新模块都要多花时间绕过它）超过改造成本，就改。
> 这个判断必须写进变更申请，**不能只凭感觉**。

## 四、框架变更的标准动作（七步，不可跳）

| 步骤 | 动作 | 产出 | 责任人 |
|---|---|---|---|
| 1 | 提起变更申请 | 变更申请单：动机、触发条件编号、现象证据 | 实现者 |
| 2 | 影响分析 | 受影响模块清单、受影响需求（RTM 反查）、需重跑的测试、工作量估算 | 实现者 + 设计者 |
| 3 | 技术评审 | 变更方案对比（至少 2 案：改 vs 不改/最小改 vs 重构） | 评审组 |
| 4 | 批准/驳回 | 批准则确定新框架版本号 vN+1；驳回则记入技术债清单 | 技术负责人 |
| 5 | 实施变更 | 改框架代码 + **同步改 HLD 与模块契约** | 实现者 |
| 6 | 回归验证 | 按影响分析执行回归（不必全量，但必须有依据） | 测试 |
| 7 | 新基线冻结 | 打标签 `framework/vN+1`，更新框架假设清单 | 配置管理员 |

### 变更申请最小字段集

```yaml
变更编号: FC-2026-007
触发条件: FC-1 契约不足
现象证据: M03 需要向 M05 传递带优先级的任务，现有 Msg 契约无优先级字段，
          当前用 payload 强转字符串 hack，已在 3 处出现
受影响模块: [M03, M05, M07]
受影响需求: [REQ-F-012, REQ-F-019]
需重跑测试: 单元(M03,M05,M07) + 集成(IT-004) + 冒烟
方案A: 扩展 Msg 契约增加 priority 字段（低成本，1人日）
方案B: 引入独立优先级队列层（高成本，5人日，但FC-4也会受益）
决策: 采纳方案A；方案B记入技术债 DEBT-011
框架新版本: v0.4
批准人: <姓名> 日期: <日期>
```

## 五、版本号规范（框架版本与产品版本分离）

| 对象 | 版本格式 | 示例 | 递增规则 |
|---|---|---|---|
| **框架基线** | `vMAJOR.MINOR` | `v0.4` | MAJOR：模块划分/契约不兼容变更；MINOR：兼容性扩展 |
| **模块** | `MAJOR.MINOR.PATCH` | `1.3.2` | 语义化版本（见 `docs/04-配置与版本/`） |
| **产品发布** | `MAJOR.MINOR.PATCH` | `2.1.0` | 语义化版本 + 构建号可选 |

> **为什么框架版本要从 v0 开始**：v0.x 明确表达"框架尚未稳定，允许破坏性调整"。
> 一旦宣布 v1.0，就意味着**契约冻结**，此后任何破坏性变更都必须走完整变更流程并通知所有使用方。
> **不要过早宣布 v1.0** —— 这是框架演进最常见的自伤。

## 六、框架假设清单（S2 必须产出，S4 持续维护）

这是最容易被忽略、但对迭代最关键的一份**活文档**。格式：

```markdown
| 编号 | 假设内容 | 置信度 | 若不成立的后果 | 验证时点 | 状态 |
|---|---|---|---|---|---|
| A-01 | 上游数据源为同步阻塞调用 | 中 | 需引入异步/回调机制，影响全部 IO 模块 | M02 实现时 | ✅ 已验证 |
| A-02 | 单机部署，无需分布式锁 | 高 | 需引入协调服务，框架层大改 | S5 压测时 | ⏳ 待验证 |
| A-03 | 数据量 < 1000 万行，可全量内存排序 | 低 | 需改流式/分页处理 | M04 实现时 | ❌ 已推翻 → 触发 FC-3 |
```

**规则**：每个假设都必须有**验证时点**。没有验证时点的假设 = 定时炸弹。

## 七、反模式清单（看到就要停下来）

| 反模式 | 症状 | 为什么致命 | 正确做法 |
|---|---|---|---|
| **大设计先行** | S2 停留数周，试图设计完所有细节 | 抽象基于想象，实现一碰就碎 | S2 只定**边界与契约**，细节留到 S4 |
| **框架万能化** | 为"以后可能要用"提前抽象 | 制造无人能懂的间接层 | YAGNI：第 3 次重复再抽取（FC-4） |
| **静默改框架** | 改完继续写模块，不通知不记录 | 其他人基于旧契约开发，集成时爆炸 | 走七步变更流程 |
| **文档漂移** | 代码改了，HLD 还是半年前的 | 文档失去可信度，等于没有 | 同一次提交里改代码 + 改文档 |
| **追新弃稳** | 频繁引入新框架/新范式 | 框架版本抖动，模块永远追不上 | 框架版本变更频率应递减 |
| **只测正常路径** | 单元测试只测 happy path | 异常路径是缺陷重灾区 | 每个模块至少覆盖：正常/边界/异常/空值 |
| **无痕返工** | 推倒重来但没记录原因 | 同一个坑踩三次 | 每次框架变更写明触发条件与教训 |

## 八、健康度自检（每个里程碑问一次）

| 指标 | 健康值 | 危险信号 |
|---|---|---|
| 框架变更次数 / 已实现模块数 | < 0.5 | > 1.0：抽象层次选错了 |
| 框架变更的触发条件分布 | FC-1/FC-3 为主（结构性发现） | FC-6（个人偏好）为主：在设计上折腾 |
| 因框架不适配导致的模块返工率 | < 10% | > 30%：S2 做浅了 |
| 文档与代码的滞后提交 | 0 | > 0：文档体系已失效 |
| 回归测试范围可解释性 | 每次都能从影响分析推导 | 靠"感觉没影响"：风险敞口 |

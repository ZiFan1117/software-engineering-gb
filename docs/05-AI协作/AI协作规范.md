# AI 协作规范

> 前提判断：**AI 让"写"这件事的边际成本趋近于零，但让"判断"和"签字"的价值上升了。**
>
> 所以正确的用法不是"让 AI 少写点文档"，而是：**用 AI 把流程的吞吐量抬起来，同时把门禁守得更严。**
> 本文规定 AI 在流程各环节能做什么、必须人工确认什么、以及红线在哪。

---

## 一、核心原则

| 原则 | 说明 |
|---|---|
| **AI 可代写，不可代签** | 任何评审结论、批准、验收签字必须由人做。AI 生成的"评审通过"无效 |
| **AI 可生成候选，不可生成事实** | 需求来源、性能基线、合规要求等事实必须由人提供或核验 |
| **AI 产出必须可追溯** | AI 生成的文档/代码要在提交信息或文档元数据中标注，便于事后审计 |
| **门禁不因 AI 而放松** | 恰恰相反：AI 提升产出速度后，门禁是唯一的质量控制点，必须更严 |
| **人对最终产物负责** | 提交了 AI 生成的代码/文档，就等于你为它背书。不懂的代码不许提交 |

---

## 二、各环节的 AI 用法与人工责任

| 环节 | AI 可以做什么 | **必须人工确认** | 风险等级 |
|---|---|---|---|
| **S0 策划** | 起草可行性报告框架、风险清单候选、裁剪说明草案 | 范围与约束的真实边界；质量目标的数值；裁剪批准 | 中 |
| **S1 需求** | 把口语化需求改写为可验证需求；生成验收准则候选；发现需求冲突与遗漏 | **每条需求是否真实反映用户意图**；优先级；TBD 的处置 | **高** |
| **S2 框架设计** | 生成方案候选与对比；识别潜在循环依赖；起草模块划分与契约 | 架构选型理由；模块边界的合理性；**框架假设清单的置信度判断** | **高** |
| **S3 骨架** | 生成骨架代码、桩模块、构建脚本、CI 配置 | 骨架是否真的跑通（**必须实际执行验证**）；依赖解析是否正确 | 中 |
| **S4 模块实现** | 生成详细设计、实现代码、单元测试；生成边界与异常用例 | **代码逻辑正确性**；是否命中框架不适配（FC-1…FC-5）；覆盖率真实性 | **高** |
| **S5 测试** | 生成测试用例候选（尤其边界/异常/等价类）；生成测试数据；分析缺陷根因 | 用例是否覆盖真实风险；预期结果是否正确；**测试结论必须人工判定** | **高** |
| **S6 验收** | 起草验收报告、用户手册、版本说明 | 八项质量特性的逐项结论；验收是否通过 | **高** |
| **S7 维护** | 影响分析候选（受影响模块/需求/测试范围）；起草变更申请与回归范围 | 影响范围是否完整；回归策略选择；回归结论 | **高** |
| **全流程** | 检查单核对辅助、RTM 一致性校验、文档格式规范检查 | 所有评审结论与批准 | — |

## 三、AI 使用红线（绝对禁止）

| 红线 | 为什么 |
|---|---|
| ❌ 让 AI 生成"评审通过""验收合格"等结论性内容并直接采用 | 结论必须有责任主体 |
| ❌ 提交自己看不懂的 AI 生成代码 | 无法维护、无法定责、埋雷 |
| ❌ 用 AI 编造需求来源、用户访谈结论、性能实测数据 | 伪造事实是工程欺诈 |
| ❌ 用 AI 生成测试报告中的"实际结果" | 测试结果必须来自真实执行 |
| ❌ 把密钥、内部数据、客户信息贴给外部 AI 服务 | 数据泄露 |
| ❌ 因为"AI 写得快"而跳过评审与门禁 | 门禁是 AI 时代唯一的刹车 |

## 四、AI 生成内容的标注要求

### 提交信息标注

```
feat(M03): 实现订单金额校验

AI 辅助：是（Claude/DeepSeek 生成初稿，人工修改并验证）
追溯：REQ-F-012 / M03 / TC-003
验证：单元测试 12 项全部通过，覆盖率 行 87% / 分支 92%
```

### 文档元数据标注

文档头部引用块中增加一行：

```markdown
> 编写方式：AI 辅助起草 + 人工修订（修订人：<姓名>，日期：<YYYY-MM-DD>）
```

> 标注的目的不是"限制使用 AI"，而是**让审计者知道该重点检查哪里**。
> 一堆未标注的 AI 文稿，和一堆标注过的 AI 文稿，可信度完全不同。

## 五、AI 协作的推荐工作流

### 5.1 需求可验证化改写

```
输入：口语化需求 + 业务背景 + 约束
提示：把下列需求改写为可验证形式，每条必须给出：唯一编号 / 描述 / 输入输出 /
      异常与边界 / 可测量的验收准则 / 非功能指标（若有）。
      凡无法量化的，明确标出"需要人工补充指标"，不要编造数值。
输出：需求候选卡 → 人工逐条确认 → 入库
```

**关键约束**：明确告诉 AI **不要编造数值指标**，指标必须来自业务方。

### 5.2 框架方案对比

```
输入：需求基线 + 现有框架假设清单 + 约束
提示：给出 2–3 个架构方案，逐个说明：满足哪些需求 / 不满足哪些 / 引入哪些新假设 /
      实现成本 / 变更成本（若已实现部分模块）/ 风险。最后给出推荐并说明理由。
输出：方案对比 → 人工决策 → 写入 HLD
```

### 5.3 测试用例生成（AI 收益最高的环节）

```
输入：需求编号 + 需求描述 + 接口契约
提示：按等价类划分与边界值分析生成测试用例卡片，覆盖四类路径：
      正常、边界、异常、空值。每条给出前置条件、测试数据、步骤、可判定的预期结果。
      预期结果必须具体（状态码/文案/数据变化），不许写"显示正确"。
输出：用例候选 → 人工审核预期结果 → 执行并填写实际结果
```

**注意**：AI 生成的用例**最容易在"预期结果"上出错**（编造错误码、编造文案）。
人工审核的重点就在预期结果这一栏。

### 5.4 影响分析辅助

```
输入：本次变更的 diff + 需求追溯矩阵 + 模块依赖关系
提示：列出可能受影响的模块、需求、接口、需重跑的测试范围，并说明推导依据。
      不确定的项标为"待人工确认"，不要猜测。
输出：影响分析候选 → 人工确认 → 填写变更申请单
```

### 5.5 反模式：不要让 AI 做的事

| 反模式 | 后果 |
|---|---|
| "帮我写完整套 SRS" | 得到一份漂亮的、与真实业务无关的文档 |
| "帮我把覆盖率刷到 90%" | 得到一堆无断言的测试 |
| "帮我通过这次评审" | 得到形式化的评审记录，风险原封不动 |
| "帮我改框架让它更好" | 得到未经影响分析的静默框架变更 |

## 六、AI 时代流程的净效果

| 环节 | 传统成本 | AI 辅助后 | 变化 |
|---|---|---|---|
| 文档起草 | 高（数天） | 低（数小时） | ↓↓↓ |
| 需求可验证化改写 | 高 | 中 | ↓↓ |
| 测试用例设计 | 高 | 中 | ↓↓ |
| 代码实现 | 高 | 中 | ↓↓ |
| **评审与判断** | 中 | **中（不降）** | → |
| **验证与回归** | 中 | **中（不降）** | → |
| **需求确认与决策** | 中 | **中（不降）** | → |

**结论**：AI 压缩的是"写"的成本，**没有压缩"判断"和"验证"的成本**。
所以流程的重心应当从"逼人写文档"转向：
1. **门禁自动化**——机器能判的别交给人；
2. **把人的注意力集中在判断上**——契约合理性、假设成立性、测试覆盖真实风险；
3. **追溯机制更硬**——产出变快后，唯一能防止失控的就是追溯与门禁。

> 这正是 GB/T 8566-2022 过程框架 + 本仓库 S0–S7 门禁体系在 AI 时代依然成立、
> 而且**比以往更必要**的原因。

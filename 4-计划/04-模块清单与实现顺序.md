## 二、逐个模块详解

### 2.1 本体（法律）——**最先要有，但第一版只要一小块**

| 项 | 内容 |
|---|---|
| **形态** | 一个文件（JSON / YAML 都行），随程序分发 → 这就是"**出厂设置**" |
| **内容** | ① **事件信封的字段规定**（`world`/`kind`/`id`/`seq`/`at`/`actor`/`trace`/`flags`/`body`）② **三个家族的必填字段** ③ **概念集**（世界里有哪些实体、各有哪些字段）④ **版本号** |
| **对外** | 被运行时**加载** + **校验版本** |
| **依赖** | 无。它是最底层的东西 |
| **什么时候建** | ⚠ **分两次**（见 §四）：**Step 0.5 只要"信封"那一小块**；完整版在 Step 3 |
| **怎么验** | 能加载；版本对不上时**拒绝启动**；遇到不认识的事件家族**拒绝** |

**最小形态示意**（只是形状，不是最终格式）：

```yaml
world: 1                       # 词表版本
families:
  change: [subject, path, before, after]
  act:    [capability, verb, request_id]
  notice: [type, subject]
concepts:
  notice: { muted: bool }
  job:    { status: "enum(todo,doing,done)" }
```

**为什么它必须先有**：账本要**按格式写**、运行时要知道"什么算合法事件"——**没有法律，账本就无从落笔**。

---

### 2.2 账本（事实）——**第一个动手做的模块**

| 项 | 内容 |
|---|---|
| **形态** | **一个只追加的文件**；每行一条完整的事件（JSON Lines） |
| **内容** | 就是语义事件本身，按 `seq` 顺序排 |
| **对外只两个操作** | **`append(事件)`** 和 **`read(from_seq)`**。**没有 update、没有 delete** |
| **依赖** | 本体（信封格式） |
| **什么时候建** | **Step 1**（第一个实现的东西） |
| **怎么验** | 追加 3 条 → 按序读回一致 → **重启进程后事件还在** |

**文件长什么样**（示意）：

```
{"world":1,"kind":"change","id":"e-1","seq":1,"at":"…","actor":"world://user","trace":null,"flags":[],"body":{"subject":"world://notice/n-42","path":"muted","before":false,"after":true}}
{"world":1,"kind":"act",   "id":"e-2","seq":2,"at":"…","actor":"world://user","trace":"e-1","flags":[],"body":{"capability":"notice.mute","verb":"do","request_id":"r-1"}}
```

**三个工程要点（第一版就要处理，别留坑）**：

| # | 要点 | 怎么做 |
|---|---|---|
| 1 | **`seq` 谁分配** | 第一版**世界核心自己分配**：启动时读最后一行的 `seq` + 1，之后内存计数器递增 |
| 2 | **写入必须原子** | 一次只写**一整行** + flush。这样崩在最坏情况只会留下**半行**，前面所有行都是完整的 |
| 3 | **半行怎么办** | 启动读账本时，**最后一行若解析失败就丢弃**（因为只追加，这是唯一可能残缺的位置） |

> **顺带说清一件事**：**"每行一条"就是最简的分帧**（前面几轮讨论的那个"分帧"）。
> 它决定了"什么算一条完整的事件"——所以"行分隔"这个约定要在**本体里写清**（比如"内容里不得出现真实换行"）。

---

### 2.3 读模型（现在）——**算出来的缓存**

| 项 | 内容 |
|---|---|
| **形态** | **进程内存里的一个数据结构**（第一版**不落盘**） |
| **内容** | "现在每个实体是什么样" |
| **对外** | **按 subject 查"现在"** |
| **依赖** | **账本**——**只能由它派生** |
| **什么时候建** | **Step 2** |
| **怎么验** | 追加一条 `change` → 正确反映；★ **删掉它，能从账本重算出一模一样的结果** |

**形态示意**：

```
读模型 = {
  "world://notice/n-42": { muted: true },
  "world://job/t-7":     { status: "done" }
}
```

**它怎么算出来**（fold）：从头读账本，按家族分发：

| 家族 | 对读模型做什么 |
|---|---|
| `change` | `读模型[subject][path] = after` |
| `act` | 追加到"**待批集**"（`awaiting-approval` 的那种）或改状态 |
| `notice` | 通常不改状态，只记"发生过"（如完工铃） |

**★ 它必须是缓存，不是第二本账**。判据一句话：

> **删掉读模型，能不能 100% 从账本重建？**
> - **能** → 缓存（安全，随你怎么持久化加速）
> - **不能** → 它已经是第二本账了，**必须去掉**

---

### 2.4 运行时（机制）——**把上面三样装起来的那个进程**

| 项 | 内容 |
|---|---|
| **形态** | **进程的主循环**（就是"世界核心"那个可执行程序的身体） |
| **职责** | 启动装配（`03 篇` §五 那 7 步）+ 处理请求（收到的动作 → 查门禁 → 追加事件 → 更新读模型 → 推投影） |
| **依赖** | 本体 + 账本 + 读模型 |
| **什么时候建** | **Step 4**（第一次把东西组装成能跑的样子） |
| **怎么验** | 能起来；能连上；发一条 `change` 能读回状态 |

**它处理的每一条请求，都是同一个固定流程**（这个流程就是全系统的"心跳"）：

```
收到动作
  → 查门禁（允许吗？可逆吗？）
  → 追加事件到账本            ← 唯一的写入口
  → 更新读模型（重算受影响的部分）
  → 推给订阅的投影
  → 回一句结果
```

---

### 2.5 门禁（治理）——**第一版放运行时里面，不拆**

| 项 | 内容 |
|---|---|
| **形态** | 运行时里的**一块模块**（`agentd` 已经有这个逻辑） |
| **依赖** | 本体（能力表）+ 账本（审计流水） |
| **什么时候建** | **Step 5**（先把"能做"跑通，再上"不许做"） |
| **怎么验** | ★ 以 Agent 身份改门禁配置 → **失败**；绕过世界核心直接写账本文件 → **失败** |

**它的最小形态**：

| 部分 | 第一版 |
|---|---|
| **能力表** | 一个文件（`cap.d/*.yaml`），**归 root 所有** |
| **判定** | 每条 `act` 进来 → 查表 → 允许 / 拒绝 |
| **拒绝也要留痕** | **拒绝本身也追加一条事件**（这就是"流水人能读懂"） |

**强制力从哪来**（`03 篇` §三的落点）：**文件权限**（规则归 root，Agent 非 root）+ **Landlock**（内核强制"只碰这些路径"）。

---

### 2.6 投影（出口）——**最后建，先建最简陋的**

| 项 | 内容 |
|---|---|
| **形态** | **端口注册表**（有哪些投影、各自看什么范围、用哪版词表）+ **渲染实现** |
| **依赖** | 读模型（取"现在"）+ 本体版本（出示 hash） |
| **什么时候建** | **Step 4 就有雏形**（命令行打印读模型 = 语言投影的雏形）；**Step 7/8** 做正式的两个 |
| **怎么验** | **同一屏**（人与 Agent 读到同一份读模型）；**词表 hash 一致** |

**两个投影的差别只在"给谁看 + 怎么渲染"**：

| 投影 | 给谁 | 第一版实现 |
|---|---|---|
| **语言投影** | Agent | 一个命令行 / 一条 socket 返回结构化读模型 |
| **视觉投影** | 人 | 一个最简网页或终端界面 |

**两条不变的红线**：**投影不持有状态**（只持有渲染偏好）；**投影之间不交互**（只跟世界核心打交道）。

## 三、依赖图（谁必须在谁之前，以及为什么）

```
                     ┌───────────────┐
                     │  1 本体（信封）│  ← 最先：账本要按格式写
                     └───────┬───────┘
                             │ 规定格式
                             ▼
                     ┌───────────────┐
                     │   2 账本       │  ← 真相；只追加
                     └───────┬───────┘
                             │ 只能由它派生
                             ▼
                     ┌───────────────┐
                     │   3 读模型     │  ← 缓存；算出来的
                     └───────┬───────┘
                             │ 装配
                             ▼
        ┌────────────────────────────────────────┐
        │   4 运行时（把 1/2/3 装成一个进程）      │
        └───────┬────────────────────┬───────────┘
                │ 查表               │ 取"现在"
                ▼                    ▼
        ┌───────────────┐    ┌───────────────┐
        │  5 门禁        │    │  6 投影（×2）  │
        │ （本体能力表） │    │ （读模型+版本）│
        └───────────────┘    └───────────────┘
```

| 顺序 | 为什么必须在前 |
|---|---|
| **本体（信封）→ 账本** | 账本要按**格式**落笔；没有格式，写出来的东西没法读 |
| **账本 → 读模型** | 读模型**只能**由账本派生（这是"一个真相"的全部含义） |
| **读模型 → 运行时** | 运行时启动时**必须先算出"现在"，才能开 socket**——否则连上来的人看到空世界（`03 篇` §五） |
| **本体（能力表）→ 门禁** | 门禁要**查表**才知道允许什么 |
| **读模型 + 本体 → 投影** | 投影要取"现在"，还要**出示它用的是哪版词表** |

## 四、实现顺序（把 Step 1–8 展开成"每个模块先建哪一半"）

> ⚠ 这里有个细节要先修正：**Step 1 建账本时，就已经需要本体的一小块了**——至少要知道"一条事件长什么样"。
> 所以顺序上要插一个 **Step 0.5**。

| 顺序 | 建什么（模块的哪一半） | 为什么必须在这时候 | 验收 |
|---|---|---|---|
| **0** | ✅ 词表草稿 + 架构总图（14 篇 / 15 篇） | 先立法律，再动手 | 手工推演通过 |
| **0.5** | ★ **本体·信封部分**（只要：字段规定 + 三个家族名） | 账本要按格式写——**这一步之前没有它，Step 1 无从落笔** | 能加载，能据它校验一条事件 |
| **1** | ★ **账本**（只追加 + 按 seq 读回） | 它是真相，后面全部建立在它上面 | 追加 3 条 / 按序读回 / **重启还在** |
| **2** | ★ **读模型**（fold，内存） | 有它才有"现在"；它必须由账本派生 | 追加 `change` 正确反映 / **删掉能重算** |
| **3** | **本体·完整部分**（概念集 + 版本校验 + 拒未知） | 到这一步才有真实概念要定义 | 拒得了不认识的事件 |
| **4** | **运行时装配** + 语言投影雏形 | 三样齐了才能装；装了才能对外说话 | 命令行发 `change` → 读回状态 |
| **5** | ★ **门禁**（不可绕过第一刀） | "能做"通了才上"不许做" | 改配置失败 / 绕核心失败 |
| **6** | **检查点**（读模型的持久形态） | 等账本大了才需要 | 重放 1 万条 ≡ 快照 + 10 条 |
| **7** | **视觉投影** | 到这才有第二个人看的出口 | **同一屏** |
| **8** | **同源可核验**（投影出示词表 hash） | 两个投影都在了才能比对 | 换词表能被检出 |

**从这张表能看出实现逻辑的主轴**：

> **先立法律（0/0.5）→ 再记事实（1）→ 再算现在（2）→ 再装成人（3/4）→ 再上规矩（5）→ 最后才是快（6）和好看（7/8）。**

**顺序一乱会怎样**：

| 乱了 | 后果 |
|---|---|
| 先做投影（7） | 没有读模型可投影，只能自己造一份状态 → **长出第二本账** |
| 先做门禁（5） | 门禁要拦的动作还不存在，只能空转 |
| 先做检查点（6） | 没有账本可检查，快照无意义 |
| 跳过 0.5 直接写账本 | 事件格式边写边改 → 账本里混着多种格式，**永远读不顺** |

## 五、第一版"最小可用形态"总表（动手时照这张表写）

| 模块 | 第一版就是 | 具体到 |

| 本体 | **一个文件** | `ontology.yaml`，含版本 + 三家族必填字段 + 最小概念集 |

| 视觉投影 | **一个最简页面/终端** | 把读模型渲染出来 |

## 六、贯穿全篇的两条纪律 + 三个验收测试

### 纪律

1. **一个写入口**：只有 `append(事件)` 能改世界。**别的模块拿不到这个函数**（代码层面封死，不靠约定）。
2. **缓存可重建**：任何"看起来像状态"的东西，都必须满足"**删掉它，能从账本 100% 重建**"。

### 三个验收测试（每个 Step 都要跑）

| # | 测试 | 测的是 |
|---|---|---|
| 1 | 追加 → 读回 | 账本本身对不对 |
| 2 | **重启进程 → 事件还在** | 持久化真的生效 |
| 3 | ★ **删掉读模型 → 重算，结果一致** | **读模型没有偷偷变成第二真相** |

**测试 3 是最重要的一个**——它是"一个真相"这条纪律的**唯一自动化检验**。

## 七、待定的洞（承 03 篇 §八）

1. **读模型的新鲜度**：投影取"带 `base_seq` 快照"还是"常驻订阅增量"？
2. **权限从哪派生**：权限变更是不是也要走账本（否则权限成为第二本账）
3. **账本保留窗** + 账本大了之后的分段/归档
4. **补偿事件的语义**：回滚一条 `change` 是发反向 `change` 还是发 `notice` 声明放弃
5. **对象引用的 `rev` 并发**
6. **`trace` 因果链长度与截断**
7. **单位 / 量纲**还没进信封
8. **schema 演进（upcasting）落在哪**
9. **"真删"与不可变账本冲突**

# 03-世界核心的最小实现：分层、组件、启动顺序、分步路线

## 一、用大白话再说一遍这个结构（拿一个公司比）

| 结构里的东西 | 公司里的对应 | 干什么 |
|---|---|---|
| **本体** | **规章制度** | 规定"什么算一份合法文件、字段怎么填、什么算合法变更" |
| **账本** | **会议记录 + 收发文本** | 一条条按时间记下"发生了什么"，**只增不改** |
| **运行时** | **行政人员** | 按规章办事：记录、算现状、拦住违规 |
| **读模型** | **现状简报** | "现在谁在办什么"——由会议记录**汇总**出来的 |
| **语言投影** | 给**机器/系统**看的接口数据 | 把现状简报转成结构化数据 |
| **视觉投影** | 给**人**看的公告栏 | 把现状简报转成画面 |

**一句话链**：**规章（本体）→ 记录（账本）→ 汇总（读模型）→ 两种发布（两个投影）**，行政（运行时）在中间按规章办事。

## 二、它们算"组件"吗？——**只有两个真组件**

### 2.1 先给"组件"的判定标准（三条都满足才算）

| 判据 | 意思 |
|---|---|
| **能独立启动** | 载体能把它拉起来，不需要别的程序先跑 |
| **有独立生命周期** | 能单独升级、重启、崩掉而不牵连别人 |
| **能被人依赖** | 别的程序明确"等它"——没有它就不干活 |

### 2.2 按这三条过一遍

| 东西 | 能独立启动 | 独立生命周期 | 被人依赖 | 结论 |
|---|---|---|---|---|
| **载体**（Linux / 将来 Genode） | ✅ | ✅ | ✅ | ★ **真组件** |
| **世界核心** | ✅ | ✅ | ✅ | ★ **真组件** |
| 本体 | ❌（是它**加载**的一份法律） | ❌ | — | 内部模块 |
| 账本 | ❌（是它手里的一个文件 / 一张表） | ❌ | — | 内部模块 |
| 读模型 | ❌（是它**算出来**的缓存） | ❌ | — | 内部模块 |
| 运行时 | ❌（它就是世界核心的"身体"） | ❌ | — | 内部模块 |
| 门禁 | ❌（是运行时里的一块） | ⚠ 将来可拆 | — | 内部模块（**将来可升为组件**） |
| 语言投影 | ❌（是它开的一个端口） | — | — | **端口** |
| 视觉投影 | ⚠ 实现可以是外面的程序 | ⚠ | — | **端口**（实现可在核心外） |

**所以"组件"这个词在这里只有两个成员：载体、世界核心。**
其余的都是**它内部的东西**，或者**它开的端口**。

### 2.3 世界核心里面长什么样（一个进程，五个模块）

```
┌─ 世界核心（一个进程）────────────────────────────────┐
│                                                      │
│   ┌──────────┐   加载/校验版本   ┌─────────────────┐  │
│   │  本体     │◄─────────────────│     运行时       │  │
│   │ （法律）  │                  │ （身体：按法律办事）│  │
│   └──────────┘                  │                 │  │
│                                 │ · 追加事件→账本  │  │
│   ┌──────────┐   追加 / 读回     │ · 算读模型       │  │
│   │  账本     │◄────────────────►│ · 执行门禁       │  │
│   │ （事实）  │                  │ · 注册投影端口   │  │
│   └────┬─────┘                  └────────┬────────┘  │
│        │ 算出                            │ 开         │
│        ▼                                 ▼            │
│   ┌──────────┐                  ┌────────────────┐    │
│   │  读模型   │─────────────────►│ 语言投影（端口）│    │
│   │ （现在）  │      显示         ├────────────────┤    │
│   └──────────┘                  │ 视觉投影（端口）│    │
│                                 └────────────────┘    │
└──────────────────────────────────────────────────────┘
```

**"端口"是什么意思**：**投影的定义住在世界核心里**（有哪些投影、每个投影看什么、按什么范围过滤）；
**投影的"渲染实现"可以在里面，也可以在核心外面**——浏览器里的前端就是一个**外面的实现**。
所以"视觉投影"既是"世界核心的一个端口"，又是一个"跑在外面的程序"，这两句话不矛盾。

### 2.4 ⚠ 硬纪律：第一版**不要**做成四个进程——三条理由，逐条展开

**理由一：进程间通信会带来新的一致性问题——而你们全部的难点就在一致性上**

如果本体 / 账本 / 读模型各是一个进程，那么"**事件已经写进账本了，但读模型进程还没跟上**"就会变成常态。
于是你立刻需要：消息确认、重试、幂等、乱序处理、部分失败回滚……
——**这些东西恰恰是你们做"事件账本"想要消灭的复杂度**。做成多进程，等于把刚扔掉的问题又请回来了。

**理由二：启动顺序会变复杂，而且会出现"半个世界"的窗口期**

一个进程时，启动顺序是**内部函数调用**（本篇 §五 那 7 步，几毫秒就跑完，外界看不见中间态）。
拆成四个进程，就变成"谁先起、谁等谁、谁没起来时别人怎么表现"——
而且**在第 2 到第 4 个进程起来之前，世界是残缺的**：那时连上来的 Agent 会看到
"有账本但没读模型"、"有本体但没门禁"这种半成品状态。

**一个进程时，世界要么没起来（对外不接连接），要么就是完整的**——这正是"**世界不能处于半成品状态**"的直接实现。

**理由三："一个写入口"要求它们在一起（最硬的一条）**

**读模型只能由账本派生**——想改世界，只能追加事件。分成两个进程后，这条规则就只能靠**约定**维持：
"读模型进程绝不自己改状态"。而**约定是挡不住 bug 的**，尤其挡不住"绕过世界核心直接写"的那条路。

一个进程时，你可以用**代码层面的封装**把这条规则焊死：**只有一条函数能追加事件，别的模块拿不到写入口**。

### 2.5 那什么时候该拆？拆成什么？

**不是"永远不拆"，而是"等有理由再拆"。** 触发条件（任一条成立才考虑）：

| 触发条件 | 那时候怎么拆 |
|---|---|
| 门禁要独立升级，不想重启整个世界核心 | 门禁 → **总线上的一个独立内核实例**（"治理非地基"这时才兑现） |
| 账本要独立扩容（存到别的机器 / 别的介质） | 账本 → 独立的存储服务（此时它**进总线**，有明确的读写协议） |
| 出现第二个消费者要直接订阅账本 | 引入中央汇接点（11 篇原话的时机：**"多适配器 + 多消费者同时在线"**） |

**关键**：将来拆的时候，它们是**沿着"总线"拆**的（各自变成总线上的一个内核实例），不是随便切文件。

所以现在要做的只有一件事——**留结构，不留进程**：

> 把每块的边界在代码里划清（**一个模块一份职责、只有一条写入口**），
> 这样将来拆出去只是"**搬家**"，不是"**重写**"。

## 三、各自属于哪一层软件

从下往上数：

| 层 | 谁在这一层 | 备注 |
|---|---|---|
| 硬件 | — | — |
| **内核** | Linux（**买**） | 进程 / 内存 / 文件 / IPC / 隔离 / 配额 |
| **系统服务层** | ★ **世界核心（一等组件）** | **和 systemd / journald / dbus 同一层**——这就是"像 systemd 一样内生"的确切含义 |
| **应用层** | 各种 app；**视觉投影的 v1 实现**（浏览器里的前端） | 它们**依赖**世界核心 |
| **使用层** | 人 / Agent | 只写事件、只读投影 |

### 为什么世界核心必须在"系统服务层"，不能只做"应用层"

| 理由 | 说明 |
|---|---|
| **门禁的规则要落在被管者碰不到的地方** | 应用层的门禁，被管者（Agent）能改它 → **纸门禁**（总纲 §2.4） |
| **"世界不能有关掉这个状态"** | 应用可以关、可以绕过；世界不行（15 篇判据：缺了你系统照常 = 应用级） |
| **开机就要在** | 应用是"点图标才起"；世界核心是"开机就起、别人依赖它" |

**但注意——它不需要在内核里**：门禁的**强制力**靠内核能力（文件权限 / Landlock / systemd 沙箱指令），
门禁的**规则**在世界核心手里。**这两样合起来就是"不可绕过"，而且完全在用户态做到。**

## 四、分工表（每块负责什么、**不**做什么）

| 模块 | 负责 | **不**负责 |
|---|---|---|
| **本体** | 定义有什么、怎么说、什么算合法变更；版本化、内容寻址 | 不存数据、不管运行时 |
| **账本** | 记"发生了什么"；只追加、按 `seq` 有序、可重放 | **不算"现在"** |
| **运行时** | 加载本体、追加事件、算读模型、执行门禁、注册投影、开端口 | **不持有真相**（真相在账本） |
| **读模型** | "现在是什么样"；可随时从账本重算 | **不是真相**（丢了不怕） |
| **门禁** | 按能力 + 不可逆性拦动作、留审计 | 不决定世界状态 |
| **语言投影** | 把读模型显示给 Agent（结构化） | **不持有状态**，只持有渲染偏好 |
| **视觉投影** | 把读模型显示给人（画面） | 同上；**不与另一个投影通信** |

**两条贯穿全表的纪律**：

1. **读模型只能由账本派生**；任何"直接改读模型/对象"的路径都不许存在（一个写入口）；
2. **投影之间不交互**——它们只跟世界核心打交道。一旦需要"投影 A 通知投影 B"，就是真相分裂了（15 篇 §7.5 漏水信号）。

## 五、启动顺序（世界核心起来时，按什么顺序做什么）

```
载体（systemd / Genode init）
  │  ① 启动它，给它：一个状态目录 + 一条 socket 路径
  ▼
世界核心启动
  │  ② 打开状态目录 → 打开/创建账本
  │  ③ 加载本体 → 校验版本（对不上就拒绝启动，别带病跑）
  │  ④ 重放账本 → 算出读模型（有检查点就：载入检查点 + 只重放增量）
  │  ⑤ 打开 socket（开始接受连接）
  │  ⑥ 注册投影端口（语言 / 视觉）
  │  ⑦ 报告"就绪"（sd_notify / 打印一行 READY）
  ▼
客户端（Agent、视觉投影实现）连上来
```

**两个关键点**：

| 关键 | 为什么 |
|---|---|
| **④ 必须在 ⑤ 之前** | 必须先把"现在"算出来，才能让别人连——否则连上来的人会看到一个**空世界** |
| **③ 失败就拒绝启动** | 本体版本对不上 = 法律不对，**带病跑比不跑更危险** |

**开机时间 = 重放时间**。账本大了就慢 → 这就是**检查点（快照）**存在的唯一理由：它只是加速，不是真相。

## 六、分步实现路线（每步都能验，别跳步）

> 原则：**先让它能跑起来，再让它变对，最后让它变不可绕过。**
> 每步都用 `.\linux.ps1 ./check.sh` 验（见 [02-开发工作流](02-开发工作流.md)）。

| Step | 做什么 | **验收（做完的标准）** | 卡住说明什么 |
|---|---|---|---|
| **0** | ✅ **已完成**：词表（14 篇）+ 架构总图（15 篇） | 手工推演一个任务能跑通 | — |
| **1** | **账本**：一个只追加的事件文件 + 按 `seq` 顺序读回 | 追加 3 条 → 按序读回一致；**进程重启后事件还在** | 连追加/读回都做不到 → 说明数据格式没定死 |
| **2** | **读模型**：把账本 fold 成"现在"（内存即可） | 追加一条 `change` → 读模型正确反映；**删掉读模型能重算出来** | 重算不出来 → 说明有东西绕过账本直接改了状态 |
| **3** | **本体最小版**：一个词表文件（三个家族 + 最小概念集） | 能加载、能版本校验、**能拒绝不认识的事件类型** | 拒不了 → 说明"未知即忽略"这条没落 |
| **4** | **一条 socket + 语言投影雏形** | 命令行发一条 `change` → 读回状态（**这就是语言投影的雏形**） | 连不上/读不到 → 说明 ④⑤ 顺序错了 |
| **5** | ★ **门禁不可绕过的第一刀** | ① 以 Agent 身份改门禁配置 → **失败**；② 绕过世界核心直接写账本文件 → **失败** | 能改/能绕 → **那它还是应用，不是世界** |
| **6** | **检查点**：账本 + 快照 | 重放 1 万条 vs 载入快照 + 重放 10 条，**结果一致** | 不一致 → 快照与账本对不上，说明快照不是派生出来的 |
| **7** | **视觉投影** | **同一屏**：人看到的和 Agent 读到的来自同一份读模型 | 对不上 → 说明有一个投影自己存了状态 |
| **8** | **同源可核验**：两个投影出示词表 hash | 两 hash 一致；**故意给一个投影换词表 → 能检测到不一致** | 检测不到 → "同源"还是靠纪律，不是靠结构 |

### 停机线（做不出来时，说明哪里想错了）

| 现象 | 说明 |
|---|---|
| Step 1–2 反复做不对 | 事件格式没定死，回 `14 篇` 改词表 |
| Step 5 做不到"不可绕过" | 世界核心的部署位置错了（可能跑成了普通用户 / 规则放在可写目录） |
| Step 7 两个投影对不上 | 有模块在绕过账本直接改状态（违反"一个写入口"） |
| Step 8 检测不到不一致 | 词表没有内容寻址——回 `14 篇 §4.2` |

## 七、第一版的三条纪律（贴在墙上）

1. **一个进程**：本体 / 账本 / 读模型 / 运行时 / 门禁都在世界核心里，不拆；
2. **一个写入口**：想改世界，**只能追加事件**——没有人（包括世界核心自己）能直接改读模型；
3. **门禁不可绕过**：规则住在被管者写不了的地方（文件权限 / Landlock），否则这一整套就只是"一个应用"。

## 八、待定的洞（承 [15 篇](../2-依据/15-世界核心的组成与职责.md) §十二）

1. **读模型的新鲜度**：投影取"带 `base_seq` 的快照"还是"常驻订阅增量"？混用时怎么判断"我落后了"？
2. **权限也要从事件派生**——否则权限成为第二本账（Step 5 只解决"不可绕过"，没解决"怎么表达"）
3. **账本保留窗**：留多久、存哪、代价多少
4. **补偿事件的具体语义**：回滚一条 `change` 是发反向 `change`，还是发 `notice` 声明放弃？
5. **对象引用的 `rev` 并发**：两个投影同时改一个字段，谁递增 `rev`
6. **`trace` 因果链的长度与截断**
7. **单位 / 量纲**：词表信封里还没写进去
8. **事件不可变下的 schema 演进（upcasting 落在哪）**
9. **"真删"与不可变账本冲突**（总纲 §6 `存` 要求"记忆的条目级权限"）

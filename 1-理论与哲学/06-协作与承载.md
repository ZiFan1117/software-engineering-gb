# 06-协作与承载：三对闭环、高效判据与沟通的承载（原 00.5-协作篇）

## 一、高效的判据（先立尺子）

协作效率 ≠ 速度、≠ 吞吐量。定义：**单位人的注意力换到的可靠结果**，三个分量：
结果可靠（错误率 × 可纠正性）、注意力省（人为协作付出的关注）、纠错快（错误从发生
到暴露的延迟）。尺子立在这，下面所有"应该形态"都按它度量。

## 二、三个辩证定义 → 三条协作约束

| 定义（00.4） | 推出的协作约束 |
|---|---|
| Computer = 被争夺的场所 | 协作机制必须让**争夺显形**（谁在通过机器做什么，可见） |
| 人 = 循环且监督衰减的位置 | 协作机制必须**补偿衰减**（监督从注意力问题变成架构问题） |
| Agent = 定型战场 | 协作机制必须**中立化**（基础设施属于使用者，否则协作设计变成厂商定型的助攻） |

## 三、三对协作的应该形态

### ① 人 ↔ Agent：契约协作（目标—授权—证据）

现状低效的根源：自然语言对话每轮都在**重新谈判**（目标漂移、授权含糊、验收靠感觉）。
应该形态：把反复出现的三样东西结构化——**目标**（一次一个可陈述的"把 X 做到 Y"）、
**授权**（范围 + 不可逆动作的预案级别）、**证据**（结果 + 过程留痕 + 哪步是推测）。
高效 = 不重复谈判；监督衰减由结构补偿（人不盯过程，只在预设高危检查点出现）。

### ② Agent ↔ Computer：门禁协作（请求—过滤—执行）

现状：模拟人（慢而脆）或裸调（快而危险）双轨并存。应该形态：**声明即请求，场所按
混合产权三档过滤**（00.3）。高效 = 请求可预算（执行前有确定的通过/拒绝/需确认，
没有"跑半天才发现没权限"的浪费）；争夺格局显形为过滤规则，协作不靠猜。

### ③ 人 ↔ Computer：投影协作（一个表面看全）

现状：人看什么由 UI 厂商决定（渲染第一）。应该形态：**界面成为三方协作状态的投影**
——进行中任务、待确认请求、高危预案，投影在同一可见表面（= 08 项目六条边盘点 +
对偶界面的协作含义）。高效 = 一个表面看全，不在终端/日志/通知之间拼凑状况。

### 咬合

```
人 --目标+授权--> Agent --请求--> Computer(门禁过滤)
人 <--结果+证据-- Agent <--执行+事件-- Computer
     ^                                        |
     +-------- 投影（一个表面看全）<-----------+
```

## 四、四条高效判据（可检验）

1. **谈判一次**：同一件事不需在对话里反复重新约定（目标/授权/预案的结构化程度）；
2. **监督零盯守**：人不看时制度仍在运转（留痕、事件推送、完工铃）；
3. **纠错在最近点**：执行前过滤 > 执行后审计 > 事后发现，延迟越短越高效；
4. **争夺可见**：每个动作能回答"谁授的权、谁的场所、谁受益"。

## 五、现状差距清单

| 边 | 现状 | 缺口 | 对应工作 |
|---|---|---|---|
| ③④（人↔Agent） | 纯自然语言 | 缺契约层（目标/授权/证据结构） | 待做（新） |
| ⑤（Agent→Computer） | 模拟人/裸调双轨 | 缺统一门禁 | agentd |
| ⑥（Computer→Agent） | 默认静默 | 缺事件流 | transferor v0.2（浏览器面已补） |
| ①②（人↔Computer） | 渲染第一 | 缺协作状态投影 | 08 项目对偶界面 |

警示（00.4 第三节）：以上设计必须中立化（用户主权），否则协作效率变成给"产品定型"
的助攻——高效 but 争夺不可见的协作，是最坏的协作。

## 七、沟通的承载：用什么说话，效率最高（2026-09-24 补）

前六节讲协作的流程，本节讲协作的**通道**——沟通本身用什么承载。这是媒介问题，不是
组织问题；两类问题混谈会互相污染。

### 7.1 先证伪"中间点"模型

直觉方案是找一个"三方都能懂的中间语言"——像谈判桌，三方各讲方言、在桌上互相翻译。
**此模型不成立**（12 篇已证伪，此处收录结论）：三方的"硬件"不可通约——人要听懂的
语言、agent 要的结构、机器要的指令，任何单一格式都必然降级到三方最低公共水平，
三方都别扭。**中间点是求交集，交集必然小于全集。**

### 7.2 正确结构：底座 + 分层投影

```
真相层：语义总线（一份数据：结构化的状态/动作/事件）
   │
   ├── 投影 1：自然语言（人对话时用）
   ├── 投影 2：图形界面（人看状态时用）
   ├── 直连：Agent 原生读写（它本来就说结构化）
   └── 直连：Computer 原生执行（它本来就要指令）
```

与中间点的三个区别：

1. **位置 vs 底座**：中间点是谈判桌（三方到桌前互译）；总线是同一份档案（三方各取
   自己看得懂的版本，底料同一份）；
2. **妥协 vs 不妥协**：中间点必降级（交集 < 全集）；分层让每方拿到自己格式里的
   最优版本——人的版本是流畅的语言与好看的界面，agent 的版本是紧凑结构，谁也不将就；
3. **平等 vs 不对称**：中间点假设三方对等；分层承认 agent 与 computer 同为机器、
   直连底座（零翻译），唯人是特殊物种、配两个"随行翻译"（对话投影 + 界面投影）。
   数据库的类比：不是把库压成"中间格式"让财务销售都能读，是同一份数据出多张视图。

### 7.3 三对沟通各自的最优承载

| 对 | 最优承载 | 理由 |
|---|---|---|
| Agent ↔ Computer | **声明式语义调用**（JSON-RPC/varlink/能力接口） | 唯一双方皆机器的对：零歧义、可校验、可门禁。D-Bus 二十年已验证；自然语言让机器执行需"解析→猜参→执行"三步有损 |
| 人 ↔ Agent | **自然语言 + 语义骨架的混合** | 人端只能自然语言（人的 I/O 硬件决定），但纯语言对 agent 是有损压缩：由系统在对话之上提取语义骨架（目标/授权/验收）；agent 回程给"结构化结果+证据骨架"，比大段 markdown 快 |
| 人 ↔ Computer | **语义状态的渲染投影** | 人不能读 JSON，机器不该逼人点像素：界面底料必须是语义模型（对偶界面，08 项目）——与②的骨架同一份数据，不翻译两次 |

### 7.4 效率账

中间点模型：三方两两互译，N² 次翻译、每次有损、随对话轮次累积。
底座模型：翻译只发生在"底座→人的两个投影"，2 次、单向、机械、从同一真相出发
——**损耗点从九个减到两个，且都可控**。所有相关技术（UI-IR、JSON-RPC、D-Bus、
声明式能力）长得像不是巧合：它们都是"语义总线"这一最优承载的具体实现。

### 7.5 与两个项目的对位

transferor 铺浏览器段（网页→语义）、agentd 铺系统段（能力→语义+门禁）、对偶界面铺
渲染段（语义→人看的界面）——不是三个工具，是同一条总线的三段路。

### 7.7 三件套的关系与系统的装配（总线 · agentd · 通道）

总线是马路，agentd 是马路上唯一强制检查站，通道是并行货运专线——不是三个可选方案，
是一套系统里三种职责的部件：

```
              ┌──────── agentd（检查站+记账台：cap.d/审计/快照/铃）────────┐
 Agent ◄──────┤                                                           ├──────► Computer
（原生语义）  └─────────────────────┬─────────────────────────────────────┘        （执行）
                              语义总线（唯一真相：状态/动作/事件）
                                 │              ════ 内容通道（字节货运）════
                    ┌────────────┴────────────┐      总线只放 hash 引用（焊接）
                    ▼                         ▼
              投影A：自然语言            投影B：界面渲染
                    └────────────┬────────────┘
                                 ▼
                              人（免检，留痕）
```

- **agentd ≠ 总线**：总线是被动的传（基础设施），agentd 是总线上的主动服务（治理）。
  agentd 挂了总线照跑（人↔Computer 交通不断），只是 agent 暂时进不来——解耦是设计使然：
  **治理是服务，不是地基**；
- **通道 ≠ 总线**：语义走总线（小、结构化、可审计），字节走通道（大、异构、保真），
  内容寻址焊接（引用即证据）；不混载——混载同时毁掉审计与带宽；
- **UI 的身份**（前述端口论的收口）：UI 不是总线的对话方，是总线的**人向端口**——
  出（渲染状态）、入（人的操作翻成语义事件），自身无意志；
- **流量表**：Agent 做事必过 agentd；人做事免检留痕；读状态不设卡；搬字节走通道、
  引用上总线时检。

**搭新系统的装配顺序**：① 定总线协议（IR schema + 行分隔 JSON-RPC，一切部件的合同）
→ ② agentd 做第一个房客（07 已有）→ ③ 适配器逐面接入（08 transferor 是浏览器面的桥）
→ ④ 投影补上（界面/语言）→ ⑤ 内容通道最后加（早期 hash+路径凑合）。
新系统不是从零造，是把两个项目按总线图纸重新站位。

### 7.8 本节待批判项

1. "两个投影"假设人的需求只有对话与看状态两类（听觉/触觉/多设备场景未计）；
2. 语义骨架的提取由谁做（agent 自己提取=裁判球员合一；系统提取=又一层需治理的机器）；
3. 直连假设 agent 与 computer 无利益冲突——但场所是被争夺的（00.4），门禁即冲突的
   显形处，"零翻译"在门禁处其实是"一次有政治的翻译"。

## 八、总待批判项

1. "单位注意力换可靠结果"的三个分量未加权（可靠性 1% 的提升值多少注意力的节省？无定价）；
2. 契约协作的目标结构化与 00.1 的"标的生成于执行"矛盾未正面处理（目标先于执行 vs
   标的生于执行——契约层怎么容纳漂移的标的？）；
3. 四条判据是设计判据不是验证判据（没有实测协议）。
